# 5.3 Opening alerts

Risk: medium. No money. Sources: `docs/modules.md` module 6, `docs/plans/phase-0-architecture.md` sections 3.2, 5.6 (AlertSubscription), 6.4, and the mail rules in 4.6.

## Design

- **Module `alerts`** (`apps/api/src/modules/alerts/`, `alerts.prisma`, migration `0008_alerts`; 0007 is task 2.1's). Listed as always on (core module), like `catalogue`.
- **AlertSubscription** (pii): `email` citext, `raceId`, `editionId?`, `customerId?` (plain uuid, no FK: `Customer` arrives in 2.4), `status` pending/confirmed/unsubscribed, `confirmTokenHash?` + `confirmTokenExpiresAt?`, `confirmedAt?`, `unsubscribedAt?`, `lastNotifiedAt?`. `UNIQUE NULLS NOT DISTINCT (email, raceId, editionId)`: one row per address and scope.
- **Subscribe** `POST /alerts/subscriptions` (public, rate limited, same 202 answer whatever the state of the address, so it cannot be used to find out who is subscribed). Only published, non-demo races. New row is `pending`; a confirmation email is queued (`dedupeKey` per subscription and hour, so repeated submits do not flood). `confirmed` rows are left alone; `unsubscribed` goes back to `pending` (fresh confirmation needed).
- **Double confirmation.** The confirmation token is minted inside the mail send step (same transaction as its hash; a retry replaces it). The link is `WEB_ORIGIN/alerts/confirm#token=...` (fragment, like the magic link). The page shows a button; only `POST /alerts/confirm` (public, token in body) changes state, so a mail scanner opening the link confirms nobody. Token is single use and expires in 7 days.
- **One-click unsubscribe.** Every email carries `WEB_ORIGIN/alerts/unsubscribe?s=<id>&t=<hmac>`; `t` = HMAC(server key, `alert-unsubscribe:<id>`), nothing stored. Opening the page calls `POST /alerts/unsubscribe` and shows the result. Works from `pending` and `confirmed`; idempotent.
- **Opening notice.** Consumer `alerts.notify_open` on `catalogue.package.sale_status_changed` with `toStatus = open`: for each `confirmed` subscription of that race (race-wide, or the package's edition) it queues one email, `dedupeKey alerts:open:<packageId>:<subscriptionId>`, and sets `lastNotifiedAt`. `pending` and `unsubscribed` get nothing. Notice-only (events older than 48 h are dropped by the platform). Publishes `alerts.subscription.confirmed` on confirmation.
- **Panel.** `GET /admin/alerts/subscribers` (permission `alerts.subscription.read`) returns confirmed and pending counts per race; the races list shows the confirmed count (column hidden without the permission). No addresses are returned.
- **Web.** Alert form on the race page when an edition has no open package; `/alerts/confirm`, `/alerts/unsubscribe`; copy in `messages/en-AU.json`.
- Registered in the entity registry with `customerLink: column customerId`, export/anonymise handlers (anonymise deletes the rows, per plan 4.9).

## Failure cases to test
Unconfirmed gets no email on open; unsubscribed gets none; expired/used/forged confirm token; unsubscribe with a bad HMAC; duplicate event delivery sends once; subscribe to an unknown, draft or demo race is 404; case-insensitive duplicate address; same answer for known and new addresses; rate limit.

## Not doing
Customer-account management of alerts (5.1), marketing consent screens (5.5), editable email text (5.4: copy is in code for now), the `/unsubscribe/:emailId.token` platform route behind the `List-Unsubscribe` header.

## Assumptions
No `unsubscribeTokenHash` column: an HMAC of the id (as plan 4.6 says for unsubscribe links) needs no storage. Opening notice has category `marketing` so a global suppression is respected; the confirmation is `transactional`.
