# 0.4 Events (outbox), jobs (pg-boss), file storage and mail

Risk: medium. Source: `docs/plans/phase-0-architecture.md` sections 3.1, 4.5, 4.6, 4.7 and the 0.4 test list in section 8. No money logic (money is parked); nothing here touches payments.

## Design

All code under `apps/api/src/platform/`, tables in `prisma/schema/platform-common.prisma`, one migration `0002_platform_events_jobs_storage_mail`.

- **Tables:** `FeatureFlag`, `Setting`, `OutboxEvent`, `EventDelivery`, `IdempotencyRecord`, `StoredFile`, `OutboundEmail`, `EmailSuppression`, `NumberSequence` (columns as in plan section 5). Prisma cannot express partial indexes, so the "pending" outbox index is a plain index on `(dispatchedAt, occurredAt)`.
- **pg-boss** (`jobs/`): schema `pgboss` created by the migration as `mt_owner` (SQL from pg-boss's own `getConstructionPlans`, plus grants for `mt_app`). pg-boss starts with `migrate: false`, `createSchema: false`. Queues are declared once in `jobs/queues.ts` (name, zod payload schema, retry policy) and created by the migration (non-partitioned, so no DDL at runtime). On start the API compares the declared queues with `pgboss.queue` and refuses to start if any is missing. Payload schemas reject personal-data and amount keys.
- **Events** (`events/`): `OutboxService.publish(tx, event)` validates the type and payload (identifiers only) and inserts in the caller's transaction. The dispatcher (job `events.dispatch`, also callable directly) takes pending rows with `FOR UPDATE SKIP LOCKED`, creates one `EventDelivery` per matching consumer and one pg-boss job per delivery (`singletonKey = consumer:eventId`) in the same transaction (pg-boss `db` option). The delivery worker locks the delivery row, runs the handler in that transaction and marks `done`. A duplicate job finds `done` and does nothing.
- **Consumers** declare `module`, `eventTypes` (exact or `prefix.*`), `whenDisabled` (`hold` | `skip`) and, only if `notifyOnly`, `maxEventAge` (default 48 h). Registration throws if a consumer of `payments.*`, `bookings.*` or `changes.*` uses `skip`, or declares `maxEventAge` without `notifyOnly`. Module flag off: `skip` marks `skipped`; `hold` leaves `pending`. A sweep job re-enqueues pending deliveries whose module flag is on (this is how held events run after re-enabling). A notify-only delivery older than `maxEventAge` is `skipped` without calling the handler.
- **Failures:** handler error rolls back, then `attempts + 1` and a safe `lastError` are stored; after 5 attempts the delivery is `failed` (visible in the monitor). Stored errors (delivery, email, pg-boss) come from `safeError()`: a code and a fixed message for known classes only, never Prisma `meta`, PostgreSQL `detail` or `where`. Jobs throw a stackless `SafeJobError` so pg-boss output holds no values.
- **Retention:** purge job deletes terminal deliveries and dispatched events older than 90 days, expired idempotency records, and expired nothing else (pg-boss deletes finished jobs itself; queue `deleteAfterSeconds` = 7 days).
- **Flags and settings:** `FeatureFlagService.isEnabled(key)` reads the row on every call (no restart); a missing row falls back to the module's registered default. `SettingsService` validates with a zod schema registered in code. Administration (HTTP, audit) is 0.3. A `@RequiresModule()` guard returns 404 when a module's flag is off.
- **Idempotency** (`idempotency/`): `IdempotencyService.run` stores `(scope, key, requestHash)` with no response body; same key and body returns the stored status and resource reference (the caller renders the current resource); same key and different body gives 422; a live in-progress record gives 409; records expire after 24 h; a thrown error deletes the record so the retry runs.
- **Storage** (`storage/`): `FileStorage` interface (`put`, `get`, `delete`, `exists`, `signedUrl`) and `FilesystemFileStorage` (key validation against traversal, HMAC-signed URLs with expiry, no routes). `StoredFileService.save` writes the object, then the `StoredFile` row (SHA-256, size); if the row fails it deletes the object. A reusable contract battery (`runFileStorageContract`) is the test any adapter must pass. **No S3 adapter:** no free, light emulator was verified and the AWS SDK is heavy; the interface and battery are ready and S3 is recorded as not built.
- **Mail** (`mail/`): `MailSender` interface, `SmtpMailSender` (nodemailer; Mailpit locally), `MailService.enqueue` (inserts `OutboundEmail`, unique `dedupeKey`, enqueues `mail.send` with only the email id). The send step locks the row, applies the dev guard, renders the template (templates register by key and version; tokens are minted inside render, in the send transaction), stores `subject` and `bodySha256`, sends, marks `sent`. The body is never stored. The guard: outside `MAIL_MODE=live` with `APP_ENV=production` any recipient outside `MAIL_DEV_ALLOWLIST` (default `example.test,example.com`) becomes `suppressed`; `live` outside production is ignored with a warning; an unknown value counts as not live. `EmailSuppression` stores only an HMAC of the address; marketing mail consults it, transactional does not.
- **Entity registry** (`entities/`): `EntityRegistry` for models with a `customerLink` and `export`/`anonymise` handlers (0.3 and 5.5 consume it); only registration and lookup here.
- **NumberSequence:** `NumberSequenceService.next(tx, key)` with an atomic `UPDATE ... RETURNING`.
- **Config** adds `SMTP_*`, `MAIL_MODE`, `MAIL_FROM`, `MAIL_DEV_ALLOWLIST`, `EMAIL_HASH_KEY`, `FILE_SIGNING_KEY`, `FILE_STORAGE_DIR`, `FILE_MAX_BYTES`, `JOBS_WORKERS`. Keys have development defaults only when `APP_ENV` is development, test or ci; elsewhere they are required.

## Assumptions (instead of questions)

1. One `events.deliver` queue for all consumers (not one queue per consumer), so adding a consumer never needs DDL.
2. `OutboundEmail` gains `category` (transactional | marketing) and `attempts`; `EmailSuppression` gains `emailHashKeyVersion`. Subject is empty until render.
3. Dependencies: `pg-boss` (MIT) and `nodemailer` (MIT-0), both maintained and free.

## Tests (written first where practical)

Transaction rolled back leaves no event; double delivery processed once; `skip` with flag off marks `skipped` and `hold` stays `pending` and runs after enabling; no `payments.*`/`bookings.*`/`changes.*` consumer with `skip`; `stale_notify_event_skipped_after_reenable`; idempotency (no body, same status and resource, 422, 409, expiry); mail guard (allowlist and `MAIL_MODE` table); `dedupeKey` unique; API refuses to start without its queues and never creates the schema; `mt_app` cannot create in `pgboss`; `unique_violation_error_does_not_store_value`; file storage contract battery; sequence concurrency; entity registry.

## Not doing

S3 adapter, HTTP routes, admin UI for flags/settings (0.3), templates for real emails (5.4), marketing campaigns, Redis, any monetary logic.
