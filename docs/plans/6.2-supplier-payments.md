### 2.3 Database guards (two layers with the service; each has a failure test, section 11)

1. `mt_supplier_payment_guard` (BEFORE UPDATE OR DELETE on `supplier_payments`): no DELETE; on UPDATE, every column except `status`, `voidedAt`, `voidedById`, `voidReason`, `version` is immutable; `status` only `recorded → voided`; a status change bumps `version`. TRUNCATE rejected by a statement trigger.
2. `mt_supplier_payment_item_guard` (BEFORE INSERT OR UPDATE OR DELETE on items): INSERT only into a `recorded` payment created in the same database transaction (a `createdTxId` set by trigger on the payment, as the ledger does), with the cost item's `supplierId` equal to the payment's and `amountMinor` equal to the cost item's `amountMinor`; UPDATE only `active true → false`, and only when the parent is `voided`; no DELETE, no TRUNCATE.
3. Deferred constraint trigger `mt_supplier_payment_balanced` (AFTER INSERT on payments and items, DEFERRABLE INITIALLY DEFERRED): at commit a payment has at least one item and `sum(items.amountMinor) = payment.amountMinor` (P12 `supplier_payment_items_sum_to_payment`).
4. Deferred constraint trigger `mt_cost_item_paid_matches_payment` (AFTER UPDATE OF status on `cost_items`, AFTER INSERT OR UPDATE on items): at commit, `cost_items.status = 'paid'` **if and only if** an active item exists for it. So `paid` cannot be set by any code path except recording a payment, and a void that forgets to free its cost items fails.
5. `REVOKE DELETE, TRUNCATE ON supplier_payments, supplier_payment_items FROM mt_app`.

## 3. What is owed to suppliers, and when (the schedule)

The schedule is a **read**, worked out on request; nothing is stored except what staff record.

1. **Obligations are cost items.** Each `planned` or `due` cost item is an amount owed to its supplier, in its currency, on its `dueDate` (or "no due date"). `paid` and `cancelled` items are not owed. Amounts come from the row (`amountMinor`, worked out by 6.1's `costAmount`).
2. **Instalments by contract date.** An instalment is its own cost item (plan 0.1 5.7: "a deposit and balance are two `CostItem`s"), dated from the contract by staff. To make that quick, a new endpoint creates 2 to 12 `fixed` instalments of one contract in one transaction: each with its own description, unit amount and due date; same supplier, contract, package and currency; due dates strictly increasing. The server works out each `amountMinor` with `costAmount(1, unit)`. **No percentages**, so no rounding: staff type each amount (the contract states them). The schedule groups rows by contract reference.
3. **Release dates of contracted allotments.** A held allotment with a release date is a decision, not a debt: until the release date the unsold places can go back to the supplier at no cost. The schedule lists each held allotment with `releaseDate` in the window as an "at stake" row: places held, unit cost, `atStakeMinor = costAmount(quantity, unitCostMinor)` (the most it could cost if every place is kept), currency. At-stake rows have their **own totals** and never add into "owed". After the release date, if the allotment is still `held`, the row shows "release date passed" and the sweep opens one task (section 7) asking staff to record the cost of the places kept as a cost item. 7.3's key-dates tasks before the release date stay as they are.
4. **Cancellation effects.**
   - A booking cancelled (6.4's existing event `bookings.booking.cancelled`, payload with `packageId`): a consumer opens one system task per package while open (`suppliers:cancellation_review:<packageId>`) when that package has `planned`/`due` cost items, or its edition has held allotments whose release date is today or later: "A booking on <trip> was cancelled: check supplier costs and places still held before their release dates". No amounts, no customer data; the booking reference goes in the description only (an identifier, not personal data). Nothing changes by itself: staff edit or cancel cost items, or release places (6.1).
   - A trip cancelled by the operator cancels its bookings one by one; the open task absorbs them (one per package while open).
   - A cost item set to `cancelled` (6.1, by hand) leaves the schedule and its alert tasks close at the next sweep.
   - A `paid` cost item cannot be cancelled (6.1's `paid: []`). Money a supplier gives back (a refund or credit) is **not** recorded by 6.2: it is a real movement into the bank, which belongs to 6.6 with the bank side. Until then the panel says "If a supplier refunds you, note it and tell your accountant" and a void is only for a payment recorded by mistake.
   - Customer refunds after a supplier was paid show in the report as money paid beyond customer funds (section 6), never netted against another trip.
5. **Buckets, Brisbane dates.** `today = todayInBrisbane(dbNow)`. A cost item due on day D is due until the end of D in Brisbane (plan 0.1 1.2): `overdue` when `D < today`, `due_today` when `D = today`, `upcoming` when `today < D ≤ today + 7`, `later` beyond, `undated` without a date. Overdue items are always listed, whatever the window start. Brisbane has no daylight saving: D's end is `D 14:00:00Z`; tests at `13:59:59.999Z` and `14:00:00.000Z`.
6. **Totals per currency and bucket**, never across currencies (`schedule_totals_per_currency_never_mixed`). Sums of integer minor units are the only arithmetic.

## 4. Recording and voiding a payment

### 4.1 State machines

| Object | From | Event | To | Who |
|---|---|---|---|---|
| `SupplierPayment` | — | record | `recorded` | staff, `suppliers.payment.record`, step-up |
| `SupplierPayment` | `recorded` | void | `voided` (terminal) | staff, `suppliers.payment.void`, step-up, reason required |
| `CostItem` | `planned`, `due` | record | `paid` | only the record path (guard 4) |
| `CostItem` | `paid` | void | `due` | only the void path (it is still owed) |
| `CostItem` | others | (6.1, unchanged) | `planned ⇄ due`, `→ cancelled` | `suppliers.cost.manage` |
| `SupplierPaymentItem` | `active` | void | inactive (terminal) | only the void path (guard 2) |

Every transition is compare-and-set (`WHERE status = $from AND version = $v`) after the locks of 4.2; the guards of 2.3 back it up.

### 4.2 Record (`POST /admin/suppliers/:supplierId/payments`)

Body (strict zod, an unknown field is 422, so an `amountMinor` field is refused): `items: [{ costItemId, version }]` (1–100, unique), `paidOn` (ISO date), `reference`, optional `base: { amountMinor: digits string, currency }`. Header `Idempotency-Key` required.

One database transaction (the helper retries `40P01`/`40001` up to 3 times):

1. Lock the cost items `FOR UPDATE` **in ascending id order** (lock order CostItem → SupplierPayment).
2. Check each: exists (404 `cost_item_not_found`), belongs to the supplier (422 `cost_item_supplier_mismatch`), the version the panel read (409 `version_conflict`), status `planned` or `due` (409 `cost_item_already_paid` for `paid`, 409 `cost_item_not_payable` for `cancelled`); all in one currency (422 `cost_items_currency_mismatch`); the supplier not soft-deleted (404). `paidOn ≤ today` in Brisbane (422 `paid_on_in_future`). `base.currency ≠ currency` (422 `base_currency_same_as_payment`); `base.amountMinor` digits only, `> 0`, under the same per-line cap as 6.1 (`MAX_UNIT_MINOR`).
3. `amountMinor = Σ costItem.amountMinor`, from the locked rows.
4. Insert the payment (`status recorded`, `mode` = environment), the items (`amountMinor` = cost amount), set each cost item `paid` (compare-and-set on status and version, `version + 1`).
5. Post the ledger (section 5) under `supplier_payment:<id>`.
6. Audit `suppliers.payment.recorded` (ids, supplier, amounts as strings, currency, base, mode, `paidOn`, item ids; **no reference, no cost description**). Outbox event `suppliers.payment.recorded` with the same payload; **not** added to the outbound webhook catalogue.
7. Close the open alert tasks of those cost items (`closeSystemIn`, section 7).

A unique violation on the partial index (a concurrent payment that got past the checks) becomes 409 `cost_item_already_paid` and rolls back everything. `POST …/payments/preview` takes the same body without the header, runs steps 1–3 with `FOR SHARE` and writes nothing: the panel shows the server's total before confirming (the browser never adds amounts).

### 4.3 Idempotency

- HTTP: `IdempotencyService.run` with scope (staff id + route) and the client key: a repeat with the same body returns the stored response; another body under the same key is 422 (existing behaviour).
- Business key (plan 0.1 1.2, second form): `SupplierPayment.idempotencyKey = 'staff:' + sha256(IdempotencyService.scope(req) + '\n' + clientKey)`, never the raw header, unique in the table. Two staff users with the same client key get different keys (`same_client_key_different_staff_isolated`).
- Ledger: `supplier_payment:<id>` and `supplier_payment:<id>:voided` (P5), with the content fingerprint: the same posting again returns its id, other content is `LedgerKeyConflictError` and rolls back.
- Paying a cost item again after a void is a new payment with a new key; the old one stays voided (`voided_supplier_payment_frees_cost_item`).

### 4.4 Void (`POST /admin/suppliers/payments/:id/void`)

Body `{ version, reason }`; `Idempotency-Key` required. One transaction: read the payment's item cost ids without a lock; lock those cost items `FOR UPDATE` ascending; lock the payment `FOR UPDATE`; check `recorded` (409 `supplier_payment_already_voided`) and `version` (409); set `voided` with `voidedAt`, `voidedById`, `voidReason`, `version + 1`; set every item inactive; set each cost item `paid → due` (compare-and-set, `version + 1`); post the reversal (section 5); audit `suppliers.payment.voided` (without the reason text); outbox `suppliers.payment.voided`. Voiding never deletes or edits amounts.

## 5. Ledger postings

Kind `supplier_payment`, key `supplier_payment:<id>`, `bookingId` null, `supplierPaymentId` set, mode = the payment's. Positive = debit.

| Case | Lines |
|---|---|
| Paid in the supplier's currency C (no `base`) | `supplier_payable` C `+A`; `bank` C `−A` |
| Paid from a bank account in B (`base` given) | `supplier_payable` C `+A`; `fx_conversion` C `−A`; `fx_conversion` B `+X`; `bank` B `−X` |

Each currency balances on its own (the existing commit trigger checks it per currency). `A` is the payment amount, `X` the staff-typed bank amount; **no rate, no conversion**: each amount stays in its own currency's minor units as given (JPY with exponent 0 stays as typed). The `fx_conversion` balances per currency are what 6.6 reads to report the exchange difference (plan 0.1 1.1).

Void: kind `reversal`, key `supplier_payment:<id>:voided`, `reversesTransactionId` = the original, same `supplierPaymentId`, every line mirrored exactly (`supplier_ledger_reversal_mirrors_original`).

Accounting meaning (for Oscar's accountant, section 14): cash basis for now. `supplier_payable` is debited when paying; the matching credit (the obligation, accrual basis) is 6.6's decision, so until then its debit balance equals what was paid to suppliers and not reversed. `bank` is the business's bank account; until 6.6 posts gateway payouts, only supplier payments touch it, so its balance is **not** a bank balance and nothing reads it as one (comment in `ledger.ts`, and no screen shows it).

Code: `LedgerService` (still the only writer, `only_ledger_service_writes_ledger` stays green) gains `postSupplierPayment(tx, sp)` and `postSupplierPaymentVoided(tx, sp)` and a private insert that writes each line in its own currency (the booking path is untouched). `contentSha256` adds `supplierPaymentId` and per-line currency **only when `supplierPaymentId` is set**, so every existing hash is unchanged (`existing_posting_hashes_unchanged`). The payments public API exports a narrow `SupplierLedger` (those two methods and `mode`) for the suppliers module; payments never imports suppliers (no module cycle). The daily ledger check (`ledger-check.service.ts`) gains `missing_supplier_payment_posting` (a `recorded` payment without its posting, or a `voided` one without its reversal) and must keep ignoring booking-less postings in its per-booking checks (test).

## 6. Link to the 4.6 customer money report

The report stays per trip (package) and currency C, environment mode only, one REPEATABLE READ read-only transaction. 6.2 fills `paidToSuppliersMinor` and corrects how it is used.

**Source.** `P_C` = Σ `supplier_payment_items.amountMinor` where `active`, the payment is `recorded`, `mode` = environment, the cost item's `packageId` = the trip and its currency = C. Read with SQL in `ClientMoneyService` (it already reads `cost_items` that way).

**Rule (pure `tripMoney`, table-tested).** With `A` = customer money applied (Σ per booking of `max0(funds)`, as now), `K` = comparable supplier cost (or null), `P` = `P_C`:

- `S = min(P, A)`: customer money already spent on this trip's suppliers.
- `paidBeyondCustomerMoneyMinor = P − S`: paid from the business's own money ahead of customers (own column; never offsets any other trip, customer or currency).
- `U = max0(K − P)` (unpaid cost), `R = A − S`.
- `owedToSuppliersMinor = min(R, U)`; `margin = R − owed` (≥ 0), split into not earned / earned as now (all bookings returned before today in Brisbane).
- `keepSeparateMinor = owed + marginNotEarned + overpayments = held − earned − S`.
- K null (no costs, or some in another currency): owed and margin null, as now; `keepSeparateMinor = held − S` (money paid out in C is gone either way).

With `P = 0` every existing row gives exactly 4.6's numbers, so 4.6's tests stay as they are. Note: 4.6's current code would keep `held − earned` even after a supplier is paid, which would ask Oscar to keep aside money that has left the account; this rule is the 4.6 plan's own definition ("debido + margen aún no ganado + sobrepagos") once payments exist. Customer debt (receivable) stays its own column and never subtracts (`customer_debt_never_offsets_other_customers_money` unchanged).

**New parts of the report.** Columns "Paid to suppliers" (`P`) and "Paid from your own money" (`P − S`); per trip, "paid to suppliers in other currencies" as a list of `{currency, amountMinor}` (cost items of the trip in a currency other than C), shown and never netted; a separate section "Supplier costs not linked to a trip": per supplier currency, cost not cancelled, paid, unpaid (cost items without `packageId`), which never reduces any trip's amount to keep. Totals per currency, as now. Reconciliation invariant: per currency, Σ of all paid columns (trips, other-currency lists, unlinked) = the `supplier_payable` net debit in the ledger for the mode (`supplier_paid_totals_match_ledger`), the 6.2 part of the phase criterion "el resultado por viaje cuadra con el libro de pagos y con los costes registrados".

## 7. Alerts as tasks

A queue `suppliers.payments.alerts`, hourly at minute 20 (Brisbane midnight falls inside an hour, so a daily run could be up to a day late), advisory lock `suppliers:payment_alerts`, no-op with `module.suppliers` off. Per unpaid (`planned`/`due`) cost item with a due date:

- `suppliers:payment_upcoming:<costItemId>:<dueDate>` from `dueDate − 7` (constant `SUPPLIER_PAYMENT_LEAD_DAYS = 7`, like 7.3) to `dueDate`; `dueAt` = end of `dueDate` in Brisbane.
- `suppliers:payment_overdue:<costItemId>:<dueDate>` from `dueDate + 1`; the upcoming task closes then.
- `suppliers:release_passed:<allotmentId>:<releaseDate>` from `releaseDate + 1` while the allotment is `held` (section 3.3).

Rules as 7.3: a reference that ever had a task is not opened again (a task a person closed stays closed); a task whose item was paid, cancelled or re-dated closes (`closeSystemIn`); nothing older than 30 days is opened. Titles and descriptions carry **no amounts and no personal data** (cost descriptions are `@pii`; tasks are visible to staff without `suppliers.cost.read`): "Supplier payment to <supplier name> is due on <date>", "Supplier payment to <supplier name> is overdue since <date>", with the entity link to the cost item. Supplier names are business names (`@nopii`). No email is sent.

## 10. Failure cases

| Case | Result |
|---|---|
| Body carries `amountMinor` or any unknown field | 422, nothing written |
| Cost item of another supplier / mixed currencies / cancelled / already paid / stale version | 422 / 422 / 409 / 409 / 409, nothing written |
| Two staff pay the same cost item at once | one 201, the other 409 `cost_item_already_paid` (lock, then partial index) |
| Two payments over [A, B] and [B, A] | ascending locks: one waits, then 409; never `40P01` surfaced |
| Pay vs edit or cancel the same cost item | the loser gets 409 (`version_conflict` or `cost_item_not_payable`) |
| Same `Idempotency-Key`, same body | same response, one payment, one posting |
| Same key, other body | 422 `idempotency_key_reused` |
| Ledger key taken with other content (injected) | `LedgerKeyConflictError`, the whole transaction rolls back, cost items stay unpaid |
| Void twice, or void racing a void | one voids, the other 409 `supplier_payment_already_voided`; one reversal |
| Void without reason / without step-up / without permission | 422 / 403 `step_up_required` / 403 |
| `paidOn` tomorrow in Brisbane (incl. 13:59Z vs 14:00Z) | 422 `paid_on_in_future` |
| Base currency equal to the payment's, base amount 0, non-digits, above cap | 422 |
| Direct SQL as `mt_app`: UPDATE amount, DELETE, TRUNCATE, set `paid` without an item, re-activate an item, item amount ≠ cost, items ≠ total, item added after commit, ledger supplier posting with a booking or in a third currency, reversal with another `supplierPaymentId`, test-mode ledger row for a live payment | rejected by the guard, CHECK, FK or privilege |
| Module flag off | 404 on routes, sweep and consumer do nothing |
| Booking cancelled on a trip with nothing unpaid and no held places | no task |
| Report: test-mode supplier payment in production, voided payment | not counted |

## 15. Plan review (Opus, "approve with changes"): changes applied

1. **Retry after a lost completion (major).** `IdempotencyService.run` marks its record `completed` after the payment's transaction commits, so a crash between the two lets the retry run the handler again. Recording therefore looks up `SupplierPayment` by its business key inside the transaction, right after the locks: same content (supplier, sorted cost item ids, `paidOn`, SHA-256 of the reference, base amount and currency) returns the existing payment (200, nothing written); other content is 422 `idempotency_key_reused`. A unique violation on `idempotencyKey` (two retries racing) goes to the same lookup. Voiding a payment already voided **by the same staff user with the same reason** returns the payment instead of 409. Tests `supplier_payment_retry_after_lost_completion_returns_original` (the `IdempotencyRecord` is deleted, then the same request is repeated) and `supplier_void_retry_after_lost_completion_returns_payment`.
2. **Prepayments in the report (major).** The set of trips is the union of packages with customer ledger entries and packages with active supplier payment items in the environment's mode (with `A = 0` and no bookings when only the second applies), so a hotel deposit paid before any customer money shows as "Paid from your own money". Tests `prepayment_before_any_customer_money`, and the case inside `supplier_paid_totals_match_ledger`.
3. **A paid cost is frozen in the database (major).** Guard 6 (`mt_cost_item_paid_frozen`, BEFORE UPDATE on `cost_items`): while an active item points at the cost, `amountMinor`, `quantity`, `unitAmountMinor`, `packageId`, `supplierId` and `currency` cannot change. Added to the SQL row of section 10 and to `supplier_payments_append_only`.
4. Guard 1: `voidedAt`, `voidedById` and `voidReason` are written only by the `recorded → voided` transition, and `version` changes only with the status.
5. "Paid to suppliers in other currencies" is the sum of **active paid items** of the trip's cost items in another currency (not their cost). The base amount and currency are shown as information only, and the panel says that for suppliers in another currency nothing is subtracted from what must be kept aside. `fx_conversion_respects_currency_exponents` and every read of `fx_conversion` move to 6.6, written in `docs/done/6.2.md` (finding 3 of "Aparcado" names 6.2).
6. D2 is recorded as a deviation from a binding requirement (P11 and plan 0.1 5.7's FK `(costItemId, mode, currency)`; 6.1's done note expected 6.2 to add the column). The report filters by `supplier_payment_items.mode`.
7. `bookings.booking.amended` opens the same cost review task as a cancellation (same rule, same reference per package). Releasing an allotment (6.1) closes its `release_passed` task at the next sweep (test).
8. Overdue tasks have no age limit: an overdue reference opens once whatever the age (a cost created with a due date long past still gets one). The 30-day limit applies only to upcoming tasks.
9. `paidOn` more than 366 days before today in Brisbane is 422 `paid_on_too_old`.
10. The migration aborts at the start if any `cost_items.status = 'paid'` exists (guard 4 fires only on updates).
11. `recording_supplier_payment_sends_nothing` also checks that `suppliers.payment.*` events cannot trigger an automation (not in the automation trigger catalogue).
