# Plan 7.2: runner data exports in each race organiser's format

Risk: medium, but it is personal data leaving the system to third parties. Money is parked and untouched: no payment data in any export. Row: "Exportación de datos de corredores en el formato de cada organizador." Criterion: an organiser export includes only the fields that format asks for. Dependencies in `main`: 5.2 (`Traveller`, `TRAVELLER_ENTITIES`), 1.x catalogue (races, editions, distances), 2.x bookings (`BookingTraveller`). Erasure conventions from 5.2/5.5: an erased traveller keeps its row with `anonymisedAt` set and `[redacted]` names. Reference: `docs/modules.md` module 10, `.claude/rules/*`.

## 1. Assumptions (conservative, reversible)

1. **No migration.** Format definitions are code (declarative data, reviewed in a PR), not a table: a change to what we send an organiser is a code review of PII leaving the system, not a panel toggle. The module has an empty `organiser-exports.prisma` only because the module-boundaries test wants one schema file per module folder.
2. **Who is exported.** Places whose `participationType` is `runner_with_entry` (we submit their entry), not removed (`removedInVersion` null), in bookings of the edition in status `deposit_paid`, `confirmed` or `balance_paid` (the same journey as the traveller details window; `completed` and every closed state are out). `runner_own_entry` runners are out by default (the organiser already has their data) but a format may list them explicitly in `participation`. Supporters and companions never: not selectable by any format.
3. **Only data we already hold.** The sources a column may read are a closed list (`SOURCES`): given name, family name, date of birth, estimated finish time, emergency contact name and phone, race distance (name, km), and the booking's declared country of residence. Nothing else exists to export: no customer email or phone, no gender or nationality or passport (never collected, 5.2), no price, payment, status, notes, custom fields. The country of residence is the one the booking customer declared with the request (the booking's, not proven per runner); it is only in the `international` format.
4. **Formats shipped.** `entry_list_basic` (names, date of birth, distance) and `entry_list_international` (adds estimated finish, country, emergency contact; semicolon-separated, UTF-8 with BOM because Excel in Europe needs it, `DD/MM/YYYY`, country as a name). Both are samples of how a format is declared; a real organiser format is one more definition, with `appliesTo.raceSlugs` when it is only for one race. The real organisers' own templates are not known yet: a format is added when one is.
5. **Permissions.** Two new ones, neither API-key scopable, no role gets them by default (the owner holds every permission, so owner-only for now): `exports.runnerData.read` (list formats for an edition, dry-run check: counts and per-runner problems, no personal values) and `exports.runnerData.generate` (the file; `requiresStepUp: true` because data leaves the system). A staff user without either gets 403 (`bookings.booking.read` or any other permission is not enough).
6. **Blocking validation.** The file is never produced while any runner has a problem: 422 `export_has_issues` with the list. No "skip invalid runners" mode (a silent partial list to an organiser is worse than a blocked one). An edition with no exportable runner is 422 `no_runners`.
7. **Web panel is not in this task.** API and tests only; a panel screen (format picker, check, download with the step-up dialog) is a follow-up. Said in the done note.

## 2. Design

`apps/api/src/modules/organiser-exports/`:

- `sources.ts`: `SOURCES`, the closed list. Each source has a type (`text`, `date`, `duration`, `country`, `distance`), the database columns it needs (so the read selects only those) and a function from a `Runner` record to a raw value. `Runner` is a plain interface with exactly the fields above.
- `formats.ts`: `FormatDefinition { id, label, organiser, appliesTo: { raceSlugs?, years? }, participation, file: { delimiter, bom, eol }, columns: [{ header, source, required, as?, maxLength? }] }` and `defineFormat()`, which validates and deep-freezes it: each `source` in `SOURCES`, `as` valid for the source type (date `iso|dmy|mdy`, duration `hms|minutes`, country `name|alpha2`, distance `name|km`), unique non-empty headers, no control characters in headers, at least one column, delimiter one of `,` `;`. A definition that fails throws at start-up, so a bad format never ships. `FORMATS` is the list.
- `render.ts` (pure): `checkRunner(format, runner)` returns the problems (`missing`, `too_long`) per column; `renderCsv(format, runners)` builds the file **only** by walking `format.columns`: every cell is `column.render(runner)`, a string. The runner record is never iterated, so a field the format does not name cannot be written, however the record is extended. Every cell goes through the formula guard (`guardCell`, from the platform CSV helper: a leading `=`, `+`, `-`, `@`, tab or CR gets a quote in front) and RFC 4180 quoting; header cells are format constants. BOM only when `file.bom`. Date, time and country formatting per column.
- `reader.ts`: reads the runners of an edition in one transaction. The `select` is built from the columns of the chosen format (a format that does not ask for date of birth never loads it). Traveller rows with `anonymisedAt` (or the `[redacted]` marker) are not exported and not listed: they are counted in `erased`. A booking whose country is `ZZ` (erased) reads as no country. A runner place with no traveller row is a runner with every required field missing.
- `service.ts`: `formatsFor(editionId)`, `check(...)`, `generate(actor, ...)`. `generate` re-reads and re-checks inside the transaction, writes the audit entry in the same transaction, then returns `{ filename, body, rowCount }`. Nothing is written to storage or cached: the CSV only lives in the response.
- `controller.ts`: `GET /admin/organiser-exports/formats?editionId=`, `POST /admin/organiser-exports/check`, `POST /admin/organiser-exports`. Body `{ editionId, formatId, raceDistanceId? }` (strict zod in `packages/shared/src/schemas/organiser-exports.ts`). Response of the file: `200`, `text/csv; charset=utf-8`, `Content-Disposition: attachment; filename="<race-slug>-<year>-<format-id>-<YYYYMMDD>.csv"` with every part reduced to `[a-z0-9-]` (never a name or a free text), `Cache-Control: no-store`, `Pragma: no-cache`, `X-Content-Type-Options: nosniff`, `X-Row-Count`.
- `rate-limit.guard.ts`: in memory like the customer document guard: 10 files per hour per staff user and per IP; 60 checks per hour per user. 429 with `Retry-After`.
- Audit: one entry per generated file, `exports.runnerData.generated`, entity `RaceEdition` (id = edition), `after: { formatId, raceDistanceId, rowCount }` all classified `nopii`, in the file's transaction (no entry, no file). No name, date, header or cell value. Failed attempts (422) write nothing (nothing left the system); the check writes nothing.
- Order of checks: guard (401, 403 permission, step-up) then rate limit then body (422) then edition (404 unknown or deleted race) then format (404 `format_not_found` when unknown or not for this race, same answer so formats of other races are not revealed) then distance (404 when it belongs to another race) then the data.

## 3. Failure cases and tests written first

`apps/api/test/modules/organiser-exports/`:

- **Access:** anonymous 401; a customer session 401/403; staff without the permissions 403 on every route; staff with `bookings.booking.read` and everything else but not ours 403; read-only holder can check and list but gets 403 on the file; stale step-up gets 403 `step_up_required` on the file (and nothing is audited); an API key (any scopes) never reaches it; neither permission is API-key scopable and neither is in a seeded non-owner role; unknown edition 404; edition of a deleted race 404; unknown format 404; a format for race A on an edition of race B 404 (same body as unknown); a distance of another race 404; malformed body 422 (extra key, bad uuid).
- **Cross-race leakage:** two editions with runners: the file of A holds none of B's names; the distance filter keeps to its distance; a booking in another edition is never read.
- **Whitelist, structurally:** (a) the file's header is exactly the format's headers; (b) a runner record extended with extra fields (`passportNumber`, `email`, `price`, `notes`) renders exactly the same file; (c) a format whose source is not in `SOURCES`, a duplicate header, a bad `as`, an empty column list all throw in `defineFormat`; (d) a definition is frozen (pushing a column or changing a source throws); (e) sources list has no key of the forbidden set (email, phone of the customer, passport, price, status, notes) and nothing else is selectable; (f) the database read of a format that does not ask for date of birth does not select it (spy on the query args); (g) supporters and `runner_own_entry` places never appear (and a format that opts into `runner_own_entry` gets them but still never supporters).
- **Formula injection:** table of cells starting with `=`, `+`, `-`, `@`, tab, CR, and `'=`; they come out with a quote in front, also in a quoted cell with a comma or newline; a normal name is untouched; the generated date, time and distance cells never start with a formula character.
- **Encoding and formats:** BOM present only when the format says so; delimiter and EOL per format; accents and apostrophes survive (`García-López`, `O'Neil`); dates `iso|dmy|mdy`, durations `hms|minutes`, countries `name|alpha2`; file name is safe (race slug with odd characters cannot break out; no names in it).
- **Validation:** a table of missing required fields (no traveller row, no date of birth, no distance, name too long) listed per runner by booking reference and place, with the column header and code, and no personal value in the answer; the file is 422 `export_has_issues` with the same list and writes no audit; an optional empty column does not block.
- **Erased and anonymised:** an erased traveller (anonymised by the real `TRAVELLER_ENTITIES` handler) is not in the file, is counted in `erased`, and `[redacted]` never appears in any output; a country `ZZ` is not written; a customer closed after the check cannot sneak in (re-checked in the generating transaction).
- **Response and audit:** no-store headers, content type, safe `Content-Disposition`, `X-Row-Count` equals the rows; one audit row per file with only the three nopii fields and no PII value rows (`audit_pii_values` unchanged); nothing in the file storage directory; two requests give two audit rows; rate limit: the 11th file in an hour is 429 with `Retry-After`.
- Convention tests: module-boundaries (no writes to other modules' tables; imports only through indexes), schema conventions, field-class generation, route walkers (every route has one access mark; every `permission` route's key is registered), permission-registry tests still pass.

## 4. Not in this task

A panel screen; an organiser-supplied template parser; fields we do not collect (gender, nationality, passport, shirt size); xlsx or XML output; scheduled or emailed exports (data would leave without a person present); storing generated files; a "skip invalid runners" mode; any money field.
