# Plan 5.2: traveller details (minimum data, editable until a deadline)

Risk: medium (personal data, customer authorisation, a deadline enforced on the server). Money is parked and untouched. Row: "Datos de viajeros con el mínimo necesario, editables por el cliente hasta una fecha límite." Phase criteria: a customer cannot see or change another customer's booking; no form asks for a passport or medical data (`no_form_asks_passport_or_medical`, plan 0.1 section 7). Dependencies: 5.1 (customer area, `ownsBookingReference`, entity registry use) is in `main` (46ae34c). Reference: `docs/modules.md` module 5 ("nombre como en el documento, fecha de nacimiento, contacto de emergencia, tiempo estimado de carrera"), plan 0.1 section 5.4 (`Traveller`, `BookingTraveller`), `.claude/rules/web.md`.

## 1. What exists

`BookingTraveller` is a place in a booking (slot, participation type, lead flag), created at request time with no personal data. `customer-portal` (5.1) has the account routes, `ownsBookingReference` (404 for unknown and for someone else's, misses capped) and the `account-booking*` fixtures. The entity registry (`customerLink`, `export`, `anonymise`) is how 5.5 finds personal data. `KeyDate` has one `entry_submission` date per edition (7.3).

## 2. Scope decisions (conservative, reversible)

1. **Data collected, and nothing else.** Per place: given name and family name "as on the travel document" (everyone); date of birth (runners only: needed for the race entry and age category); estimated finish time in seconds (runners only, optional); an emergency contact (name and phone, both or neither, optional, everyone). No passport or ID number, nationality, gender, address, email, phone of the traveller, medical, dietary or allergy data, and no free text: names and phone numbers are validated against a character set, which keeps out digits, symbols and sentences with punctuation but not a few plain words. The customer is the contact for every place; the plan 0.1 optional `email`/`phone` of a traveller are left out (minimum necessary). Strict schemas reject any other key (422), so a client cannot send a passport number even by mistake.
2. **Model.** `Traveller` (table `travellers`) in `customer-portal.prisma`, owned by `customer-portal`: one row per place, keyed `(bookingId, slot)`, with a composite FK `(bookingId, customerId)` to `bookings (id, customerId)` and an insert trigger that requires the place to exist in `booking_travellers`. No FK into `booking_travellers`: it is append-only and a referencing FK makes `TRUNCATE` fail on the FK before the append-only trigger answers (`bookings/db.test.ts` expects the trigger's message), and that test is not to be weakened. Deviation from plan 0.1, which put a reusable `Traveller` plus `BookingTraveller.travellerId`: the link points from the new table to the place, so `bookings` keeps writing only its own tables (module-boundaries test) and nothing in `bookings` changes. A person is not reused across bookings: the customer types the details once per booking (a saved-travellers list is out; it is more personal data for no criterion). The FK and the trigger make "a traveller of another customer assigned to this booking" impossible in the database (`traveller_of_other_customer_cannot_be_assigned`). `anonymisedAt` as in plan 0.1. No `customFields` (custom fields for travellers join 7.5 later).
3. **Who and when.** The booking's own customer, through `@OwnedBy` + `ownsBookingReference` (a closed customer reads nothing). Details can be saved while the booking is `deposit_paid`, `confirmed` or `balance_paid` (the order in the phase journey: deposit, then traveller details). `completed` is read-only. Any other status: the places are listed without a form (`editable: false`, `reason: booking_status`).
4. **Deadline, decided on the server from the API's clock.** The last editable day (Brisbane calendar day, inclusive) is the edition's `entry_submission` key date when staff set one; otherwise the race start date minus the setting `travellerDetailsCutoffDays` (default 14, 0 to 120). With neither date known (provisional edition) there is no deadline (`editableUntil: null`) and the form stays open; staff set the key date once the race date is firm. After the deadline `PUT`/`DELETE` answer 409 `travellers_not_editable` and GET says `reason: deadline_passed`. Staff can reopen by moving the key date (7.3). The response carries `editableUntil`; the browser never computes it.
5. **Staff side is out.** No panel screen and no staff route here: the organiser export (7.2) reads these rows with its own permission. Nothing staff-facing exposes them in 5.2.
6. **Events.** Plan 0.1 lists `customerPortal.traveller.updated`; no consumer exists yet (7.2/7.4), so it is not published. Audit records every change.

## 3. API (`customer-portal`)

- `GET /account/bookings/:reference/travellers` — `@OwnedBy` booking (fixture `account-booking-travellers`). `{ editable, reason: null|'booking_status'|'deadline_passed', editableUntil: 'YYYY-MM-DD'|null, travellers: [{ slot, participationType, isLead, details: null | { givenName, familyName, dateOfBirth|null, emergencyContactName|null, emergencyContactPhone|null, estimatedFinishSeconds|null }, complete }] }`, ordered by slot, places with `removedInVersion` set left out. No ids. `Cache-Control: no-store`.
- `PUT …/travellers/:slot` — fixture `account-booking-traveller-save`. Strict body `{ givenName, familyName, dateOfBirth?, emergencyContactName?, emergencyContactPhone?, estimatedFinishSeconds? }`; replaces the whole record (absent = null). Runner-only keys on a supporter's place: 422. Runner without `dateOfBirth`: saved (incomplete), shown as incomplete. Answers the same view as GET.
- `DELETE …/travellers/:slot` — fixture `account-booking-traveller-clear`. Removes the details of that place (idempotent, 200 with the view).
- Order of checks: ownership (guard, 404) → slot valid and present (404) → body (422) → in one transaction: booking row `FOR SHARE`, window from the DB clock (409), place row `FOR UPDATE`, upsert, audit. Two saves of one place serialise on the place row.
- Validation: names `^[\p{L}\p{M}][\p{L}\p{M} '’.\-]*$`, trimmed, 1 to 100 characters; phone `^\+?[0-9 ()\-]{6,20}$` with at least 6 digits; date of birth a real calendar date between 1900-01-01 and today in Brisbane, runners only; finish time an integer from 600 to 259200 seconds.
- Audit: `customerPortal.traveller.saved` / `.cleared`, entity `Traveller`, fields classified by the field-class mechanism (`@pii` for names, date of birth, emergency contact, finish time; `@nopii` for slot, ids, timestamps), `customerId` in the row so the PII values carry `subjectCustomerId`. Actor is the customer user.

## 4. Privacy hook for 5.5

`TRAVELLER_ENTITIES` in `customer-portal/entities.ts`, registered by `CustomerPortalModule.onModuleInit` like `PAYMENT_ENTITIES`: `entityType: 'Traveller'`, `customerLink: { kind: 'column', column: 'customerId' }`; `export` returns the places' details (slot, names, date of birth, emergency contact, finish time, dates); `anonymise` overwrites names with `[redacted]`, nulls the rest and sets `anonymisedAt` (rows stay, so a trip still counts its places; no immutable table is touched). The data is only in `travellers`; audit PII values are already keyed to the customer. Lock order for 5.5: Customer → Booking → Traveller (the handler only locks `travellers` rows after the bookings are locked by the Booking handler).

## 5. Web

`/account/bookings/[reference]/travellers` (server component reads the API with the session; client form per place). The booking page gains a "Traveller details" section: how many places have details (from `complete`, counted by the page from the API's flags), and a link while the window is open or read-only otherwise. Copy in `messages/en-AU.json`, labels explain why each field is asked and say plainly that we do not ask for passport or medical details; one `h1`, one fieldset per traveller with a legend, every input has a label, errors in `role="alert"`, deadline shown as the API's date. The finish time input is hours and minutes converted to seconds by a pure helper (not money, not a price). No client-side deadline logic: the form is shown or hidden from `editable`.

## 6. Failure cases and tests written first

API `apps/api/test/modules/customer-portal/travellers.test.ts` (table-driven where it fits):
- Authorisation: fixtures for GET/PUT/DELETE in `every_owned_route_rejects_other_customer`; cross-customer matrix (B reads, saves and clears A's slot: 404, A's data unchanged; unknown reference and slot the same 404); signed out 401; staff session refused; closed customer 404; B cannot see A's details through the booking page routes.
- `traveller_of_other_customer_cannot_be_assigned` (SQL as `mt_app`: a row with another customer's id, or for a place the booking does not have, is refused by the FK and the trigger).
- Window table: status × (before / on / after the last day) — `deposit_paid`, `confirmed`, `balance_paid` open; `completed`, `requested`, `approved`, `declined`, `expired`, `cancelled`, `refunded` closed; key date wins over the race-start rule; the day itself is open, the next day closed (Brisbane calendar day); no dates = open with `editableUntil: null`; setting changes the cutoff. PUT/DELETE after the deadline: 409 and nothing written.
- Validation table: unknown key (passport, medical, nationality, gender, email, notes) 422; names with digits, symbols, empty, 101 characters; date of birth in the future, before 1900, impossible (30 February), on a supporter; finish time 0, 599, 259201, a fraction, a string, on a supporter; phone too short/long/with letters; emergency name without phone and the reverse.
- Round trip: save, read back exactly, overwrite, partial (absent = null), clear; `complete` flags; response keys exact (no ids); concurrent saves of one place end with one row.
- Audit: PII values have `subjectCustomerId`; `changes` shows `[pii]`, never the values; `erasure` handler: export has the details, anonymise redacts and sets `anonymisedAt` and a later GET shows nothing personal (`erasure_handler_redacts_travellers`).
- Schema conventions and field-class generation pass with the new model; module-boundaries test passes.

Shared: schema unit tests for the strict body. Web unit: the form posts only the six keys, converts h/m to seconds, hides the form when `editable` is false and shows the API's date, never renders passport or medical fields (`no_form_asks_passport_or_medical`: field names of the form, the schema keys and the message catalogue), copy test. E2E: customer fills the details after the deposit in `customer-area.spec.ts` (slot 18, already built for this journey), plus a stranger gets the neutral page.

## 7. Not in this task

Staff view or edit of travellers, organiser export (7.2), changes of names after the deadline, a saved-travellers list, ID or medical data of any kind, custom fields on travellers, the `traveller.updated` event, reminders to complete details (5.6 or automations).
