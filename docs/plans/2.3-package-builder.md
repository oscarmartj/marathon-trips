# 2.3 Package builder (web)

Risk: medium. Web only: no API change, no migration, no new dependency.

## What it is
`/races/[slug]/build?edition=<year>&package=<slug>` (the link 1.3 already emits) becomes the package builder. A visitor picks rooms and who sleeps in them, each traveller's participation (and distance for a runner with an entry), extra nights before and after, and extras. The page shows the total, deposit, balance and line-by-line breakdown **exactly as the API returns them**.

## Design
- Server page loads the package from `GET /catalogue/races/:slug/editions/:year/packages/:packageSlug` (already public, three-state availability, no stock numbers). 404 if missing; if `saleStatus` is not `open` it explains and offers no builder (the quote endpoint would 404 anyway).
- One small client component (`PackageBuilder`) holds the form state, initialised from the URL, and asks `POST /api/pricing/quotes` (same-origin proxy) after each change (debounced, stale answers dropped with a request counter). The URL is kept in sync with `history.replaceState` so a configuration can be shared.
- `lib/builder.ts` (pure, no arithmetic on money): URL <-> state, state -> quote request (a configuration only, never an amount), message key for an error status, and `formatMoney`. `formatMoney` only formats the API's digit-string: it inserts the decimal point by string operations and passes the decimal string to `Intl.NumberFormat`; no `Number`, no floats, no sums.
- Display of the answer: total, deposit, balance and due date, subtotals, each `lines` entry (label from room/extra names via `refId`, discount lines shown as returned), `perTraveller`, promo status as returned. Nothing is added up in the browser; if a number is not in the response it is not shown.
- Mandatory extras are listed as "included" and not sent (the API adds them). Per-person extras: a checkbox per eligible traveller (slots). Per-booking extras: a quantity from 0 to `maxPerBooking ?? 1`.
- Rules/promo codes: 2.2 owns them. The builder shows `promo.status` and any `rule`/`promo` lines the API returns. No promo input in this task (supposition: 2.2 adds the field to the quote request; adding an input then is a few lines). Documented, not built.
- Errors by status, never by parsing messages: 409 prices not ready, 422 "this combination is not available, adjust it", 429 slow down, 404 not open, other generic. No stale total is kept after an error (it is hidden, so a total never refers to a different configuration).
- Availability: `none` rooms are disabled with the text "Sold out"; `low` shows "Limited availability". Entries with `none` likewise. Informational only; the API decides.
- Accessibility: fieldsets/legends, labels on every control, results in an `aria-live="polite"` region, errors with `role="alert"`, visible focus from the design system, no colour-only meaning, works at 320 px.
- Copy: all strings in `messages/en-AU.json` under `builder.*`; `copy.test.ts` already guards hard-coded text. No claim of guaranteed entry/partner/accreditation: only `guaranteedEntry` from the API is shown, with the existing message.
- Static/incremental: the page reads `searchParams` so it is dynamic; the package fetch uses the same 60 s revalidate as the rest of the catalogue. Client JS is the one component.

## Failure cases to test
API down on package load; package not found; package not open; quote 409/422/429/500 and network failure; rapid changes (older response arriving late is ignored); amounts with 12+ digits; currencies with 0 and 2 decimals; request body never contains an amount-like key.

## Tests first
`lib/builder.test.ts` (URL round trip and defaults, request building, no money keys, formatMoney table, error key by status), `components/builder/package-builder.test.tsx` (render with fixtures; responses rendered verbatim; late response ignored; error states; extras/slots), page test for the server component.

## Not doing
Booking submission (2.4), promo input (2.2), checkout (3.5), prices in the browser, no-JS fallback (the builder needs JS to quote; a `noscript` note says so), e2e against a real API (CI e2e of the whole flow belongs to the phase close).

## Assumptions (no Oscar)
Max 4 rooms in the UI (API allows 20). Rooms start at one room with minimum occupancy. Default traveller: runner with entry if the package offers it, else the first offered type.
