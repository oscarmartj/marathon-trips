# 8.6 Backups, restore test, system monitor and maintenance mode

Risk: medium. Source: `docs/phases/phase-8.md` (row 8.6), `docs/architecture.md` ("Monitor del sistema", "Copias de seguridad"), `docs/research/hosting.md` section 4 (copies off the server and a tested restore are the two conditions for the single-server option), `docs/deploy/guide.md` ("Copias de seguridad"). No money logic is touched (money stays parked). Nothing is deployed and no account or key is created.

## Design

**1. Backups** (`scripts/backup/`, bash + `pg_dump`/`pg_restore`/`tar`/`openssl`; no new dependency).
- `backup.sh`: one consistent snapshot. A single `psql` session opens `REPEATABLE READ`, exports a snapshot, counts rows of every table (`public` and `pgboss`, top-level tables only) in that same snapshot, and `pg_dump --snapshot` (custom format) runs against it. Then the file directory is archived (after the dump, so every file a dumped row points to is in the archive; files are write-once). The bundle is one `mt-backup-<UTC>.tar` holding `db.dump`, `files.tar`, `MANIFEST` (sha256 of each part, row counts, migration count, format version). Optional encryption (`openssl enc -aes-256-cbc -pbkdf2`, passphrase read from a file, never from the command line) gives `.tar.enc`. The bundle is written to a temp name and renamed, so a half-written bundle never looks complete.
- Off-server copy behind a small contract: `BACKUP_REMOTE_KIND=none|dir|rclone`. `dir` copies to a mounted path (also what the tests use); `rclone` runs `rclone copyto` to `BACKUP_REMOTE_TARGET` (placeholder like `b2:example-bucket/marathon-trips`; remote credentials live in rclone's own configuration, never in the repository). `none` is allowed only with `BACKUP_ALLOW_LOCAL_ONLY=yes`, and the status file then says `offsite: false`. A failed copy makes the script exit non-zero.
- Local retention: keep the newest `BACKUP_KEEP` (default 14) bundles; the off-server retention is the bucket's lifecycle rule (guide).
- Status: `BACKUP_DIR/last-backup.json` (`finishedAt`, `bundle`, `sha256`, `offsite`, `encrypted`, `bytes`), written atomically only on success. The system monitor reads it.
- `restore.sh <bundle> --database <name> --files-dir <dir>`: decrypts if needed, checks every sha256 in `MANIFEST`, refuses an existing database or a non-empty files directory unless `--replace` (and never restores over the database named in `DATABASE_URL` unless `--i-know-this-replaces-live-data` too), creates the database owned by `mt_owner`, runs `pg_restore` as the admin role (roles must already exist: `deploy/db-init-prod.sql` or `scripts/db-init.sh`), extracts files, then runs the same row counts and compares them with `MANIFEST`. Exit 0 only if everything matches.
- `verify-restore.sh <bundle>`: restore into a throw-away database and directory, compare, drop both. This is the routine monthly check and what the real restore test in `docs/done/8.6.md` ran.
- Compose: a `backup` service under profile `tools` in `deploy/docker-compose.prod.yml` (image `postgres:16`, scripts mounted read-only, `filedata` read-only, a `backups` volume), run by cron on the host with `docker compose run --rm backup`. `scripts/check-deploy-config.mjs` is extended to keep this service from publishing ports and from mounting `filedata` read-write.

**2. System monitor** (`apps/api/src/platform/monitor/`). `GET /admin/system/status`, permission `platform.system.read` (new, no step-up: read only, no personal data). Returns: database up and round-trip time; maintenance on/off; per-queue counts by state and age of the oldest waiting job (`pgboss.job`); outbox (pending events, oldest age, failed and pending deliveries); mail (queued, oldest queued age, failed in the last 24 h); failed jobs in the last 24 h; last backup (read from `BACKUP_STATUS_FILE`, optional): `ok` (< 26 h), `stale`, `unknown`. An overall `status` (`ok` | `attention` | `down`) with reason codes. Only counts, ages, queue names and fixed codes: no addresses, no job data, no error text. Webhook-out health is not here: the tables arrive with 8.4 (it adds its section then).

**3. Maintenance mode.** Platform flag `platform.maintenance` (default off, changed through the existing flag admin API, audited). A global guard, first in the chain, answers `503 {code: maintenance}` with `Retry-After: 120` for every request except `GET /health`, `/auth/staff/*` and `/admin/*` (staff can still sign in, see the monitor and switch it off). Background workers keep running. CLI `maintenance:on|off|status` (audited as `system`) for when nobody can sign in. The web shows its generic error page for a 503; a web maintenance page is not in this task (noted in `docs/done/8.6.md`).

## Failure cases

Backup: database unreachable, `pg_dump` fails midway, disk full, remote copy fails, wrong passphrase on restore, tampered or truncated bundle (sha256 mismatch), target database already exists, restore counts differ. Monitor: database down (endpoint still answers `down`, from the guard-free path; `/health` already covers liveness), missing or corrupt status file (`unknown`, never an exception), no permission (403). Maintenance: flag read fails (500, not open), staff routes stay reachable.

## Tests (first)

- `scripts/backup/backup.test.mjs` (`node --test`, runs in `pnpm lint`; needs PostgreSQL, so it skips only when `PGHOST` tooling is absent in lint... see assumption 3): backup then restore into a new database gives identical row counts and file hashes; tampered bundle rejected; wrong passphrase rejected; existing database refused; remote `dir` copy present; `none` refused without the allow flag; half-written bundle never named `mt-backup-*`.
- `apps/api/test/platform/monitor.test.ts`: permission required; shape; a failed delivery and an old queued email move the status to `attention`; stale and missing backup file; no personal values in the response.
- `apps/api/test/platform/maintenance.test.ts`: on gives 503 with `Retry-After` on public and customer routes, `/health`, staff sign-in and `/admin/*` pass, off restores; flag change audited; CLI on/off; route walk still passes (`every_route_has_exactly_one_access_mark`).

## Assumptions (instead of questions)

1. Off-server store: rclone (MIT, free, supports S3, B2 and many others) as an optional host tool, behind `BACKUP_REMOTE_KIND`. Oscar picks the bucket. An S3 SDK inside the API is not added (a new runtime dependency for something a script does).
2. Daily backup at 03:30 server time, 14 local copies. Encryption on in production (the bundle holds personal data); passphrase kept by Oscar outside the server, like `APP_ENCRYPTION_KEY`.
3. Script tests need PostgreSQL superuser access. CI's `checks` job already has PostgreSQL for the API tests; the test reads `BACKUP_TEST_ADMIN_URL` (set in CI) and is skipped by an explicit `describe.skipIf` only when it is unset locally; `check-no-skipped` guards CI, so there the variable is set and it runs.
4. Point-in-time recovery (WAL archiving) is out of scope; the loss window is up to 24 h. Documented as a known limit with the upgrade path.

## Not doing

Deploying, creating a bucket or account, WAL archiving, an admin screen for the monitor, a web maintenance page, backing up Caddy certificates (re-issued automatically), webhook-out monitoring (8.4).
