## 1. Ledger design

### 1.1 Tables (`payments.prisma`; `finance.prisma` is not created, the ledger lives with payments as plan 0.1, 5.5 says)

**`LedgerAccount`** (`ledger_accounts`): `id`, `code`, `kind` (`asset`, `liability`, `revenue`, `expense`), `currency Char(3)`, `mode PaymentMode`, `createdAt`. `@@unique([code, currency, mode])`: test and live never share an account. `CHECK (code ~ '^[a-z_]+(:[0-9a-f-]{36})?$')`. Rows are created on demand (`INSERT … ON CONFLICT DO NOTHING`) and never change. Codes used in 3.3:

| Code | Kind | Normal balance | Meaning |
|---|---|---|---|
| `provider_clearing:<providerAccountId>` | asset | debit | money the gateway holds for us (4.6 moves it to the bank and posts fees) |
| `customer_funds` | liability | credit | customer money allocated to active plan items |
| `customer_overpayments` | liability | credit | customer money beyond the active items (P7), owed back |
| `customer_receivable` | asset | debit | created by 4.5 (chargebacks); not posted in 3.3 |

**`LedgerTransaction`** (`ledger_transactions`): `id`, `occurredAt` (`clock_timestamp()`), `kind` (enum `LedgerTransactionKind`: `payment`, `refund`, `fee`, `chargeback`, `supplier_payment`, `adjustment`, `reversal`, the list of plan 0.1), `mode`, `bookingId?`, `paymentId?`, `refundId?`, `reversesTransactionId?` (unique), `idempotencyKey` (unique, P5), `description` (`@nopii`, a code such as `reallocation`, `CHECK ~ '^[a-z0-9_.:-]{1,120}$'`), `contentSha256 Char(64)` (§1.3).
- FKs `(paymentId, mode)` → `payments(id, mode)`, `(refundId, mode)` → `refunds(id, mode)`, `(reversesTransactionId, mode)` → `ledger_transactions(id, mode)`, `bookingId` → `bookings`; all `Restrict`. `@@unique([id, mode])`.
- `CHECK`: `kind = 'payment'` ⇒ `paymentId` not null; `kind = 'refund'` ⇒ `refundId` not null; `kind = 'reversal'` ⇔ `reversesTransactionId` not null; `bookingId` not null whenever `paymentId` or `refundId` is.
- `BEFORE INSERT` trigger: `bookingId` equals the payment's and the refund's (`ledger_booking_must_match_payment_and_transaction`).
- Columns `disputeId` and `supplierPaymentId` of plan 0.1 are added by 4.5 and 6.2 with their tables (an FK to a table that does not exist cannot be declared).

**`LedgerEntry`** (`ledger_entries`): `id`, `transactionId`, `accountCode`, `currency`, `mode`, `amountMinor BigInt` (`/// @signed`, positive = debit, negative = credit, `CHECK (amountMinor <> 0)`), `bookingId?`, `createdAt`. FKs `(accountCode, currency, mode)` → `ledger_accounts(code, currency, mode)` (`ledger_entry_currency_must_match_account`, `ledger_entry_mode_must_match_account_and_transaction`) and `(transactionId, mode)` → `ledger_transactions(id, mode)` (`ledger_transaction_mode_must_match_payment` through the transaction's own FK). Indexes `(bookingId, accountCode)` and `(accountCode, currency, mode)`.

**Database rules, all three tables:**
- `BEFORE UPDATE OR DELETE` and `BEFORE TRUNCATE` triggers raise; plus `REVOKE UPDATE, DELETE, TRUNCATE … FROM mt_app` (two layers). `LedgerAccount` and `LedgerEntry` carry `/// @appendOnly` (their FKs point only at append-only rows, as the convention test requires); `LedgerTransaction` points at payments and refunds, which are never deleted but are updated, so it gets the triggers without the tag, like `booking_snapshots`.
- Deferred constraint trigger (`DEFERRABLE INITIALLY DEFERRED`, at commit) on `ledger_entries` and on `ledger_transactions`: every transaction has at least two entries, sums to 0 **per currency**, every entry's `bookingId` equals its transaction's, and a transaction with `paymentId` has all its entries in the payment's currency (`payment_ledger_entries_in_payment_currency`). A transaction inserted without entries fails at commit.
- No personal data: the ledger is kept when a customer is erased (plan 0.1, 5.5). Its models go in the entity registry as "kept, no personal data", so `registry_covers_every_customer_table` passes.

### 1.2 Posting service (`core/ledger.service.ts`; the only code that inserts into the ledger, checked by a source test like the one for `payments.status`)

`LedgerService.post(tx, { key, kind, mode, bookingId, paymentId?, refundId?, reversesTransactionId?, description, lines: [{ accountCode, currency, kind, amountMinor }] })`:
1. Drops zero lines, rejects lines in two currencies for a payment, checks the sum is 0 per currency in code (the trigger checks again).
2. Ensures the accounts exist (`INSERT … ON CONFLICT DO NOTHING`).
3. `INSERT INTO ledger_transactions … ON CONFLICT ("idempotencyKey") DO NOTHING RETURNING id`. If nothing was returned, reads the existing row: same `contentSha256` → returns it (a retry, nothing posted); different → throws `ledger_key_conflict` (an `AppError`: the whole transaction is undone, never a second or different posting).
4. Inserts the entries.

Callers always hold the booking lock (`LockedBooking`, lock order `Booking → Payment → Refund`, plan 0.1, 6.3): two postings for one booking never interleave. Ledger accounts are never locked.

### 1.3 Idempotency

- One key per business fact, never per gateway event (P5): `payment:<paymentId>:succeeded`, `refund:<refundId>:succeeded`, `refund:<refundId>:reversed`, `schedule:<bookingId>:v<n>:reallocation` (with `PaymentSchedule.version` after the change, which goes up with every plan change; 3.2 and 6.3 already do this), and for 3.4: `inbound:<paymentId>:voided` (§1.6).
- A posting is only made on the state transition that creates the fact, and the transition is compare-and-set: two webhooks for the same success (two Stripe event types) or a retried job reach the posting at most once; if they did, the unique key would make the second a no-op.
- `contentSha256` = SHA-256 of the canonical JSON of kind, mode, ids and sorted lines (amounts as strings). It makes "same key, different content" detectable instead of silently ignored.

### 1.4 What each posting contains (sign: + debit, − credit)

The customer side is computed by one pure function, `customerSide(before, after)`, where `before` and `after` are `allocate(activeItems, netCollected)` (3.2's `core/allocation.ts`) just before and just after the fact. `fundsDelta = Σpaid(after) − Σpaid(before)`, `overpaymentDelta = overpaid(after) − overpaid(before)`. It never reads ledger balances, so a classification error can never block recording money; the daily check (§4) compares the ledger with the derived allocation and reports drift.

| Fact | Cash side | Customer side |
|---|---|---|
| Payment succeeded (any origin) | `provider_clearing:<accountId>` +A | `customer_funds` −fundsDelta, `customer_overpayments` −overpaymentDelta (fundsDelta + overpaymentDelta = A) |
| Refund succeeded | `provider_clearing:<accountId>` −R | `customer_funds` +|fundsDelta|, `customer_overpayments` +|overpaymentDelta| (overpayment first, then the last items backwards, which is what allocation by sequence gives) |
| Refund reversed (`kind = reversal`, `reversesTransactionId` = the refund's posting) | the refund's cash line mirrored exactly (+R) | recomputed from the allocation now, since the plan may have changed since the refund |
| Plan change: amendment (6.3), approval expiry or cancellation supersedes items (3.2) | none | `customer_funds` ±d, `customer_overpayments` ∓d; nothing posted if d = 0 |

`netCollected` becomes Σ succeeded payments − Σ refunds in `succeeded` (a `reversed` refund no longer counts), in the environment's mode (P11). `CollectedAmountSource` of 3.1 is replaced by this one source, so payable amounts, coverage and the ledger read the same number.

### 1.5 Where the postings are called (same transaction as the fact)

- `PaymentStateMachine.apply`, on `→ succeeded`, before coverage. A failed posting goes down the existing `CoverageFailedError` path (transaction undone, task for Oscar, webhook retried): a payment is never recorded without its posting.
- `PaymentRefundStateMachine` (new, §3) on `→ succeeded` and `→ reversed`.
- `PaymentScheduleService.supersede` (expiry, cancellation) and `AmendmentPlanService` (6.3) after creating the new plan version: `ledger.reallocate(tx, booking, version)`.
- 3.4 (parallel): an `inbound` payment calls the same `postPaymentSucceeded`; voiding one calls `postReversal(tx, booking, { key: 'inbound:<id>:voided', original: 'payment:<id>:succeeded' })`. Both are exported for it; whichever of 3.3 and 3.4 merges second wires them.

### 1.6 Corrections

Entries are never edited. A correction is a new transaction: `reversal` (cash lines mirrored, `reversesTransactionId` unique so a fact is reversed once) or `adjustment` with its own key. No route in the API writes the ledger: the only writer is `LedgerService`, called by the state machines and plan changes; the test `ledger_tables_have_no_write_routes` walks the route manifest.

## 2. Allocation, coverage and P7/P8

2.1. The split between `customer_funds` and `customer_overpayments` follows the derived allocation of 3.2 on **net** collected, at booking level. This equals P7 for everything 3.3 can do (money in, gateway refunds, plan changes). It differs from P7's per-payment rule only when refunds and chargebacks of specific payments meet overpayment reserved by an app refund in progress (P10), which only 4.5 can create. 4.5 creates `PaymentAllocation` from this split (batch `approval:<bookingId>:plan`, as plan 3.2 §2 set) and, if its per-payment rule classifies differently, posts the reallocation with its own key.

2.2. Coverage C still only moves forward. After money out, if the booking's status claims coverage it no longer has (for example `deposit_paid` with the deposit uncovered), 3.3 opens a task (`payments:coverage_lost:<refundId>`) and changes nothing; 4.5 implements those cells.

2.3. After a gateway refund the plan shows the refunded amount as outstanding again (payable reads net collected). The task tells Oscar to cancel or adjust the booking. Assumption 4 covers the reminder risk.

## 3. Refunds (gateway side only in 3.3)

### 3.1 Table `refunds` (plan 0.1, 5.5, with what exists today)

`id`, `paymentId`, `bookingId`, `providerAccountId`, `mode`, `currency`, `amountMinor` (> 0), `origin` (`app`, `external`), `purpose?` (`price_reduction`, `overpayment_return`, `cancellation`; `CHECK (origin = 'external' OR purpose IS NOT NULL)`), `reason?` (`@pii`, null for external), `status` (`requested`, `pending`, `succeeded`, `failed`, `reversed`), `idempotencyKey` (unique; external: `refund:external:<providerAccountId>:<providerRefundRef>`), `providerRefundRef?`, `failureCode?`, `requestedById?`, `succeededAt?`, `version`, timestamps.
- FK `(paymentId, bookingId, providerAccountId, mode, currency)` → `payments` (its unique of plan 0.1 exists). `@@unique([id, mode])`, `@@unique([providerAccountId, providerRefundRef])`. `CHECK`: reference not null if `succeeded` or `external`; `CHECK (origin = 'external')` until 4.5.
- Status trigger with the allowed pairs (`requested→pending|succeeded|failed`, `pending→succeeded|failed`, `succeeded→reversed`), mirrored by `REFUND_STATUS_PAIRS` in code and checked to match, like 3.1 does for payments.
- `cancellationId` and `amendmentId` come with 4.5 and 6.4.
- `WebhookEvent` gets `refundId?` (FK, filled when matched).
- Entity registry: `reason` erased with the customer; a refund in `requested` or `pending` blocks erasure like an unfinished payment.

### 3.2 Interface additions (`core/provider.ts`)

- `ProviderRefund { ref, status: 'pending' | 'succeeded' | 'failed' | 'cancelled', amount, paymentRef, ourRefundId?, failureCode? }`. `paymentRef` is what the gateway calls the payment; `retrievePayment({ ref: paymentRef })` must resolve it (Stripe sends the PaymentIntent id; the adapter maps it to the Checkout Session).
- `createRefund(ctx, { paymentRef, amount, idempotencyKey, metadata: { refundId, paymentId, bookingId }, createdAt })` and `retrieveRefund(ctx, { ref } | { idempotencyKey, paymentRef, createdAt })`. No caller in 3.3's core; the contract suite proves them for 4.5.
- `NormalisedEvent.kind` adds `'refund'` with `refund?: ProviderRefund`. Disputes stay `unsupported` (4.5).
- `CreatePaymentInput` and the retrieve-by-key form gain `createdAt: Date` (our row's): Stripe has no lookup by idempotency key, so the adapter searches a bounded time window (§5.3); it also makes every create parameter deterministic for a key.
- `GatewayOperation` adds `'refund'`: allowed on paused and retired accounts (plan 0.1, 6.4), blocked for live outside production (`non_production_refund_on_live_account_rejected`); the guard matrix test grows a column.

### 3.3 Webhook processing of refund events (`PaymentWebhooksService`)

1. Outside any transaction: `retrievePayment(ctx, { ref: refund.paymentRef })` through the gateway of the account that received the event. Match the payment by `ourPaymentId` **among that account's payments only**, then by `(providerAccountId, providerPaymentRef)` (finding 2: `webhook_metadata_id_from_other_account_not_matched`, for payments and refunds). No match: event `ignored` (`unknown_payment`) and a task, as today for payments.
2. Transaction, `Booking → Payment → Refund` locked: if the payment is not `succeeded` locally but the gateway says it is, apply that first through the payment state machine (`refund_event_before_payment_success_syncs_payment_first`; its own posting comes first).
3. Find the refund by `ourRefundId` (same account; none exist in 3.3), then by `(providerAccountId, providerRefundRef)`; otherwise create it `external` in the status the event says. One task per external refund (`refund_initiated_outside_app_recorded_once`).
4. Refusals without posting (event `ignored` with code, task, nothing else changes): currency differs from the payment's; amount + other non-failed refunds of the payment above the payment's amount (`refund_over_payment_not_posted`; Stripe cannot do this; P10's receivable for external overruns needs 4.5's allocation table, so 3.3 refuses and tells Oscar); amount of a known refund changed.
5. State machine (6.2, refund table, the rows without app requests): `pending → succeeded` posts `refund:<id>:succeeded`; `→ failed` from `pending` posts nothing; `failed` after `succeeded` is checked with `retrieveRefund` and, if the gateway confirms, becomes `reversed` with its posting (`refund_failed_after_success_treated_as_reversal`); duplicates and older states change nothing. The event is linked (`refundId`, `paymentId`, `bookingId`) and its raw body dropped if the customer was erased, as for payments.

### 3.4 Booking effects

Only §2.2's task and the change in net collected. No booking transition.

## 4. Reconciliation in 3.3: the internal ledger check

A daily job (`payments.ledger_check` on the payments maintenance queue, 03:40 business time) and the same function behind a test helper. In the environment's mode it checks:
1. every `succeeded` payment has `payment:<id>:succeeded`; every `succeeded` or `reversed` refund has its postings;
2. per booking: −(funds + overpayments + receivable) = net collected (`booking_ledger_balance_equals_collected_minus_refunded`), and funds/overpayments = the derived allocation;
3. per gateway account: `provider_clearing` balance = Σ succeeded payments − Σ succeeded refunds of that account;
4. no transaction exists without entries (the trigger already prevents it; counted as a canary).

Each difference opens one task (`payments:ledger_check:<check>:<entityId>`, description with codes and ids only) and is never fixed automatically. The test `ledger_check_flags_injected_difference` inserts a balanced adjustment as the owner role and expects the task. Against the gateway (balance transactions, payouts, fees): 4.6, which reconciles `provider_clearing` per account; this design gives it one clearing account per gateway account for that.

Rows that existed before `0032` (succeeded payments in local development databases; production has none, CI starts empty) have no posting: the check reports them as tasks. No backfill (assumption 3).

## 5. Stripe adapter (`adapters/stripe/`, `experimental`)

### 5.1 Manifest and options

`key: 'stripe'`, `status: 'experimental'`, `testOnly: false`, `cardDataHandling: 'hosted_only'`, methods `card`, `apple_pay`, `google_pay` (all through Checkout's card method), currencies `['AUD']` (payments.md: we charge in AUD; more later), countries `'any'`, `checkoutOrigin: 'https://checkout.stripe.com'`, capabilities `{ refunds: 'partial', deferredCapture: false, lookupByIdempotencyKey: true }`. API base fixed at `https://api.stripe.com`, `Stripe-Version: 2026-10-28.endive` pinned (the current version on 2026-11-19, docs.stripe.com/api-versions). The constructor takes an optional `transport` (a fetch-like function) only so tests can inject the fake; `createAdapters` never passes one and no environment variable can change the base URL, so a key can only ever go to Stripe. No new dependency: Node 22's `fetch` and `node:crypto`; form encoding written in the adapter (bigint amounts as decimal strings).

### 5.2 Calls

- **Create**: `POST /v1/checkout/sessions` with `Idempotency-Key` = our key; `mode=payment`, one line (`price_data`: `currency` lower case, `unit_amount` = our amount, `product_data.name` "Booking payment"), `success_url` and `cancel_url` = our return URL, `client_reference_id` and `metadata` = `mt_payment_id`, `mt_booking_id`, `mt_idempotency_key`, `payment_intent_data.metadata` the same, `expires_at` = `createdAt` + 45 min (deterministic for the key; under the attempt's 60 min `pendingExpiresAt`, so the sweep finds it ended). No customer email or name is sent. Amounts below Stripe's minimum (50 AUD cents) or above 99 999 999 are refused before the call (`provider_rejected`, definitive). If the answer carries `Idempotent-Replayed: true`, the adapter fetches the session again: a replay returns the object as created, not as it is now.
- **Retrieve by ref**: `GET /v1/checkout/sessions/:id?expand[]=payment_intent`. A ref that is a PaymentIntent (from a refund event): `GET /v1/checkout/sessions?payment_intent=…`, then the session.
- **Retrieve by key**: `GET /v1/checkout/sessions?created[gte]=createdAt−5min&created[lte]=createdAt+15min&limit=100`, paginated (at most 10 pages), matching `metadata.mt_idempotency_key`. Read-only: retrieving never creates anything (a replayed create after Stripe's 24 h idempotency window would).
- **Cancel**: `POST /v1/checkout/sessions/:id/expire`; on a session no longer open, returns its current state (so cancelling a paid one says `succeeded`).
- **Refund**: session → PaymentIntent, `POST /v1/refunds` (`payment_intent`, `amount`, `metadata` with `mt_refund_id`, `mt_idempotency_key`), `Idempotency-Key`. Retrieve by key: `GET /v1/refunds?payment_intent=…`, matching the metadata.
- **Connection test**: `GET /v1/checkout/sessions?limit=1` (the permission we need), `livemode` must be false.
- Every response object with `livemode: true` while the account is test mode → `provider_auth_failed` (a live key in a test account); keys starting `sk_live_` or `rk_live_` are refused before any network call.

### 5.3 Status mapping (pure, table-tested)

| Session | PaymentIntent | Ours |
|---|---|---|
| `open` | any | `requires_action` (redirect to `session.url`) |
| `complete`, `payment_status = paid` | any | `succeeded` |
| `complete`, `unpaid` | `processing` or none | `pending` |
| `complete`, `unpaid` | `requires_payment_method` or `canceled` | `failed` |
| `expired` | any | `cancelled` |

Event types: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed` (→ `failed`), `checkout.session.expired` → `payment`; `refund.created`, `refund.updated`, `refund.failed` → `refund` (Stripe `requires_action` and `pending` → `pending`; `canceled` → `cancelled`); everything else → `unsupported`. Normalised from `data.object` only: no network in `verifyWebhook` or `parseEvent`.

### 5.4 Webhook signature

Header `stripe-signature` (`t=<unix>,v1=<hex>[,v1=…]`). HMAC-SHA256 over `<t>.<raw body>` with the endpoint secret (`whsec_…`, used as given), compared in constant time against every `v1`; `v0` is ignored. ±300 s around `now` (`stale_timestamp` outside). Header over 4 KB, missing `t`, no `v1`, non-JSON body, `livemode` different from the account's mode → refused without throwing. `providerEventId` = `evt_…`.

### 5.5 Errors (closed list; never Stripe's message)

401/403 → `provider_auth_failed`; 404 `resource_missing` → `provider_not_found`; 400 `idempotency_error` (same key, other parameters) and other 400s → `provider_rejected` (definitive); 409 and 429 → `provider_busy` (retryable); 5xx → `provider_unavailable` (retryable; Stripe saves 500s under the key, so a retry may get the same 500, and the sweep finds the session by key); network failure → `provider_unavailable`; timeout → `provider_timeout`.

### 5.6 Accounts

CLI `pnpm api:cli payments:stripe-test-account --name <text>`: reads `STRIPE_TEST_SECRET_KEY` and `STRIPE_TEST_WEBHOOK_SECRET` from the environment (never from arguments, which shell history keeps), refuses anything that is not a test key, runs the connection test, creates the account `mode = test` encrypted as 3.1 does, and prints the webhook URL once. Only where `APP_ENV` is not production. Guide section in `docs/adding-a-payment-adapter.md`: subscribe the endpoint to the event types of §5.3, pinned to the same API version.

## 6. Contract suite (3.6) changes

- `CreatePaymentInput` keys gain `createdAt` (the compile-time clause is updated, not removed).
- **Decline**: a Checkout Session survives a declined card (the customer can try another), so a subject declares `declineOutcome: 'failed' | 'stays_payable'`. `failed_is_terminal` runs as today for `failed`; for `stays_payable` it checks the object stays `requires_action` and can still be paid, and `failed` is then reachable only through the async path, covered by the mapping table. No clause is removed; the clause count changes, so a future `verified` adapter's evidence line must use the new N.
- **New clauses** (both adapters): `refund_full_and_idempotent`, `refund_partial_follows_capability`, `refund_over_amount_refused`, `refund_of_unpaid_payment_refused`, `refund_retrieve_by_ref_and_key_agree`, `refund_webhook_verifies_and_resolves_payment` (event `refund`, `paymentRef` resolves through `retrievePayment` to the original ref), `gateway_refund_has_no_our_id` (a dashboard refund: subject hook `gatewayRefunds`), and C20 extended to refund calls.
- **Simulator**: gains refunds (`partial`), a "refund on the dashboard" helper and refund webhooks, so the core's DB tests run refunds against it.
- **Stripe local subject**: `StripeProvider` (the registered class) with the fake's transport. **Sandbox subject** (`SANDBOX_SUBJECTS.stripe`): credentials `STRIPE_SANDBOX_SECRET_KEY` and `STRIPE_SANDBOX_WEBHOOK_SECRET`, test keys only; `customerCompletes` drives Stripe Checkout with Playwright and Stripe's test cards; `webhookFor` reads the event from `GET /v1/events` and signs it with the endpoint secret. ## 9. Risks

1. **Classification drift.** The split is derived and posted at every fact and every plan change; a plan-change site that forgets to call `reallocate` leaves the ledger split wrong. Mitigation: money is always recorded (the customer side does not depend on ledger balances), the daily check reports drift, the property test and the scenario table cover every site that changes items today (approval, expiry, cancellation, amendment); a source test lists the writers of `payment_schedule_items` and requires a `reallocate` call next to each.
2. **The fake is not Stripe.** Checkout semantics (decline keeps the session open, replay returns the created object, no lookup by key, 500s saved under the key) are built from the documentation and tested only against my fake. The adapter stays `experimental`; `test:sandbox` and the real e2e are blocked on Oscar's keys.
3. **Money out without 4.5.** External refunds change net collected without moving bookings backwards (task only), refuse over-payment refunds, and leave reminders active; and 3.4 runs in parallel on the same files (`payments.prisma`, the migration number, the state machine), so the second to merge integrates.

## 12. Changes after the plan review (verdict "cambios"; these replace the sections they name)

1. **Process.** Money is un-parked in `main` (PR #70, merged into this branch). Hard limits unchanged.
2. **No entries added to a committed transaction (§1.1).** `ledger_transactions` gets `createdTxId xid8 DEFAULT pg_current_xact_id()` (`@nopii`); a `BEFORE INSERT` trigger on `ledger_entries` refuses an entry whose parent was not created by the current database transaction (`pg_current_xact_id()` is the top-level id, so savepoints do not matter). Test `entries_cannot_be_added_to_committed_transaction` (a balanced pair added later is refused, also as the owner).
3. **Booking under review after money out (§2.2, §2.3, assumption 4).** A gateway refund that leaves the booking claiming coverage it no longer has opens the task `payments:coverage_lost:<bookingId>`. While that task is open (not done or cancelled), the booking gets no balance or deposit reminders and no new charge attempt (409 `booking_payment_under_review`, also through payment links). Tests `coverage_lost_suppresses_reminders` and `coverage_lost_blocks_new_attempt`. Oscar closes the task once he has cancelled or adjusted the booking.
4. **Decline in the contract (§6).** `declineOutcome` is part of the manifest (`capabilities.declineOutcome: 'failed' | 'stays_payable'`), not the subject. `failed_is_terminal` runs unchanged when it is `failed`; when it is `stays_payable` it checks that a declined object stays `requires_action` and can still be paid. A new clause, `terminal_state_is_final`, drives a fresh object to its real terminal state through the subject hook `endAtGateway` (simulator: decline → `failed`; Stripe fake and sandbox: the session expires → `cancelled`; the fake also has the async failure) and repeats the three checks of `failed_is_terminal`: it can no longer be paid, the same key gives the same object in the same state, cancel returns that state. No clause is removed or loosened.
5. **Charging (§5.2, §5.5).** a) `idempotency_error` means "an object already exists under this key": the adapter looks it up by key and returns it (only if none is found is it `provider_rejected`, definitive). `createdAt` always comes from the payment row (`create_retry_uses_row_createdAt`). b) Stripe wants `expires_at` at least 30 min after the call. A create retried more than 14 min after `createdAt` therefore never calls create: it looks the session up by key and returns it, or, if there is none (the first call never arrived), refuses definitively, so the attempt ends `failed` without an object and the customer starts a new one. Test in the fake: `late_create_retry_looks_up_then_refuses`. The same rule removes the risk of a replay creating a second session after Stripe's 24 h idempotency window.
6. **Stale local refunds (§3.3).** Before refusing a refund for exceeding the payment, every local `requested`/`pending` refund of that payment is re-read with `retrieveRefund` and moved to its real state first; only then is the cap checked. A sweep re-reads `requested`/`pending` refunds older than 24 h (every hour on the payments maintenance queue): `refund_pending_requeried`. The daily check also compares, per payment, local succeeded refunds with what the gateway says when a refund event could not be posted (the event stays visible with its code and task).
7. **Customer side reads the ledger (§1.4).** With the booking locked, the posting reads the booking's `customer_funds` and `customer_overpayments` balances and posts `fundsDelta = targetFunds − fundsBalance` (signed) and `overpaymentDelta = customerAmount − fundsDelta` (signed), where `customerAmount` is what the cash side moves (+A in, −R out, 0 for a reallocation). Every posting balances by construction and corrects any split drift; only a drift of the booking's total (a missing posting) is left, and the daily check reports it. Opposite-sign deltas are normal (a refund after a plan change). Plan creation at approval also calls `reallocate` (`approval:<bookingId>:plan`; nothing is posted when nothing was collected).
8. **3.4 (inbound transfers, parallel).** Its `InboundPaymentHooks.onConfirmed` posts `payment:<id>:succeeded` (cash side `provider_clearing:<manual account id>`) and `onVoided` posts `inbound:<id>:voided` as a `reversal` of it: the cash line mirrored exactly, the customer side recomputed by rule 7, like a refund reversal. Tests `inbound_payment_posts_once` and `mistaken_inbound_voided_reverses_ledger_and_allocation`, written by whichever of 3.3 and 3.4 merges second, in the PR that wires them, which goes through the reviewer. 3.4 uses `0032_manual_transfers`: if it merges first, my migration becomes `0033`.
9. **Minor.** `second_plan_split_does_not_collide_with_first` (two plan changes post two keys `schedule:<bookingId>:v<n>:reallocation`). Stripe refund `canceled` maps to `failed` (no money moved). An external refund created already `succeeded` is posted in the same step (checked in `refund_initiated_outside_app_recorded_once`). If `retrievePayment` fails while processing a refund event, the event is `failed` and retried, never `ignored`. The daily check runs in one `REPEATABLE READ` read-only transaction.
