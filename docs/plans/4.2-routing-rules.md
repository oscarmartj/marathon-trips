### 1.1 `payment_routing_rules` (`RoutingRule`)

| Column | Type | Meaning / net |
|---|---|---|
| `id` | uuid v7 | |
| `providerAccountId` | uuid, FK `provider_accounts` ON DELETE RESTRICT | the account this rule sends payments to |
| `method` | `PaymentMethod` | one method per rule |
| `countries` | `text[] NULL` | customer's country of residence; NULL = any country; non-NULL must be non-empty, each `^[A-Z]{2}$`, no duplicates (CHECK via immutable SQL function) |

| `minAmountMinor` / `maxAmountMinor` | `bigint NULL` | inclusive limits, minor units **of `currency`**; `min >= 0`, `max > 0`, `min <= max`, `max <= 10^12` (CHECKs) |
| `priority` | `int` | 0–1000, lower first (CHECK) |
| `enabled` | `bool` default true | |
| `fallbackForRuleId` | `uuid NULL`, FK self ON DELETE RESTRICT, `<> id` | this rule is the backup of that rule (§2.3) |
| `version`, `createdById`, `updatedById`, `createdAt`, `updatedAt` | | optimistic lock, audit columns (`@nopii`) |

One currency per rule (stricter than plan 0.1's `currencies[]` + `CHECK (currencies = ARRAY[currency])`, D1): a limit can only ever be compared with an amount of its own currency, which makes `routing_limit_ignored_for_other_currency` structural.

Trigger `mt_routing_rule_guard` (BEFORE INSERT OR UPDATE), the net behind the service checks: a fallback's target exists, is not itself a fallback (no chains), has the same `method` and `currency`, and belongs to a different account; a rule that is the target of a fallback cannot become a fallback, nor change `method` or `currency`; `providerAccountId` never changes (a rule is moved by deleting and creating). DELETE is allowed (config, fully audited); the self-FK RESTRICT refuses deleting a rule that still has backups. Index `(currency, method, enabled)`.

### 1.2 `provider_account_health` (`ProviderAccountHealth`)

Operational, not money, no PII. Grants: `mt_app` SELECT/INSERT/UPDATE (no DELETE). Rules: `mt_app` SELECT/INSERT/UPDATE/DELETE. `mt_privacy`: nothing.

### 1.3 Backfill

Each existing `active` or `paused` account gets the default rules of §6 for its adapter as of today (`simulator`, `stripe`: card, apple_pay, google_pay; `manual`: payid_transfer, manual_other; all AUD, any country, no limits, priority 100, enabled), with `createdAt = account.createdAt` so today's "oldest account first" order is preserved exactly. Unknown adapter keys get none (warning `active_account_without_rules`). Retired and archived accounts get none (they take no charges). Test `backfill_matches_default_rules` reads the migration SQL and compares its per-adapter method list with `defaultRules(manifest)` of the current code.

## 2. Routing semantics

### 2.1 Query

`{ method?, country, currency, amountMinor: bigint | null, now }`. `country` is the booking's `residenceCountry`, `currency` the booking's, `amountMinor` **always the server's due amount** (`payable(...)` in transaction A, the link target's amount for a payment link, the next payable item for the plan view). The request body never carries an amount (schemas are strict; unchanged). `null` (nothing due, coverage) means limits are not applied.

### 2.2 Algorithm (pure `route(rules, accounts, health, q, env)` in `core/routing-rules.ts`, table-tested; `PaymentRouting` loads the rows in the caller's transaction)

1. A rule **matches** `q` when: enabled; `method` equals (if given); `currency` equals; `countries` is NULL or contains `country`; `amountMinor` is null or `min <= amount <= max` (each bound only if set); and it is inside its adapter's manifest today (method, currency and country supported). A rule outside the manifest (an adapter that dropped a method in a later release) never matches and raises warning `rule_outside_adapter_capabilities`.
2. A rule's account **can serve** when: `status = 'active'`; `callBlockReason(account, manifest, 'create', env) === null` (planned, missing, test-only outside its envs, live outside production, **live with a non-verified adapter**: all excluded here, by the same function the gateway applies again at call time); for the manual adapter, `ManualMethodsService.offered(method, country)`; and, unless the caller asks to ignore health, its breaker is not open (`openUntil <= now` or no row).
3. **Primaries**: matching non-fallback rules whose account can serve.
4. **Backups**: a fallback rule F (target T) is eligible when F matches `q`, F's account can serve, **T's criteria match `q`** (method, currency, country, limits; T's `enabled` ignored for this test) **and T cannot take it** (T disabled, or T's account cannot serve). So a backup takes exactly the payments its primary would take, whenever the primary cannot; it never widens what is offered (a payment outside T's limits is not taken by F).
5. Order: primaries by `(priority, createdAt, id)`, then backups by the same key. Accounts are de-duplicated keeping the first position. Result: `[{ accountId, ruleId }]`; the first one takes a **new** attempt.
6. `methods(q without method)`: every method for which step 1–5 gives at least one account, sorted (as today).

### 2.3 Why rule → rule (not account → account)

`docs/payments.md` asks "cuál es el respaldo de cuál"; plan 0.1 fixed `fallbackForRuleId`. Binding to a rule keeps method and currency equal by construction (trigger) and lets one account back up another for card only. One level only (D2): no chains, no cycles, no recursion; a backup of a backup is expressed with priorities among backups of the same rule.

## 3. Gateway health (the "pasarela caída" signal)

- **Fed only by `ProviderGateway`** (the single door): after every network call (`create`, `retrieve`, `cancel`, `refund`, `test_connection`; never `webhook`, which has no network), a success resets the row (`consecutiveFailures = 0`, `openUntil = NULL`, `lastSuccessAt = now()`); a `ProviderError` with code `provider_unavailable`, `provider_timeout` (and the wrapper's own timeout) or `provider_auth_failed` counts as a failure. `provider_busy`, `provider_rejected`, `provider_not_found` and our own 409 refusals do not count (they are about one request, not the gateway).
- **One atomic UPSERT** with the database clock: failures outside the window restart at 1; reaching the threshold sets `openUntil = now() + cooldown`; `RETURNING` the previous `openUntil` so only the transition to open is audited (`payments.providerAccount.unreachable`, `SYSTEM_ACTOR`, code only) — concurrent failures open it once.
- Settings (editable, validated, in `core/settings.ts`): `paymentGatewayBreakerFailures` (default 3, 2–20), `paymentGatewayBreakerWindowSeconds` (300, 60–3600), `paymentGatewayBreakerCooldownSeconds` (120, 30–3600).
- **Half-open:** after the cooldown the account is routable again; the count is not reset until a success, so one more failure reopens it at once. A connection test from the panel that answers `ok` is a success and closes it.
- The health write runs outside the caller's transaction and is best effort: if it fails, the original result or error of the gateway call is returned unchanged (code-only log line). It never decrypts anything and stores no gateway text.
- **Health never changes an account's status** and never runs the coverage guard (D5): it is automatic and transient; status is staff's decision.

## 4. Fallback safety: never two charges

1. **Fallback only chooses the account of a new attempt.** It never ends, moves or re-sends an existing attempt. The DB guarantees one live attempt per booking (`payments.liveBookingId` unique, P2), so two gateways never hold live collection attempts for the same booking at the same time from our side.
2. **No fallback inside a request.** If `createPayment` fails retryably (timeout, unavailable), the object may exist (plan 3.1 §16 contract): the attempt stays live on its account, the customer gets the neutral 503 as today, and the same idempotency key is retried on **the same account** only. A non-retryable refusal followed by the existing lookup-by-key that returns a clear "none" ends the attempt as failed (3.1, unchanged); only then can a new attempt go elsewhere.
3. **Resume is independent of rules and health (D7):** a live attempt is resumed when its account is still `active` and `callBlockReason` allows `create` (plus same path, method and amount, as today). A rule edit or an open breaker never strands or duplicates it: retries keep its key on its account. Today's code checks membership in `candidates()`; that check moves to this explicit account test.
4. **Replacement keeps P2 exactly** (`replaceLiveAttempt`): only after the gateway confirms cancellation or state; with the gateway down it stays `unresolved` → 409 `payment_attempt_in_progress`, no new attempt. Superseding an unanswered attempt across gateways is **not** built (D6; open question Q1).
5. **Idempotency across gateways:** the gateway key is per attempt (`booking:<id>:attempt:<n>`), so a new attempt on a backup has a new key and the old key is never sent to another gateway. The HTTP `Idempotency-Key` record stores the Payment id: a replay returns the same attempt on the same account whatever the rules say now.
6. A late success on an attempt that was ended keeps the existing path (`late_success_of_cancelled_attempt_becomes_overpayment`).
7. Routing is evaluated in transaction A with the booking locked (unchanged lock order `Booking → Payment`); rules and health are read in the same transaction (plain reads; a rule change committing meanwhile affects the next attempt only).

What "ofrece las demás sin error" means here, precisely: once a gateway is unreachable (breaker open) or paused, the plan view lists only methods other accounts can serve, and a payment started without a live attempt goes to the next account or backup with a 201 and a redirect; if nothing can serve, the plan view answers 200 with `notPayableReason: 'no_payment_method_available'` (no 5xx). The one customer whose own attempt hit the outage keeps the neutral 503/409 of 3.1–3.2 until that attempt is answered or swept (`paymentAttemptExpiryMinutes`): that is the price of never charging twice.

## 5. Coverage (interaction with the 4.1 guard)

- `PaymentRouting.coverage()` keeps its signature and becomes rule-based: for each sales country and AUD, the methods for which some **enabled** rule (primary or backup) matches with `amountMinor = null` and its account can serve **ignoring health** (and the excluded accounts). A backup counts, because it serves when its primary is gone; so pausing a primary with a working backup is not a loss (`pausing_primary_with_backup_rule_no_warning`).
- Every rule create, update and delete runs inside `CollectionCoverageGuard.guard` under its advisory lock (same lock as account status and manual-method changes): before → change → after in one transaction; a loss without `confirmCoverageLoss: true` is `409 coverage_loss_unconfirmed { lost }` and rolls back; with it, the lost pairs go to the audit context. Two people deleting the last two card rules at once: one of them gets the warning (`concurrent_rule_deletes_warn_once`).
- Limits and health are deliberately outside coverage (D8): they would make coverage change with traffic or with each amount. Two non-blocking warnings cover them: `method_unreachable_now` (a covered method/country whose every serving account has an open breaker) and `account_unreachable`.

## 6. Default rules

`defaultRules(manifest)` = one rule per manifest method **except `bnpl`** (born off, `docs/payments.md`), per manifest currency, `countries` = the manifest's list or NULL for `'any'`, no limits, priority 100, enabled. Created in the same transaction as the account by every creation path: the panel (`accounts.service` create, still born paused) and the console commands (`payments:simulator-account`, `payments:stripe-test-account`, the manual account). So behaviour is identical to today until someone edits rules. The panel offers "restore default rules" (adds the missing defaults; same guard and audit).

## 11. Decisions taken without Oscar (conservative and reversible; copied to `docs/done/4.2.md`)

- **D1** One currency per rule; limits in that currency only.
- **D2** Backup = rule → rule, one level, same method and currency, different account.
- **D3** A backup takes over when its primary rule is disabled or its account cannot serve, only for payments the primary would match.
- **D4** Breaker defaults 3 failures / 5 min / 2 min cooldown, as settings.
- **D5** Health never changes account status nor counts for coverage.
- **D6** P2 unchanged: an unanswered attempt is never superseded on another gateway.
- **D7** Resume depends on the account being active and allowed, not on current rules or health.
- **D8** Coverage ignores limits and health (warnings instead).
- **D9** No global switch for non-manual methods: each account's rules are the switch; manual methods keep their `PaymentMethodConfig` switch as well as rules.
- **D10** Default rules for every new account and a backfill; `bnpl` never in defaults.
- **D11** New step-up permission `payments.routingRule.manage`; roles beyond the owner are Oscar's call.
- **D12** Planned catalogue entries are metadata only and are removed when the real adapter lands.
- **D13** Rules can be deleted (audited with the full before state); a rule with backups cannot.
