# Plan 7.4: automations (trigger, conditions, actions, test mode and run log)

Risk high. Reference: `docs/phases/phase-7.md` (row 7.4 and the criteria "an automation cannot move money or change permissions" and "test mode sends no email and changes no data"), `docs/architecture.md` ("Plataforma": automations), `docs/plans/phase-0-architecture.md` (3.1 consumers, 4.3 permissions, 4.5 events, 4.6 mail guard, 4.8 production guard, 4.9 personal data, 5.8 `AutomationRule`/`AutomationRun`, 8 tests, 9.30 deviation), `docs/decisions.md` row 2026-11-12 (automations never approve, decline or cancel bookings), `docs/done/2.5.md`, `docs/done/5.4.md`, `.claude/rules/web.md`. No money: no action reads or writes payments, prices, ledger or booking states.

## 1. What is built

**Module** `apps/api/src/modules/automations/` (business module with flag `module.automations`, one line in `modules.registry.ts`), schema `automations.prisma`, migration `0019_automations`. It imports `CommonModule` (tasks, tags), `TemplatesModule` (wording) and the exported `WebhookDeliveryService`; it only **reads** other modules' tables (bookings, quotes, packages) and writes them only through their services.

**Data.**

| Table | Columns | Guards |
|---|---|---|
| `automation_rules` | `name` (`@pii`, staff text, 1..120), `triggerType` event/schedule, `eventType?` (`@nopii`), `schedule Json?` (`@nopii`, strict zod), `conditions Json` (`@nopii`, strict zod: fact keys, operator codes, uuids and enum values only), `actions Json` (`@pii`: task titles are staff text), `enabled`, `testMode` (default **true**), `enabledAt?`, `ownerUserId` + `ownerKind` (FK to `users(id, kind)`, kind always staff, as `api_keys`), `version`, `deletedAt?`, timestamps | CHECKs: event rule has `eventType` and no `schedule`, schedule rule the opposite; `enabled` implies `enabledAt` and `deletedAt IS NULL`; the API role `mt_app` has no `DELETE` or `TRUNCATE` on it (soft delete only). Index `(triggerType, eventType) WHERE enabled` |
| `automation_runs` | `ruleId` (FK, restrict), `ruleVersion`, `source` event/schedule/manual, `triggerEventId?` (no FK: the outbox is purged), `triggerEventType?`, `scheduledFor?`, `entityType?`, `entityId?`, `testMode`, `status` pending/succeeded/skipped/failed, `reasonCode?`, `steps Json` (`@nopii`), `attempts`, `startedAt`, `finishedAt?` | CHECKs: `event` ⇒ `triggerEventId`; `schedule` ⇒ `scheduledFor`; **`manual` ⇒ `testMode`** (a panel test can never act, enforced by the database). Unique `(ruleId, triggerEventId, scheduledFor) NULLS NOT DISTINCT WHERE source <> 'manual'`: one run per event or per scheduled time, also across API instances. Purged after 90 days |

`steps` is a list of `{ index, action, status: done|simulated|skipped|failed|rolled_back, code?, entityType?, entityId? }` (codes from a closed list, ids only; never rendered text, addresses or titles). The schedule shape is `{ frequency: daily|weekly, time: "HH:MM" (5-minute steps), weekdays?: 1..7[] }` in the `businessTimeZone` setting, instead of the `cron` column of plan 5.8: easier to edit in the panel, no cron parser to add, and no "every minute" rule by mistake (decision 1).

**Triggers** (closed catalogue in code, `triggers.ts`). Each entry: event type, the entity it is about (always the event's aggregate), and the **facts** that conditions may test, loaded read-only at run time:

| Trigger | Entity | Facts |
|---|---|---|
| `bookings.booking.requested`, `.approved`, `.declined`, `.cancelled`, `.expired` | Booking | `status` (current), `packageId`, `editionId`, `raceId`, `fromQuote`, `actorType`, `tagIds` |
| `crm.quote.sent`, `.accepted`, `.expired` | Quote | `status`, `packageId`, `editionId`, `raceId`, `actorType` |
| `catalogue.package.sale_status_changed` | Package | `packageId`, `editionId`, `raceId`, `fromStatus`, `toStatus`, `actorType` |
| schedule | none | none (conditions must be empty) |

Payments, changes, access, auth and automations events are not triggers (decision 2).

**Conditions.** All must hold (AND), at most 10: `is`, `is_not`, `in`, `not_in` on id, enum and boolean facts; `has_tag`, `lacks_tag` on `tagIds`. A fact the trigger does not offer, an operator the fact does not accept, or a value of the wrong kind is a 422 on save; ids that do not exist (package, edition, race, tag) are a 422 too. Evaluation is a pure function, table-tested.

**Actions** (closed list in an `ActionRegistry`, at most 10 per rule, run in order in one transaction):

| Action | Input | Allowed triggers | Permissions the owner must hold | Effect |
|---|---|---|---|---|
| `create_task` | `title` (1..200), `description?` (≤2000), `dueInHours?` (0..8760), `assigneeId?` | all | `common.task.write` | `TasksService.createAutomatedIn`: `source = automation`, `sourceRef = automation:<ruleId>:<runId>:<index>`, linked to the entity; an assignee no longer active leaves it unassigned (step code `assignee_unavailable`) |
| `add_tag`, `remove_tag` | `tagId` | Booking triggers | the entity table's `annotate` permission (`bookings.booking.annotate`) | `TagsService.addTagIn` / `removeTagIn` (new single-tag helpers, insert-or-nothing, audited like `setTags`) |
| `close_tasks` | `onlyThisRule?` | entity triggers | `common.task.manageAutomated` | closes open `source = automation` tasks on the entity ("change state", the safe part of it) |
| `send_email` | `template`: `customer_notice_1..3` or `staff_notice` | customer notices: Booking and Quote triggers; staff notice: all | customer notices: `bookings.customer.read`; staff: none extra | `MailService.enqueue`, `dedupeKey = automation:<runId>:<index>`; customer of the entity (skipped `recipient_unavailable` if anonymised or deleted) or the rule's owner. Wording comes **only** from the 5.4 templates `automations.customer_notice_1..3` / `automations.staff_notice` (four new definitions in `templates/definitions.ts`); the rule never carries text that reaches a customer. Enabling needs a live revision of each template used (422 `automation_template_not_in_use`); one taken out of use later fails the email (`mail_not_sendable`), visible in the mail monitor |
| `call_webhook` | `subscriptionId` | all | `integrations.webhook.manage` | `WebhookDeliveryService.insertDelivery` to that existing subscription, `eventId = runId`, type `automations.rule.fired`, body ids only (`ruleId`, `runId`, `triggerEventType`, `entityType`, `entityId`, `scheduledFor`), so SSRF checks, signing, retries and the development allow-list of 8.4 apply unchanged. A deleted or disabled subscription is a skipped step (`webhook_unavailable`) |

**Never an action:** anything in payments, finance, pricing, changes, access, audit, platform settings or flags, API keys, roles, booking transitions (decision of 2026-11-12) or automation rules themselves. Enforced three ways: (a) the request schema is a closed discriminated union, so an unknown action is a 422; (b) `ActionRegistry.register` throws `automation_action_forbidden` for a definition flagged `movesMoney`/`changesPermissions` or declaring a permission matching `^(payments|finance|pricing|changes|access|audit|platform)\.`, `^integrations\.apiKey\.`, `^automations\.` or `^bookings\.booking\.(approve|decline|cancel)$`; (c) a convention test fails if any file under `modules/automations/` imports the payments, pricing or finance modules, the access admin services, `BookingStateMachine` or the flags/settings admin services. No action publishes a trigger event, so rules cannot chain; events whose actor is `automation` never start a run either (loop guard, defence in depth).

**Execution.**

1. *Event fan-out.* Consumer `automations.rules` (module `automations`, events = trigger list, `whenDisabled: hold`, required because `bookings.*` is listed). In the delivery's transaction: skip events with actor type `automation`; for each enabled, not deleted rule with this `eventType` and `enabledAt <= occurredAt`, insert a run (`ON CONFLICT DO NOTHING`) and its `automations.run` job (`bossDb(tx)`). An event older than 48 h (module was off) inserts the runs as `skipped`/`event_too_old` instead: visible, never acted on.
2. *Schedule.* `automations.tick` every minute: for each enabled schedule rule, the latest occurrence `<= now` in the business time zone; if it is after `enabledAt`, after the last scheduled run and at most 6 h old, insert the run (`ON CONFLICT DO NOTHING`) and its job. Missed older occurrences are not caught up (no flood after an outage).
3. *Run job* (`automations.run`, `{ runId }`). One transaction: lock the run (`FOR UPDATE SKIP LOCKED`, only `pending`), lock the rule `FOR SHARE` (an edit waits), then in order: module off → `skipped/module_disabled`; rule disabled or deleted → `skipped/rule_disabled`; stored rule fails today's schema → `failed/rule_invalid`; owner not active staff → `skipped/owner_inactive` and a system task once (`createSystemIn`, `sourceRef automations:owner_inactive:<ruleId>`); owner's **current** permissions (`AccessService.effective`) miss any action's permission → `failed/automation_cannot_exceed_author_permissions`, nothing executed, system task once; load facts (entity gone → `skipped/entity_gone`); conditions false → `skipped/conditions_not_met`; otherwise run every action. In test mode each action only validates its inputs against current data and records `simulated`. Real runs audit each action with actor `{ type: automation, id: ruleId }` and context `runId`, and publish `automations.run.completed` (`runId`, `ruleId`, `status`). A thrown error rolls everything back; a second transaction marks the run `failed` with the safe code, earlier steps `rolled_back`; known `AppError` codes fail at once, other errors are retried by pg-boss up to 3 attempts.
4. *Manual test* (`POST /admin/automations/:id/test`, `{ entityId? }`): the same pipeline, synchronously, as `source = manual`, `testMode = true` (CHECK), any rule state; returns the steps and each condition's result. The caller also needs the read permission of the entity (`bookings.booking.read`, `crm.quote.read`, `catalogue.package.read`).

**Permissions** (none API-key scopable: a rule acts in the background with its owner's permissions, so an integration that could write rules would act beyond its scopes):

- `automations.rule.read`: rules and runs.
- `automations.rule.manage`: create and edit disabled rules, disable, delete (disabled only), test.
- `automations.rule.enable` (**step-up**): enable, and any change to an enabled rule (including switching test mode off).

Creating, changing or enabling checks that the caller holds every action's permission, through `AccessService.assertPermission` with the caller's session (so `integrations.webhook.manage` also asks for a fresh TOTP); the caller then becomes the owner. Every run re-checks the owner's current permissions (above). Rule writes are audited (`automations.rule.created|updated|enabled|disabled|deleted|tested`) with model `AutomationRule`, so `name` and `actions` go to `AuditPiiValue`.

**Routes** (`/admin/automations`, `@RequiresModule('automations')`): `GET /` list, `GET /catalogue` (triggers, facts and allowed values, actions with their permissions, template slots), `POST /`, `GET /:id`, `PATCH /:id` (with `version`), `POST /:id/enable` (`version`, `testMode`), `POST /:id/disable`, `POST /:id/test`, `DELETE /:id`, `GET /:id/runs` (paged). Zod schemas in `packages/shared/src/schemas/automations.ts`.

**Queues** (`queues.ts` and the migration): `automations.run` (retry 3, backoff), `automations.tick` (every minute), `automations.maintenance` (hourly: purge runs older than 90 days).

**Panel.** `/admin/automations` (list with trigger, on/off, test mode, last run; "New automation" form) and `/admin/automations/[id]` (edit form built from `/catalogue`: trigger, schedule, condition rows, action rows; enable/disable; test-mode switch; "Run a test" with an optional record id showing each condition and step; runs table). Nav link; all copy in `messages/en-AU.json`; step-up handled like the integrations page. Playwright `apps/web/e2e/automations.spec.ts` with `E2E_STAFF_13` (owner).

## 2. Assumptions (conservative, reversible)

1. Structured schedule instead of a cron string (above). Undo: add a `cron` field to the schedule schema.
2. Triggers limited to bookings, quotes and package sale status. Payments events (parked money) and the rest can be added as catalogue entries with their facts.
3. New rules start disabled and in test mode; leaving test mode is an enable-level change with step-up.
4. Whoever last created, changed or enabled a rule becomes its owner (the person who vouched for its current behaviour).
5. "Change state" means closing automation tasks. No booking, quote or package transition (decision 2026-11-12; quote withdrawal could be added later with `crm.quote.withdraw`).
6. "Call a webhook" targets an existing outgoing webhook (8.4) rather than a free URL, so the rule holds no secret or address, and only one that subscribed to `automations.rule.fired` (see section 5, point 2).
7. Emails use four fixed template slots edited in `/admin/templates`, so customer-facing wording always goes through 5.4 (preview, revisions, put into use). More slots is one line each.
8. Tasks created by a rule are titled with the rule's text only, never with customer data; the link to the record carries the context.
9. `AutomationRun` holds ids and codes only; it is registered in the entity registry without a customer link (nothing to anonymise). Erasure (5.5) already handles the tasks, tags and emails the runs created.

## 3. Failure cases and tests (written first)

`apps/api/test/modules/automations/pure.test.ts` (no database): condition evaluation table (every operator, fact kind, empty list, unknown fact); rule schema (closed action union, limits, per-trigger facts and actions, schedule shapes, condition values); schedule occurrence in Australia/Brisbane and Australia/Sydney across a DST change and the 6-hour window; `registering_money_or_permission_action_fails` (each forbidden pattern and flag); every registered action's permissions pass the same check.

`apps/api/test/modules/automations/automations.test.ts` (PostgreSQL):

- `automation_test_mode_sends_and_changes_nothing`: a rule with all five action kinds, enabled in test mode, fired by a real booking event, and the manual test route: counts of `outbound_emails`, `tasks`, `taggings`, `webhook_deliveries`, `outbox_events`, booking `version` and pg-boss jobs in `mail.send`/`webhooks.send` are unchanged; the run is `succeeded` with every step `simulated`. Inserting a `manual` run with `testMode = false` fails on the CHECK.
- `automation_cannot_exceed_author_permissions`: create or enable with an action whose permission the caller lacks → 403; owner loses `common.task.write` after enabling → run `failed`, nothing executed, one system task even after two runs; owner disabled → `skipped/owner_inactive`; webhook action without a fresh TOTP → `step_up_required`.
- Routes: 403 per permission, enable without step-up refused, an API key cannot reach any route, module flag off → 404, unknown action/trigger/fact → 422, delete only when disabled, version conflict 409, audit rows with `[pii]` for `name`.
- Real run: booking requested → task (automation source, linked), tag added, customer email queued with the live template, webhook delivery inserted (ids only), `automations.run.completed` published, actions audited with actor `automation`.
- Idempotency and races: the consumer handling the same event twice and two run jobs at once give one run and one of each effect; two `tick` calls for the same minute give one run; an edit waits for a running run (`FOR SHARE`).
- Atomicity: a failing later action (injected) leaves no task or tag from earlier actions; the run is `failed` with `rolled_back` steps; a deterministic error is not retried.
- Skips: conditions false; event actor `automation`; event older than 48 h; rule enabled after the event; rule disabled between fan-out and run; customer anonymised (`recipient_unavailable`); webhook deleted (`webhook_unavailable`); template taken out of use → enable refused.
- Purge removes runs older than 90 days only.

`apps/api/test/conventions/automations-boundaries.test.ts`: the import rule of point (c). Existing tests that walk routes, permissions, queues, consumers and schema annotations cover the new pieces without changes.

Web: `apps/web/src/lib/automations-panel.test.ts` (form state to request body and back, step and reason labels), `copy.test.ts` keys, and e2e `automations.spec.ts`: create a schedule rule with a task action, run a test and see the simulated step while the task list does not grow, enable it (step-up within five minutes of sign-in), see it listed as on and in test mode, disable it.

## 4. Not done

Payments or other triggers beyond the table, booking/quote/package transitions, free-URL webhooks, rule-specific email text, variables in task titles, cron expressions, catch-up of missed schedules, retrying a failed run from the panel, per-record scoping of rules, a dashboard of automation statistics.

## 5. Changes after the plan review (round 1)

Where this section and sections 1 to 4 differ, this section wins.

1. **Test mode never writes.** A run is a test if `run.testMode` (copied from the rule at dispatch) **or** the rule's `testMode` at execution is true. System tasks (`owner_inactive`, `automation_cannot_exceed_author_permissions`, `rate_limited`) are opened only by real runs; a test run records the reason code and nothing else. `automation_test_mode_sends_and_changes_nothing` adds both cases: owner without `common.task.write` + "Run a test" adds no task; an event dispatched in test mode and executed after test mode is switched off acts in test mode.
2. **Webhooks go through the 8.4 catalogue.** `automations.rule.fired` is added to `WEBHOOK_EVENT_CATALOGUE` (read permission `automations.rule.read`, contract `ruleId`, `runId`, `triggerEventType?`, `entityType?`, `entityId?`, `scheduledFor?`, ids and codes only). The body is built with `buildOutboundBody`. Saving a rule with `call_webhook` needs the subscription to list that type (422 `webhook_not_subscribed`); at save and at every run, the subscription's creator must still hold `automations.rule.read` and the read permission of the trigger's entity (`bookings.booking.read`, `crm.quote.read`, `catalogue.package.read`); otherwise 422 at save and step `skipped/webhook_unavailable` at run. Nothing is ever fanned out to that type from the outbox (it is never published).
3. **Retries.** A non-`AppError` failure rolls back, then a second transaction keeps the run `pending`, increments `attempts` and stores the safe code; pg-boss retries. Only the last attempt (3) marks it `failed`. Known `AppError` codes fail at once. The hourly maintenance moves runs `pending` for more than 6 h to `failed/stale`. Test: transient error, retry, success with one effect.
4. **Rule changed after dispatch.** If the rule's `triggerType`/`eventType` no longer match the run (or the entity type differs), `skipped/rule_changed`. The run stores the `ruleVersion` actually executed (updated at execution). Test.
5. **Volume caps.** At most 50 enabled rules (422 `too_many_enabled_rules`, checked under an advisory lock); at most 100 real runs per rule per rolling hour, beyond that `skipped/rate_limited` and one system task while open; at most one customer `send_email` per rule (422). Tests for all three.
6. **Customer emails.** `customer_notice_1..3` are service notices about the customer's booking or quote (no promotions: said in the template label and description shown in the editor), sent as `transactional`, and the action **skips customers whose address is in `EmailSuppression`** (any scope) with `skipped/recipient_suppressed`. No unsubscribe link (no generic unsubscribe route exists; noted for Oscar). Variables: customer notices `givenName`, `reference`, `trip`, `link`, `brandName` (no money). `staff_notice`: `ruleName`, `reference`, `adminLink`, `brandName` (no customer name or address); on an entity trigger it needs the entity's read permission (`bookings.booking.read`, `crm.quote.read`, `catalogue.package.read`), re-checked at run like every action permission.
7. **Revocation race.** The run locks the owner row (`SELECT … FROM users WHERE id = $owner FOR SHARE`) before `AccessService.effective`, so a concurrent role change (which takes `FOR UPDATE` through `lockUsers`) is either fully before or fully after the check.
8. **Decision (explicit):** unlike an API key (plan 4.3), a run exercises `integrations.webhook.manage`, a step-up permission, without a session. Accepted because the owner passed a fresh TOTP check when saving or enabling the rule, the permission is re-checked at every run, and the action can only target an already-configured, opted-in subscription. Also in `docs/done/7.4.md`.
9. Two `call_webhook` actions to the same subscription in one rule are a 422 (`duplicate_webhook_action`).
10. Tags: at save the tag must exist and its `entityTypes` must be empty or include `Booking`; at run a tag that no longer exists is `skipped/tag_unavailable` (checked before writing, no FK error).
11. **Facts are snapshotted at dispatch** (in the consumer's transaction, stored as `facts Json @nopii` on the run, strict schema), so every rule of one event sees the same facts whatever order the jobs run in, and a tag added by one rule never decides another. The manual test loads facts at test time. Actions still check that the entity exists at run (`skipped/entity_gone`). Test: two rules on one event, the first adds a tag, the second has `lacks_tag` on it and still runs.
12. Migration conventions: `deletedById`; CHECKs on `status` and `reasonCode` (closed list), on `entityType`/`entityId` (both or neither) and on `source`/`triggerEventId`/`scheduledFor`; every `ON CONFLICT` repeats the partial-index predicate. Bookings, quotes and packages are read through small read functions exported from each module's `index.ts` (`readBookingForAutomations`, `readQuoteForAutomations`, `readPackageForAutomations`), as `readBookingForPayments` does, not with Prisma from `automations`.
13. Schedules: one occurrence per local calendar date. A local time that does not exist (DST gap) moves forward by the gap (02:30 becomes 03:30); a repeated hour fires once, at the earlier instant. A rule never gets a second scheduled run on a local date that already had one (checked in the zone in force at the tick), so a change of `businessTimeZone` cannot fire a rule twice in one day. The tick is idempotent (unique index plus the one-run-per-local-date check, tested with two ticks at once), so pg-boss's one scheduled job per minute needs no extra `singletonKey`. Tests in `pure.test.ts`.
14. A manual test of a deleted rule is a 404. `GET /:id/runs` shows entity ids to holders of `automations.rule.read` only (no names or other data): accepted and noted.
15. Tests added to section 3: points 1, 3, 4, 5, 9, 10 and 11; module switched off while a run is pending (`skipped/module_disabled`); a table of every action × every trigger (allowed or 422); a test that every stored `steps` entry and `reasonCode` matches the closed lists (no free text), including after a failure.
