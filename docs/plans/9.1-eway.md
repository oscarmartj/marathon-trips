## 3. Assumptions the sandbox run must confirm

Each assumption gets a test against the fake now and a line under "Sin verificar" in `docs/done/9.1.md`.

- **A1** A `SecuredCardData` code given to `POST /3dsenrol` can still be used once for the `POST /Transaction` that follows, within its lifetime. If false, the adapter switches to the documented token-customer route (`CreateTokenCustomer`, then `TokenPayment`). That change is local to the adapter and keeps card data at eWAY, but it stores a card at eWAY, so it would get its own reviewed change.
- **A2** The code lives long enough for a 3-D Secure challenge (minutes). If not, a slow challenge ends in `V6148`, and the session fails as `card_not_authenticated` with no money moved.
- **A3** The `Cerberus` SDK runs on our card page, and its `onComplete` fires for both success and failure. The SDK's script and frame origins are put in the CSP. If wrong, the card page shows no challenge, and the session expires as cancelled with no money moved (§6.5).
- **A4** `GET /Transaction/InvoiceRef/{ref}` finds a `POST /Transaction` within seconds of its answer or timeout, for approved and declined transactions alike. It answers a not-found error (a `V6…` code under HTTP 200 or 404) when there is none.
- **A5** The `InvoiceReference` of a refund is stored and found by the same query, and its result says it is a refund of our transaction (`OriginalTransactionId`). If false, an unknown refund outcome can only be resolved by staff (§7).
- **A6** A refund answer with `TransactionStatus: true` means done. eWAY has no pending refunds.
- **A7** `MaxRefund` on the original transaction is what can still be refunded, so it covers refunds made in MYeWAY.
- **A8** A call with bad credentials answers 401, and a sandbox call with a live key is refused. eWAY keys carry no documented test or live marker, so the host protects test money, as for PayPal and Pin.
- **A9** `GET /Transaction/InvoiceRef/mt_probe_<random>` with good credentials answers the not-found error and moves nothing. It is the authenticated probe of `testConnection` and of every call that would otherwise answer from our store.
- **A10** Direct Connection never adds a surcharge. The answer's `TotalAmount` equals ours; anything else opens a mismatch task (§6.8).
- **A11** The public API key (`epk-…`) is meant for the browser and can only set up Secure Fields: it cannot charge, refund or read transactions.
- **A12** Error answers carry HTTP 4xx or 5xx with `Errors`, or HTTP 200 with `TransactionStatus: false`. `S5666` is an unknown outcome, never a decline.
- **A13** A transaction refused for `D4494` (duplicate) charged nothing.
- **A14** eWAY sends payers no receipt by default (the guide tells Oscar to check and turn it off, as for Pin).

## 4. Architecture: reuse card sessions, with two structural capabilities

`CardSessionProvider` (4.4) keeps the state before the card in our store and makes **at most one charge per session**. eWAY Secure Fields work the same way: nothing exists at eWAY until the card is submitted, and eWAY has no idempotency key. So the registered class is `CardSessionProvider(EwayGateway, store)`, and `EwayGateway` implements `CardTokenGateway`. Two things differ from Pin, and each becomes a capability any gateway can declare. Neither is an exception in a subject.

### 4.1 Authentication before the charge (`CardTokenGateway.authentication: 'before_charge'`)

Pin charges first and then challenges: its charge answers 202 and a redirect, and `verify` reads the charge afterwards. eWAY authenticates first (`3dsenrol` → challenge → `3dsverify`) and only then charges.

- `CardTokenGateway` gets a member `authentication: 'after_charge' | 'before_charge'`. Pin declares `'after_charge'`, which keeps today's path unchanged.
- For `'before_charge'` the gateway also implements:
  - `beginAuthentication(ctx, req)`. It moves no money. It answers `{ kind: 'challenge', authRef }`, `{ kind: 'declined', code }` or `{ kind: 'refused', code }`.
  - `completeAuthentication(ctx, authRef)`. It moves no money. It answers `{ authenticated: true, proof }` or `{ authenticated: false }`. `proof` is opaque and lives only in memory, within one request: it is the `ThreeDSecureAuth` object, which is never stored or logged.
  - `charge(ctx, req)` takes the `proof`.
- Session path for `'before_charge'` (store transitions in §11):
  1. `open`: the card page shows Secure Fields.
  2. **submit**: CAS from `open` to `authenticating`, with `authRef` and `authCardHash` set once and `submittedAt` still null. Then `beginAuthentication`. Nothing at eWAY can move money from here, because only our `POST /Transaction` can.
  3. **authorise** (new endpoint, §10.1): the browser sends back `accessCode` and `secureFieldCode` after `Cerberus` completes. The service locks the attempt and checks that it is live, the booking is payable and the account is `active`, through `ProviderGateway.call(…, 'create', …)`. Then:
     - `completeAuthentication`;
     - CAS from `authenticating` to `submitting`, with `submittedAt` set (the **one** `POST` marker, as in 4.4);
     - `charge`.
     `accessCode` must equal `authRef`, and `sha256(secureFieldCode)` must equal `authCardHash`. Otherwise the request is refused and the session is unchanged. This stops a second card being charged on another card's authentication.
  4. Not authenticated (`Enrolled: false`, or an `AuthStatus` other than `Y`/`A`): the session ends `failed` with `card_not_authenticated`, and nothing is posted (as D6 of 4.4, `fallback_ok: false`).
- **Cancel and expiry before the charge are final.** An `authenticating` session with no `submittedAt` can go to `cancelled`, because no charge can follow. The authorise CAS fails on a cancelled session. So the contract clause `cancel_is_idempotent_and_final` holds without guessing at eWAY. An abandoned challenge expires as `cancelled` (`expired`), never `pending`, and it never brings late money. This is simpler than Pin's A5/A6.
- **View for the core** (checked against `nextStatus`): `open` → `requires_action`; `authenticating` without `submittedAt` → `requires_action` (the customer still has to act); `submitting` → `requires_action` (as Pin); then `succeeded`, `failed` or `cancelled`. Nothing moves from `pending` back to `requires_action`. Pin's `authenticating` (with `submittedAt`) stays `pending`.

### 4.2 A gateway with no events (`capabilities.gatewayEvents: 'none'`)

Today every adapter has signed webhooks, and nine clauses exercise them. eWAY has none. The options were an exception for eWAY, which is forbidden, a fake event, which 4.4 refused to invent, or a declared capability with checks that replace the webhook checks. This plan takes the third.

- **Manifest.** `capabilities.gatewayEvents?: 'none'`. Absent means "signed events", as today. It is declared on the gateway's own manifest, a fact about eWAY, and `CardSessionProvider` copies it.
- **Registry rules** (`registry.ts`, both directions). With `'none'`:
  - `signatureHeaders` is empty;
  - `prepareWebhook`, `disputes`, `reconciliation.activity` and `refundEventOurId` are absent;
  - `account.webhookSecret.source` is `'generated'`.
  Without it, `signatureHeaders` must be non-empty. `CardSessionProvider` does not set `refundEventOurId` when the gateway has no events.
- **Adapter behaviour.** `verifyWebhook` always answers `{ ok: false, code: 'malformed' }` and never throws. `parseEvent` always answers `null`. A delivery to such an account's webhook URL is refused with 400 and recorded in `webhook_rejections`, as any malformed body is today. This needs no change in `webhooks.service.ts`.
- **Contract branches.** Same clause names, still 37, so the evidence line `N/N` is unchanged. The subject's `webhookFor` answers `NO_GATEWAY_EVENT` for every object. Today that marker is allowed only with `preCardSession` and only before payment; it becomes allowed always with `gatewayEvents: 'none'`, and a subject that answers it without the capability still fails. With the capability:

  | Clause | What it checks instead (no check is dropped without a replacement) |
  |---|---|
  | `webhook_verifies_and_matches_retrieve` | The pull path: after `customerCompletes`, `retrievePayment` by ref and by key agree on the final state without any event. `signatureHeaders` is empty |
  | `webhook_previous_state_and_duplicate` | Two retrieves give the same state, and an older read never overrides a newer one: a read before payment is `requires_action`, a later one `succeeded`, and nothing goes back |
  | `webhook_rejections` | `verifyWebhook` refuses (`ok: false`) a body shaped like an eWAY transaction result, with and without any header, at any time |
  | `verify_and_parse_never_throw` | Same garbage bodies and huge headers as today: never throws, `parseEvent` is `null` |
  | `refund_webhook_verifies_and_resolves_payment` | `retrieveRefund({ ref })` of an app refund carries our refund id, and its `paymentRef` resolves through `retrievePayment` |
  | `gateway_refund_has_no_our_id` | `retrieveRefund({ ref })` of a dashboard refund (made by the fake) carries no id of ours, and its `paymentRef` resolves |
  | `dispute_*` | Unchanged: no `disputes`, so each checks that nothing dispute-like is claimed |
  | `no_secret_in_results_or_errors` | Unchanged, without the webhook outputs |

- **Why this is safe.** P6 is about webhooks that exist; an adapter with none has nothing to forge. Every state the core needs it already gets by pulling:
  - the answer of the one charge, on `authorise`;
  - `sync` when the customer is back (`refresh`);
  - `drive`, the expiry sweep (`maintenance.service.ts`) and `PaymentAttemptSyncService`;
  - the refund sweep (`refund-sync.service.ts`);
  - 4.6's object comparison.

  eWAY's results are synchronous, so the one gap is money moved at eWAY without us (§8).

### 4.3 Gateway-owned reference shapes

`CardSessionProvider` and migration 0039 hard-code Pin's `^ch_…$` and `^rf_…$`. The gateway gets `chargeRefPattern` and `refundRefPattern`. The eWAY adapter names its objects `ewt_<TransactionID>` (charge) and `ewr_<TransactionID>` (refund), with `TransactionID` digits only (1–19). So no reference can be taken for another gateway's. The DB checks of 0039 become the union of the two shapes (§11). `sessionOf` uses the gateway's pattern.

### 5.1 Manifest

- `key: 'eway'`, `displayName: 'eWAY'`, `status: 'experimental'`, `testOnly: false`, `cardDataHandling: 'hosted_only'`.
- `methods: ['card']` (Apple Pay and Google Pay need domain verification: out of scope), `currencies: ['AUD']`, `countries: 'any'`.
- `cardFields`:
  - `driver: 'eway_secure_fields'` (new member: the card page picks its driver, §10.2; Pin gets `'pin_hosted_fields'`, which keeps its page unchanged);
  - `scriptUrl: 'https://secure.ewaypayments.com/scripts/eWAY.min.js'`;
  - `frameOrigins: ['https://secure.ewaypayments.com']` (A3);
  - `challengeOrigins.test`: the `Cerberus` and challenge origins (A3);
  - `challengeOrigins.live: []`.
- `capabilities`: `{ refunds: 'partial', deferredCapture: false, lookupByIdempotencyKey: true, declineOutcome: 'failed', gatewayEvents: 'none' }`. `preCardSession` comes from `CardSessionProvider`. No `disputes`, no `reconciliation` (§9).

### 5.2 Credentials (4.1 account setup)

- `apiKey`, label "API key (sandbox account)", and `apiPassword`, label "API password (sandbox account)". Anchored patterns that allow the documented characters only; their samples are built at runtime from filler, never shaped like a real key.
- `publicApiKey`, label "Public API key (sandbox account)", pattern `^epk-[A-Za-z0-9-]{20,60}$`, `exposure: 'card_page'` (as Pin's publishable key, D4 of 4.4; A11). It is stored encrypted, never returned by the panel, and only sent in the view of an open session of that account.
- `webhookSecret: { source: 'generated' }`. It is unused, and every delivery is refused (§4.2). D7 keeps 4.1's account flow unchanged instead of adding a `none` source.
- `testConnection`: the probe of A9. A good answer is `{ ok: true }`; 401 or 403 gives `provider_auth_failed`. It never throws, and no webhook check applies.

### 5.3 HTTP layer (`adapters/eway/http.ts`)

- The host is fixed in code by `ctx.mode`: test `https://api.sandbox.ewaypayments.com`, live `https://api.ewaypayments.com` (unreachable while `experimental`). No option or variable changes it. A unit test checks that a test context never reaches another host.
- `fetch` with `redirect: 'error'`, a 4.5 s timeout (8 s for `POST /Transaction`, still inside the wrapper's 10 s), JSON, body capped at 1 MiB.
- Only codes are read (`ResponseMessage`, `Errors`, `ResponseCode`), compared with closed lists in `mapping.ts`. eWAY's free-text messages, the customer's details and the card fields of the answer never leave the adapter.
- Mapping:
  - 401/403: `provider_auth_failed`, not retryable;
  - 404: `null` or `provider_not_found`, as the member requires;
  - 429/5xx: `provider_busy` or `provider_unavailable`, retryable;
  - a timeout: `provider_timeout`, retryable;
  - `S5666`: unknown (A12).
- References are checked before they go in a URL: `ewt_` or `ewr_` with digits; invoice references `^cs_[0-9a-f]{32}$` or `^mtr_[0-9a-f]{32}$`. They are checked after the probe, so bad credentials still give `provider_auth_failed`.
- API key, password, public key, the payer's details, `secureFieldCode`, `AccessCode` and `ThreeDSecureAuth` never appear in a `ProviderError`, a result or a log (C20 and a unit test).

## 6. Payments

### 6.1 Money
`TotalAmount` is the session's `amountMinor`, as an integer (≤ 10 digits, checked; ours is capped at 999 999 999). `CurrencyCode: 'AUD'`. No float is ever involved.

### 6.2 Create
As Pin: `createPayment` calls the probe and creates or gets the session by our idempotency key, then answers the session's state. Nothing exists at eWAY.

### 6.3 Submit: `beginAuthentication`
- The card page sends `secureFieldCode`. The server takes the payer's first and last name, email and phone, which 3-D Secure 2 requires, from the booking's lead traveller (5.2) under the attempt lock. They are sent only to eWAY and not stored in our tables (as D10 of 4.4). If the phone is missing, the page asks for it, and it is sent once and not stored.
- CAS `open → authenticating` with `authCardHash = sha256(secureFieldCode)`, then `POST /3dsenrol` with the payer's `Customer` fields, our amount and `SecuredCardData` (no money moves).
  - Answer with `AccessCode`: store `authRef`, and answer `{ kind: 'authenticate', accessCode }` to the page.
  - A definitive refusal (`V6…` validation, an expired code): `failed` with `card_declined` or `provider_rejected`; nothing was charged.
  - Unknown outcome: the session stays `authenticating` without `authRef`. The page shows "try again", which starts a new attempt. A session in that state cannot be authorised and expires `cancelled`, because no charge can come from it.

### 6.4 Authorise: the one charge
1. Check `accessCode === authRef` and the card hash (constant-time compare). The verify counter (`MAX_VERIFY_CALLS`, 3) is shared with Pin's.
2. `POST /3dsverify`. If not authenticated, the session ends `failed` with `card_not_authenticated`, and nothing is posted. If unknown, the session is unchanged and the page may retry within the counter.
3. CAS `authenticating → submitting` with `submittedAt`. Only one request wins; the loser answers `not_open`.
4. `POST /Transaction` with `Method: ProcessPayment`, `TransactionType: Purchase`, `SecuredCardData`, `PaymentInstrument.ThreeDSecureAuth = proof`, `Payment.InvoiceReference = <session ref>` (36 characters, ≤ 50), our amount, and `CustomerIP`.
   - `TransactionStatus: true` with `A2000` and our amount: `succeeded`, `chargeRef = ewt_<id>`.
   - A decline (`D4…`, `F…`): `failed` with a mapped code and `chargeRef` (the transaction exists, unsuccessful).
   - `D4494` duplicate: `failed` with `provider_rejected` (A13), no money.
   - Timeout, 5xx or `S5666`: unknown. The session stays `submitting`. It is **never posted again**: `settle` searches `GET /Transaction/InvoiceRef/<session ref>` (A4) on every read, as 4.4's step 5 does.

### 6.5 Statuses and sweeps
`settle` for `'before_charge'`:
- `open` or `authenticating` with no `submittedAt`, past `expiresAt`: `cancelled` (`expired`).
- `submitting`: search by invoice reference. A successful transaction gives `succeeded`; an unsuccessful one gives `failed`; none, past `expiresAt`, gives `failed` (`outcome_unknown`).
- `failed` with `outcome_unknown` and no `chargeRef`: searched again on every read. A late success becomes `succeeded` (4.4, 18 M2) and is refundable.
- If the query errors because the invoice reference is non-unique: `provider_unavailable` (retryable) and an `extra_charge` task. One `POST` per session means this cannot come from us, but it is never lost.

Expiry is the same as 4.4 (D12): `pendingExpiresAt` + 30 min.

### 6.6 Retrieve, lookup, cancel
- By key: the session. By `cs_` ref: the session, settled.
- By `ewt_` ref: the linked session, or `GET /Transaction/{id}` and its `InvoiceReference` to find and link the session (4.4, 18 M3).
- Cancel: `open` or pre-charge `authenticating` becomes `cancelled`. `submitting` is answered as it is, so it is never replaced while unknown (P2).

### 6.7 The core's guards
`authorise` goes through `ProviderGateway.call(accountId, 'create', …)` after the service's checks under lock (live attempt, payable booking, active account). So paused, retired, unverified-live and live-outside-production are refused by the existing guard matrix, and the circuit breaker counts it as a create. `submit` moves no money, but it uses the same path, as in 4.4.

### 6.8 No surcharge, amount from the server
The amount comes only from the session, which got it from the core. The answer's `TotalAmount` must equal it; otherwise the payment is applied as received and the core's existing amount mismatch task opens (A10). There is no surcharge code anywhere in the integration. The guide tells Oscar to keep surcharging off in MYeWAY.

## 7. Refunds

- `createRefund` (core of 4.4, unchanged): an intent first, then one `POST /Transaction/{id}/Refund` with `Refund.TotalAmount`, `CurrencyCode` and `InvoiceReference = mtr_<intent id hex>`. Our refund id is therefore at eWAY. The amount is checked first against `MaxRefund` (A7): an amount over it is `provider_rejected`, as are `V6150` and `V6151`.
- Answer with `TransactionStatus: true`: `succeeded`, `ewr_<id>` (A6). `false`: `failed`, with a mapped code.
- **Unknown outcome: never posted again** (D8 of 4.4). The gateway gets an optional `refundByOurRef(ctx, intentRef)`, which is `GET /Transaction/InvoiceRef/mtr_…` (A5). When a gateway has it, `bindCandidate` binds by that exact match instead of the time-window search, which stays for Pin. If A5 is false, the intent stays `submitting`. Its lookups answer `provider_unavailable`, the 4.5 sweep keeps asking, and after 24 h its task asks staff to check MYeWAY. Nothing is sent again.
- `retrieveRefund({ ref: 'ewr_…' })`: `GET /Transaction/{id}`; `paymentRef` comes from `OriginalTransactionId`; `ourRefundId` comes from the intent bound to it.
- `refundState(chargeToken)`: the transaction's amount and `amount - MaxRefund`, so dashboard refunds lower what we can refund (A7).
- **Refund race (4.4 lessons):** two concurrent `createRefund` calls with one key share one intent (the store's unique key and CAS); with two keys each has its own intent and `MaxRefund` is read before each `POST`. eWAY's `V6151` refuses an over-refund either way. The store battery covers both.

## 8. What no events costs (recorded limits)

- **A refund made in MYeWAY** is not seen until someone reads that payment, for example when staff start an app refund (`refundState` shows less), or 4.6's object comparison. 4.6 compares our objects only, so an unknown dashboard refund would go unnoticed. Follow-up 9.1-F2: give the eWAY reconciliation `listSettlements` from eWAY's settlement search (named in the reference, not read in detail), and flag refunds that are not ours. Until then the guide says: "refund from the panel only".
- **A chargeback or a fraud reversal at eWAY** is not reported to us at all. The reference documents no disputes API. Oscar's MYeWAY email notices are the only channel. Recorded for Oscar; disputes are out of this task (§9).
- **No extra latency for customers.** The result is known when `authorise` answers. A lost answer is found by the return page's `refresh`, then the sweeps.

## 9. Disputes, reconciliation and fees: not declared

No `disputes`, no `reconciliation`, `feesImported` false, and the report says "fees not imported", as for Pin and PayPal. The dispute clauses check that nothing dispute-like is claimed; the reconciliation clauses check that the methods are absent.

## 19. Lessons of the 4.4 reviews, applied

| 4.4 finding | Here |
|---|---|
| One charge per session, ever | `submittedAt` once, set by the `authorise` CAS; the trigger refuses a second; a concurrency test (§6.4, §11) |

## 20. Plan review, round 1 (approve with changes): how each finding is resolved (overrides the sections above)

**Source note.** Every eWAY fact in §2 was read through the agents' fetch tool, which returns a summary. The plan reviewer's proxy could not open eway.io or eway.com.au. So **all eWAY facts are UNVERIFIED** until the sandbox run, not only A1–A14. The response codes named below (A2008, A2010, A2011, A2016) come from the reviewer and are unverified too.

- **M1, `ManualProvider` has no signature headers.** The registry gets one direction only: `gatewayEvents: 'none'` ⇒ `signatureHeaders` empty. There is no "otherwise non-empty" rule. `manual` is not touched and keeps `bad_signature`. Its manifest is in the snapshot of §14.
- **M2, migration 0041.**
  - `card_sessions_submitted_check` also allows `failed` with `submittedAt` null, but only with `flow = 'before_charge'`, `authCardHash` set, `chargeRef` null and a pre-charge failure code (`card_not_authenticated`, `card_declined`, `provider_rejected`, `provider_auth_failed`, `too_many_attempts`).
  - The trigger lists the exact edges out of `authenticating` without `submittedAt`: to `submitting`, to `cancelled`, or to `failed` with those codes. Never to `succeeded`.
  - `card_refund_intents_charge_ref_check` widens to the union of the two shapes.
  - Each edge gets a store test.
- **M3, approvals other than `A2000`.** `TransactionStatus: true` means charged, whatever the `A…` code. The amount is taken from the answer's `TotalAmount`. If it differs from ours, the core's existing amount mismatch handling opens a task. A table-driven test covers `A2000`, `A2008`, `A2010` (partial amount), `A2011` and `A2016`, all unverified.
- **M4, `D4494` duplicate.** It gets its own outcome, `duplicate`, and never counts as "no money". The session fails with `provider_rejected`, and a `duplicate_transaction` task opens. Then every session of the same booking and account that ended `failed` with `outcome_unknown` (or is still `submitting`) is searched again by its invoice reference. A charge found there is applied through the 4.4 M2 edge (`failed → succeeded`). Test: `duplicate_after_unknown_reveals_earlier_charge`.
- **M5, nobody rereads a `failed` attempt.** For `gatewayEvents: 'none'`, a `submitting` session goes to `failed` with `outcome_unknown` only on a **definitive** not-found answer (the documented not-found error, never a transport error). That answer must also come at least `NOT_FOUND_GRACE` (15 min) after `submittedAt` and past `expiresAt`. Until then the attempt stays live, so P2 still blocks a second payment, the sweeps keep reading it, and the 24 h "unresolved" task fires. What remains after a definitive not-found is 4.6's `compareObjects`, which rereads `failed` payments within `lookback`. It opens a `payment_status_differs` task and does not record the money. A reconciliation test on an eWAY account with a late success pins that.
- **M6, events or reconciliation.**
  - `reconciliation.activity` is **not** forbidden with `'none'`.
  - The registry refuses `status: 'verified'` with `gatewayEvents: 'none'` unless the manifest declares `reconciliation` (activity or settlements) and `disputes`. eWAY declares neither, so it **cannot become `verified`** until 9.1-F2 brings settlements and a disputes channel.
  - `EVENTLESS_ADAPTER_KEYS = ['eway']` is a closed list. The registry refuses `'none'` on any other key, and a test pins the list.
  - P5 ("a refund made at the gateway becomes an external `Refund` and a task") is **not met for eWAY** until 9.1-F2. This is recorded in `docs/done/9.1.md`.
- **M7, stronger replacement checks.** For `'none'`, two subject hooks are required:
  - `loseNextAnswer(kind: 'charge' | 'refund')`: the fake processes the request, then times out;
  - `postCount(ref)`: how many money posts the fake received for that session or intent.

  `webhook_verifies_and_matches_retrieve` loses the charge answer. A read must then find the charge, link it and answer `succeeded`, with `postCount = 1`. `webhook_previous_state_and_duplicate` loses a refund answer. `retrieveRefund` by key must then find the refund with our id, a second `createRefund` with the same key must not post, and `postCount = 1`. These are the eventless form of P5's `webhook_before_provider_response_matches_app_payment` and `…_refund`.
- **m8, the DB knows the flow.** `card_sessions.flow` (`after_charge` or `before_charge`) is set at insert and fixed. The trigger requires `before_charge` exactly for accounts whose `adapterKey` is `eway`, reading it as it reads `mode`. Each flow's CHECK allows only its own prefixes (`ch_`/`rf_` or `ewt_`/`ewr_`) and its own edges. Pin sessions can never take an eWAY edge or prefix.
- **m9, the payer's details.** Name, email and phone come from the payment's `payerCustomerId`, as the email does today, never from the lead traveller. With no phone, `submit` answers 409 `card_session_phone_required` and moves nothing. A test checks that a 400 or 409 answer never echoes `secureFieldCode`, `accessCode` or the phone.
- **m10, a non-unique reference.** The task (`card_reference_not_unique`) tells staff to find the transaction in MYeWAY. A CLI command, `pnpm api:cli payments:card-session-bind --ref cs_… --transaction <id>` (owner-only use, audited), binds the session after `GET /Transaction/{id}` confirms that the transaction carries that session's `InvoiceReference`, our amount and our currency. Nothing else can bind it.
- **m11, CSP and the bank's challenge frame.** In 3-D Secure 2 the challenge iframe usually comes from the issuer's ACS, on any domain. The closed `frame-src` (eWAY's origins only) may block it. The payment then fails without a charge (`card_not_authenticated` or expiry), so it never moves money, but it may never work. Opening `frame-src https:` weakens the CSP and needs its own review after the sandbox run. A3 now says this. Reconsidering D5 (keeping the code in the browser across a redirect to `Default3dsUrl`) belongs to that review too.
- **m12, D1 is conditional.** The phase rule asks for a sole trader **of travel**. For eWAY, travel is unknown, as it is for every other candidate, so §1 overstated it. `docs/decisions.md` (2026-11-20) chose Pin because Pin has signed webhooks, a disputes API and metadata search, and eWAY still lacks the first two. **D1 is conditional:** eWAY comes first only for a free sandbox, a sole trader accepted and a readable API. If eWAY refuses travel in writing, it goes back to `planned` and GoCardless (F1) or another candidate takes its place.
