# Plan 6.3: changes to a confirmed booking, with the difference recalculated (partial: money parked, simulator only)

Risk: high (prices, payments, stock, personal data, permissions). Row of `docs/autonomous.md`: "6.3 | 5.1 | Alto · parcial: cambio con instantánea nueva y diferencia calculada por la API; cobro de la diferencia contra el simulador, sin reembolsos". Phase criterion: "Un cambio genera un registro con la diferencia y no modifica la copia original de la reserva" (plan 0.1 names it `amendment_records_difference_and_keeps_original_snapshot`). Reference: `docs/modules.md` module 9; plan 0.1 sections 5.4 (`BookingAmendment`), 5.5 (P7, P8, P9), 6.2 (row "Cambio de total (6.3)" and coverage rule C), 6.3 (lock order "cambiar el total o el plan: Booking → PromoCode → pools → Payment"); `.claude/rules/pricing.md`, `payments.md`, `web.md`; done notes 2.1, 2.2, 2.4, 2.5, 3.1, 3.2, 3.5, 5.1, 5.2, 6.1, 6.5.

**Parked, stated once and repeated in the done note and the UI:** no refunds, no credit notes, no amendment fees, no cancellation penalties, no GST, no FX. A change that lowers the total below what was already paid records the excess as a **credit pending (parked)**: it is stored, shown to staff and customer, and a task is opened for Oscar, but no money is paid out. A positive difference is collected only through the existing 3.1/3.2/3.5 payment attempt flow, against the simulator.

## 1. What exists and what is missing

Exists: immutable `booking_snapshots` (version, kind `original`/`amendment`, CHECK `kind = original ⇔ version = 1`), `bookings.currentSnapshotVersion` that only goes up by one and totals mirrored from the current snapshot (deferred trigger); places `booking_travellers` with `addedInVersion`/`removedInVersion` and a 5.2 trigger that freezes everything but `removedInVersion`; `booking_rooms` and `booking_extras` (never deleted, no version columns); `inventory_claims` (held → released once, quantity fixed, `UNIQUE (bookingId, poolId)`); the payment plan with versions and superseded items, and the deferred trigger "active items = booking total"; coverage rule C (`coverageEvents`, only payments applies it); derived allocation (`allocate`, `payable`, `coverageFacts`); payment links that stop working when their item is no longer active; traveller details (5.2) per slot.

Missing: the `BookingAmendment` record; pricing a new configuration of an existing booking; versioned rooms, extras and claims; restating the plan for a new total; the coverage cell `balance_paid` with the total no longer covered → `confirmed`; routes, panel and customer pages.

## 2. Scope decisions (conservative, reversible)

1. **Where it lives: the `bookings` module, not a new `changes` module.** Plan 0.1 3.2 lists `changes` (6.3, 6.4), but every row an amendment writes (snapshots, places, rooms, extras, claims, status) is owned by `bookings` and the boundary test forbids other modules writing them. `BookingAmendment` goes in `bookings.prisma`; payments and customer-portal join through a hook (as for approval and cancellation). Event `bookings.booking.amended` (instead of `changes.amendment.applied`). Undo: move the service when 6.4 builds `changes`.
2. **Which bookings:** `deposit_paid`, `confirmed`, `balance_paid`. `requested`/`approved` (nothing paid yet: decline/cancel and request again), `completed`, `declined`, `expired`, `cancelled`, `refunded`: 409 `amendment_not_allowed`. Plan 0.1 6.2 also allows `approved`; left out of this partial task (stated in the done note).
3. **Price basis: "as if booked with the new configuration at the same moment".** The new configuration is priced by the engine with the **price version of the current snapshot** and `now` = the current snapshot's `computedAt` (the instant it was priced; amendment snapshots keep it), the rules as stored, the catalogue as it is now, and the booking's own redeemed promo code (point 5). So the difference reflects the change, not later price rises or the loss of an early-bird discount. Alternative for Oscar: current prices at the moment of the change (one function to swap).
4. **Basis drift check.** The engine also re-prices the *unchanged* current configuration on the same basis. If that is not the current total (a rule was edited or deleted since, an option repriced), the difference would carry an unrelated drift: the preview shows `basisDriftMinor`; a customer change is refused (409 `amendment_needs_staff`); staff must send `acknowledgeBasisDrift: true` (a flag, never an amount). If the current configuration cannot be priced at all (option deleted, version gone), 409 `amendment_price_basis_unavailable`.
5. **Promo code.** No new code on an amendment. The code the booking redeemed (unreleased `PromoRedemption`) is re-evaluated by the engine on the new configuration: its availability (enabled, validity, count) is not re-checked, because the booking already holds the use; its conditions and stacking are. If the engine no longer applies it (`conditions_not_met`, `not_combinable`), the change is priced without it and the redemption is released in the same transaction (Booking → PromoCode). The preview shows the promo status.
6. **Customer-initiated vs staff-initiated.**

   | Rule | Customer (`/account`) | Staff (panel) |
   |---|---|---|
   | What can change | extra nights before/after; extras added, removed or re-quantified | rooms, occupancy, travellers added or removed, a traveller's participation or distance, nights, extras |
   | Places | none removed or replaced (structurally: the body has no rooms) | any, lead rules in section 7 |
   | Difference | must be ≥ 0, else 409 `amendment_needs_staff` (a reduction may need a refund or a penalty, both parked) | any sign; negative → credit pending (parked) |
   | Basis drift | must be 0 | needs `acknowledgeBasisDrift` |
   | Last day | departure date (old and new, the earlier) minus `bookingAmendmentCustomerCutoffDays` (setting, default 14), Brisbane calendar, last day inclusive | the day before departure (old and new departure after today) |
   | Switch | setting `customerAmendmentsEnabled` (default true) → 409 `amendments_unavailable` | permission `bookings.booking.amend`: owner only by default, step-up, not an API key scope, not usable by automations |
   | Terms | the current terms text must be accepted for the booking (existing 3.5 acceptance; 409 `terms_not_accepted` sends the customer to the checkout terms) | — |
   | Reason | `customer_request` | reason code: `customer_request`, `correction`, `supplier_change`, `other` (no free text: notes on the booking hold any detail and 5.5 already redacts them) |
7. **Payment in progress:** a live attempt (`payments.liveBookingId`) blocks the change (409 `amendment_blocked_by_payment`), as it blocks approval expiry: its amount was computed for the old plan.
8. **No amendment fees** (`feeMinor` of plan 0.1 is not created) and **no `proposed`/`rejected` rows**: a proposal is a preview, not stored; every row is an applied change. Undo: add the columns.

## 3. Data model (migration `0029_booking_amendments`, renumbered at merge)

`BookingAmendment` (`booking_amendments`), in `bookings.prisma`, append-only (UPDATE, DELETE and TRUNCATE refused by trigger for every role; no personal data):

- `id`, `bookingId` + `currency` (FK `(bookingId, currency)` → bookings), `fromVersion`, `toVersion` (`UNIQUE (bookingId, toVersion)`, CHECK `toVersion = fromVersion + 1`).
- `initiatedBy` enum `customer | staff`, `actorUserId` uuid, `reasonCode` enum, `changes` enum array (`room`, `nights`, `travellers_added`, `travellers_removed`, `participation`, `extras`; at least one).
- `previousTotalMinor`, `newTotalMinor`, `priceDifferenceMinor` (`/// @signed`), `collectedMinor`, `outstandingMinor`, `creditPendingMinor`, `basisDriftMinor` (`/// @signed`). CHECKs: `newTotal = previousTotal + priceDifference`; `outstanding − creditPending = newTotal − collected`; `outstanding = 0 OR creditPending = 0`; the rest ≥ 0.
- `requestKeyHash` (`@secret`, SHA-256 of `booking-amendment:<userId>:<Idempotency-Key>`), `requestBodyHash` (`@secret`), `UNIQUE (bookingId, requestKeyHash)`; `createdAt`.
- Deferred constraint triggers: an amendment's `previousTotalMinor`/`newTotalMinor` equal the totals of the snapshots `fromVersion`/`toVersion`; a snapshot of kind `amendment` has its amendment row. So an amendment and its snapshot exist together or not at all.

Changes to existing bookings tables (minimal, declared in the PR):

- `inventory_claims`: `snapshotVersion INT NOT NULL DEFAULT 1` (frozen by the guard trigger); `UNIQUE (bookingId, poolId)` becomes `UNIQUE (bookingId, poolId, snapshotVersion)`, plus `EXCLUDE USING btree ("bookingId" WITH =, "poolId" WITH =) WHERE (status = 'held')`: at most one held claim per booking and pool. A change of quantity releases the old claim and inserts a new one (claims stay "released once, never edited").
- `booking_rooms`, `booking_extras`: `addedInVersion INT NOT NULL DEFAULT 1`, `removedInVersion INT NULL` (CHECK `> addedInVersion`), guard trigger: only `removedInVersion` NULL → value, once. `booking_extras` unique key gains `addedInVersion` (still `NULLS NOT DISTINCT`). An amendment marks every current room and extra row removed and inserts the new set ("as it stands" = `removedInVersion IS NULL`); readers (staff view) filter on it.
- `booking_travellers`: the 0026 guard also refuses changing a non-null `removedInVersion`. CHECK `isLead = (slot = 1)` becomes `slot >= 1 AND (slot <> 1 OR isLead) AND (NOT isLead OR slot = 1 OR addedInVersion > 1)` plus `EXCLUDE USING btree ("bookingId" WITH =) WHERE ("isLead" AND "removedInVersion" IS NULL)`: one current lead, and only an amendment can move the lead to another place.
- Entity registry: `BookingAmendment` via `Booking` (export: versions, changes, amounts, date; anonymise: nothing to do).

## 4. Pricing (pricing module; the only place a total is computed)

- `QuoteService.priceAmendmentIn(tx, request, basis)` with `basis = { priceVersionId, at, redeemedPromoCodeId | null }`: loads the catalogue view (no sale status check: the trip is already sold), the given version (same package and currency, else 409), its rates, the package's rules and the redeemed code by id with availability forced (decision 5), and calls the pure `price()` with `now = at`. Engine errors map like the panel's quote (`pricingErrorToHttp`).
- `priceDifference(previous: { totalMinor, currency }, next: PriceBreakdown)` in `pricing/engine/difference.ts`: `next.totalMinor − previous.totalMinor` in bigint, refusing another currency. **Rounding rule, stated once:** the difference involves no rounding of its own; both totals were rounded line by line by the single rule in `rounding.ts` (half up on the absolute value, to the minor unit), and the difference is their exact integer subtraction (test `difference_is_exact_subtraction_of_engine_totals`, and the existing AST test keeps division out of every pricing file but `rounding.ts`).
- Slots: the engine numbers travellers 1..N in room order. The booking's places keep their numbers across changes, so before storing, bookings relabels every slot of the new breakdown (configuration, extras' slots, line keys, `travellerSlot`, `perTraveller`) from engine position to place number with a pure bijection (`relabelSlots`), tested to change no amount. Places are numbered up to 80 (the snapshot schema); beyond that 409 `amendment_limit_reached`.

## 5. The amendment, step by step (`BookingAmendmentService`, one transaction, READ COMMITTED, `runTransaction` retries 40P01/40001)

Lock order (plan 0.1 6.3 plus 5.1/5.2): **Customer (FOR SHARE, must not be erased or deleted) → Booking (FOR UPDATE) → Package (FOR SHARE) → PromoCode → pools (id ascending) → places, traveller details, payment plan and links (no Payment lock: a live attempt is only read)**. Nothing that locks a Payment then locks a booking, pool or code (3.2).

1. Lock customer and booking (`readBookingForPayments(…, true)` gives the `LockedBooking` payments needs).
2. Same `Idempotency-Key` (header, 16 to 64 characters, required): an existing row for `(bookingId, requestKeyHash)` with the same body hash returns the stored result (200, `created: false`); another body → 422 `idempotency_key_reused`. Checked before the version, so a retry after success is not a 409.
3. `expectedSnapshotVersion` must equal `currentSnapshotVersion` (compare-and-set; else 409 `version_conflict`); status (decision 2); cutoff (decision 6, clock = `dbNow`); live attempt (decision 7); customer switch.
4. Price new and current configurations (section 4); currency equals the booking's; deposit configured; new departure after today; actor rules (decision 6); on commit, `previewDigest` (SHA-256 of booking id, from-version, relabelled configuration, totals and promo status as previewed) must match, else 409 `amendment_price_changed`; no change at all → 422 `amendment_has_no_change`.
5. Insert snapshot `toVersion` (kind `amendment`, checked by the strict snapshot schemas), update the booking (totals, deposit, dates, balance due date, `currentSnapshotVersion + 1`, `version + 1`).
6. Places: kept places stay; removed places get `removedInVersion`; replaced and new travellers get new place numbers (`max(existing) + 1…`). Rooms and extras: section 3.
7. Promo: release the redemption if the engine dropped it.
8. Stock: old held claims vs `demandFor(new configuration)`, per pool in id order: net delta through `InventoryService.hold`/`release` (compare-and-set on `consumed`, CHECK `0 ≤ consumed ≤ capacity`), old claim released and new claim inserted for every pool whose quantity changes. A pool without room → 409 `inventory_unavailable`, nothing written. Places given back → `WaitlistOffersService.promoteIn` in the same transaction (as the state machine does).
9. Hook `amend` (bookings `BookingTransitionHooks`, phase `before` with the booking locked): customer-portal carries and clears traveller details (section 7); payments restates the plan and applies C (section 6) and returns the money facts.
10. Insert the `BookingAmendment` row; audit `bookings.booking.amended` (ids, versions, changes, amounts, initiator; no names); outbox `bookings.booking.amended`.

**Preview** runs steps 1–4 without locks or writes and returns: configuration with place numbers, the breakdown (public shape for customers, with trace for staff), previous and new totals, difference, collected, outstanding and credit pending after the change, basis drift, changes, promo status, retired and added places, new dates, `previewDigest`.

## 6. Payment plan, coverage and parked credit (payments module, hook `amend`)

Pure `amendedPlanItems(active, newTotal, adjustmentDue)` in `core/schedule.ts`:
- Difference 0: plan unchanged (no new version).
- Difference > 0: a new plan version with the old items restated (same kind, amount and due date, sequences 1..n) and an `adjustment` item for the difference, due on the later of the new snapshot's balance due date and today (Brisbane).
- Difference < 0: a new version where the difference is taken from the last item backwards; items that reach 0 are left out.
- Always: active items add up to the new total (the deferred trigger checks it too); no item ≤ 0; due dates never go backwards.

In the hook: supersede every active item in version `v + 1` (existing `supersede` with cause `amendment`), insert the new items, revoke active payment links (reason `plan_changed`; they would 404 anyway), compute `collected`, `payable()` and `allocate()` (derived allocation, P7/P8 without a table), apply coverage C with the locked booking, and, when `allocate().overpaidMinor > 0`, open a task for Oscar ("Credit pending after a change on booking MT-…: refunds are not available yet") with `sourceRef payments:overpaid:amendment:<bookingId>:v<n>` and the existing `payments.payment.overpaid` events.

Coverage rule C gains the cell plan 0.1 6.2 already lists: **`balance_paid` with the total no longer covered → `confirmed`** (new coverage event `total_uncovered`, no route, pair already allowed by the trigger). With the others: `confirmed` covered → `balance_paid` (`amendment_lowering_total_to_paid_moves_to_balance_paid`); `deposit_paid` never moves on its own. A deposit item reduced by a large reduction only makes the deposit easier to cover.

Paying the difference: nothing new. The customer area's "Pay" button, the checkout (3.5) and staff payment links (5.1) take the next uncovered item from `payable()`; the attempt amount comes from the plan on the server.

## 7. Places and traveller details (customer-portal hook)

Staff body: `rooms[].travellers[]` is either `{ keepSlot }` (the place stays as it is) or `{ participationType, raceDistanceId?, replacesSlot? }` (a new place). Per-person extras use engine positions (order of travellers in `rooms`), like the public quote.
- A place's participation and distance never change (5.2 trigger): changing a runner's distance is a new place with `replacesSlot`; the old place is retired.
- **Details are carried explicitly:** a new place with `replacesSlot: n` gets a copy of place `n`'s details in the same transaction (names and emergency contact always; date of birth only if the new place is a runner; estimated finish time never, since it belongs to a distance). Then the details of every retired place are deleted (data minimisation; audit without values). A new place without `replacesSlot` starts empty and the customer completes it (5.2 window).
- Lead: the lead's place can only be retired if one new place replaces it; that place becomes the lead (CHECK and EXCLUDE in section 3). Removing the lead otherwise: 422 `lead_place_required`.
- Validation (422): every current place appears once as `keepSlot` or `replacesSlot`, or is removed (staff only); no unknown or retired slot; `replacesSlot` used once.

## 12. Assumptions (what I would ask Oscar)

1. Price basis "same moment, same price version" (decision 3), not current prices.
2. Customers can change nights and extras only, never lower the price, until 14 days before departure; staff can change anything until the day before departure.
3. A change made while a payment is in progress is refused until it ends.
4. The positive difference is a separate "adjustment" instalment due on the balance due date (or today if that has passed); the deposit asked at approval does not change.
5. A redeemed code stays with the booking if its conditions still hold; otherwise it is released.
6. Changing a runner's distance keeps the traveller's names and emergency contact but asks again for the estimated finish time.
7. A credit pending is a task for Oscar; nothing is refunded (4.5 parked).

## 13. Not in this task

Refunds, credit notes, fees, penalties (6.4), GST, FX; changes to `requested`/`approved` bookings; changing package, edition or currency; new promo codes on a change; supplier allotments (6.1 only compares); amendment emails (notification templates can come with 7.4); a `changes` module.
