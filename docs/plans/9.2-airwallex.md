## 3. Assumptions the sandbox run must confirm

Each one gets a test against the fake now and a line under "Sin verificar" in `docs/done/9.2.md`. If one is false, the failure is safe (no money moves, or a task opens), and the fix is a reviewed PR.

- **A1** The API version is sent as header `x-api-version: 2026-05-29`, and the webhook subscription is created on the same version. If false: requests are refused (no money), fixed in one constant.
- **A2** `GET /api/v1/pa/payment_intents?merchant_order_id=` returns exactly the intents with that order id, and a session copies `payment_intent_data.merchant_order_id` onto the intent it creates. This is the **key fact** of §4: if false, payment events cannot be matched to our reference, the contract does not fit, and the adapter goes back to `planned` (follow-up F3).
- **A3** A checkout session creates **at most one** PaymentIntent, and only on completion. A declined card leaves the session `ACTIVE` (the customer may try again: `stays_payable`).
- **A4** `metadata` given at creation is returned by `GET` and in list items of checkout sessions.
- **A5** The list of checkout sessions accepts `from_created_at` and `to_created_at` in ISO 8601 and pages with `page_after`; `page_size` up to 100. If smaller, the scan cap (§6.4) is reached sooner and answers "unknown", never "none".
- **A6** `unit_amount` accepts a decimal string with two places for AUD, and the intent's `amount` equals `unit_amount × quantity` (quantity 1, no tax, no discount, no surcharge).
- **A7** `payment_options.payment_method_types: ['card']` shows only cards on the hosted page (no Afterpay, Klarna or other pay-later method, no wallet), and `auto_capture: true` makes a completed card checkout `SUCCEEDED` or `PENDING`/`PENDING_REVIEW`, never `REQUIRES_CAPTURE`.
- **A8** The sandbox hosted page is served from `https://checkout.sandbox.airwallex.com` (a guess from the sandbox hosts; the documented example is `checkout.airwallex.com`). If wrong, the core refuses to hand out the URL (§6.2): the customer cannot pay and no money moves.
- **A9** `x-timestamp` is Unix time in milliseconds. The adapter also reads a 10-digit value as seconds (§7); both are exact, the signed string is always the raw header.
- **A10** Payment events `payment_intent.succeeded`, `payment_intent.cancelled` and `payment_intent.requires_payment_method`/`…requires_customer_action`/`…pending` (names to confirm) carry the full PaymentIntent in `data.object`, with `id`, `status`, `amount`, `currency`, `merchant_order_id`, `created_at`.
- **A11** Refund objects carry `id`, `payment_intent_id`, `amount`, `currency`, `status`, `metadata`, `created_at`, and `GET /api/v1/pa/refunds?payment_intent_id=` lists the refunds of one intent. If the filter does not exist, the adapter falls back to the time window (§8.3).
- **A12** A refund over what is left answers 400 (or a `FAILED` refund) and moves nothing. The adapter also refuses it before the network (§8.2).
- **A13** A refund goes `RECEIVED` → `ACCEPTED` → `SETTLED`, or ends `FAILED`, and never goes from `SETTLED` to `FAILED`.
- **A14** 401 means bad credentials; 404 `resource_not_found` means the object does not exist; 429 means rate limited; `validation_error` on a create means nothing was created.
- **A15** Client ID and API key have no documented test or live marker, so the **host** protects test money, as for PayPal: in test mode the adapter only talks to `api.sandbox.airwallex.com`.
- **A16** Dispute events are named `payment_dispute.*`. The adapter only opens a review task for them (§9).
- **A17** Airwallex sends payers no receipt that calls itself a tax invoice, and adds no surcharge or fee to the customer's total. The guide tells Oscar to check both in the web app.
- **A18** Checkout Session (beta) is available to a new sandbox account. If not, F2 (PaymentIntent + hosted page through Airwallex.js) is the way, with its own plan.
- **A19** (review, point 4) Each webhook retry is signed again with a **new** `x-timestamp`. If retries keep the first one, a delivery that failed for more than 300 s arrives stale and is refused: payments and our refunds are still found by pulls, but a refund made in the web app or a dispute would be lost until F6. Recorded as a risk (§17).
- **A20** (review, point 1) `checkout_session.created` and `checkout_session.cancelled` carry the whole session in `data.object`, with `payment_intent_data.merchant_order_id`, `metadata` and the line item. If not, they are unreadable, the payment event before payment does not exist, and the contract is changed in a reviewed plan (never in the fake or in a subject).
- **A21** (review, point 6) `unit_amount` is accepted as a JSON string (`"12.50"`, the documented example), and refund `amount` as a JSON number written as a decimal literal (`12.50`).
- **A22** (review, point 7) The `x-signature` hex may come in either case: the adapter decodes it as hex (case-insensitive) and compares bytes, so this assumption cannot refuse valid deliveries.
- **A23** (review, point 7) PaymentIntent ids start with `int_` (the documented example `int_hkpdskz7vg1xc7uscdj`). If not, a refund made in the web app cannot be resolved to our payment, and the core opens its "unknown payment" task: no money is recorded wrongly.
- **A24** (review, point 7) How long Airwallex remembers a `request_id` (sessions and refunds) is unknown. The design does not depend on it: a search runs before every create (§6.3, §8.1).
- **A25** (review, point 5) `payment_intent_data.merchant_order_id` and `metadata` are returned by `GET` and in list items of checkout sessions (A4 widened). A missing field is "unknown" (retryable), never "not ours" (§19, point 5).

## 4. Architecture: a plain `PaymentProvider`, like Stripe

No card session, no card page, no capability. The adapter is `AirwallexProvider implements PaymentProvider` in `adapters/airwallex/`, with `http.ts` (login, transport, error mapping), `money.ts` (§5), `mapping.ts` (statuses, events) and `webhook.ts` (§7). It talks only to Airwallex, reads no environment, writes no logs and touches no Prisma (`adapter_sources_are_isolated`).

**The one design problem, and how it is solved without changing the contract.** The core applies a payment event **from the event alone** (`webhooks.service.ts`, `processOnce`): it matches by our payment id, then checks `p.providerPaymentRef === event.payment.ref` and the amount, then moves the state. The contract clause `webhook_verifies_and_matches_retrieve` checks the same: the event's `ref`, `status`, amount and `ourPaymentId` equal what `retrievePayment` says. At Airwallex:
- the **session** (what we create, with its URL) has no payment status and no amount, so a `checkout_session.*` event cannot say whether money came in;
- the **PaymentIntent** (which has status and amount) only exists after the customer pays, so its id cannot be our reference at creation.

So our payment reference is **neither Airwallex id: it is the order id we give Airwallex**, which both objects carry (`payment_intent_data.merchant_order_id` on the session, `merchant_order_id` on the intent, A2):

```
ref = "mt-" + <our payment id, a UUID> + "-" + <the attempt row's createdAt, Unix seconds, 10 digits>     (50 characters, ≤ 64)
```

- It is fixed by our own data (`metadata.paymentId` and `createdAt`, which are the same on every retry of one key), so `same_idempotency_key_same_object` holds by construction, as long as at most one session is ever created per ref (§6.3).
- A `payment_intent.*` event carries it in `merchant_order_id`, so the event gives `ref`, `status`, amount and `ourPaymentId` (the UUID inside the ref) with no network, exactly as the core and the clause need.
- The time inside it bounds every search (§6.4): the adapter never needs to store anything.
- The pattern is strict: `^mt-[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}-[0-9]{10}$`. Anything else is refused before the network (`retrievePayment` answers null after an authenticated probe, `cancelPayment` and `createRefund` throw `provider_not_found`, as the clauses ask).

`checkout_session.created` and `checkout_session.cancelled` events are parsed as payment events in a state that moves no money (`requires_action`, `cancelled`), with the same ref; `checkout_session.completed` is ignored, because it says nothing about money (review round 1, point 1, §19). Pulls (`sync` on the customer's return, `drive`, the attempt sweep) read the session and the intent and fill any gap (§6.5).

## 5. Money (no floats anywhere)

- `money.ts`, modelled on PayPal's: `toAirwallexAmount(minor, currency)` builds `"<units>.<cents>"` from a `bigint` with string operations; only `AUD` (two decimals) is accepted; bounds A$0.01 to A$9,999,999.99 (as PayPal's D14). Anything else is refused before the network, non-retryable (`definitive_refusal_means_no_object`).
- `fromAirwallexAmount(text, currency)`: accepts only `^(0|[1-9][0-9]{0,11})(\.[0-9]{1,2})?$` and returns `bigint` minor units. Exponents, signs, more than two places or anything else answer null, and a null amount makes the whole answer unreadable (retryable `provider_unavailable`), never a guess.
- Responses are parsed with `JSON.parse(text, reviver)` where the reviver returns **the number's source text** (`context.source`, supported by Node 22's V8; checked locally: `100.10` stays `"100.10"`). So a JSON number never becomes a float on its way to `bigint`. A unit test pins this, and the adapter refuses to start parsing if `context.source` is absent (a startup check in the module, so an older runtime fails closed).
- The amount reported for a session with no intent yet comes from its own line item (`unit_amount × quantity`) if returned, else from our `metadata.mt_amount_minor`. It is only ever used for `requires_action` and `cancelled` states, which move no money. Every money state takes its amount from the intent.

- `signatureHeaders: ['x-signature', 'x-timestamp']`.
- `account`: fields `clientId` (`^[A-Za-z0-9_-]{8,64}$`) and `apiKey` (`^[A-Za-z0-9_-]{32,256}$`), webhook secret `entered` (`^[A-Za-z0-9_+/=-]{16,256}$`), labels saying "sandbox". The patterns are shape checks only (A15); `samples.rejected` holds malformed values (spaces, too short, another field's shape). `manifestProblems` passes.
- Registered in `createAdapters` with one line; new accounts get the default routing rules (card, AUD, any country, priority 100), as every adapter.

### 6.2 Create: one Checkout Session, the customer goes to Airwallex

`createPayment(ctx, input)`:
1. Refuse before the network: currency or amount outside §5, or a method other than `card`. Non-retryable `provider_rejected`: no request was sent, so no object exists and none ever will under that key.
2. **Look for an existing session first** (§6.3). Found: return it as it is now. Not found (whole window listed) and `now > input.createdAt + CREATE_HORIZON` (6 h): non-retryable `provider_rejected`, because none exists and the adapter will never create one for that key. The horizon is checked **after** the search, so a session whose answer was lost earlier is always found, never declared absent.
3. `POST /api/v1/checkout/checkout_sessions/create` with `request_id = ref`, `mode: 'PAYMENT'`, `currency: 'AUD'`, one line item (`quantity: 1`, inline price with `unit_amount` from §5 and a fixed product name, "Booking payment"), `success_url` and `back_url` = `input.returnUrl` (built by the server), `payment_intent_data.merchant_order_id = ref`, `payment_options: { payment_method_types: ['card'], auto_capture: true }`, and `metadata: { mt_ref, mt_payment_id, mt_booking_id, mt_key: sha256(idempotencyKey) hex, mt_amount_minor }`. No customer data is sent (D6): the hosted page asks for what the card needs.
4. Answer `requires_action` with `nextAction: { type: 'redirect', url }`. The core hands the URL to the customer only if it starts with `checkoutOrigin + '/'` (`attempts.service.ts`, unchanged).
5. `duplicate_request_id`: the session exists (an earlier answer was lost). Search again (§6.3); found, return it; not found yet, throw retryable `provider_busy` (the object may be about to show).
6. Timeout, 5xx, 429: retryable; the next try starts at step 2, so it never creates a second session.

### 6.3 One session per reference

Before every create, and on `duplicate_request_id`, the adapter lists sessions created in `[createdAt − 5 min, createdAt + CREATE_HORIZON + 5 min]` and keeps those whose `metadata.mt_ref` **and** `payment_intent_data.merchant_order_id` equal `ref`. Exactly one: that is the payment. More than one: impossible by step 2, but if Airwallex shows two, the adapter throws retryable `provider_unavailable` and the core's 24 h "unresolved attempt" task tells staff; it never picks one. None, with the whole window listed: no session. Because the search runs before each create and every create uses the same `request_id`, a second session needs both Airwallex's duplicate check to have expired and our search to have missed it; and a missed one would only be a second **unpaid** session whose URL nobody received (§6.6).

### 6.4 Lookup and retrieve

- **By key** (`{ idempotencyKey, createdAt }`): the lookup does not carry our payment id, so it searches the window from `createdAt` and matches `metadata.mt_key = sha256(idempotencyKey)`; the session found gives the ref (`metadata.mt_ref`, which must equal its `merchant_order_id`), and the payment is then read as by ref. No session in the fully listed window: null.
- **By ref:** first `GET /api/v1/pa/payment_intents?merchant_order_id=<ref>` (A2). One intent: its status and amount decide (§6.5). More than one: retryable error and the 24 h task (A3 false). None: the session decides, found by the window search with the time inside the ref.
- **By an intent id** (`int_…`, the `paymentRef` of a refund made in the web app): `GET /api/v1/pa/payment_intents/{id}`; its `merchant_order_id` must match the ref pattern, and the answer carries that ref, so `processRefund` and the clause `gateway_refund_has_no_our_id` resolve our payment. An intent without our order id is not ours: null.
- **Bounded search.** `CREATE_HORIZON` (6 h) bounds when a session can exist, so the window is fixed by the ref. Pages are walked with `page_after` up to 20 pages; if the cap is reached before the window ends, the answer is "unknown" (retryable `provider_unavailable`), **never "none"**. Null is answered only after the whole window was listed.
- **Unknown values are unknown.** A status, amount or currency the adapter cannot read throws retryable `provider_unavailable` (lesson of 4.4 M1 and 9.1): never `failed`, never "none".
- `retrieve_unknown_is_null`: a well-formed ref with no intent and no session in a fully listed window is null; a malformed ref is null after an authenticated probe (the login), so bad credentials still answer `provider_auth_failed`.

### 6.5 Statuses

An intent in a money state (`REQUIRES_CAPTURE`, `PENDING`, `PENDING_REVIEW`, `SUCCEEDED`, `CANCELLED`) decides. With no intent, or an intent in a state without money (`REQUIRES_PAYMENT_METHOD`, `REQUIRES_CUSTOMER_ACTION`), **the session decides** (review round 1, point 3):

| Airwallex | Ours | Why |
|---|---|---|
| session `ACTIVE`; no intent or intent `REQUIRES_*` | `requires_action` (with the URL) | The customer has not paid; still payable (`stays_payable`) |
| session `EXPIRED` or `CANCELLED`; no intent or intent `REQUIRES_*` | `cancelled` | Nothing was paid; final. Money arriving later anyway is the core's existing late-payment path (task, refundable) |
| session `COMPLETED`, no intent | throw retryable | Contradicts A3; read again later |
| session `COMPLETED`, intent `REQUIRES_*` | `requires_action` | Contradicts A3 too, but no money; the sweep keeps reading |
| intent `REQUIRES_CAPTURE`, `PENDING`, `PENDING_REVIEW` | `pending` | Money not final (A7) |
| intent `SUCCEEDED` | `succeeded` | Captured; amount from the intent |
| intent `CANCELLED` | `failed` (`failureCode: 'provider_cancelled'`) | The checkout ended but no money came (an expired authorisation, a review refusal). Terminal |
| anything else | throw retryable | Never guessed |

Statuses only move forward; an older event never undoes a newer state (the core's state machine and `webhook_previous_state_and_duplicate`).

### 6.6 Cancel

`cancelPayment(ctx, ref, key)` (review round 1, point 3): an intent in a money state → answer that state (a paid payment is not cancelled here; a refund is a refund). Otherwise: find the session (§6.3); `ACTIVE` → `POST …/checkout_sessions/{id}/cancel`; an intent in `REQUIRES_*` → also `POST /api/v1/pa/payment_intents/{id}/cancel`; then **read again** and answer what §6.5 says, which is `cancelled` unless money moved meanwhile (then that money state). Already `CANCELLED` or `EXPIRED` → `cancelled` (idempotent). No session in a fully listed window → `provider_not_found`. A `validation_error` on either cancel (it completed meanwhile) → read again and answer what it is. So `cancel` never answers `requires_action`. A second unpaid session (§6.3, impossible by design) is harmless: nobody has its URL and it expires in an hour.

### 6.7 No surcharge, amount from the server

The only amount sent is `input.amount`, which the core takes from pricing and the payment plan. No fee, surcharge or method-dependent price is added. A succeeded intent whose amount or currency differs from ours goes through the core's existing mismatch handling (task, nothing recorded as paid). Test: `no_surcharge_by_payment_method` for this adapter, and `amount_mismatch_opens_task` with a fake that adds A$1.

## 7. Webhooks

- `verifyWebhook(ctx, body, headers, now)`, no network, never throws:
  - both headers present, single-valued, `x-timestamp` all digits (10 or 13), `x-signature` 64 hex characters in either case (decoded as hex, compared as bytes; A22, §20.6); else `malformed`;
  - HMAC-SHA256 with the account's secret over the raw `x-timestamp` string followed by the raw body, compared with `timingSafeEqual`; else `bad_signature`;
  - the timestamp (13 digits = milliseconds, 10 = seconds; A9) within 300 s of `now`, both ways; else `stale_timestamp` (the suite tests 299 s, 301 s and one hour);
  - an empty secret (not set yet) is `bad_signature`, never a pass.
- `parseEvent(body)`:
  - `payment_intent.*` with a full intent whose `merchant_order_id` matches the ref pattern → `kind: 'payment'`, `ref` = that order id, status (§6.5), amount (§5), `ourPaymentId` = the UUID inside the ref;
  - `refund.received|accepted|settled|failed` → `kind: 'refund'` (§8.4);
  - `payment_dispute.*` → `unsupported` with `review: 'dispute'` (the core opens a task, §9);
  - `checkout_session.created` → `kind: 'payment'`, `requires_action`; `checkout_session.cancelled` → `kind: 'payment'`, `cancelled`; both with ref = `payment_intent_data.merchant_order_id` and the amount of §5's last bullet (§19, point 1); `checkout_session.completed` → `unsupported`;
  - any other name containing `dispute`, `chargeback` or `reversal` → `unsupported` with a review task (§19, point 4); every other name → `unsupported` (ignored);
  - an unreadable body or amount → null (`malformed`).
  - `providerEventId` = `id`, `occurredAt` = `created_at`.
- The raw event is stored by the core before processing; duplicates are dropped by `providerEventId`; out-of-order delivery is handled by the state machine. None of this changes.

## 8. Refunds

### 8.1 Create

`createRefund(ctx, input)`:
1. Refuse before the network: malformed `paymentRef`, currency or amount outside §5.
2. Read the payment (§6.4). Not `succeeded`: `provider_rejected` (`refund_of_unpaid_payment_refused`).
3. **Already there?** Search the intent's refunds for `metadata.mt_refund_key = sha256(idempotencyKey)` (§8.3). Found: return it.
4. **Over what is left?** Captured amount minus every refund of the intent that is not `FAILED` (ours and the web app's). Over: `provider_rejected`, nothing posted (A12).
5. `POST /api/v1/pa/refunds/create` with `request_id = 'mtr-' + refundId`, `payment_intent_id`, `amount` (§5), `reason: 'requested_by_customer'` (A11), `metadata: { mt_refund_id, mt_refund_key, mt_ref }`.
6. `duplicate_request_id` → search again (step 3); not found yet → retryable `provider_busy`. Timeout or 5xx → retryable; the retry starts at step 3, so a refund is never posted twice.

### 8.2 Statuses (D5, the conservative reading)

`RECEIVED` and `ACCEPTED` → `pending`; `SETTLED` → `succeeded`; `FAILED` → `failed`; anything else → retryable error. Airwallex says `ACCEPTED` "generally means it has succeeded", which is not a promise, so our ledger records the money as gone only when it is settled. Reversible in one mapping line once the sandbox shows that `ACCEPTED` never fails (A13). Pending refunds count against what is left (step 4), so no over-refund can slip in while one settles.

### 8.3 Retrieve

- By ref (`GET /api/v1/pa/refunds/{id}`): `paymentRef` = our ref when `metadata.mt_ref` is present and the intent's order id agrees; otherwise the intent id (a web-app refund), which `retrievePayment` resolves (§6.4). `ourRefundId` only from `metadata.mt_refund_id` (a UUID).
- By key: the refunds of the intent (`GET /api/v1/pa/refunds?payment_intent_id=`, A11; if refused, the window from the refund row's `createdAt` to +24 h), matched on `mt_refund_key`. Same paging cap and "unknown, never none" rule as §6.4.

### 8.4 Refund events

`refund.*` events carry the refund object (A11): `ref`, status (§8.2), amount, `paymentRef` and `ourRefundId` as in §8.3. A refund made in Airwallex's web app has no metadata: the core records it as external and opens its existing task (P5; `gateway_refund_has_no_our_id`).

## 11. HTTP, credentials and secrets

- `http.ts`: fixed base URL per mode (`test` → `https://api.sandbox.airwallex.com`; `live` → `https://api.airwallex.com`, unreachable while `experimental`); `redirect: 'manual'`; 15 s timeout; JSON only; the response body is read as text and parsed with the source-text reviver (§5).
- **Login per operation**, no cache (as PayPal's D): each adapter call logs in once and uses the token for its requests. The token lives in a local variable only. If the token is refused mid-call (401), the call fails `provider_auth_failed`; it never logs in twice in a loop.
- Header `x-api-version: 2026-05-29` (A1) on every request, from a constant (`AIRWALLEX_API_VERSION`), like `STRIPE_API_VERSION`.
- Error mapping: 401 → `provider_auth_failed` (not retryable); 404 `resource_not_found` → null on reads, `provider_not_found` on cancel and refund; 429 → `provider_busy` (retryable); 5xx, network, timeout → `provider_unavailable`/`provider_timeout` (retryable); 400 `validation_error` on create → `provider_rejected` (not retryable: Airwallex validated and created nothing, A14); 400 `duplicate_request_id` → §6.2 step 5, §8.1 step 6; any other 4xx on create → retryable (unknown, never "no object").

## 20. Plan review, round 2 (approve with changes): how each finding is resolved (overrides the sections above)

- **1 (medium), an open intent must always be cancelled.** Two holes: a cancel whose intent call timed out answered `cancelled` on the retry (the session was already `CANCELLED`); and an `EXPIRED` session over an intent still in 3-D Secure read `cancelled`, so `settle` (`attempt-sync.service.ts`, around line 149) never called cancel and a late 3-D Secure could charge a released booking. Resolution:
  - **Reading.** An intent in `REQUIRES_PAYMENT_METHOD` or `REQUIRES_CUSTOMER_ACTION` reads `requires_action` **whatever the session says**. So the core's `settle` and `cancelOrphan` call `cancelPayment` for it. Table of §6.5 becomes: money state of the intent decides; else an open intent (`REQUIRES_*`) → `requires_action`; else intent `CANCELLED` → `failed` if the session is `COMPLETED`, `requires_action` if the session is `ACTIVE`, `cancelled` if it is `CANCELLED`/`EXPIRED`; no intent → the session (`ACTIVE` → `requires_action`, `CANCELLED`/`EXPIRED` → `cancelled`, `COMPLETED` → unknown).
  - **Cancel.** `cancelPayment` cancels an open intent **every time it sees one**, whatever the session's state, and cancels an `ACTIVE` session; then it reads again and answers that. There is no "already cancelled" shortcut while an intent is open.
  - Tests: `expired_session_with_open_intent_is_cancelled_and_unblocks_booking` now also requires the intent to end `CANCELLED` at the fake; `cancel_retry_after_intent_cancel_timeout_cancels_the_intent` (case A); `expired_session_with_intent_in_3ds_reads_requires_action_then_settle_cancels_it` (case B).
- **2 (medium), the sandbox run must prove A20.** Sandbox subjects build and sign their events from a `GET`, so they cannot show that Airwallex really sends the session in `checkout_session.*` events, nor that those events exist. Resolution:
  - §14: the subscription also includes `checkout_session.created` and `checkout_session.cancelled`.
  - The sandbox subject's `checkRecorded` (run once, before any clause, as PayPal's) **requires** at least one real recorded `checkout_session.created` delivery that verifies with the account's secret and reads `kind: 'payment'`, `requires_action`, with `ourPaymentId`; and one real `payment_intent.succeeded` and one `refund.*` delivery. Without them the run fails, so no `N/N` line exists and the manifest cannot become `verified`.
  - A20 is widened: the events `checkout_session.created` and `checkout_session.cancelled` **exist with these names** and carry the whole session. §2 documents those names only through the hosted-page guides (the migration and quickstart pages list `checkout_session.created`, `.cancelled`, `.completed`), and research §4c says the full event list could not be read; so the round 1 phrase "only events §2 documents" means "only these names, all UNVERIFIED".
- **3 (medium), a foreign session must not block payments.**
  - A list item in the window that lacks `metadata` or `payment_intent_data.merchant_order_id` is read with `GET …/checkout_sessions/{id}`. If the `GET` has the fields, it decides. If it has neither `metadata.mt_*` nor `merchant_order_id`, the item counts as "not ours" **only when A25 is confirmed for `GET`** (a constant, `GET_RETURNS_ORDER_FIELDS`, `false` until the sandbox run; flipping it is a one-line reviewed change). Until then the answer is "unknown" (retryable). So the risk of a foreign session (made in Airwallex's web app) in the window is a temporary block of creates and reads for that window (at most 6 h 10 min), never a wrong answer. It is written in §17 and in the guide ("do not create checkout sessions in the Airwallex web app"). Test: `foreign_session_without_metadata_in_window` (unknown with the constant `false`, not ours with `true`, via a constructor option used only by tests).
  - The intent list is bounded in time too: `from_created_at`/`to_created_at` from the ref's window (`createdAt − 5 min` to `createdAt + CREATE_HORIZON + 1 h + 5 min`, since an intent is created at most an hour after its session). Every item is still checked one by one.
  - §14 checks A2 with **at least two** payments: each ref's intent search must answer only its own intent, item by item.
- **4 (medium), a stale delivery must not vanish.**
  - `verifyWebhook` returns `claimedEventId` (the body's `id`, if it is a plausible id: `^[A-Za-z0-9_-]{1,128}$`) for `stale_timestamp` and `bad_signature` too, so the rejection row (`webhooks.service.ts`, around line 99) names the event.
  - A19 becomes a **mandatory check** of the sandbox run (§14): with our endpoint answering 500 for more than 300 s, Airwallex's retry is recorded; `checkRecorded` requires a pair of deliveries with the same event `id` and different `x-timestamp`, both verifying at their own time. Without that pair the run fails (no `verified`). If A19 turns out false, Airwallex stays `experimental` until F6 (reconciliation and disputes) exists, written in the guide.
- **5 (low), subscribe to every dispute event.** The guide lists the subscription: `checkout_session.created`, `checkout_session.cancelled`, `payment_intent.*` (all), `refund.*` (all), and **every** dispute event Airwallex offers (all names with `dispute`, `chargeback` or `reversal`), so the review-task safety net of §19.4 sees them.
- **6 (low), contradictions removed.** §7: `x-signature` must be 64 hex characters, **either case** (decoded as hex, compared as bytes in constant time; A22); a non-hex or wrong-length value is `malformed`. §13: `checkout_session.created` → `requires_action` payment event, `checkout_session.cancelled` → `cancelled` payment event, `checkout_session.completed` → `unsupported`. (§19.1 governs.)
- **7 (low), foreign currencies and unreadable refund events.**
  - Amount table: a JPY answer `"1250"` and a KWD answer `"12.500"` are **unreadable** (only AUD is readable: never multiplied, never guessed) → retryable `provider_unavailable` on reads, null from `parseEvent`.
  - A `refund.*` event that verifies but cannot be read (unknown currency, unreadable amount or status) is parsed as `unsupported` with `review: 'reversal'`, so the core opens its review task ("money taken back… check the booking and the gateway") instead of dropping it as `malformed`. A `payment_intent.*` event that cannot be read is dropped (null): every payment of ours is also read by pulls.

## 21. Code review, round 1 (approve with changes): how each finding is resolved (overrides the sections above)

- **1 (high), a lost refund answer must never be posted again.** `refundsOf` treats an item without `payment_intent_id` as unknown (retryable), never skips it. A refund of our intent without a `metadata` **object** (an empty `{}` is an answer; absent or null is not) is read again with `GET /api/v1/pa/refunds/{id}`. If the `GET` has none either, the answer is unknown until the sandbox confirms that a refund's `GET` returns its metadata (`REFUND_GET_RETURNS_METADATA`, `false`; a one-line reviewed change, like `GET_RETURNS_ORDER_FIELDS`). `retrieveRefund` by ref applies the same rule, so the core never records one of our refunds as external on a missing field. So the lookup by key never answers "none" for a refund it could not read, and the design still does not rely on A24. The fake gets modes for refund lists and `GET`s without metadata and one that forgets `request_id`s; the test makes at most one refund per lost answer.
- **2 (medium), cancel the session before looking for the intent.** `cancelPayment` now: (a) answers a money state if the intent already has one; (b) cancels an `ACTIVE` session; (c) **then** searches for the intent and cancels it if open; (d) reads again. A card submitted between (b) and the search is seen and cancelled. Test: the fake opens a 3-D Secure intent just before the session cancel arrives; the intent ends `CANCELLED`. What remains: if a `checkout_session.cancelled` event ends the attempt and our intent cancel then fails, the money of a late 3-D Secure goes through the core's existing late-payment path (task, refundable).
- **3 (low), an intent read by id without `merchant_order_id`** is unknown (retryable) until A25 is confirmed, never "not ours". So a refund made in the web app is retried, not sent to the "unknown payment" task.
- **4 (low), refund events no longer trust `metadata.mt_ref`.** Their `paymentRef` is always the refund's own `payment_intent_id`. The core resolves it with `retrievePayment`, which reads the intent's own `merchant_order_id` (it only uses the ref that read returns). `retrieveRefund` keeps cross-checking `mt_ref` against the intent's order id (§8.3).
- **5 (low), paging.** `listAll` follows `page_after` (the documented cursor of the checkout session list) and, for lists that page by number, `has_more` with `page_num` (the SDK's list parameters, A5). `has_more: true` with no items cannot be finished: unknown, never "none".
