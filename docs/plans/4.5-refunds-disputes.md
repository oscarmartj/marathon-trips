## 2. Money model: collected, reserved, allocatable, caps

Everything below is computed in one place (`core/allocation.ts` and `core/payable.ts`), with the booking and all its payments locked, in the environment's mode (P11).

- **Net of a payment** `net(p) = p.amount − Σ succeeded refunds(p) − Σ withdrawn(p) + Σ reinstated(p)` (succeeded payments only; a `voided` inbound counts 0). Can be negative (a chargeback after a full refund).
- **Reserved of a payment** `reserved(p) = Σ app refunds(p) in requested or pending`. External refunds are never "in flight" for caps: they are recorded when the gateway says so.
- **Collected** (booking) = Σ net(p). **Allocatable** = collected − Σ reserved(p).
- **Allocation** = `allocate(activeItems, allocatable)`: items filled by `sequence`, the rest is overpayment; if allocatable < 0, every item is 0, overpayment 0 and **receivable = allocatable** (≤ 0). What comes in later pays the receivable first, by construction. `allocate` stops throwing on negative input.
- Coverage C (§7) and what the customer owes (P1) read the allocation; the "collected something / net 0" facts of `cancelled ↔ refunded` read **collected** (succeeded money only, not reservations).
- **Overpayment owned by a payment:** `allocateByPayment(activeItems, payments with net − reserved, ordered by (succeededAt, id))` gives each payment its share of the items and of the overpayment (negative nets count 0 there and their excess is the booking's receivable). This is what P10's "the overpayment allocated to that same payment" means here.
- **Refundable now on payment p** (the only amount a refund from the app can have):
  `refundable(p) = min(overpaymentShare(p), bookingOverpayment)`, then `0` if the payment has a dispute in `open`, `evidence_submitted` or `lost` (refunding a disputed charge risks paying twice; `refund_of_disputed_payment_rejected`), and clipped by the per-payment cap `requested + pending + succeeded + new ≤ p.amount − withdrawn + reinstated` (holds by construction; asserted).
- **Reservation (P10):** because in-flight refunds are taken off *allocatable*, a plan change (6.3 amendment, approval, expiry), a reallocation or a chargeback cannot use reserved money while the refund is in flight; a `failed` refund releases it (`reallocation_does_not_consume_overpayment_reserved_by_pending_refund`, `reversed_refund_frees_cap`).
- The ledger's customer side (`customerSide`) gains the receivable line: target funds = Σ items paid, target receivable = −min(0, allocatable), overpayments take the rest, so every posting still balances and reserved money stays in `customer_overpayments` until it leaves.

## 3. Refund from the app through a gateway

### 3.1 Request (transaction A)

`POST /admin/payments/payments/:id/refunds` with `Idempotency-Key` header (platform idempotency, as other money routes), body `{ paymentVersion, purpose, reason, destination? }`, strict schema: **no amount field** (`refund_amount_field_rejected`, 400). Step-up (`payments.refund.request`).

1. Outside any transaction, read the payment's account and adapter manifest: gateway guard for `refund` (adapter `planned` or missing, live account outside production, account mode not the environment's → 409 with the code; `non_production_refund_on_live_account_rejected` keeps passing); capability `refunds: 'none'` on a non-manual adapter → 409 `refunds_not_supported`. Paused, retired and archived accounts refund (plan 0.1, 6.4; `retired_account_refunds_app_refund`).
2. `runTransaction`: lock `Booking` → all its `Payment`s by id → nothing else. `purpose = 'cancellation'` → 409 `cancellation_refund_rejected_until_cancellations_exist`; `price_reduction` → 409 `price_reduction_refund_rejected_until_amendments_exist` (§12.2). Payment not `succeeded` → 409 `payment_not_refundable`. `paymentVersion ≠ version` → 409 `stale_payment_version`. `refundable(p) = 0` → 409 `nothing_to_refund`. Capability `full` only and `refundable(p) < net(p)` → 409 `partial_refund_not_supported`.
3. Insert `Refund { origin: app, purpose, status: requested, amountMinor: refundable(p), reason, requestedById, idempotencyKey: refund:app:<refundId> }` (id generated server-side), bump `Payment.version`, audit `payments.refund.requested` (amount, currency, purpose; reason as `@pii`), commit. The reservation is now visible to every other request (`concurrent_refunds_cannot_exceed_payment`, `concurrent_overpayment_returns_cannot_exceed_overpayment`).

### 3.2 Call and settle (outside, then transaction B)

- `gateway.call(account, 'refund', createRefund({ paymentRef, amount, idempotencyKey, metadata: { refundId, paymentId, bookingId }, createdAt: row.createdAt }))`, outside any transaction (P5).
- Transaction B (Booking → Payment → Refund): set `providerRefundRef` if null (a webhook may have set it already), then the state machine with the gateway's status (`pending`, `succeeded`, `failed`/`cancelled` → `failed`). Answer 201 with the refund as it stands.
- Definitive refusal (`provider_rejected`, `provider_not_found`, `provider_auth_failed` non-retryable): → `failed` with that code, frees the cap, 409 `refund_refused_by_gateway` to staff, no posting.
- Retryable error or timeout: the row stays `requested`, `requestAttempts + 1`, `nextAttemptAt = now + backoff (1, 5, 15, 60 min)`; 202 `refund_requested_pending_gateway`. The money stays reserved.

### 3.3 Retries and the sweep (`refund_request_without_response_requeried_and_retried_same_key`)

The payments maintenance job (exists, every 10 min) picks app refunds `requested` with `nextAttemptAt ≤ now`:
1. `retrieveRefund({ idempotencyKey, paymentRef, createdAt })` first. Found → adopt its ref and status (transaction B). This is how a crash between the call and transaction B is repaired.
2. Not found and the row is younger than 23 h (inside the gateways' idempotency-key lifetime; Stripe keeps keys 24 h) → `createRefund` again with the **same key and the same parameters** (all derived from the row).
3. Not found and older than 23 h, or 5 attempts without an answer → no more calls; a task for Oscar (`payments:refund_unanswered:<id>`) and the row stays `requested` (reserved) until Oscar checks the gateway. Never a second object under a new key.
The 24 h re-query of 3.3 (`requested`/`pending` with a ref) is unchanged.

### 3.4 Webhook before the response (`webhook_before_provider_response_matches_app_refund`)

3.3's webhook code already finds a refund by `ourRefundId` within the receiving account; it now also fills `providerRefundRef` when the row has none, then applies the state. Transaction B later sees the ref set and the state moved, and does nothing more (forward only). A refund event carrying our id but for another account's payment is not matched (finding 2, `webhook_metadata_id_from_other_account_not_matched` extended to app refunds).

## 4. Manual refunds (P13: bank transfer and PayID payments)

A payment made by bank transfer (`adapterKey = manual`, origin `inbound`) is refunded by Oscar from his bank. The app records it; it never moves money.

1. **Request** (same route, same caps, same step-up): `destination` is required for a manual payment and refused for any other (`destination_only_for_manual_payments`): `{ kind: 'payid', payIdType, payId, accountName }` or `{ kind: 'bank_account', bsb, accountNumber, accountName }`, validated with 3.4's validators. Stored encrypted with the platform `SecretBox` (AAD `refund:<id>:destination`), plus a masked hint. The refund stays `requested`; no gateway call.
2. **See the destination** to make the transfer: `GET /admin/payments/refunds/:id/destination`, permission `payments.refund.confirmManual` with step-up, `Cache-Control: no-store`, audited (`payments.refund.destination_viewed`), only while `requested`.
3. **Confirm** `POST /admin/payments/refunds/:id/confirm-manual { version, bankReference }`, step-up: bank reference = the movement id of the outgoing transfer on Oscar's statement (same rules as 3.4's inbound statement id; empty → 422 `bank_reference_required`), stored as `providerRefundRef` (unique per account: the same reference twice → 409 `bank_reference_already_used`). Booking → Payment → Refund locked, compare-and-set `requested → succeeded`, `confirmedById`, destination ciphertext nulled in the same `UPDATE`, posting `refund:<id>:succeeded` on `provider_clearing:<manual account>`, C. A second confirmation (double click, other tab) changes nothing and posts nothing (`manual_refund_confirmed_once_with_bank_reference`); without step-up → 403 (`manual_refund_requires_step_up`).
4. **Cancel** `POST /admin/payments/refunds/:id/cancel-manual { version }`, step-up: `requested → failed` (`cancelled_by_staff`), destination nulled, cap freed.
5. **Erasure:** a manual refund `requested` already blocks erasure (`live_payment`, 0033). After it, only the hint is left and erasure empties it with the reason (`manual_refund_destination_erased_with_customer`, plus the 5.5 sweep, which writes a marker in every text column of the registry).
6. A manual refund `requested` for 7 days gets a task (`payments:manual_refund_waiting:<id>`).

## 5. Disputes and chargebacks

### 5.1 Provider interface (optional, so 4.3 and 4.4 are not broken)

- `capabilities.disputes?: 'events'` in the manifest (absent = none). `NormalisedEvent.kind` adds `'dispute'` with `dispute?: ProviderDispute`.
- `ProviderDispute { ref, paymentRef, amount, reasonCode (closed list of §1.2, unknown → other), status: 'open' | 'evidence_submitted' | 'won' | 'lost' | 'closed', evidenceDueBy?, fundsWithdrawn: boolean, fundsReinstated: boolean }`: the funds flags are the **cumulative** state the gateway reports in every dispute event (Stripe's dispute object lists its balance transactions), so any one event is enough and order does not matter.
- Optional method `retrieveDispute?(ctx, ref): Promise<ProviderDispute | null>`, required when `disputes` is declared (manifest check).
- Simulator: disputes on its accounts (open, move, withdraw, reinstate, signed events, retrieve). Stripe adapter: `charge.dispute.created|updated|closed|funds_withdrawn|funds_reinstated` mapped (`needs_response`/`warning_needs_response` → open, `under_review`/`warning_under_review` → evidence_submitted, `won`, `lost`, `warning_closed` → closed; funds from `balance_transactions`), `retrieveDispute` against the fake Stripe; stays `experimental`.
- Contract suite: three clauses that run only when `disputes` is declared (otherwise they pass as "not declared"): `dispute_webhook_verifies_and_resolves_payment`, `dispute_retrieve_matches_webhook`, `dispute_statuses_only_move_forward`. `CONTRACT_CLAUSES` grows to 34; no adapter is `verified`, so no evidence line changes.

### 5.2 Dispute state × event (`dispute_state_event_matrix`)

Rank: `open` 0, `evidence_submitted` 1, `won`/`lost`/`closed` 2 (final). A status of a lower or equal rank changes nothing; a different final status after a final one (won after lost) changes nothing, asks the gateway (`retrieveDispute`) and opens a review task (`payments:dispute_review:<eventId>`).

| Event ↓ / state → | (none) | open | evidence_submitted | won | lost | closed |
|---|---|---|---|---|---|---|
| Gateway: open | create `open`; task with due date | — | — | — | — | — |
| Gateway: evidence submitted / under review | create `evidence_submitted` | → evidence_submitted | — | — | — | — |
| Staff marks "evidence submitted" (panel, version) | n/a | → evidence_submitted | 409 | 409 | 409 | 409 |
| Gateway: won | create `won` | → won; task | → won; task | — | review | review |
| Gateway: lost | create `lost` | → lost; task | → lost; task | review | — | review |
| Gateway: closed (inquiry closed) | create `closed` | → closed | → closed | review | review | — |
| Funds withdrawn = true, not posted | post §5.3 | ídem | ídem | ídem | ídem | ídem |
| Funds reinstated = true, not posted | post withdrawn first if missing, then reinstated | ídem | ídem | ídem | ídem | ídem |

Funds postings are independent of status ("money only moves with the funds events", plan 0.1, 6.2): a dispute can be `won` and still need its reinstatement posted.

### 5.3 Processing a dispute event (`PaymentWebhooksService.processDispute`)

1. Outside any transaction, through the account that received the event: `retrievePayment({ ref: dispute.paymentRef })` and `retrieveDispute(ref)` (the gateway's current word wins over the event; if the gateway does not know the dispute, the event fails and is retried). Match the payment by our id **within that account**, then by `(providerAccountId, providerPaymentRef)` (finding 2). No match → event `ignored` (`unknown_payment`) and a task.
2. Transaction, Booking → all its Payments → Dispute. Payment not `succeeded` locally but succeeded at the gateway → caught up first through the payment state machine (as for refunds, `dispute_event_before_payment_success_syncs_payment_first`). Currency ≠ payment's → ignored with task (`dispute_currency_mismatch`). Amount above the payment's amount → ignored with task (impossible at a real gateway).
3. Find by `(providerAccountId, providerDisputeRef)`; else insert. Apply status (§5.2). Funds:
   - `fundsWithdrawn` and `fundsWithdrawnAt IS NULL` → set it and post `chargeback:<disputeId>:withdrawn` (kind `chargeback`, `disputeId`): cash `provider_clearing:<account>` −amount; customer side recomputed (§2), which may post to `customer_receivable`; then §7.
   - `fundsReinstated` and `fundsReinstatedAt IS NULL` → (withdrawn first if missing) set it and post `chargeback:<disputeId>:reinstated` (kind `reversal`, reverses the withdrawal): cash +amount; customer side recomputed; then C.
   - The same event twice, or the withdrawn and created events of one dispute in any order, post once (`dispute_created_and_funds_withdrawn_posts_once`).
4. Event linked (`disputeId`, `paymentId`, `bookingId`), raw body dropped if the customer was erased. Works on paused, retired and archived accounts (`archived_account_still_processes_dispute_webhook`).
5. Tasks: opened (`payments:dispute:<id>`, due `evidenceDueBy − 2 days`, link to the booking and the package), outcome (`payments:dispute_outcome:<id>`), review. Audit `payments.dispute.status_changed` and outbox events `payments.dispute.opened|won|lost|closed`, `payments.chargeback.withdrawn|reinstated`.

### 5.4 Staff actions

- No accept/concede, no submission through the API (§12.4).

## 6. Evidence package

`GET /admin/payments/disputes/:id/evidence` (permission `payments.dispute.evidence`, step-up: it is a copy of personal data), `Cache-Control: no-store`, `Content-Disposition: attachment; filename="dispute-<ref>-evidence.json"`, audited with the SHA-256 of the body (`payments.dispute.evidence_downloaded`). Built on demand, never stored (so nothing extra to erase; erasure is refused while the dispute is open, §1.4). Content, all from immutable or audited sources:

1. Dispute: gateway ref, reason code, amount, status, evidence due by.
2. Booking: reference, status history (from the audit log: transitions with dates), package and race names, travel dates, travellers' names (as booked).
3. Customer: name and email as held now (or "erased"), the customer's country.
4. **Terms accepted**: each `TermsAcceptance` of the booking with `acceptedAt`, slug, locale, version, digest and the full text accepted.
5. **Configuration and price**: every `BookingSnapshot` (version, created at, configuration, price breakdown, total, deposit) and every amendment (6.3) with its difference.
6. Payments of the booking (method, amount, dates, gateway ref) and their refunds (amount, status, dates; reasons excluded: internal notes).
7. **Emails sent**: `OutboundEmail` rows related to the booking or its customer (template, subject, recipient, status, sent at). Bodies are not stored by design (0.4), so the package lists them with their body fingerprint; noted for Oscar.
8. A `summary` block in plain Australian English sentences (generated from the data, via the API's template strings) that Oscar can paste into the gateway's text field.

A test asserts the package contains the terms with date, the snapshot and the emails, and no card data, no secrets and no staff notes (`evidence_package_contains_terms_snapshot_and_emails`).

## 7. Booking effects (money-out cells of 0.1 §6.2)

`coverageEvents` (bookings) gains two facts, `collectedMinor` and `everCollected` (a non-voided succeeded payment exists), and the cells:

- `balance_paid` with total no longer covered → `confirmed` (exists since 6.3; now also reached by refunds and chargebacks, `refund_or_chargeback_moves_balance_paid_to_confirmed`).
- `cancelled` with `everCollected` and collected = 0 → `refunded`; `refunded` with collected > 0 → `cancelled` (`overpayment_return_refunds_cancelled_booking`, `refund_reversed_moves_refunded_back_to_cancelled`, `voided_only_payment_keeps_cancelled`). Pairs already allowed by the state machine; events `fully_refunded` / `money_returned` added to its coverage events.
- `deposit_paid` or `confirmed` whose deposit is no longer covered: no transition; the 3.3 "coverage lost" task (blocks reminders and new charges until Oscar closes it), confirmation 409 `deposit_not_covered` (exists), and the panel shows `depositReversed: true` (`lost_chargeback_on_deposit_flags_unpaid_and_blocks_confirm`, `lost_chargeback_reopens_item_pending`).
- `completed` after money out: task. `requested`, `declined`, `expired`: only overpayment changes.
- `reinstated_chargeback_moves_to_balance_paid`: money back through C.

PaymentRefundStateMachine calls `coverage.apply` after `succeeded` (today it only opens the task) and keeps the task for the deposit case.

## 9. External refunds above the cap (P10)

3.3 refuses (event ignored, task) an external refund that makes refunds exceed the payment's **gross** amount; that stays (no real gateway does it). New: when it fits the gross amount but exceeds the payment's net of chargebacks, it is recorded and posted; the excess shows as receivable; task `payments:refund_over_cap:<id>` (`external_refund_over_cap_recorded_with_task`).

## 12. Decisions taken without Oscar (conservative, reversible)

1. **No `PaymentAllocation` table.** The allocation stays derived (§2), now with per-payment nets, reservations and receivable; it is a pure function under the booking lock, property-tested, and the ledger follows it. Difference from P7's letter: a refund or chargeback of an earlier payment reduces the overpayment first and then the **last** items, not necessarily the items that payment paid; coverage and amounts owed are the same, only which item shows as reopened can differ. Alternative rejected: an append-only table with batches and a backfill of every booking, a much larger change to money paths 3.2–6.3 already rely on. Undo: create the table later from this function (it is deterministic).
2. **`price_reduction` stays 409** although 6.3 exists: 6.3 shipped amendments without the combined "lower the total and refund in one transaction" flow. Today an amendment that lowers the total turns the excess into overpayment, which 4.5 refunds as `overpayment_return`. Undo: a later task adds the purpose with `amendmentId` and widens the CHECK.
3. **No amount in any refund request**: the amount is always `refundable(p)` (§2). "Total" is a payment refunded whole (e.g. a cancelled booking with a late payment); "partial" is part of a payment (its overpayment share) or one payment of several. A refund of part of an overpayment is not possible. Undo: an optional amount ≤ `refundable(p)` with step-up, like 3.4's staff-entered transfer amount.
4. **Evidence is not submitted through the gateway API**, and disputes cannot be accepted from the app: Oscar downloads the package and submits it at the gateway, then marks it. Undo: optional adapter method `submitDisputeEvidence`.
5. **Package generated on demand, not stored**; erasure refused while a dispute is open. Undo: store a file with `evidenceDocumentId` and an erasure handler.
6. **Refunds of disputed payments refused** (open, evidence submitted or lost).
7. **Manual refund destination encrypted and dropped when the refund leaves `requested`**; only a masked hint remains, erased with the customer.
8. **No four-eyes rule** (requester ≠ confirmer): Oscar works alone; step-up on both.
9. **No customer email or customer-area display of refunds** in 4.5 (receipts and adjustment notes are 4.6). Undo: a template and a section in 5.1's area.
10. Retry backoff 1/5/15/60 min, five attempts, never after 23 h; manual refunds waiting 7 days get a task. Settings later if Oscar wants.
11. Overpayment tasks of 3.2 are not closed automatically when the overpayment is refunded (Oscar closes them).
