# Plan 7.5: custom fields defined from the panel

Risk medium. Reference: `docs/phases/phase-7.md` (row 7.5), `docs/architecture.md` ("Capacidades comunes", "Plataforma"), `docs/plans/phase-0-architecture.md` (`customFields`, `CustomFieldDefinition`), `docs/done/1.2.md` (CSV of races and packages), `docs/done/0.5.md`, `.claude/rules/web.md`. No money: there is no `money` field type and no custom field can feed a price, a total or a payment.

## 1. What is built

**Data** (migration `0013_custom_fields`): table `custom_field_definitions` (`entityType`, `key`, `label` LocalizedText, `type` text/number/date/boolean/select/multiselect, `options`, `validation`, `required`, `visibleToCustomer`, `editableByCustomer`, `displayOrder`, `archivedAt`, `version`). `@@unique([entityType, key])`. Triggers: a definition is never deleted and `entityType`, `key` and `type` never change. CHECKs: `editableByCustomer` implies `visibleToCustomer`; select types carry options. GIN `jsonb_path_ops` indexes on `races`, `packages` and `suppliers` `customFields` (the columns already exist since 1.1 and 6.1).

**Platform** (`apps/api/src/platform/common/custom-fields/`, registered in `CommonModule`, no new Nest module): `values.ts` (pure: validate one value per type, CSV cell in and out, filter to Prisma JSON condition), `custom-fields.service.ts` (definitions CRUD with audit, `forWrite` merge and validate inside the caller's transaction, `filterWhere`, `csvColumns`, `publicView`), `custom-fields.controller.ts` (`/admin/custom-fields`). Supported entities today: `Race`, `Package`, `Supplier` (a table in the service; Customer, Traveller and Booking add a line when 2.4 and 5.x create them).

**Where it shows up without touching code:** the admin create/update bodies of races, packages and suppliers take `customFields`; their lists take a `cf` filter; the race and package CSV (1.2) gain `cf:<key>` columns on export and import; the public race and package views carry the values of fields marked visible to customers; the panel forms and list filters render from the definitions.

**Panel:** `/admin/settings/custom-fields` (create, edit, reorder by display order, archive, restore) plus `CustomFieldsEditor` and `CustomFieldsFilter` components used on the race, package and supplier pages and lists.

## 2. Assumptions (conservative, reversible)

1. New permissions `common.customField.read` and `common.customField.manage`, **not** `apiKeyScopable` (they define structure, and the rule file says no by default). Staff who edit values need `read` to see the form fields.
2. `key` is `^[a-z][a-z0-9_]{0,39}$`, unique per entity, never reused or changed; `type` never changes (archive and create another). Select options can be added, relabelled and retired, never removed, so a stored value never loses its meaning.
3. `required` is enforced when a record is created and when a patch tries to clear that field; adding a required field does not block edits of older records.
4. Archived fields disappear from forms, filters, exports and the public views, but their values stay in the row and come back on restore.
5. No `pattern` validation (ReDoS); text has min/max length, number min/max/integer, date min/max, multiselect min/max items.
6. `editableByCustomer` is accepted only for entities a customer can edit; none of the three today, so the API rejects it for now. `visibleToCustomer` is rejected for `Supplier`.
7. Values are personal-data class (`@pii`, as `customFields` already is) so audit stores them in the PII table; error messages name the field key, never a value.
8. Public web pages do not render the new values yet (the public API carries them); the panel is the user-facing surface of this task.

## 3. Failure cases and tests (written first)

`apps/api/test/platform/custom-fields-values.test.ts` (pure, table-driven): every type with valid, boundary and invalid values; JSON null clears; CSV cell round trip per type; filter conditions per type and operator; unknown operator rejected.

`apps/api/test/platform/custom-fields-api.test.ts` (PostgreSQL): permissions (403 without read or manage, anonymous refused); create/update/archive/restore with audit; duplicate key 409; key, type and entity immutable (API and trigger); delete does not exist and the trigger refuses it; options cannot be removed; customer flags rules; write path for race, package and supplier (valid, unknown key 422, archived key 422, wrong type 422, required on create, required cannot be cleared, merge keeps other keys, null removes, value never echoed); filters on lists (text contains, number range, date range, boolean, select, multiselect); CSV export columns and import round trip, one bad cell writes nothing and shows no value; public views carry only visible, active fields; a staff user without catalogue permission cannot set values through the definitions routes.

Web: copy keys exist and no hard-coded text (`copy.test.ts`), pure helpers (`custom-fields.test.ts`), e2e `apps/web/e2e/custom-fields.spec.ts`: define a field in settings, see it in the race form, set it, filter the race list by it, export CSV with the column.

## 4. Not done

Automations (7.4), organiser exports (7.2), report builder (7.7), customer-side forms (5.x), rendering on public pages, CSV of suppliers (none exists), custom fields on Customer/Traveller/Booking (tables do not exist yet), any money-valued field.
