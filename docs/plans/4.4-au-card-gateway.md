## 3. Assumptions the sandbox run must confirm

Each assumption has a test against the fake now and a line under "Sin verificar" in `docs/done/4.4.md`.

- **A1** `v1` is lowercase hex of the HMAC. `t` is Unix seconds. One header may carry several `v1` values, and any match is accepted. If Pin uses base64, only the decoder changes (one test).
- **A2** The endpoint's `key` (as returned by the API and shown in the dashboard) is the signing key.
- **A3** A webhook body is the Events object `{ token, type, data, created_at }` (no `response` wrapper), with `data` the charge or refund as the API returns it.
- **A4** A test-host call with a live key, or with any unknown key, answers 401.
- **A5** `GET /charges/{token}` gives the final state of a 3-D Secure charge after the customer finishes at the ACS, even if we never call `verify` (customer closed the tab). If false, a charge whose callback was lost stays `pending` until the expiry task (§6.8).
- **A6** An abandoned 3-D Secure charge ends unsuccessful at Pin within hours, and never succeeds later without the customer.
- **A7** A declined charge answers 400 with one of the listed codes, and a decline leaves no charge that can still succeed.
- **A8** Charge `metadata` is copied to the webhook `data` and is searchable at once (`query=<value>` finds the charge within seconds of the create answer).
- **A9** Refunds accept no metadata (we send none). If they do accept it, a later change can add our id. Our id comes from our store meanwhile (§7).
- **A10** A refund appears in `GET /charges/{token}/refunds` as soon as the create call has answered or timed out at Pin.
- **A11** The 3-D Secure `redirect_url` is always under `https://sandbox.checkout.com` in test mode. Any other host is refused (§6.4), so a wrong guess blocks payment but never redirects a customer somewhere unexpected.
- **A12** The Hosted Fields iframes and their tokenisation calls come from `https://cdn.pinpayments.com` and the API host of the mode (the CSP of §10.3). If wrong, the card page shows no fields. Only the CSP list changes.
- **A13** Pin sends the payer no email by default. The guide tells Oscar to check this and turn receipts off, because our receipts (4.6) are the ones sent.
- **A14** `GET /balance` needs no permission beyond the secret key, moves nothing and returns no personal data. It serves as the authenticated probe of §5.2.
- **A15** With `fallback_ok: false`, a card that is not enrolled is refused (400 or 422 `three_d_secure_unavailable`), and nothing is charged.
- **A16** The signature timestamp `t` is new on every delivery attempt and replay. If Pin keeps the first attempt's `t`, our 300 s window refuses every retry after five minutes. A lost first delivery is then recovered only by the sweeps (§6.8) and the reconciliation's object comparison, never by Pin's retries. The verification is not loosened for this. The sandbox run records two retried deliveries.
- **A17** A declined charge leaves a charge object at Pin. The reviewer recalls a `charge_token` in the error body; this is not in the pages read. Either way there is at most one charge per session (§6.3), and when the error carries a `charge_token` of the right shape, it is bound as the session's `chargeRef`, in state `failed`.
- **A18** Pin answers 429 when it rate-limits, and a 429 means the request was not processed. 409 is not documented for charges and is treated as an unknown outcome.

## 4. Architecture: card sessions in the core, the adapter only talks to Pin

### 4.1 The mismatch

Stripe and PayPal create an object at the gateway when we call `createPayment`, so the customer pays on the gateway's page and cancel is a gateway call. Pin has no such object. A charge needs a card token, and the token exists only after the customer has typed the card into Pin's iframes on our page. Between "we start a payment" and "the customer submits a card", the state (open, submitted once, cancelled, expired) has to live with us. An adapter is stateless and may not touch Prisma.

### 4.2 The design

- **`adapters/pin_payments/`** implements a narrow, gateway-neutral interface `CardTokenGateway` (new, its types added to `core/provider.ts`, review finding 5): `probe`, `charge(token, …)`, `verifyAuthentication(sessionToken)`, `retrieveCharge`, `searchCharges(metadataValue)`, `createRefund`, `retrieveRefund`, `listRefunds(chargeToken)`, `testConnection`, `verifyWebhook`, `parseEvent`, `signatureHeaders`. The isolation rules apply as for every adapter (`adapter_sources_are_isolated`): imports only `../../core/provider` and `node:crypto`, so `adapter_sources_are_isolated` passes unchanged. No environment, logs or Prisma.
- **`core/card-sessions/provider.ts`**: `CardSessionProvider implements PaymentProvider`, built from a `CardTokenGateway` and a `CardSessionStore`. This is what `createAdapters` registers under the key `pin_payments`. It owns the pre-card state and the refund intents (§7), and maps everything to `ProviderPayment` and `ProviderRefund`. It also has two members only the card-session service calls: `submitCard` (§6.3) and `finishAuthentication` (§6.4).
- **`CardSessionStore`**: a port with two implementations. `PrismaCardSessionStore` (tables of §11) is for the API. `MemoryCardSessionStore` is for the contract subject and unit tests. Every change is a compare-and-set on `(id, version)`.
- **`core/card-sessions/card-sessions.service.ts` and `.controller.ts`**: the customer endpoints of §10.1. They lock the attempt, check that it is live, the booking is payable and the account is `active`, then call `submitCard` through `ProviderGateway.call(accountId, 'create', …)`. So paused, retired, live-outside-production and unverified-live are all refused by the existing guard matrix, and the circuit breaker counts submits as creates.

### 4.3 Why this keeps the contract unchanged

The contract runs against the registered `PaymentProvider`, so here against `CardSessionProvider(PinAdapter(fake transport), MemoryCardSessionStore)`. `CreatePaymentInput` is untouched, so `create_input_has_no_card_fields` holds as written: the card token reaches only `submitCard`, never `createPayment`. The subject's `customerCompletes` is "the customer submits a card on our page": fake tokenisation, then `submitCard`, then the fake 3-D Secure if asked. That is what a subject is for ("how a customer pays comes from the subject"). No clause is skipped or loosened. The one clause whose first step has no Pin equivalent (an event before any charge exists) is handled by the amendment of §12.2, which applies to every adapter.

The design is reusable. Any later hosted-fields gateway (eWAY Secure Fields, Fat Zebra, Windcave drop-in) implements `CardTokenGateway` and gets sessions, the card page and the contract for free.

## 5. Manifest, credentials, HTTP

### 5.1 Manifest

- `key: 'pin_payments'`, `displayName: 'Pin Payments'`, `status: 'experimental'`, `testOnly: false`, `cardDataHandling: 'hosted_only'`.
- `methods: ['card']`: Apple Pay and Google Pay through Pin need domain verification, out of scope. `currencies: ['AUD']`, `countries: 'any'`.
- `checkoutOrigin`: the card page's origin, which is `WEB_ORIGIN`, passed in `AdapterOptions` as for the simulator. `manifestProblems` gets one rule. An adapter with `cardFields` (below) must have `https` outside `development`, `test` and `ci`. Inside them, the simulator's `TEST_ONLY_ORIGIN` shape applies, so `http://localhost:3000` works in `pnpm dev`. Production already requires an `https` `WEB_ORIGIN` (`scripts/check-deploy-config.mjs`).
- New optional manifest member `cardFields`, read by the card page and the CSP. Its values are fixed in code, and only the mode selects between them:

  ```ts
  cardFields?: { scriptUrl: string; frameOrigins: readonly string[]; challengeOrigins: { test: readonly string[]; live: readonly string[] } };
  ```

  Pin: `scriptUrl: 'https://cdn.pinpayments.com/pin.hosted_fields.v1.js'`, `frameOrigins: ['https://cdn.pinpayments.com']` (A12), `challengeOrigins.test: ['https://sandbox.checkout.com']` (A11), `challengeOrigins.live: []` (unreachable while `experimental`; empty means nothing live is ever followed). `manifestProblems` requires `https` origins without paths and `scriptUrl` under one of `frameOrigins`.
- `capabilities: { refunds: 'partial', deferredCapture: false, lookupByIdempotencyKey: true, declineOutcome: 'failed', preCardSession: true }`. A declined card ends the session (§6.3, D7); `preCardSession` is the capability of §12.2. No `disputes` (§9), no `reconciliation` (§9).

### 5.2 Credentials (4.1 account setup)

- `secretKey`: label "Secret API key (test account)", pattern `^[A-Za-z0-9_-]{16,128}$`. Pin keys carry no documented test or live marker, so as with PayPal the host keeps a test account on test money: a test context only ever calls `test-api.pinpayments.com` (A4).
- `publishableKey`: label "Publishable API key (test account)", same pattern, and a new optional field flag `exposure: 'card_page'` (D4). Pin designs this key for the browser (`tokenize({ publishable_api_key })`). It is stored encrypted like every field and never returned by the panel's API. The only place it leaves the server is the card-session view of §10.1, for that session's account, while the session is open. `manifestProblems` allows `exposure` only on adapters with `cardFields`, and at most one such field. A test checks that the panel's responses, the audit log and the logs never contain it, and that the card-session view contains only it and no other field.
- `webhookSecret`: `{ source: 'entered', label: 'Signing key of the webhook endpoint', pattern: '^[A-Za-z0-9_-]{16,64}$' }` (A2: the example `key` has 22 characters).
- Samples are built at runtime from filler, never a key-shaped literal. Rejected samples: values with spaces, `.`, `:`, `=`, too short, too long.
- `testConnection`: `GET /balance` (auth), then, with a webhook key set, `GET /webhook_endpoints` (at most 5 endpoints, documented), and one endpoint's `key` must equal `ctx.webhookSecret`, compared with `timingSafeEqual` on equal-length buffers. No key: `webhook_secret_missing`. No endpoint with that key: `provider_rejected` (as PayPal does for a webhook that is missing). Never throws.

### 5.3 HTTP layer

- Hosts fixed in code by `ctx.mode`: test `https://test-api.pinpayments.com/1`, live `https://api.pinpayments.com/1` (unreachable while `experimental`). No option or variable changes them. A unit test checks that a test context never reaches another host.
- Each request: `fetch` with `redirect: 'error'`, a 4.5 s timeout (8 s for `POST /charges`, which Pin calls long-running, still inside the wrapper's 10 s), JSON in and out (`application/x-www-form-urlencoded` is not used), body capped at 1 MiB, else `provider_unavailable`.
- Errors are read only for `error` (a code), compared with closed lists. Pin's `error_description` and `messages` never leave the adapter. 401 and 403 mean `provider_auth_failed`, non-retryable. 404 means `null` or `provider_not_found` as the member requires. 409, 429 and 5xx mean `provider_busy` or `provider_unavailable`, retryable. A timeout means `provider_timeout`, retryable.
- Tokens are checked before they are put in a URL: `^ch_[A-Za-z0-9_-]{10,40}$`, `^rf_…`, `^dis_…`, `^se_…`. Malformed ones never reach Pin. They are checked after the probe, so bad credentials still give `provider_auth_failed` (contract `bad_credentials_are_auth_failed`).
- **Probe (A14).** Every `CardSessionProvider` operation that would otherwise answer from the store alone (create, retrieve of a session without a charge, cancel of an open session, refund lookups) first calls `gateway.probe()` (`GET /balance`). So bad credentials are `provider_auth_failed` everywhere, and an account Pin no longer accepts never shows a card page. No cache (as PayPal, D7 of 4.3).
- Secret key, publishable key, webhook key, email and IP never appear in a `ProviderError`, a result or a log (C20 and a unit test).

## 6. Payments

### 6.1 Money

- Only `AUD` (manifest). Anything else is refused before any call or store write (`provider_rejected`, definitive: `definitive_refusal_means_no_object`).
- `1n ≤ amount ≤ 999_999_999n`, else refused before any call. Pin takes a JSON integer: a `bigint` checked to be ≤ 2^53 − 1 is turned into a number in one function, with a test. Answers are read with `Number.isSafeInteger`, then `BigInt`. No floats and no arithmetic on them. A static test greps the adapter for `parseFloat`, `toFixed` and `Math.`.
- No rounding: the amount arrives in minor units from the core. The rounding rule of `.claude/rules/pricing.md` is not involved.

### 6.2 Create: a session, no money

`createPayment(ctx, input)`: currency and amount checks, probe, then `store.createOrGet(accountId, idempotencyKey, { amount, paymentId, bookingId, returnUrl, createdAt: input.createdAt, expiresAt })`:

- **New:** a session with `ref = 'cs_' + 32 random hex` (a bearer value, like a Stripe Checkout URL) and `status: 'open'`.
- **Expiry (finding 10, review round 2 m6).** `expiresAt = payments.pendingExpiresAt + 30 min`, read from the payment row (`metadata.paymentId`) by the Prisma store at creation. So it always follows the attempt's own expiry, whatever the setting said then. The memory store of the contract takes `input.createdAt + 60 min + 30 min`. The 30 min margin lets the core's own expiry (P3) query and cancel first. Test: `session_outlives_attempt_expiry`.
- **Existing (same key):** returned as stored, whatever amount is asked now, so a key never gives a second object (`same_key_other_amount_never_a_second_object`). The core's amount check sees the difference.
- **Answer (review round 2 m5):** the session's current state as §6.5 maps it: `requires_action` with `nextAction: { type: 'redirect', url: `${checkoutOrigin}/pay/card/${ref}` }` for a new or open session, and `failed`, `cancelled` or `succeeded` for one that ended (`failed_is_terminal` creates again with the same key).

### 6.3 Submit a card: `submitCard` (exactly one charge per session)

Findings 1 and 2 are resolved by option (a). A session makes **at most one `POST /charges` in its life**. A decline, a failed 3-D Secure, a refusal or a rate limit ends it as `failed`, and the customer starts a new attempt from the return page (the core already allows one after `failed`; `PaymentAttemptRateLimitGuard` limits how often). `declineOutcome: 'failed'`.

`submitCard` is called only by the card-session service (§10.1). Sync, drive, expire, cancel, replace, orphans and refunds never call it.

1. The service locks the payment (attempt) row and checks:
   - the attempt is `requires_action` and its `providerPaymentRef` is this session's ref;
   - the booking is payable and not under review (`bookingUnderPaymentReview`);
   - the account is `active`.

   Otherwise the answer is 409 and nothing is called.
2. Store compare-and-set `open → submitting` (with `now < expiresAt`), setting `submittedAt`. If it fails, 409 `card_session_not_open`. `submittedAt` is set once: the trigger refuses to clear or change it, and no state leads back to `open`. So a double click, two tabs, a replay or a retry can never send a second `POST` for a session.
3. Outside any transaction, via `ProviderGateway.call(accountId, 'create', …)`, the adapter sends `POST /charges` with:
   - `amount`, `currency: 'AUD'`, `description: 'Booking payment'`;
   - `email`: the payer's, read by the service from the booking;
   - `ip_address`: the request's client address, as the platform's trusted-proxy rule resolves it;
   - `card_token`, `capture: true`;
   - `metadata: { mt_session: ref, mt_payment: paymentId }`;
   - `three_d_secure: { enabled: true, fallback_ok: false, callback_url: `${checkoutOrigin}/api/payments/card-sessions/${ref}/authenticated` }` (D6, A15).

   No booking reference, no name, no other personal data.
4. Outcomes, each a compare-and-set from `submitting`, and **only forward**:

| Pin answer | Session | What the core sees (§6.5) | Card page |
|---|---|---|---|
| 201, `success: true` | `succeeded`, `chargeRef` | `succeeded` | goes to `returnUrl` |
| 202 with `redirect_url` under `challengeOrigins[mode]` | `authenticating`, `chargeRef` | `pending` | goes to `redirect_url` |
| 202 with another host, or without `redirect_url` | `authenticating`, `chargeRef` (A11) | `pending` | "We could not start your bank's check". The charge ends at Pin (A6) and the sweep reads it |
| 400 decline code, 422 `three_d_secure_unavailable` | `failed`, `failureCode` from a closed list (`card_declined`, `insufficient_funds`, `expired_card`, `card_not_authenticated`, `processing_error`, `suspected_fraud`); `chargeRef` if the body carries one (A17) | `failed` | "Your card was declined. Start again to use another card." Link to the return page |
| 422 `invalid_resource`, 400 `token_already_used` | `failed`, `provider_rejected` | `failed` | "This payment cannot be completed" |
| 401, 403 | `failed`, `provider_auth_failed` (also reported to the breaker) | `failed` | error |
| 429 (A18) | `failed`, `provider_busy` (nothing was created) | `failed` | "Too many attempts, try again in a few minutes" |
| Timeout, 5xx, 409, network | stays `submitting` (unknown) | `requires_action` (§6.5) | "We are checking your payment" |

5. **Unknown outcome.** A session in `submitting` is resolved only by reading Pin: `GET /charges/search?query=<ref>` (A8). Search matches metadata values, so the result is filtered on `metadata.mt_session === ref` exactly.
   - **One match:** binds it as in the table.
   - **No match:** it stays `submitting` until `expiresAt`. At or after that, one last search that still finds nothing moves it to `failed` with `outcome_unknown` (`requires_action → failed` exists). A charge that appears later arrives as `failed → succeeded`, which the core records as a late success with an overpayment and a task (it exists today).
   - **More than one match:** this cannot come from our code, because there is one `POST` per session. It is still handled (finding 2): the first successful one, or the first one if none succeeded, is bound. Every other charge goes to `card_session_charges` (§11) and opens a task (`payments:card_session_extra_charge:<chargeToken>`). If any of them succeeded, the task says that money came in outside the payment and must be refunded or registered. Test: `second_charge_on_session_surfaces_task`.

### 6.4 3-D Secure: `finishAuthentication`

`GET /api/payments/card-sessions/:ref/authenticated?session_token=se_…`. Pin sends the customer there "regardless of outcome".

- It runs through `ProviderGateway.call(accountId, 'retrieve', …)` (finding 11). It moves no money: it only reads the charge, so a paused or retired account can still finish a 3-D Secure that started while it was active.
- `session_token` must match `^se_[A-Za-z0-9_-]{10,64}$`. Otherwise no call is made, and the browser gets 303 to `returnUrl`.
- The session must be `authenticating`, else 303 to `returnUrl` and nothing else.
- The call is `GET /charges/verify?session_token=…`. The charge's `token` must equal the session's `chargeRef`, else `reference_mismatch`: nothing is recorded and a task opens.
  - `success: true` gives `succeeded`.
  - `success: false` gives `failed` with `card_not_authenticated`.
  - Still pending, 403, 404 or 422 leave the session unchanged.
  - Then 303 to `returnUrl`, where the existing return page refreshes the attempt (`sync`).
- The redirect target is always the session's stored `returnUrl` (built by the core), never a parameter.

### 6.5 Statuses: session to `ProviderPayment`, checked against the core's machine

The mapping only uses transitions that `nextStatus` (`core/attempt-state.ts`) allows from whatever the core holds, and no session state ever goes back.

| Session | Reported | Core transitions it can cause |
|---|---|---|
| `open` (before `expiresAt`) | `requires_action`, redirect to the card page | `created → requires_action` |
| `submitting` (unknown outcome) | `requires_action`, redirect to the card page, which shows "processing" | none from `requires_action`. The attempt stays live, so P2 blocks a second attempt and the expiry sweep keeps asking |
| `authenticating` | `pending` (a charge exists and may still succeed) | `requires_action → pending` |
| `succeeded` | `succeeded`, with the charge's `amount` as Pin reports it | any live status → `succeeded` |
| `failed` | `failed` with its code | `requires_action`/`pending` → `failed`; later `failed → succeeded` only through the late-success path |
| `cancelled`, or `open` past `expiresAt` | `cancelled` (the read moves the store to `cancelled` with `expired`) | `created`/`requires_action` → `cancelled` |

- **Why `submitting` is `requires_action`, not `pending`.** Its two possible ends are `succeeded` and `failed`. Both are allowed from `requires_action`, and the core never has to go from `pending` to `cancelled`, which does not exist.
- **`authenticating` is `pending`.** Its ends are `succeeded` or `failed`, both allowed from `pending`. Nothing from it ever reports `cancelled` or `requires_action`.
- **A session is `cancelled` only from `open`.** No charge was sent, and the core holds `created` or `requires_action`.

Test (finding 1): `card_session_paths_with_real_state_machine`, on a fresh database, with the real `PaymentAttemptStateMachine`, `PaymentAttemptSyncService` and webhooks service, one case per path:

- pay;
- decline;
- 3-D Secure succeeds;
- 3-D Secure fails after the sweep already saw `pending`;
- 3-D Secure abandoned;
- unknown submit, then success;
- unknown submit, then nothing until `expiresAt`, then a late charge;
- cancel while open;
- expiry while open;
- replace while `submitting` (refused).

Each case asserts that the attempt ends in the state the table says and that no call of the machine is refused.

`ourPaymentId` comes from the store, or from `metadata.mt_payment` when the charge has no session (a charge made in Pin's dashboard).

### 6.6 Retrieve, lookup, cancel

- **`retrievePayment({ ref })`.**
  - A `cs_` ref reads the store. Unknown means `null` after the probe.
  - In `submitting`, it runs the resolution of §6.3 step 5 first.
  - In `authenticating` (or when asked for a `succeeded` session), it reads `GET /charges/{chargeRef}` and applies any final state to the store first.
  - A `ch_` ref (the `paymentRef` of a refund event) uses the store's index on `chargeRef`. Without a session, it uses the charge itself (`ref` = the charge token, `ourPaymentId` from metadata).

  It is read only: it never charges, captures or verifies.
- **`retrievePayment({ idempotencyKey })`.** The store by `(accountId, key)`, then as above. Exact, with no time window. Unknown means `null` after the probe.
- **`cancelPayment(ref)`.**
  - Unknown ref means `provider_not_found` after the probe.
  - `open` becomes `cancelled` (compare-and-set).
  - `submitting` is resolved first. If still unknown, it answers `requires_action` unchanged: not cancelled, so P2 does not replace it.
  - `authenticating` reads the charge and answers `pending`, `succeeded` or `failed`.
  - `succeeded`, `failed` and `cancelled` are answered as they are.

  The key argument is unused: a compare-and-set on the store needs none.
- **A cancelled session cannot be paid.** `submitCard` needs `open`. That is `cancel_is_idempotent_and_final`, held by our own state.

### 6.7 No surcharge, amount from the server

The card page shows and charges exactly the session's amount, which `createPayment` received from the core (P1). Hosted Fields do not surcharge. The Payment Page, which can surcharge, is not used. Test `no_surcharge_by_payment_method (task 4.4)`: the same booking routed to the simulator and to Pin gives the same amount on the card page and in the charge sent to the fake.

### 6.8 Sweeps and known limits

- The core's existing expiry and sync paths call `retrievePayment` and `cancelPayment`, and they resolve `submitting` and `authenticating`. No new job.
- An abandoned 3-D Secure keeps the attempt `pending` until Pin ends the charge (A6). It cannot be replaced at once: `abandoned_3ds_resumed_or_replaced_immediately` is a simulator property. The return page says so. If Pin never ends the charge, the existing 24 h stuck-attempt task reaches Oscar, as for PayPal in 4.3. A lost callback (A5 false) behaves the same.
- If A16 is false, Pin's retries are refused as stale. These sweeps and 4.6's object comparison are then the only recovery.

## 7. Refunds

Pin documents neither idempotency nor metadata for refunds (A9). The store keeps a **refund intent** per `(accountId, idempotencyKey)`:

- `refundId`, `chargeRef`, amount, `createdAt`;
- status `new`, `submitting`, `bound` or `refused`;
- `refundRef`.

`createRefund(input)`:

1. **Currency check.**
2. **Resolve the payment (finding 3).** `paymentRef` is a `cs_` ref or a `ch_` token. A session in `submitting` is resolved first (§6.3 step 5), so a payment the core already marked `succeeded` from a `charge.captured` webhook finds its charge. A session that the core sees as collected but the store has not bound is bound here. The webhook path never writes the store (§8.3). Then the charge is read: `GET /charges/{chargeRef}`. The refund is refused without a call (definitive) unless:
   - `success && captured`;
   - `amount > 0`;
   - `amount ≤ charge.amount − charge.amount_refunded − (pending refunds listed)`.

   So `refund_of_unpaid_payment_refused` and `refund_over_amount_refused` hold.
3. **Intent.** A compare-and-set insert `new`. An intent that already exists goes to point 5.
4. **Post.**
   - `new → submitting`, then `POST /charges/{chargeRef}/refunds { amount }`. The amount is always sent, never the empty body, which means "everything".
   - An answer binds `refundRef` (`bound`).
   - 429 (A18: nothing created) moves the intent back to `new` and answers `provider_busy`, retryable, so the next retry posts once. This is the only backward step, it is internal to the store, and it is never taken after an unknown outcome.
   - 402 `insufficient_pin_balance`, 400 and 422 give `refused`, `provider_rejected`, definitive (nothing exists under the key).
   - 401 and 403 give `provider_auth_failed` and leave the intent `new` (nothing was created).
   - Timeout, 5xx, 409 and network errors leave it `submitting` (unknown).

   This replaces "other 4xx: rejected" and agrees with §5.3 (finding 9).
5. **Existing intent.**
   - `bound`: `GET /refunds/{refundRef}`, so a retry answers the same refund (`refund_full_and_idempotent`).
   - `submitting`: `GET /charges/{chargeRef}/refunds`. Candidates are refunds with the same amount, `created_at ≥ intent.createdAt − 120 s` and not bound to another intent. Exactly one binds. More than one gives `provider_unavailable` and a task. None gives `provider_unavailable`, retryable (A10). **No refund is posted twice after an unknown outcome.** 4.5's stuck-refund sweep and "resolve" path reach Oscar.
   - `refused`: `provider_rejected`.

**Other members.**

- `retrieveRefund({ ref })`: `GET /refunds/{ref}`. 404 means `null`. If an intent in `submitting` for that refund's charge has the same amount and window, it is bound first. `ourRefundId` comes from the intent bound to that ref, so a refund we started carries our id (`refund_retrieve_by_ref_and_key_agree`) and a dashboard refund carries none (`gateway_refund_has_no_our_id`).
- `retrieveRefund({ idempotencyKey, paymentRef })`: reads the intent, then as above.
- **Statuses.**
  - `status_message` `Pending` means `pending`.
  - `Success` means `succeeded`.
  - `Failed`, or `error_message` set with `success: false`, means `failed`.
  - Any other value is `provider_unavailable`: we cannot read it.

  `paymentRef` is the refund's `charge` token, which `retrievePayment` resolves to the session's ref.

**Core change (finding 4, mandatory, adapter-neutral).** In `PaymentWebhooksService.processRefund`, an event with no `ourRefundId` and no refund matching `providerRefundRef` would today be recorded as `external`. Before that, outside the transaction, it calls `provider.retrieveRefund(ctx, { ref })` through `ProviderGateway.call(accountId, 'retrieve', …)`.

- When the answer carries an `ourRefundId` of an app refund of this account and payment, that refund is the match. It is locked in the transaction, gets the reference, and the event is applied to it as the code does today for `byOurs`.
- When the call fails, the event stays `failed` and is retried, never recorded as `external`.
- For Stripe and PayPal it changes nothing in practice: they always send our id.

Tests:

- `webhook_before_provider_response_matches_app_refund (pin)`: the `POST` times out, `refund.created` is processed, then the intent binds. Exactly one refund row and one ledger posting.
- `refund_event_unmatched_and_unknown_still_external`.
- `refund_after_webhook_only_success`: the submit timed out, `charge.captured` marked the payment succeeded, the store was still `submitting`. The refund succeeds, and the session ends `succeeded`, not `failed`, at expiry.

Refunds on paused and retired accounts work as for every adapter (`retired_account_refunds_but_rejects_new_charges` extended to Pin).

## 8. Webhooks

### 8.1 Verification (synchronous, no network)

1. Header `pin-signature`, at most 512 characters, ASCII. It is parsed as comma-separated `k=v` parts: exactly one `t` (`^[0-9]{1,12}$`) and one to four `v1` (`^[0-9a-f]{64}$`, A1). Missing, oversized or other shapes give `bad_signature`. `malformed` is used only for a body that is not an event. It never throws.
2. An empty `ctx.webhookSecret` gives `bad_signature`.
3. The expected value is HMAC-SHA256(`ctx.webhookSecret`, `${t}.` + the raw body bytes), compared with each `v1` by `timingSafeEqual` on 32-byte buffers. No match gives `bad_signature`.
4. `|now − t| > 300 s` either way gives `stale_timestamp`, checked after the signature (contract: 299 s, 301 s, 1 h). See A16 for retries.
5. Body: a JSON object with:
   - `token` (`^evt_[A-Za-z0-9_-]{10,40}$`);
   - `type` (≤ 64 characters);
   - `created_at` (strict ISO 8601);
   - `data`, an object.

   Otherwise `malformed`, with `claimedEventId` when `token` is readable. The core's 256 KiB limit (P6) applies before.

`signatureHeaders: ['pin-signature']`. Webhook URLs in Pin's examples carry a `signature` query parameter. It is ignored: only the header scheme is accepted, and an older scheme fails closed.

### 8.2 Events (`parseEvent`, pure)

| Pin `type` | `kind` | Mapping |
|---|---|---|
| `charge.captured`, `charge.authorised` | `payment` | `data` = charge. `ref` = `metadata.mt_session` when it has the `cs_` shape, else the charge token. Status from the charge: `success && captured` gives `succeeded`, otherwise `pending`. `ourPaymentId` = `metadata.mt_payment` when a UUID |
| `charge.failed` | `payment` | `failed` |
| `charge.voided` | `payment` | `failed`. We never authorise, so this is not expected |
| `refund.created`, `refund.succeeded`, `refund.failed` | `refund` | `data` = refund. Status from `status_message` (§7), not from the event name |
| `dispute.*` | `unsupported`, `review: 'dispute'` | Stored raw, task for Oscar (§9) |
| anything else | `unsupported` | Stored raw, not processed |

- **Duplicates and order.** `providerEventId` = `token`. Duplicates share it, and the core stores one per account (P5, P6). Statuses come from `data`, and the core's machine only moves forward, so a late `charge.failed` after `charge.captured` changes nothing (`succeeded` is never left).
- **A second charge under one session.** With one `POST` per session this is impossible from our code (§6.3). If it ever happened, its event would carry the same `cs_` ref. A `succeeded` event while the core already holds `succeeded` changes nothing. Its money would show up only through the extra-charge check of §6.3 step 5 (the search returns every charge of the session) and in 4.6's comparison. This limit is stated: the event path alone does not see it.
- **Raw bodies.** The core stores them before processing, as for every adapter. They contain the payer's email and IP, and the card's masked number and name as Pin sends them. They are dropped when the customer is erased (5.5), as for PayPal.

### 8.3 Events do not update the store (finding 3: earlier claim withdrawn)

`PaymentWebhooksService.processEvent` applies `parsed.payment.status` directly (`webhooks.service.ts`, the match by our id, then the reference check, then `machine.apply`). It does not call `retrievePayment`. So a webhook never changes `card_sessions`. Every member of `CardSessionProvider` that needs the truth (retrieve, cancel, createRefund, retrieveRefund, the expiry resolution) reads Pin itself and binds the store when it is behind (§6.3 step 5, §7 point 2). Tests: `refund_after_webhook_only_success` and `expiry_after_webhook_only_success_ends_succeeded`.

## 9. Disputes, reconciliation and fees: not declared in 4.4

- **Disputes.** Pin has a Disputes API, but what was read does not document how the funds move (`chargeback_recovery` ledger entries, timing, reinstatement). Wrong funds flags would post wrong ledger entries. So we do as PayPal did in 4.3: no `capabilities.disputes` and no `retrieveDispute`. `dispute.*` events are `unsupported` with `review: 'dispute'`, so the core opens a task, and the dispute clauses check that nothing dispute-like is claimed. `docs/done/4.4.md` lists the mapping a follow-up would use once the sandbox shows real objects: statuses `evidence_required`, `evidence_under_review`, `won`, `lost`, `expired`, `accepted`, `cancelled` and `arbitration_*`, with funds read from the activity feed.
- **Reconciliation.** There is no `capabilities.reconciliation`, so 4.6 compares our objects one by one. `GET /charges`, `/refunds`, `/disputes` and Deposits could support `listActivity` and `listSettlements` later.
- **Fees (finding 12).** They are not imported. The charge's `total_fees` and `merchant_entitlement` are read by nothing. The reconciliation report for a Pin account says "fees not imported" (`feesImported` false), as for Stripe and PayPal (`docs/done/4.6.md`). Test: `pin_reconciliation_reports_fees_not_imported`.

## 10. Customer endpoints and the card page

### 10.1 API (`core/card-sessions/card-sessions.controller.ts`)

All three endpoints are `@Public()`: the session ref is the bearer. They send `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. A ref that is unknown, malformed (not `^cs_[0-9a-f]{32}$`) or from another mode gets the same 404 as an unknown route.

- **`GET /payments/card-sessions/:ref`** answers `{ status: 'open' | 'processing' | 'finished', amountMinor, currency, card?: { publishableKey, sandbox: mode === 'test', scriptUrl }, failed?: <closed code> }`.
  - `card` is present only while the session is `open` and its account is `active`.
  - It carries no booking reference, name, email, account id or other credential.
  - The amount is the session's: the web displays it and computes nothing.
- **`POST /payments/card-sessions/:ref/submit`** takes `{ cardToken }`, with a strict schema (`^card_[A-Za-z0-9_-]{10,64}$`).
  - Any other field (number, cvc, expiry, amount, URL) is a 422 and nothing is written (`card_data_never_reaches_api` extended).
  - It returns `{ next: 'redirect', url }` (3-D Secure, or `returnUrl` on success and on every `failed`) or `{ next: 'wait' }`.
- **Rate limits (finding 8).** One `POST` per session (§6.3). 10 submits per IP per 10 min. `PaymentAttemptRateLimitGuard` already limits new attempts per user and per IP, so each new card needs a new attempt. Nothing is counted per account, so nobody can block all card payments. Instead, more than 20 declines on one account within an hour opens a task for Oscar (`payments:card_declines_spike:<accountId>:<hour>`) without blocking anything. Over a limit gives 429 and Pin is not called. CSRF: a same-origin `fetch` from the card page, through the existing CSRF guard as for checkout.
- **`GET /payments/card-sessions/:ref/authenticated`** (§6.4) always answers 303 to the session's `returnUrl`, or to the generic return page if the ref is unknown. It never redirects to a parameter. It is rate-limited (finding 8): 20 per IP per 10 min, and at most 3 `verify` calls per session (more give 303 with no call; the sweep reads the charge).

### 10.2 Web: `apps/web/src/app/pay/card/[ref]/page.tsx`

- **Rendering.** Dynamic, `noindex`, no ISR: a payment page, like checkout. A server component fetches the view.
- **Client component.** Small. It loads `scriptUrl` once and calls `HostedFields.create({ sandbox, fields: { name, number, cvc, expiry } })`. On submit it calls `tokenize({ publishable_api_key })`, posts only the token, then follows `url` with `window.location.assign`. Only `https` or same-origin URLs are followed; the API has already checked the challenge host.
- **No card data in our inputs.** The four containers are empty `div`s that Pin fills with iframes. A static test fails if the page or component declares an `input` or `name` for number, cvc, expiry or name. A component test checks that the posted body is `{ cardToken }` only.
- **Copy.** In `messages/en-AU.json`: amount label, declined (start again), processing, not open, bank check. Brand from `brand.config.ts`. No claims of accreditation or "official".
- **WCAG 2.2 AA.**
  - Visible labels outside the iframes, and errors in an `aria-live` region.
  - The submit button is disabled only while a request is in flight.
  - Keyboard order runs through the iframes, focus is visible, targets are 24 px and colours use the contrast tokens.
  - Unit tests use a mocked `HostedFields` global (no network in CI).

### 10.3 CSP for that route only

In `apps/web/src/proxy.ts`, the route `/pay/card/*` gets its own nonce-based CSP:

- `script-src 'nonce-…' 'strict-dynamic' https://cdn.pinpayments.com`
- `frame-src https://cdn.pinpayments.com` (A12)
- `connect-src 'self'`
- `form-action 'self'`
- `frame-ancestors 'none'`
- `base-uri 'none'`
- `object-src 'none'`

The origins come from one shared constant in `packages/shared`, which the manifest also uses, so they cannot drift (test `csp_card_route_origins_match_manifest`). Every other route's CSP is unchanged. This is the "wider `frame-src`" that plan 8.5 anticipated, limited to this route.

### 10.4 PCI (finding 14)

An iframe page keeps card data out of our systems.

- **What applies (unverified).** The reviewer recalls that under PCI DSS v4.0.1, SAQ A covers pages that embed a compliant provider's iframes, with an eligibility criterion about the page not being open to script attacks. This is not verified here. The question goes to Pin (§16).
- **What we can test.** Test `card_page_loads_no_third_party_script_but_pins` renders `/pay/card/[ref]` and asserts three things:
  - every `<script src>` is same-origin or `scriptUrl`;
  - no inline script lacks the nonce;
  - the CSP header allows no other script origin.

  The page also has no analytics, tag manager or font CDN.
- **What we never keep.** Nothing in this design stores, logs or forwards card data. The card token is single-use and is not stored.

## 11. Migration `0039_card_sessions` (only adds)

**`card_sessions`**

- **Identity and links.** `id uuid` and `ref text UNIQUE` (`CHECK ~ '^cs_[0-9a-f]{32}$'`). `providerAccountId` FK and `mode "PaymentMode"`, which a trigger keeps equal to the account's (P11). `idempotencyKey text` with `UNIQUE (providerAccountId, idempotencyKey)`. `paymentId uuid NOT NULL` FK to payments and `bookingId` FK.
- **Money and return.** `currency`, `amountMinor bigint CHECK > 0`, and `returnUrl text`, built by the core.
- **State.** `status` is one of `open`, `submitting`, `authenticating`, `succeeded`, `failed`, `cancelled`. `chargeRef text NULL`, `UNIQUE (providerAccountId, chargeRef)`, `CHECK ~ '^ch_'`. `failureCode text NULL`, limited to a closed list by a `CHECK`.
- **Time and version.** `submittedAt NULL`, `createdAt`, `expiresAt`, `updatedAt`, `version int`.
- **Trigger (forward only).** It allows only these transitions: `open → submitting | cancelled`, `submitting → authenticating | succeeded | failed`, `authenticating → succeeded | failed`. Any other change of `status` is refused, as is any change of `submittedAt` once set, or of `chargeRef` once set. There is **no** way back to `open`.

**`card_session_charges`** (append-only, finding 2)

- `id`, `sessionId` FK, `providerAccountId`, `mode`, `chargeRef UNIQUE`, `success boolean`, `amountMinor`, `currency`, `seenAt`.
- One row for every charge Pin reports under a session's `mt_session`, the bound one included.
- An anti-modification trigger, as for other append-only tables.

**`card_refund_intents`**

- `id`, `providerAccountId`, `mode`, `idempotencyKey`, with `UNIQUE (providerAccountId, idempotencyKey)`.
- `refundId uuid` FK refunds, `chargeRef`, `amountMinor`, `currency`.
- `status` is one of `new`, `submitting`, `bound`, `refused`. A trigger allows `new → submitting → bound | refused`, plus `submitting → new` only when the row's `lastAnswer = 'rate_limited'`. That column is set in the same update, with a closed `CHECK`.
- `refundRef text NULL`, with `UNIQUE (providerAccountId, refundRef)`. Timestamps and `version`.

**Field classes and undo**

- Every column is `@nopii`: codes, refs, amounts, and a URL built from `WEB_ORIGIN` plus a booking path. None of the three tables has an email, IP or card column. Nothing is erased by 5.5. Database roles follow plan 0.1: the app gets `SELECT, INSERT, UPDATE` on the two mutable tables and `SELECT, INSERT` on the append-only one, with no `DELETE`.
- Undo: drop the three tables in a later migration, after the adapter is removed.

### 12.2 `webhook_previous_state_and_duplicate` (finding 6)

The clause takes `webhookFor` right after `create`, before the customer pays, and expects that event's state to equal the new payment's state (`requires_action`). **Pin emits no event for a session with no charge**: no charge exists yet, and none of the 39 documented event types describes "waiting for a card". **Proposed amendment, for every adapter, to be approved in this plan review.** No clause is skipped or loosened for the others.

- `ContractSubject.webhookFor` may return the marker `NO_GATEWAY_EVENT`. It may do so only for an object that has no counterpart at the gateway. The manifest declares this with a new capability, `capabilities.preCardSession: true`, which `manifestProblems` allows only for providers built by `CardSessionProvider`.
- For such providers, the clause:
  1. asserts that `webhookFor` before payment answers `NO_GATEWAY_EVENT`. The sandbox subject proves the absence: `GET /events` and `GET /charges/search?query=<ref>` return nothing for the session;
  2. runs the "older event keeps its own state" check on two real events of the paid object. A `refund.created` event whose `data` is `Pending`, verified after the `refund.succeeded` of the same refund, must still parse as `pending`;
  3. runs the duplicate and two-ids checks exactly as today, on `charge.captured` and the refund events.
- Every other adapter (simulator, Stripe, PayPal) runs the clause exactly as today. `NO_GATEWAY_EVENT` from a provider without the capability fails the clause.

**Flag for the reviewer.** The PayPal sandbox subject signs a `CHECKOUT.ORDER.APPROVED` envelope for an order that is not yet approved. That event would not exist at that moment either. This plan does not change it; it is noted for the phase-close review.

If the amendment is not accepted, the alternative is to leave Pin unable to pass this clause. CI would then fail, so the task would stay blocked until the contract is changed by a reviewed plan.

## 15. Decisions taken without Oscar

- **D1** Pin Payments over eWAY, on signed webhooks, the Disputes API and search by metadata (§1).
- **D2** The pre-card state lives in a core wrapper with its own store (§4). The adapter stays stateless, and its types live in `core/provider.ts`.
- **D3** Hosted Fields on our card page, not Pin's Payment Page (amount in the URL, surcharge).
- **D4** The publishable key is a credential field flagged `exposure: 'card_page'`, returned only by the view of an open session.
- **D5** `capture: true`. The gate is our session plus the core's check that the attempt is live, the booking payable and the account active.
- **D6** 3-D Secure always on, with `fallback_ok: false`. Conservative on fraud and disputes, though it may refuse some unenrolled cards. Reversible in one constant.
- **D7** One `POST /charges` per session, ever. Any non-success ends the session as `failed`, and the customer starts a new attempt (`declineOutcome: 'failed'`).
- **D8** A refund is never posted again after an unknown outcome. Only a 429 lets it post again.
- **D9** Rate limits per IP and per session, and no block per account: a decline spike only opens a task.
- **D10** The payer's email and IP go to Pin, which requires them, and nowhere else. They are not stored in our tables. Raw webhook bodies keep what Pin sends and can be erased as today.
- **D11** No disputes, no reconciliation and no fee import in 4.4.
- **D12** Session expiry = the attempt expiry setting at creation + 30 min.
- **D13** `methods: ['card']` only.
- **D14** One adapter-neutral core change in the matching of refund events (§7), and one contract amendment for every adapter (§12.2).

## 18. Plan review, round 2: changes (they override the sections above)

- **M1, four clauses and a structural marker.** Four clauses call `webhookFor` on an object that has not been paid:
  - `webhook_previous_state_and_duplicate`;
  - `webhook_rejections`;
  - `verify_and_parse_never_throw`;
  - `no_secret_in_results_or_errors` (the object is already cancelled there).

  When the subject answers `NO_GATEWAY_EVENT`, the last three take the event of `h.paid(ctx)` instead. The signature does not depend on the object's state, so no check is lost. The marker is structural:
  - the Pin adapter (`CardTokenGateway`) has no `preCardSession`. Only `CardSessionProvider` sets it on the manifest it exposes;
  - the instance check of `registry.ts` rejects `preCardSession` on a provider that is not an `instanceof CardSessionProvider`, and the reverse;
  - the local subject answers the marker only while the session has no `chargeRef` **and** the fake holds no charge with `mt_session = ref`. The sandbox subject checks the same with `GET /charges/search`.
- **M2, late success after `failed`.** The trigger allows `failed → succeeded` only when `failureCode IN ('outcome_unknown', 'provider_busy')` and `chargeRef IS NULL`. That step sets `chargeRef` and writes the `card_session_charges` row. Every read of such a session (`retrievePayment`, `cancelPayment`, `createRefund`, `retrieveRefund`) searches Pin by metadata again and applies a successful charge it finds, so the store, the core and 4.6 agree, and the late money can be refunded. Test: `late_success_after_unknown_submit_is_refundable`.
- **M3, a `ch_` ref with no link to its session.** `retrievePayment({ ref: 'ch_…' })` for a charge that no session holds reads the charge. If its `metadata.mt_session` is a session of this account, that session is resolved and linked (`chargeRef` set, charge row written), and the answer carries the `cs_` ref. So the core's reference check of a refund event matches. Test: `dashboard_refund_event_after_webhook_only_success`.

  The sweeps only act on live attempts, so what ends a session whose attempt the core already holds as `succeeded` is the first read of that session. The candidates are:
  - a refund from the panel (`createRefund`);
  - a dashboard refund event (`retrievePayment` of the `ch_` ref);
  - 4.6's object comparison (`retrievePayment` of the `cs_` ref).

  The test `expiry_after_webhook_only_success_ends_succeeded` therefore checks that a read after `expiresAt` gives `succeeded`, not `failed`: the search runs before the expiry rule.
- **m4, CSP.** The CSP is built in `apps/web/src/lib/csp.ts`. `/pay/card/` joins its list of dynamic pages, so it gets a nonce and the strict CSP, which has a `default-src`. Its `frame-src` adds Pin's origins. With `'strict-dynamic'`, browsers that support CSP3 ignore host sources, so the Pin script tag carries the nonce and is loaded from a server-rendered `<script nonce>`.
- **m5, the answer of `createPayment`.** It answers the session's state (§6.2).
- **m6, expiry.** It comes from `pendingExpiresAt` + 30 min (§6.2).
- **m7, refund answers that conflict.**
  - A `POST` answer that arrives when the intent is already bound to another `refundRef` does not rebind. It opens a task (`payments:card_refund_conflict:<intentId>`) and answers `provider_unavailable`.
  - If `retrieveRefund` finds more than one candidate, it throws `provider_unavailable` (retryable). It never answers `null`.
