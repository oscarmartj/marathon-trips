# 7.fix-2 Automations: fixes from the post-merge review of 7.4

Risk high (customer email, consent, suppression). Independent Opus review of 7.4 on `main` 21aae87. No payments code is touched.

## 1. Per-customer cap and unsubscribes (finding 1)

- **Cap across all rules.** `MAX_CUSTOMER_NOTICES_PER_WINDOW = 3` automation customer emails per customer in a rolling `CUSTOMER_NOTICE_WINDOW_MS = 24 h` (constants in `@mt/shared`, documented there). Counted on `outbound_emails` (customer id, the three `automations.customer_notice_*` keys, `createdAt` in the window, any status) under a transaction-scoped advisory lock on `automation_customer:<customerId>`, taken inside the run's transaction; concurrent runs for the same customer serialise and the count holds. Lock order is always rule lock, then customer lock (a rule sends at most one customer email), so no cycle. Over the cap the step is `skipped` with the new step code `customer_rate_limited`; the other actions still run. A test run reports the same code without locking.
- **Service messages.** The wording of a notice is staff text in Templates, so the engine cannot know it is not promotional. Conservative default: a notice honours **any** suppression (marketing unsubscribe included) at queue and send time and is queued as `marketing`, so it carries the RFC 8058 `List-Unsubscribe` header. Only a rule switched on with an explicit `serviceMessageAck: true` (step-up, audited) sends its notices as `transactional` (stopped only by an `all` suppression, the 5.5 rule). The acknowledgement is bound to the wording: it is stored as `serviceNoticeAckAt` on the rule and is void when the rule is changed or when any active wording of that template was changed or put into use after it (`message_templates."updatedAt" > serviceNoticeAckAt`). Void ⇒ conservative path. The panel has no checkbox yet (API only): every notice is conservative until one exists.

## 2. Suppression at send time (finding 2)

`MailTemplate` gains optional `suppressedBy: 'all'`: `processSend` then checks for an `all` suppression before rendering and marks the email `suppressed` (no send, no retry). Set on the automation customer templates. `marketing` emails already check any suppression at send. Not applied to every transactional email: sign-in links, password resets and booking and payment notices must still reach an address with an old bounce (5.5 classified them as required), and payments is parked.

## 3. Lock tests and boundaries (finding 3)

Barrier tests with `beforeAction` holding a run after its locks: (a) a rule edit by another staff member waits on a lock (`pg_stat_activity`), then gets the new version; (b) a permission withdrawal through `AccessService.lockUsers` waits for the run. Each is shown to fail with its lock line removed (recorded in done). `automations-boundaries.test.ts` walks subfolders and catches static, dynamic `import()` and `require()` of the money modules at any relative depth, with a self-test of the patterns.

## 4. Backlog after `hold` (finding 4)

Rule: **oldest first**. New nullable column `automation_runs."eventOccurredAt"` (migration 0030) set at dispatch. Under the per-rule advisory lock a real run is held back as `rate_limited` when processed runs in the last hour plus pending real runs of the same rule that are older (by `eventOccurredAt`/`scheduledFor`/`startedAt`, then id) reach `MAX_REAL_RUNS_PER_HOUR`. So the oldest 100 of a backlog act whatever order pg-boss picks; newer ones are skipped and never retried. Test: 103 pending runs processed newest first.

## 5. Time zone (finding 5)

No `businessTimeZone` setting exists (pricing and payments use a constant too). Defining one only for automations would let schedules and booking deadlines disagree, so the constant stays. Tests: the constant equals pricing's, `tick()` uses it by default, and no `businessTimeZone` setting is defined (the test fails the day one is, so automations get wired to it).

## 6. Manual test run after a database error (finding 6)

`test()` runs `execute` inside `SAVEPOINT automation_test` and rolls back to it on error, so the run is recorded as `failed` (`action_failed`) instead of a 500. `beforeAction` gets the transaction as a second argument for the test that raises a PostgreSQL error. Unused `RunStop` removed.

## Review round 1 (code)

- A notice without the acknowledgement may be promotional, so it is sent only with marketing consent (latest `consent_records` entry for the customer or address, as the consent page; plan 5.5 §5: none by default), otherwise the step is `skipped` with `marketing_consent_missing`. Its body carries the one-click unsubscribe link (web `/unsubscribe#ref=`), as well as the header. The relationship basis (inferred consent) is not used.
- A service notice is re-checked at send time: wording put into use after it was queued was never acknowledged, so it is not sent (`failed`, no retries).
- Backlog: an older pending run reserves a place only if its snapshotted facts meet the rule's conditions (conditions are now checked before the cap). One whose record is gone still reserves one.
- Index `outbound_emails(customerId, createdAt)` in 0030 for the cap's count. Barrier test for the customer lock.
- `enable` without `serviceMessageAck` on a rule already on keeps the acknowledgement (changing only test mode); `false` removes it.
- Two rules with `send_email` and `add_tag` in opposite order on one booking can deadlock (customer lock against the tagging's row): PostgreSQL aborts one, its run rolls back whole and pg-boss retries it (`transient_error` only after the last attempt). Accepted rather than a global lock order.
