# Plan 8.4: claves de API con ámbitos y webhooks salientes firmados

Riesgo alto (autenticación, permisos, secretos, peticiones salientes). Rama `task/8.4-api-keys-outbound-webhooks`. Migración `0011_integrations` (la 0010 la reserva la rama de 2.2).

## 1. Alcance

`docs/phases/phase-8.md` no da criterios propios para 8.4: la fila dice "Claves de API con ámbitos y webhooks salientes firmados". Tomo como criterios de aceptación lo ya decidido en `docs/plans/phase-0-architecture.md` (4.2 step-up, 4.3 claves, 4.7 secretos, 4.8 guarda de entorno, modelo `ApiKey`/`WebhookSubscription`/`WebhookDelivery`) y `docs/architecture.md` ("Claves de API con ámbitos y webhooks salientes firmados, para integraciones futuras"; monitor con webhooks):

- **C1.** Una clave de API autentica peticiones a rutas `@RequirePermission`; sus permisos efectivos se calculan **en cada petición** como `scopes ∩ permisos actuales del dueño`, sin ningún permiso `requiresStepUp`.
- **C2.** Dueño desactivado, clave revocada o caducada = clave inválida. El secreto se enseña una sola vez y se guarda solo como HMAC.
- **C3.** Crear y revocar claves, y todo cambio de webhooks, exige permiso con step-up y queda auditado. Lo que hace una clave se audita como `api_key`.
- **C4.** Los webhooks salientes van firmados (HMAC-SHA256, formato Standard Webhooks), con reintentos, idempotentes para el receptor, carga solo con identificadores y secreto cifrado en reposo.
- **C5.** Protección SSRF (direcciones privadas, DNS fijado, sin redirecciones) y guarda de entorno: fuera de `production` solo se envía a `WEBHOOK_DEV_ALLOWLIST`; el resto queda `suppressed`.
- **C6.** El monitor del sistema (8.6) gana la sección de webhooks salientes.
- **C7.** El panel tiene una página mínima para gestionar claves y webhooks.

Todo vive en `apps/api/src/platform/integrations/` (la autenticación con clave la usa la guarda global, así que no puede ser un módulo de `src/modules`: la prueba de fronteras prohíbe que la plataforma escriba en tablas de un módulo). Esquema en `prisma/schema/platform-integrations.prisma`. Interruptor: flag `module.integrations` (declarado con `FlagRegistry.declareModule`; el seed lo enciende en desarrollo; **en producción, sin fila = apagado**). Con el flag apagado: las rutas de integraciones dan 404, **ninguna clave autentica** (401) y no se crean entregas de webhooks.

**Fuera de alcance:** dinero en cualquier forma (aparcado), webhooks entrantes de pasarelas (3.3), acción "llamar a un webhook" de automatizaciones (7.4), OpenAPI, lista de IP permitidas por clave, OAuth o mTLS, Redis (los límites siguen en memoria, una instancia), los menores abiertos de 0.3 de `docs/FINAL-REVIEW.md` (no los toco; ver §8).

## 3. Claves de API

### 3.1 Formato y verificación

- Token: `mtk_<prefix>_<secret>`; `prefix` 12 caracteres base32, `secret` 32 bytes aleatorios en base64url (43 caracteres). Se envía como `Authorization: Bearer mtk_…`. Expresión estricta; cualquier otra forma es `invalid_api_key`.
- Búsqueda por `prefix` (único) y comparación del HMAC en tiempo constante (`safeEqualHex`). Si el prefijo no existe se calcula igual un HMAC contra un valor ficticio, para que el tiempo no delate qué prefijos existen.
- Prefijo desconocido, secreto erróneo, clave revocada, caducada, dueño desactivado o flag apagado: **la misma respuesta** 401 `invalid_api_key`. El motivo real va a un `warn` con el prefijo y un código, nunca el token.
- `lastUsedAt`: `UPDATE … WHERE id = $1 AND ("lastUsedAt" IS NULL OR "lastUsedAt" < now() - 1 min)`.

### 3.2 Dónde entra en la cadena de guardas

`AuthContext` gana `via: 'session' | 'api_key'`, `apiKeyId?`, `scopes?` y `sessionId: string | null`. Para una clave: `kind = 'staff'`, `userId = dueño`, `sessionId = null`, `mfaVerifiedAt = null`.

- **`MaintenanceGuard`:** con el mantenimiento activo, toda petición con `Authorization: Bearer` recibe 503, también en `/admin/*` (la excepción de `/admin/*` es para el personal con sesión).
- **`CsrfGuard`:** se salta la comprobación de `Origin` y `X-MT-CSRF` solo si se cumplen las tres cosas: la ruta lleva `@RequirePermission`, hay `Authorization: Bearer` y **no hay cabecera `Cookie`**. Un navegador de otro sitio no puede enviar `Authorization` sin preflight, y la API no tiene CORS. En una ruta `@Public` o `@OwnedBy` nada cambia.
- **`AccessGuard`:**
  - `@Public`: ignora `Authorization`.
  - `@OwnedBy` con `Authorization`: 401 `api_key_not_allowed`. Una clave nunca actúa como cliente ni sobre rutas "self" (cerrar sesión, step-up).
  - `@RequirePermission` con `Authorization` **y** cookie de sesión: 400 `ambiguous_credentials` (no se elige una en silencio).
  - `@RequirePermission` con `Authorization`: verifica la clave (3.1), aplica el límite por clave (3.4) y llama a `assertPermission`.
- **`AccessService.assertPermission`** (la usan la guarda y las comprobaciones finas de los servicios): si `auth.via === 'api_key'`, exige además que la clave esté en `scopes` y deniega todo permiso `requiresStepUp` con 403 `api_key_cannot_use_step_up_permission`. El dueño se lee como siempre (`effective`: solo personal `active`, roles sin ámbito), así que un permiso retirado al dueño se pierde en la petición siguiente.
- **Comprobaciones que hoy no pasan por `assertPermission`:** `TableAccessService.effective(caller)` (búsqueda global) usa `effective(userId)` a secas y con una clave devolvería todo lo del dueño. Se sustituye por `AccessService.effectiveFor(db, auth)` (intersección con `scopes`, sin permisos de step-up). Al implementar repaso con `grep` cada llamada a `effective(`, `isOwner(`, `lockedActor(` y `rolesEffective(`. Las que quedan en rutas de step-up (gestión de personal y roles) no son alcanzables con clave, y aun así `lockedActor` recibe el contexto para no confiar en eso.

### 3.3 Actor y auditoría

- `actorOf(req)` devuelve `{ type: 'api_key', id: apiKeyId, sessionId: null, requestId }`. `AuditLog.actorType = api_key`, `actorId` = id de la clave (la fila `ApiKey` dice de quién es y no puede cambiar). Lo mismo en `OutboxEvent.actorType/actorId` y en las columnas `createdById`/`deletedById`/`authorId`, que guardarán el id de la clave: la acción es de la clave.
- Se corrige `notes.service.ts`, que publica `actorType: 'staff'` fijo, para que use el tipo del actor (cambio mínimo, anotado en el PR).
- Gestión: `integrations.apiKey.created` y `integrations.apiKey.revoked`, auditadas con el actor de sesión y en la misma transacción. El secreto nunca entra en `changes`: `secretHash` es `@secret`, así que solo aparece `"[changed]"`.
- Los fallos de autenticación con clave no se auditan (evita llenar el registro con un ataque): se cuentan en memoria y se registra un `warn` con código.

### 3.4 Límites

- Por clave: `API_KEY_RATE_LIMIT_PER_MINUTE` peticiones por minuto (`WindowLimiter`), 429 con `Retry-After`.
- Por IP, solo los fallos: con `API_KEY_FAILED_PER_MINUTE` fallos en un minuto, ese IP recibe 429 en todo intento con clave durante el minuto (las sesiones no se ven afectadas). Usa `req.ip`, que respeta `TRUST_PROXY`. Hasta comprobar la IP real tras Caddy (pendiente en `docs/BLOCKED.md`), todos los clientes comparten un IP y un atacante puede frenar a las integraciones legítimas un minuto: riesgo aceptado y anotado. Con 32 bytes de secreto, la fuerza bruta no es viable de todos modos.
- Como mucho 10 claves activas por dueño.

### 3.5 Gestión (API y permisos)

Permisos nuevos (manifiesto de plataforma):

| Permiso | Step-up | Para qué |
|---|---|---|
| `integrations.apiKey.read` | no | Listar claves: nombre, prefijo, ámbitos, dueño, caducidad, último uso y estado |
| `integrations.apiKey.manage` | **sí** | Crear y revocar |
| `integrations.webhook.read` | no | Listar suscripciones (sin secreto) y entregas (estado y códigos) |
| `integrations.webhook.manage` | **sí** | Crear, editar, activar o desactivar, borrar, rotar el secreto, enviar una prueba y reintentar una entrega |

Como `manage` exige step-up, una clave nunca crea claves ni webhooks (no hay escalada ni persistencia con una clave robada).

Rutas (`@RequiresModule('integrations')`):

- `GET /admin/integrations/api-keys`
- `POST /admin/integrations/api-keys`, con cuerpo `{ name, scopes, expiresInDays (1..365, por defecto 90) }`. Responde 201 con `token` **una sola vez**.
- `POST /admin/integrations/api-keys/:id/revoke`

Reglas al crear: cada ámbito tiene que ser un permiso declarado (si no, 422 `unknown_scope`), sin `requiresStepUp` (422 `scope_requires_step_up`) y del creador en ese momento (422 `scope_not_held`). El dueño es siempre el creador: nadie crea claves a nombre de otro. Cualquiera con `manage` puede revocar cualquier clave: revocar solo quita acceso.

## 4. Webhooks salientes

### 4.1 Suscripciones

- `GET/POST /admin/integrations/webhooks`, `PATCH /…/:id` (descripción, URL, tipos, `enabled`; con `version`), `DELETE /…/:id` (borrado lógico, cancela sus pendientes), `POST /…/:id/rotate-secret`, `POST /…/:id/test`, `GET /…/:id/deliveries`, `POST /admin/integrations/webhook-deliveries/:id/retry`.
- Secreto `whsec_` + base64 de 32 bytes, enseñado **una vez** al crear y al rotar. Al rotar, el anterior pasa a `previous*` con 24 h de validez y se firma con los dos.
- **Validación de la URL** al guardar y otra vez al enviar: `https:` en producción (fuera de producción también `http:`); sin usuario ni contraseña; sin fragmento; como mucho 2048 caracteres; si el host es una IP literal, se aplica la regla de direcciones de §4.4. En producción, `localhost` y los nombres de una sola etiqueta se rechazan.
- Como mucho 20 suscripciones activas. Reactivar una desactivada por fallos pone `consecutiveFailures` a 0.

### 4.2 Catálogo de eventos salientes

Solo se puede suscribir a tipos **exactos** de un catálogo declarado en código, `WEBHOOK_EVENT_CATALOGUE`, sin comodines. Cada entrada declara la forma exacta de `data` hacia fuera con un esquema `zod` `.strict()`; el cuerpo se construye validando la carga del evento contra ese esquema, de modo que un campo nuevo en un evento interno no sale hasta que alguien lo añade al contrato. Catálogo inicial:

- `catalogue.race.published`
- `catalogue.package.sale_status_changed`
- `pricing.price_version.published`
- `suppliers.allotment.released`
- `integrations.ping` (solo pruebas)

Excluidos a propósito: `auth.user.logged_in` (lleva `userId` y `sessionId`), `access.role.changed`, `common.note.added`, `catalogue.inventory.released` y `alerts.subscription.confirmed`: son internos o tienen que ver con personas. Las tareas futuras (reservas) añaden sus tipos aquí con su contrato.

### 4.3 Reparto (consumidor del outbox)

- Consumidor `integrations.webhooks`, `module: 'integrations'`, `events` = tipos del catálogo (sin `integrations.ping`), `whenDisabled: 'skip'`, `notifyOnly: true`, `maxEventAgeMs` 48 h. Ningún tipo del catálogo toca `payments.`, `bookings.` ni `changes.`. Cuando una tarea añada uno, el registro le obligará a `hold`, y esa tarea tendrá que resolver la acumulación con el módulo apagado (anotado en el código).
- En la transacción de la entrega del outbox: busca las suscripciones activas, no borradas, con el tipo y con `createdAt <= event.occurredAt` (una suscripción nueva no recibe eventos antiguos). Por cada una, construye el cuerpo (si la carga no cumple el contrato: no se crea la fila y se registra `error` con `webhook_payload_contract_mismatch`, sin valores), inserta con `ON CONFLICT DO NOTHING` y encola `webhooks.send` con `singletonKey = deliveryId` usando `bossDb(tx)`. Si el consumidor corre dos veces, sigue habiendo una sola fila.

Cuerpo (sin actor, sin datos personales):

```json
{ "type": "catalogue.race.published", "timestamp": "<occurredAt ISO>",
  "data": { "eventId": "…", "schemaVersion": 1, "aggregateType": "Race", "aggregateId": "…", "aggregateVersion": 3, "...": "campos del contrato" } }
```

Cabeceras: `webhook-id` (id de la entrega), `webhook-timestamp` (segundos Unix del intento), `webhook-signature: v1,<base64>` (más ` v1,<base64>` con el secreto anterior durante la rotación), `content-type: application/json` y `user-agent: MarathonTrips-Webhooks/1`. Firma Standard Webhooks: HMAC-SHA256 sobre `${id}.${timestamp}.${body}` con la clave en bytes (base64 tras `whsec_`). El receptor debe rechazar marcas de tiempo con más de 5 minutos y deduplicar por `webhook-id`: lo dice la guía (§6).

### 4.4 Envío y SSRF

El trabajo `webhooks.send` ejecuta tres pasos:

1. **Reclamar** (transacción corta): `UPDATE … SET status='sending', attempts=attempts+1, "leaseUntil"=now+60 s, "lastAttemptAt"=now WHERE id=$1 AND status='pending' AND ("nextAttemptAt" IS NULL OR "nextAttemptAt" <= now) RETURNING …`. Sin fila, no hace nada (otro trabajador la tiene o ya está hecha). En esa misma transacción:
   - Suscripción desactivada o borrada: `cancelled`.
   - **Guarda de entorno:** si `APP_ENV !== 'production'` y el origen de la URL no está en `WEBHOOK_DEV_ALLOWLIST`, `suppressed` sin petición HTTP.
   - Descifra los secretos. Si falla (versión de clave no configurada): `failed` con `secret_unavailable`, sin reintento.
2. **Enviar**, fuera de toda transacción, con `node:http`/`node:https`, `agent: false` y una función `lookup` propia:
   - Resuelve todas las direcciones (`dns.lookup` con `all: true`). Si **alguna** está bloqueada, rechaza con `blocked_address`. Si no, conecta a la dirección ya validada. Así se cierra el *DNS rebinding*: la dirección comprobada es la usada.
   - Una IP literal no pasa por `lookup` y se valida antes.
   - TLS con verificación normal y `servername` = host.
   - Sin redirecciones: una respuesta 3xx es un fallo (`http_redirect`).
   - Tiempo límite total de 10 s.
   - De la respuesta se leen como mucho 64 KB, que se descartan sin guardarse.
   - **Rangos bloqueados** (`net.BlockList` de Node, sin dependencia nueva). IPv4: `0/8`, `10/8`, `100.64/10`, `127/8`, `169.254/16`, `172.16/12`, `192.0.0/24`, `192.0.2/24`, `192.88.99/24`, `192.168/16`, `198.18/15`, `198.51.100/24`, `203.0.113/24`, `224/4`, `240/4`. IPv6: `::/128`, `::1/128`, `::ffff:0:0/96` (se comprueba la IPv4 de dentro), `64:ff9b::/96` y `64:ff9b:1::/48` (NAT64, IPv4 de dentro), `100::/64`, `2001::/23` (incluye Teredo), `2001:db8::/32`, `2002::/16` (6to4, IPv4 de dentro), `fc00::/7`, `fe80::/10`, `ff00::/8`.
   - **En producción la regla no tiene excepciones.** Fuera de producción, un origen de `WEBHOOK_DEV_ALLOWLIST` puede resolver a loopback: es la única forma de probar en local, y fuera de producción nada sale a otra parte.
3. **Anotar** (transacción): `UPDATE … WHERE id=$1 AND status='sending' AND attempts=<reclamado>`, compare-and-set para que un resultado tardío no pise a otro.
   - 2xx: `succeeded` y `consecutiveFailures = 0`.
   - Fallo con intentos restantes: `pending`, `nextAttemptAt` según el calendario y nuevo trabajo con `startAfter` y `singletonKey = id:attempts`.
   - Último intento, o fallo sin reintento (`blocked_address`, `invalid_url`, `secret_unavailable`): `failed`.
   - Cada fallo suma `consecutiveFailures`. Al llegar a **50**, la suscripción se desactiva (`disabledReason = consecutive_failures`) con auditoría `integrations.webhook.autoDisabled` (actor `system`) en esa misma transacción, y sus entregas pendientes pasan a `cancelled`.

Calendario: 7 intentos, a los 0 s, 1 min, 5 min, 30 min, 2 h, 6 h y 12 h (unas 21 h en total). Se reintenta cualquier respuesta que no sea 2xx y cualquier error de red.

**Mantenimiento** (`webhooks.maintenance`, cada 5 min):

- Las entregas `sending` con el arriendo vencido (la API cayó a mitad) vuelven a `pending` y se encolan: el receptor puede recibir un duplicado con el mismo `webhook-id`, que es lo previsto.
- Las `pending` vencidas sin trabajo se vuelven a encolar.
- Se purgan las terminadas de hace más de 30 días.

### 4.5 Códigos de error guardados

Lista cerrada: `timeout`, `connection_failed`, `tls_error`, `dns_failed`, `blocked_address`, `invalid_url`, `http_redirect`, `http_error` (con `lastResponseStatus`), `secret_unavailable`, `payload_contract_mismatch`. Nunca el mensaje de la excepción (puede llevar IP o host), la URL ni el cuerpo de la respuesta, ni en la base ni en los registros. Los registros nombran la suscripción y la entrega por id.

### 4.6 Monitor (8.6)

`GET /admin/system/status` gana `webhooks`: entregas `pending` y `sending`, antigüedad de la pendiente más vieja, `failed` de las últimas 24 h y suscripciones desactivadas por fallos. `attention` si hay fallidas en 24 h o alguna suscripción desactivada por fallos. Solo cuentas, sin URL.

## 5. Panel (mínimo)

Página `/admin/integrations`, visible con cualquiera de los dos permisos de lectura, con dos secciones:

- **Claves:** lista con prefijo, ámbitos, caducidad y último uso; crear (nombre, ámbitos elegidos entre los permisos propios sin step-up, caducidad); el token se enseña una vez con aviso de copiarlo; revocar.
- **Webhooks:** lista; crear (URL, descripción, tipos del catálogo), con el secreto mostrado una vez; activar o desactivar; rotar; enviar prueba; ver entregas.

Usa el componente de step-up que ya existe (`components/admin/step-up.tsx`). Textos en `messages/en-AU.json`. El proxy de la web (`lib/api-proxy.ts`) añade `authorization` a `FORWARD_REQUEST_HEADERS`: la web es la única puerta pública de la API, y sin esto ninguna integración externa llegaría.

## 7. Amenazas (STRIDE breve)

| Amenaza | Escenario | Defensa | Prueba |
|---|---|---|---|
| Suplantación | Clave robada | Ámbitos ∩ permisos del dueño, sin step-up, caducidad obligatoria, revocación inmediata, flag de corte, límite por clave | `api_key_revoked_rejected`, `api_key_cannot_use_step_up_permission` |
| Suplantación | Adivinar claves | 32 bytes de entropía, HMAC en tiempo constante, misma respuesta para todo fallo, límite de fallos por IP | `api_key_wrong_secret_same_response_as_unknown_prefix`, `api_key_failed_attempts_limited_per_ip` |
| Suplantación | Un tercero falsifica nuestros webhooks | Firma HMAC con marca de tiempo; secreto cifrado | `webhook_signature_verifies_with_independent_check` |
| Manipulación | Ampliar los ámbitos de una clave | Disparador de inmutabilidad; ámbitos ⊆ permisos del creador | `api_key_row_immutable`, `api_key_scopes_must_be_subset_of_creator_permissions` |
| Manipulación | CSRF usando la excepción de clave | Solo con `Bearer`, sin `Cookie` y en ruta de permiso; cookie y clave a la vez = 400 | `bearer_on_public_route_does_not_skip_csrf`, `api_key_with_session_cookie_rejected` |
| Repudio | "No fui yo" | Auditoría con `api_key` e id de la clave; gestión con sesión y step-up | `api_key_actions_audited_as_api_key` |
| Divulgación | Secreto en la API o en registros | `@secret`, se enseña una vez, logger sin cabeceras ni token | `api_key_token_never_logged`, `secret_columns_never_serialised_logged_or_audited` |
| Divulgación | Datos personales por webhook | Catálogo cerrado con contrato `strict`, `assertIdentifiersOnly`, sin actor | `webhook_payload_matches_outbound_contract` |
| Divulgación / SSRF | URL a la red interna o a metadatos | Rangos bloqueados, DNS fijado, sin redirecciones, sin guardar respuestas | `webhook_ssrf_blocked_addresses`, `webhook_dns_rebinding_connects_to_validated_address` |
| Denegación | Receptor lento, gigante o caído | 10 s, 64 KB, arriendo, 7 intentos, desactivación tras 50 fallos | `webhook_timeout_counts_as_failure`, `webhook_auto_disabled_after_consecutive_failures` |
| Denegación | Inundar con claves | Límite por clave y fallos por IP; máximo de claves y suscripciones | `api_key_rate_limited_per_key` |
| Elevación | Una clave crea claves o webhooks, o usa permisos de step-up | `manage` exige step-up y la clave nunca lo tiene | `api_key_cannot_use_step_up_permission` (recorre todas las rutas) |
| Elevación | Una clave en rutas de cliente o "self" | `@OwnedBy` + clave = 401 | `api_key_rejected_on_owned_routes` (recorre todas) |
| Elevación | Las comprobaciones finas ignoran los ámbitos | `assertPermission` y `effectiveFor` conocen la clave | `api_key_secondary_checks_respect_scopes` |
| Fuera de producción | Una copia de staging avisa a un sistema real | `WEBHOOK_DEV_ALLOWLIST`; el resto queda `suppressed` | `webhook_suppressed_outside_production_unless_allowlisted` |

## 8. Riesgos y supuestos

- **S1.** Sin criterios propios en la fase, los de §1 salen de la arquitectura. Si el revisor ve que falta alguno, lo añado.
- **S2.** Las claves son de personal (el dueño es quien las crea). Las de cliente o socio, si llegan, serán otra tarea.
- **S3.** El catálogo inicial es corto y se amplía por contrato. Elegido por ser lo más conservador y fácil de ampliar.
- **S4.** Límites en memoria y por instancia, como el resto de la API (una sola instancia, decisión de alojamiento).
- **S5.** No cierro los menores de 0.3 de `docs/FINAL-REVIEW.md` (arnés de rutas `self`, carrera al añadir titular a un rol, orden de bloqueo): no son de esta tarea. La comprobación de la IP real tras Caddy sigue pendiente. 8.4 no añade lógica de IP propia: usa `req.ip` y queda anotado en el riesgo de §3.4.
- **R1.** Cambiar `AuthContext.sessionId` a `string | null` toca tipos de autenticación. Los usos de `sessionId` están en rutas `self` (cerrar sesión, step-up), que la clave no alcanza; lo vigilan el compilador y `api_key_rejected_on_owned_routes`.
- **R2.** Las columnas `createdById` y similares guardarán ids de clave. Sin FK a `users` hoy (comprobado en el esquema), así que no se rompe nada; el panel mostrará "API key" cuando el id no sea un usuario.
- **R3.** Si el contenedor de la web resuelve a una red privada que un atacante pueda alcanzar desde la URL del webhook, queda bloqueado por los rangos: no hay excepción en producción.
- **R4.** Migración: la `0011` supone que 2.2 se queda la `0010`. Si `main` trae otra numeración antes de fusionar, renombro la mía encima.
