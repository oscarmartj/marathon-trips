## 2. Diseño de la capa (para toda la fase 3 y la 4)

### 2.1 Capas

```
modules/payments/
  core/        schedule, payable amount, attempts (state machine), routing, gateway, webhooks, maintenance
  adapters/    simulator/  (3.1)   ·  manual/ (3.4)  ·  stripe/ (3.3)  ·  … uno por pasarela, aislados
  index.ts     API pública del módulo
```

Un adaptador solo habla con su pasarela: no toca Prisma, no lee ajustes ni variables de entorno, no registra nada en logs y no conoce reservas. Recibe un contexto (credenciales ya descifradas, secreto de webhook, modo) y devuelve datos normalizados. Todo lo demás es del núcleo.

### 2.2 Interfaz `PaymentProvider` (TypeScript, `core/provider.ts`)

```ts
type CardDataHandling = 'hosted_only';               // único valor posible: no hay tipo para datos de tarjeta
type AdapterStatus = 'planned' | 'experimental' | 'verified';

interface AdapterManifest {
  key: string;                                        // 'simulator'
  displayName: string;
  status: AdapterStatus;
  evidence?: string;                                  // obligatorio si verified: docs/done/… con la ejecución de test:sandbox
  testOnly: boolean;                                  // true: jamás live ni en producción
  cardDataHandling: CardDataHandling;
  methods: PaymentMethod[];                           // card, apple_pay, google_pay…
  currencies: CurrencyCode[];
  countries: CountryCode[] | 'any';
  capabilities: { refunds: 'none' | 'full' | 'partial'; deferredCapture: boolean; lookupByIdempotencyKey: true };
}

interface ProviderContext { accountId: string; mode: 'test' | 'live'; credentials: Readonly<Record<string, string>>; webhookSecret: string }

interface CreatePaymentInput {                        // sin firma de índice: no cabe un campo de tarjeta
  amount: Money;                                      // { amountMinor: bigint; currency }
  method: PaymentMethod;
  idempotencyKey: string;                             // la nuestra, del servidor (§5.3)
  metadata: { paymentId: string; bookingId: string }; // solo identificadores
  returnUrl: string;                                  // construida en el servidor (WEB_ORIGIN + ruta fija)
  customerCountry: CountryCode;
}

type ProviderPaymentStatus = 'requires_action' | 'pending' | 'succeeded' | 'failed' | 'cancelled';
interface ProviderPayment { ref: string; status: ProviderPaymentStatus; amount: Money; nextAction?: { type: 'redirect'; url: string }; failureCode?: string }

interface PaymentProvider {
  readonly manifest: AdapterManifest;
  testConnection(ctx: ProviderContext): Promise<{ ok: true } | { ok: false; code: string }>;
  createPayment(ctx: ProviderContext, input: CreatePaymentInput): Promise<ProviderPayment>;
  retrievePayment(ctx: ProviderContext, by: { ref: string } | { idempotencyKey: string }): Promise<ProviderPayment | null>;
  cancelPayment(ctx: ProviderContext, ref: string, idempotencyKey: string): Promise<ProviderPayment>;
  verifyWebhook(ctx: ProviderContext, rawBody: Buffer, headers: Readonly<Record<string, string>>, now: Date):
    { ok: true; event: NormalisedEvent } | { ok: false; code: 'bad_signature' | 'stale_timestamp' | 'malformed' };
}

interface NormalisedEvent {
  providerEventId: string; occurredAt: Date;
  kind: 'payment' | 'unsupported';                    // refund/dispute/settlement: extensión de 4.5 y 4.6
  payment?: { ref: string; ourPaymentId?: string; status: ProviderPaymentStatus; amount: Money; failureCode?: string };
}
```

Errores: un adaptador lanza solo `ProviderError` con `code` de una lista cerrada (`provider_unavailable`, `provider_timeout`, `provider_rejected`, `provider_auth_failed`, `provider_not_found`) y `retryable`; nunca el mensaje ni la respuesta de la pasarela (pueden traer credenciales o datos del pagador). El núcleo traduce cualquier otra excepción a `provider_unavailable`.

**Puntos de extensión** (no se declaran métodos sin implementar; se añaden con su tarea y su batería de contrato): `refund`/`retrieveRefund` (4.5), eventos `refund`/`dispute` en `NormalisedEvent.kind` (4.5), `listSettlements`/comisiones (4.6), cobro diferido (`deferredCapture`). El manifiesto ya declara `capabilities.refunds` para que el panel (4.1) lo enseñe.

### 2.3 Registro y estados de adaptador

- `adapters/index.ts` exporta la lista estática de adaptadores; `PaymentAdapterRegistry` la valida al arrancar: clave duplicada → no arranca; `verified` sin `evidence` → no arranca y además falla la prueba de CI (`verified_manifest_requires_sandbox_evidence`); `planned` = solo ficha, no admite cuentas.
- El estado vive en el manifiesto, en código: cambiarlo exige un PR (0.1 §5.5). 3.1 registra solo `simulator` (`experimental`, `testOnly: true`, métodos `card`, `apple_pay`, `google_pay`, moneda AUD, países `any`).

### 2.4 `ProviderGateway`: una sola puerta

Toda llamada a un adaptador pasa por `ProviderGateway.call(accountId, operation, fn)`, que en este orden:

1. Lee la cuenta **sin** columnas secretas y su adaptador del registro.
2. Aplica `assertCallAllowed` (tabla; cualquier fallo se audita como `payments.gateway.call_blocked` y no cambia estados):

| Condición | Resultado |
|---|---|
| adaptador desconocido o `planned` | `adapter_unavailable` |
| cuenta `live` y `APP_ENV` distinto de `production` | `live_call_blocked_outside_production` |
| cuenta `live` y adaptador no `verified` o `testOnly` | `adapter_not_verified_for_live` |
| adaptador `testOnly` y `APP_ENV` fuera de la lista cerrada `TEST_ADAPTER_ENVS` = `development`, `test`, `ci` (staging y production fuera; revisión, punto 14) | `test_adapter_blocked_in_environment` |
| operación `create` y cuenta no `active` | `account_not_accepting_charges` |
| `retrieve`, `cancel`, `webhook` con cuenta `paused`/`retired`/`archived` | permitido (0.1 §6.4) |

3. Solo entonces lee y descifra credenciales y secreto (AAD `provider_account:<id>:credentials` y `…:webhook_secret`), llama al adaptador con un tiempo máximo (10 s) y traduce errores (§2.2).

Es el único archivo que selecciona `credentialsCiphertext` y `webhookSecretCiphertext` (prueba estática). Las credenciales `live` no se descifran fuera de producción porque la guarda va antes del descifrado.

### 2.5 Enrutado mínimo (`core/routing.ts`)

`candidates({ method, currency, country, env })`: cuentas `active` cuyo adaptador no es `planned`, soporta método, moneda y país, y pasa `assertCallAllowed('create')` en el entorno (en producción quedan fuera las cuentas `test` y los adaptadores `testOnly`: hoy, todas). Orden `createdAt`, `id`; gana la primera. Sin respaldo ni límites: `RoutingRule` es de 4.2. `availableMethods(booking)` sale de la misma función y lo usa el plan del cliente. Sin candidatos, el flujo responde 409 `no_payment_method_available` y la reserva sigue siendo una solicitud aprobada sin cobro, sin errores 500 (criterio de fase «todas las pasarelas apagadas»). `instantBooking` no cambia en 3.1: sigue en `requested` (2.4 §2.6); lo retoma 3.2 o 3.5 con la cobertura.

## 4. Plan de pagos

### 4.1 Cálculo (solo servidor, `core/schedule.ts`, función pura)

Entrada: la **instantánea vigente** de la reserva (`totalMinor`, `depositMinor`, `currency`, que el motor calculó al solicitar con la regla de redondeo única de 0.1 §1.1), `Booking.balanceDueDate` (del motor) y `approvalExpiresAt`. Payments **no redondea nada**: la única operación es `balance = total − deposit` en `bigint`.

- `depositDue` = fecha de `approvalExpiresAt` en `Australia/Brisbane` (`Setting.businessTimeZone`).
- Plazo 1 `deposit`: `depositMinor`, vence `depositDue`. Se omite si `depositMinor = 0`.
- Plazo 2 `balance`: `total − deposit`, vence `max(balanceDueDate, depositDue)` (si la salida está cerca y el saldo ya vencería, vence con el depósito y se puede pagar todo a la vez). Se omite si es 0.
- `total = 0` → plan sin plazos (nada que pagar).
- Comprobaciones antes de escribir (si fallan, `AppError` y la aprobación se deshace): `0 ≤ deposit ≤ total`, moneda de instantánea = moneda de reserva, suma = total, fechas no decrecientes por `sequence`.

### 4.2 Ganchos (`BookingTransitionHooks`, 2.4)

- **`approve`** (`payments.schedule`): con la reserva ya bloqueada por la máquina de estados, lee la instantánea vigente por una función nueva y exportada de bookings, calcula y escribe `PaymentSchedule` (`version = 1`) y sus plazos, audita `payments.schedule.created` (importes y fechas son `@nopii`) y publica `payments.schedule.created` (solo ids). Si algo falla, la aprobación entera se deshace (`schedule_failure_rolls_back_approval`).
- **`cancel`** (`payments.schedule`): si hay plan, sube `version` y pasa todos los plazos `active` a `superseded` con `supersededInVersion` (sin penalización hasta 6.4: lo exigible es 0). **No bloquea `Payment`** (el gancho corre antes de liberar código y cupos, y el orden global es `Booking → PromoCode → pools → Payment`): si hay un intento vivo, encola `payments.attempts` `{ paymentId, action: 'cancel' }`, que corre después y aparte. Si ese intento acaba cobrado, queda `succeeded`, se publica el evento y se crea una tarea para Oscar «payment received for cancelled booking <ref>» (3.2 lo llevará a sobrepago).
- **Cambio mínimo en bookings** (declarado): la máquina de estados calcula `approvalExpiresAt` antes de los ganchos y lo pasa en el contexto (`ctx.approvalExpiresAt`), y `index.ts` exporta `readCurrentSnapshotAmounts(tx, bookingId)`. Nada más del módulo cambia.

### 4.3 Importe cobrable (`core/payable.ts`, el único sitio)

Hasta que 3.2 cree `PaymentAllocation`: `collected` = suma de `amountMinor` de los `Payment` `succeeded` de la reserva en el modo del entorno. Sin reembolsos, contracargos ni reasignaciones (aparcados), esto da exactamente lo mismo que el reparto por `sequence` de P7. Para un plazo objetivo de secuencia `s`:

`payable(s) = min(max(0, Σ plazos activos con sequence ≤ s − collected), max(0, Σ plazos activos − collected))` (P1).

Sin `s`, el objetivo es el primer plazo no cubierto. `0` = «nothing to pay» (409 `nothing_to_pay`). La función **no recibe método de pago**: ningún recargo puede depender de él (`no_surcharge_by_payment_method`). Interfaz `CollectedAmountSource` para que 3.2 la sustituya por el reparto sin tocar las rutas ni las pruebas.

## 5. Intentos de cobro

### 5.1 Crear o retomar (`POST /booking-requests/:reference/payments`)

Cuerpo estricto (zod en `packages/shared`): `{ method: PaymentMethod, upToSequence?: int ≥ 1 }`. **Ningún campo de importe, moneda, tarjeta ni URL**: todo campo desconocido, también anidado, es 422 (`client_amount_field_rejected`, `card_data_never_reaches_api`). Cabecera `Idempotency-Key` (UUID) obligatoria; `IdempotencyService.run` con ruta `POST /booking-requests/<bookingId>/payments` (el id resuelto en el servidor desde la referencia, no la plantilla), así que la misma clave en dos reservas son dos registros; la repetición comprueba que el `resourceId` guardado es un intento de **esa** reserva y devuelve su representación **actual** (revisión, punto 4).

Transacción A (READ COMMITTED, `runTransaction` con reintentos ante `40001`/`40P01`; `P2024`/`P2028` → 409 `busy_try_again`):

1. `Booking` `FOR UPDATE` (propiedad ya comprobada por `@OwnedBy`). Estado cobrable: `approved` (y `deposit_paid`/`confirmed` cuando 3.2 los haga alcanzables); si no, 409 `booking_not_payable`. En `approved`, `clock_timestamp() ≥ approvalExpiresAt` → 409 `approval_expired` (P3).
2. `payable` (§4.3) → 0: 409 `nothing_to_pay`.
3. Cuenta: `routing.candidates(method, currency, residenceCountry)`; ninguna → 409 `no_payment_method_available`.
4. Intento vivo de la reserva (`FOR UPDATE`, después de `Booking`): si existe y coincide en cuenta, método e importe → **se retoma** (no se crea otro; su `pendingExpiresAt` no cambia); si no coincide o está `pending` → 409 `payment_attempt_in_progress` (sustituir tras confirmar la cancelación con la pasarela es de 3.2).
5. Si no hay vivo: `attemptNumber = max + 1`; `idempotencyKey = booking:<bookingId>:attempt:<n>`; `INSERT payments` en `created` con `pendingExpiresAt = now + paymentAttemptExpiryMinutes` (ajuste, 60); auditoría `payments.payment.created`. Commit.

Llamada a la pasarela **fuera de la transacción** (P5) con `ProviderGateway`: si el intento no tiene referencia, `createPayment` con nuestra `idempotencyKey` y nuestros ids en metadatos (repetirla devuelve el mismo objeto de la pasarela); si la tiene, `retrievePayment`. Transacción B: `UPDATE payments SET providerPaymentRef = $ref WHERE id = $id AND providerPaymentRef IS NULL` y el avance de estado que diga la respuesta por la regla de §5.4 (nunca retrocede). Respuesta 201/200: `{ status, amountMinor (cadena), currency, method, nextAction? }`; `nextAction.url` solo si es del origen declarado por el adaptador.

Fallos de la llamada: `retryable` (tiempo agotado, caída) → el intento queda `created`, respuesta 503 `provider_unavailable`; reintentar retoma con la misma clave (un solo objeto en la pasarela). Rechazo definitivo → `failed` con `failureCode`; se puede crear otro intento (`n + 1`, clave nueva).

### 5.2 Máquina de estados del intento (`core/attempt-state.ts`, único código que escribe `payments.status`)

| Evento ↓ / estado → | created | requires_action | pending | succeeded | failed | cancelled, expired |
|---|---|---|---|---|---|---|
| Pasarela: requiere acción | → requires_action | — | — | — | — | — |
| Pasarela: en proceso | → pending | → pending | — | — | — | — |
| Pasarela: cobrado (importe y moneda iguales) | → succeeded | → succeeded | → succeeded | — (duplicado) | → succeeded | → succeeded; tarea si la reserva no es cobrable |
| Pasarela: cobrado con importe o moneda distintos | sin cambio; evento `ignored` (`amount_or_currency_mismatch`) y tarea | ídem | ídem | — | ídem | ídem |
| Pasarela: fallido | → failed | → failed | → failed | — | — | — |
| Pasarela: cancelado | → cancelled | → cancelled | — (un débito en curso no se cancela) | — | — | — |
| Vence `pendingExpiresAt` (§5.3) | consultar; solo con estado confirmado: cancelado en la pasarela → expired; sin objeto o sin respuesta → sigue vivo, se reprograma y a las 24 h tarea (revisión, punto 3) | ídem | consultar; si sigue, reprogramar (nunca → expired) | — | — | — |

Cada cambio: compare-and-set `WHERE id = $1 AND status = $from`, `version + 1`, auditoría `payments.payment.status_changed` (actor `system`, contexto `from`, `to`, `source` `api`/`webhook`/`sweep`) y, al cobrar, `succeededAt` y evento `payments.payment.succeeded` (al fallar, `payments.payment.failed`), todo en la misma transacción. Un disparador en SQL repite los pares permitidos (`created→requires_action|pending|succeeded|failed|cancelled|expired`, `requires_action→pending|succeeded|failed|cancelled|expired`, `pending→succeeded|failed`, `failed→succeeded`, `cancelled→succeeded`, `expired→succeeded`).

### 5.3 Claves de idempotencia, en tres capas

1. **HTTP:** `Idempotency-Key` del cliente, por ámbito de actor y ruta (0.4); misma clave con otro cuerpo → 422.
2. **Negocio:** `booking:<id>:attempt:<n>`, calculada con la reserva bloqueada, única en `payments`, y enviada a la pasarela como **su** clave de idempotencia. Dos pestañas con claves HTTP distintas acaban en el mismo intento (retomado) o en 409, nunca en dos objetos de cobro.
3. **Eventos:** `(providerAccountId, providerEventId)` único en `webhook_events`; la transición es compare-and-set, así que el mismo cobro avisado por dos eventos distintos cambia el estado una vez.

Barrido (`payments.maintenance`, cada 10 minutos): intentos vivos con `pendingExpiresAt ≤ now` → un trabajo `payments.attempts` `{ action: 'expire' }` cada uno, que consulta antes a la pasarela (`retrievePayment` por referencia o, sin ella, por nuestra clave) y aplica la tabla. Orden de bloqueo `Booking → Payment`.

## 6. Webhooks

`POST /payments/webhooks/:pathToken`, `@Public('signed gateway webhook: nothing is returned')`, `@CsrfExempt('gateway signature')`, sin sesión:

1. Límite por IP en memoria (`PAYMENT_WEBHOOKS_PER_MINUTE_PER_IP`, 600) → 429.
2. Un middleware propio de esta ruta, montado en `configure-app` antes de cualquier parser (cambio mínimo declarado), aplica el límite por IP **antes de leer el cuerpo**, rechaza con 413 por `content-length` o al pasar de 256 KB mientras lee, y no escribe nada en la base (solo un contador en memoria y un log con el código). Revisión, punto 5.
3. Cuenta por `HMAC(pathToken)`; si no existe → 404, sin fila (contador y log).
4. `ProviderGateway` → `adapter.verifyWebhook(rawBody, headers, now)`: firma sobre el cuerpo crudo con el secreto de **esa** cuenta, comparación en tiempo constante y marca de tiempo dentro de ±300 s. Si falla → 400 y `WebhookRejection` (hash del cuerpo, tamaño, cabeceras saneadas, id de evento declarado), **sin guardar el cuerpo**; no bloquea un reintento válido con el mismo id (`invalid_then_valid_same_event_id_processed_once`).
5. Transacción: `INSERT webhook_events … ON CONFLICT (providerAccountId, providerEventId) DO NOTHING`; si es nuevo, encola `payments.webhooks` `{ webhookEventId }`. Responde 200 en los dos casos (un duplicado no hace nada más).

Procesamiento (trabajo, al menos una vez, 5 reintentos crecientes; `failed` visible en el monitor con `errorCode`):

1. `kind = 'unsupported'` → `ignored`.
2. Casar el pago **primero por nuestro id** de metadatos **filtrando por la cuenta que recibió el evento**, luego por `(providerAccountId, providerPaymentRef)`. Si no casa → `ignored` (`unknown_payment`) y tarea; nunca se crea un intento (0.1 §6.2).
3. Bloqueos `Booking → Payment`. Si el intento no tenía referencia, se completa (el evento llegó antes que la respuesta de la pasarela).
4. Importe o moneda distintos → `ignored` (`amount_or_currency_mismatch`), sin tocar el intento, y tarea.
5. Tabla de §5.2. Un estado que no avanza (fuera de orden o duplicado) no es error: `processed` sin cambios.
6. `bookingId` y `paymentId` del evento, `processed`, `processedAt`, en la misma transacción.

Cabeceras guardadas: lista blanca (`content-type`, `content-length`, `user-agent` y los nombres de las cabeceras de firma del adaptador **sin su valor**). Retención: `rawBody` a NULL a los 180 días; rechazos borrados a los 30 (barrido diario dentro de `payments.maintenance`).

**Simulador:** firma `x-sim-signature: t=<unix>,v1=<hex HMAC-SHA256(secret, "<t>.<rawBody>")>`. Estado del «proveedor» en memoria del proceso (un mapa por cuenta: objetos por referencia y por clave de idempotencia); perderlo al reiniciar deja el intento hasta el barrido, que lo caduca. Un control solo de pruebas (`SimulatorControl`, inyectable, sin ruta HTTP) programa el resultado (`succeed`, `fail`, `require_action`, `pending`, `timeout`, `decline`) y genera webhooks firmados, duplicados, desordenados o con firma mala, que las pruebas envían por HTTP a la ruta real. La página alojada para personas es de 3.6/3.5.
