# 7.fix-1 Fixes to the reports module (task 7.7)

Risk medium. An independent review of 7.7 found five issues. No new dependency, no migration, no existing assertion changes.

## Design
1. **Demo exclusion test.** `makeBookingFor` gets an `isDemo` parameter set at creation (the column is immutable afterwards). New tests: in a published world one normal and one demo booking give `bookings = 1` and funnel `requests = 1`; a draft demo race with a stats row and a demo booking gives `rows = []`. The dead conditional in the "demo race counts nothing" test is removed. Each filter is then broken by hand to confirm a test fails.
2. **Scheduled range.** `resolveRange` gets an option `completeDaysOnly`: for `last_days` the range ends on the Brisbane day before the day of the date given. `ReportEmails` passes it with `scheduledFor`, so consecutive weekly or monthly reports cover contiguous whole days and no request falls between two. Table tests incl. midnight and month and year boundaries.
3. **Module off at send time.** `ReportEmails.render` checks the flag. The mail platform gets one more template outcome, `MAIL_SKIPPED`, which marks the email `suppressed` with the reason as `error` (not failed, not retried). Report runs are write-once (UPDATE revoked), so the skip is recorded on the email, with reason `module_disabled`.
4. **Isolation.** `tick` runs each report in its own try/catch: it logs the report id and the error code only, tries to open one deduplicated system task for the report, and goes on. The run row is not written for a failed report (its transaction rolled back), so it is retried at the next tick inside the 6-hour window. Return shape unchanged.
5. **Performance.** Range bounds computed in the app as instants (Brisbane has no daylight saving) so the filter is `requestedAt >= from AND < to + 1 day`. A per-user rate limit on preview and run. `AccessService.effectiveMany` reads all the roles in one query; the catalogue uses it.
