Phase criterion: "Un cliente no puede ver ni pagar la reserva de otro, comprobado con una prueba." Dependencies 3.5 and 5.4 are in `main` (269fa31). ## 1. What exists and what is missing

Exists: magic-link customer sign-in and `/account` (a placeholder: "coming soon"); `GET /booking-requests/:ref` (request view from the snapshot), `GET …/payment-plan` (items, paid per item, outstanding, next payable, methods), `GET …/checkout-terms`, `POST …/terms-acceptance`, `POST …/payments` (method only), `POST …/payments/refresh`; web `/trips/requests/[ref]`, `/checkout/[ref]`, `/payments/return`. Every customer-resource route is `@OwnedBy` with `ownsBookingReference` (404 for unknown and for someone else's, misses capped per user and hour), and `every_owned_route_rejects_other_customer` walks all of them with fixtures. `TemplatesService.renderDocument(db, key, locale, values)` returns a PDF for `confirmation`, `itinerary`, `voucher`, `receipt`.

Missing for the row: (a) a list of the customer's bookings; (b) a booking page in the account with status, price, payment plan, payments made and documents; (c) document download; (d) payment links (`PaymentLink`, left to 5.1 by 3.2); (e) Playwright journey.

## 2. Scope decisions (conservative, reversible)

1. **Receipts: none.** The `receipt` kind is never served or listed (4.6 parked). The account shows the payments the API recorded (date, amount, method), labelled as a payment record, not a receipt or tax invoice.
2. **Documents are rendered on demand, not stored.** No `GeneratedDocument` or `StoredFile` row in 5.1: confirmation, itinerary and voucher are rebuilt from the booking's current snapshot and the live template revision at each download. Nothing personal is persisted, so 5.5 has nothing new to erase; plan 0.1 4.9 already deletes these kinds on erasure. `GeneratedDocument` stays for 4.6 (receipts must be frozen). Undo: add the table and cache the PDF.
3. **`instantBooking` stays out of 5.1.** It is not in the row and it adds an automatic `requested → approved` path to the booking state machine (plan 0.1 6.2 approval cell, with the "routable method" condition). Every request keeps waiting for Oscar's approval, which is the conservative behaviour; the public web makes no "instant" claim (checked). The panel checkbox gets a hint "Not active yet: every request waits for approval" so staff are not misled. Left to the coordinator as an unassigned item in `docs/done/5.1.md`.
4. **New module `customer-portal`** (plan 0.1 3.2 names it for 5.1/5.2), no tables of its own, **no feature flag** (like complaints: switching it off would strand customers who must pay), permissions none (customer routes only). It reads through the public services of `bookings`, `payments` and `templates`; it writes nothing.
5. **Payment links are in** (plan 0.1 5.5 and the "parked money" note list "enlaces" among the screens to have ready against the simulator; 3.2 handed them here). Constrained so that a link never does more than the signed-in owner could: §5.

## 3. API: customer area (`customer-portal`)

- `GET /account/bookings` — `@OwnedBy({ kind: 'customer', resource: 'self' })`, no params, query or body. The bookings of the customer whose `userId` is the session's user (none if there is no customer, or it is deleted or anonymised), newest request first, at most 100. Each item: `reference`, `status`, `requestedAt`, `departureDate`, `returnDate`, `currency`, `totalMinor` (from `Booking`, which equals the current snapshot by trigger), `package { name, slug, editionYear, race { name, slug } }`. No internal ids, no customer fields.
- `GET /account/bookings/:reference` — `@OwnedBy` booking with `ownsBookingReference` (fixture `account-booking`). One response so the page needs one call: `booking` (the existing `customerView`: snapshot price without trace), `plan` (the existing `PaymentAttemptsService.planView`, unchanged), `payments` (attempts of this booking in the gateway's mode with status `succeeded`: `succeededAt`, `amountMinor`, `currency`, `method`; never ids, provider references or failure codes), `documents` (the kinds available now, §4).
- `GET /account/bookings/:reference/documents/:kind` — `@OwnedBy` booking (fixture `account-booking-document`). `kind` ∈ {`confirmation`, `itinerary`, `voucher`}, anything else 404 `not_found` (so `receipt` is 404). Not available in the current status: 409 `document_not_available`. Rate-limited per user (a `DocumentRateLimitGuard` instance of the checkout limiter, review m3). Answers `application/pdf`, `Content-Disposition: attachment; filename="<reference>-<kind>.pdf"`, `Cache-Control: no-store`. The web proxy forwards `content-disposition` (one entry added to its response-header list).
- Errors and timing: unknown reference and someone else's are the same 404 through the guard (unchanged); the `:kind` check runs after ownership, so it reveals nothing about other bookings.

## 4. Documents

Availability by booking status (table-driven test generated from the `BookingStatus` enum, 10 statuses): `confirmation` and `itinerary` in `confirmed`, `balance_paid`, `completed`; `voucher` in `balance_paid`, `completed`; nothing in `requested`, `approved`, `deposit_paid`, `declined`, `expired`, `cancelled`, `refunded`. ("Confirmation" only once the booking is confirmed; a voucher only when fully paid.) Values, all from the booking and its current snapshot, never recomputed: `customerName` (customer given + family name), `reference`, `trip` (race, year, package name), `departureDate`, `returnDate` (formatted `d MMMM yyyy`), `total` (snapshot total, formatted by the API's existing money formatter), `itinerary` (lines built by code: check-in = `departureDate`, race day = the edition's `startDate` as stored in the catalogue now (the snapshot holds no race date; it is a calendar date, printed without time-zone conversion), check-out = `returnDate`). Booking dates are `@db.Date` calendar days, printed as such. Locale `en-AU`. `renderDocument` uses the live revision, or the starter wording when none is live.

## 5. Payment links (`payments`)

A payment link is a **capability issued by staff**: a single-use token, emailed only to the booking's own address, that pays **one schedule item** of **one booking** without a session. It never does more than the owner could at checkout, it never accepts terms, and it dies as soon as it has served (review G1).

**Table** `payment_links` (migration `0024_customer_area`, model in `payments.prisma`): `id`, `bookingId` (FK Restrict), `targetScheduleItemId` (**not null**: FK `(targetScheduleItemId, bookingId)` → the item of the same booking that was next payable when staff sent the link), `tokenHash` (`@secret`, unique, nullable until the send step mints it), `status` enum `active`/`used`/`revoked`, `expiresAt`, `createdById` (staff user, UUID without FK), `createdAt`, `usedAt?`, `revokedAt?`. No amount (P1), no personal data. Partial unique index: one `active` link per booking. Grants to `mt_app`: SELECT, INSERT, UPDATE (no DELETE). **Trigger** (review m5): rejects DELETE/TRUNCATE; on UPDATE only `active → used` (sets `usedAt`) or `active → revoked` (sets `revokedAt`); `tokenHash` only `NULL → value` while `active`, or `→ NULL` together with `revoked` (erasure); `bookingId`, `targetScheduleItemId`, `expiresAt`, `createdById`, `createdAt` immutable. "Expired" is not stored: it is `expiresAt <= now` (no sweep), shown as such in the panel.

`payments.paymentLinkId` (new nullable column, FK Restrict → `payment_links`, set only when an attempt is created through a link; immutable by the existing payments update path, which never writes it). Migration also adds `payment_link` to `AuditActorType` and to the outbox/automation actor lists that enumerate actor types (§9, m5).

**When a link works** (one function, `usableLink(tx, tokenHash, at)`, used by view, pay, refresh and the send step): status `active`, `expiresAt > now`, booking in `PAYABLE_STATES` (and before `approvalExpiresAt` when `approved`), target item still `active` and not fully paid. Anything else is the same 404 `payment_link_not_found` (review M1: cancelled, declined, expired, approval lapsed, fully paid, target paid by checkout, plan changed).

**Used** (review G1a): in `PaymentStateMachine.apply`, when an attempt reaches `succeeded` and has `paymentLinkId`, the same transaction runs `UPDATE payment_links SET status = 'used', "usedAt" = clock_timestamp() WHERE id = … AND status = 'active'` (lock order Booking → Payment → PaymentLink; nothing locks a link before a booking). A late success of a link attempt after revocation records the money as today and leaves the link revoked.

**Target** (review G1b): the pay route always passes `upToSequence` = the target item's sequence to `createOrReplace`, so the amount is `min(pending up to the target, pending of the booking)` (P1) and can never reach the next item.

**Staff** (new permission `payments.paymentLink.send`, owner only, not an API-key scope, no step-up: it moves no money and the email goes only to the booking's own address):
- `POST /admin/payments/bookings/:id/payment-links` (body `{}` strict). One transaction, Booking locked first, then PaymentLink: booking payable as above; target = next payable item; else 409 `booking_not_payable` / `approval_expired` / `nothing_to_pay`. Revokes the active link, inserts the new one (`expiresAt` = now + setting `payments.paymentLinkValidDays`, default 7, 1–30; for an `approved` booking capped at `approvalExpiresAt`), enqueues the email (`dedupeKey` `payment-link:<id>`), audits. Answers the link without any token.
- `POST /admin/payments/payment-links/:id/revoke` (same permission): Booking then link locked; `active → revoked`, audited; already `revoked`/`used` is 200 no change. A live attempt started through it is not touched (its money, if it arrives, is recorded as always).
- `GET /admin/payments/bookings/:id` gains `links` (id, status, `expired` boolean, expiresAt, createdAt, usedAt, revokedAt, `sent` boolean, target sequence). Never the hash.

**Email** `payments.payment_link` (registered in the 5.4 definitions; variables `givenName`, `reference`, `trip`, `expiresAt`, `link`, `brandName`; no amount). The token is minted **in the send step** (plan 0.1 4.6) by `PaymentLinkService.mint(tx, linkId)`: inside `processSend`'s transaction it locks the **booking first, then the link** (review M2), refuses with `mail_not_sendable` unless `usableLink` holds for the link and the booking's customer is open, generates 32 random bytes, stores only the SHA-256 (`NULL → value`), and puts `${WEB_ORIGIN}/pay#token=<token>` in the body. A failed send rolls the hash back with it; neither `OutboundEmail` nor job data holds the token.

**Public routes** (`@Public`, CSRF header like every POST, token in the **body** so it never reaches access logs or `Referer`; the page reads it from the URL fragment, as the magic link does). Rate limit per IP and per token hash (`PaymentLinkRateLimitGuard`, same limiter as checkout). The token never appears in logs, audit, error bodies or 422 messages (test, §7).
- `POST /payment-links/view` `{ token }` → `{ reference, package { name }, race { name }, editionYear, departureDate, returnDate, currency, amountDueMinor, payable, notPayableReason?, methods, termsAccepted, liveAttempt { status, method } | null, expiresAt }`. Exactly these keys. No name, email, travellers, price breakdown or plan items.
- `POST /payment-links/payments` `{ token, method }` (strict: any amount, sequence or replace key is 422) with `Idempotency-Key`: idempotency actor `token:<tokenHash>`, route `POST /payment-links/<linkId>/payments`; audit actor `{ type: 'payment_link', id: linkId }`. Calls `createOrReplace` with `upToSequence` = target and `viaLink = linkId` (same payable states, approval expiry, one live attempt, amount from the plan). **Terms must already be accepted by the signed-in customer** (409 `terms_not_accepted`; the page sends them to sign in and use checkout). No `replaceLiveAttempt` on this path (review M2): a live attempt of the other path, or of another link, is 409 `payment_attempt_in_progress`; the page says a payment is already under way and to try later or use the account.
- `POST /payment-links/refresh` `{ token }` → the latest attempt of **this link** (status, method, amount, currency) and whether the link was used. Creates nothing. Looks the link up as `active` **or `used`** (so the return page can say "paid" right after success), within its expiry.

**Return and resume across paths** (review G2): `drive()` chooses the return URL from the attempt: `paymentLinkId` set → `${WEB_ORIGIN}/pay/return`, otherwise `/payments/return?ref=…` as today. `createOrResume` resumes a live attempt only when its `paymentLinkId` equals the caller's (null for checkout): checkout never resumes a link attempt and a link never resumes a checkout attempt or another link's; that case is 409 (checkout keeps its explicit `replaceLiveAttempt`, which ends any live attempt only after the gateway confirms, as today).

**Erasure handler** (registry, `customerLink` via Booking): export `{ bookingId, status, expiresAt, createdAt, usedAt, revokedAt }`; anonymise sets active links `revoked` with `tokenHash = null`.

## 6. Web

- `/account`: signed out → sign-in link (as now); signed in → list of bookings (reference, trip, dates, status label, total) linking to `/account/bookings/[ref]`, plus sign out. Server component, `no-store`, `noindex`.
- `/account/bookings/[ref]`: status explanation (never "confirmed" before `confirmed`), trip and dates, price lines and total exactly as the API sends them, payment plan table (item, due date, amount, paid), outstanding and deposit due-by (Brisbane time), "Pay now" → `/checkout/[ref]` only when `plan.payable`, payments made, documents as download links (`/api/account/bookings/[ref]/documents/[kind]`). Not found / signed out → one neutral page with a sign-in link.
- `/pay` and `/pay/return` get `Referrer-Policy: no-referrer` and `X-Frame-Options: DENY` in `next.config.mjs` (review M3).
- `/pay` (client): reads `#token`, clears the fragment with `history.replaceState`, calls `view`; shows the minimal facts, the API's methods and "Pay" (body `{ token, method }`, one `Idempotency-Key` per load and method; redirect guard reused from checkout). Terms not accepted → message and sign-in link. Payment already under way (409) → says so. Keeps the token in `sessionStorage` only to call `refresh` on `/pay/return`, then deletes it.
- `/trips/requests/[ref]` and `/payments/return` link to the account booking page. Panel booking page: "Send payment link" and "Revoke" (shown with the permission), link list.
- All copy in `messages/en-AU.json`; no accreditation, "official partner" or "guaranteed entry" claims; tables with `caption`/`th scope`, one `h1`, `role=status` for notices, links with discernible names.
