## 3. Assumptions the sandbox run must confirm

Each one gets a test against the fake now (where code can test it) and a line under "Sin verificar" in `docs/done/9.3.md`. If one is false, the failure is safe (no money moves, or a task opens), and the fix is a reviewed PR.

- **A1** A Checkout Session with `payment_method_types` = a subset of `afterpay_clearpay`, `klarna`, `zip` (and no `card`), `mode: payment`, AUD, one line item, shows only those methods on Stripe's page. If Stripe also showed cards, the customer could pay by card through this account: still the server's amount, no surcharge, but a card fee would be lower, not higher; the run checks it.
- **A2** Stripe refuses the session (400) when a listed method cannot take the amount, the currency or the account, rather than silently dropping it. Either way nothing is charged: a 400 is `provider_rejected` (non-retryable, §6.2), a silently dropped method only narrows the page. The adapter lists only methods whose documented range holds the amount (§6.1), so this should not happen for the amount.
- **A3** Stripe Checkout collects whatever Afterpay, Klarna and Zip need (name, email, billing address; Afterpay possibly a shipping address) on its own page, with no extra session parameter. If false, creation fails 400 (no money) and the parameter is added in a reviewed PR.
- **A4** A declined or abandoned pay-later authorisation returns the customer to Checkout with the session still `open` (`declineOutcome: 'stays_payable'`), as a declined card does. If it instead completes the session `unpaid`, the existing `sessionStatus` table reads `failed` or `pending` by the PaymentIntent (`mapping.ts`), which the contract suite will show in the sandbox run.
- **A5** All three complete the session `complete`/`paid` with a `succeeded` PaymentIntent on authorisation ("Immediate" for Afterpay and Zip; Klarna's timing is "Customer-initiated" in the summary). If Klarna is asynchronous, the existing `checkout.session.async_payment_succeeded`/`failed` handling applies unchanged.
- **A6** Refunds of these payments use the same Refund object, statuses (`pending` → `succeeded`/`failed`) and events (`refund.created`, `refund.updated`, `refund.failed`) as card refunds. A refund outside the method's window (Afterpay 120 days, Klarna and Zip 180) is refused by Stripe (400 → `provider_rejected`) or ends `failed` (`refund.failed`, money back to the Stripe balance). Both are existing core paths; staff then use a manual refund (P13). Never retried as if nothing happened.
- **A7** Disputes of these payments arrive as `charge.dispute.*` with the Dispute object 4.5 already reads (`payment_intent`, `amount`, `status`, `balance_transactions`). Reason codes outside Stripe's card list map to `other` (existing mapping).
- **A8** Stripe adds no surcharge or fee to the customer's total for these methods (Klarna's rule says we may not; Afterpay's and Zip's pages say nothing). The customer's provider may charge them its own fees (Zip's account fees), which are between the customer and Zip, not part of our price.
- **A9** **Stripe lets one business hold a second Stripe account** (for pay later) next to the card one, each with its own keys, webhook endpoints and payouts, and pay later can be enabled on it. If false, see §4.2 and F4.
- **A10** Zip Money's interest-free period, and so its fee (5.49 % to 11 %), is chosen by Zip and the retailer's qualification, not by the session; with no qualification the default is the 5.49 % tier. If false, a payment can cost more than expected; the guide tells Oscar to check the Zip settings before turning pay later on.
- **A11** A Checkout Session's object in `checkout.session.*` events and in `GET`/list answers carries `payment_method_types` as sent. Only the subject's checks and the guide rely on it; the adapter's state machine does not.
- **A12** In test mode each method's page offers "authorise" and "fail" test actions (the sandbox subject's browser script presses them). If not, the sandbox subject is changed before the run; nothing in production depends on it.
- **A13** Stripe applies the method's amount limits to the session total, so the adapter's own table (§6.1) is never wider than Stripe's. The table is the documented one; if Stripe's limits change, Stripe refuses (A2) and the table is updated in a reviewed PR.
- **A14** A Stripe restricted key (`rk_test_…`) with Checkout Sessions, PaymentIntents, Refunds and Disputes read/write works for these methods as for cards (the `stripe` adapter already accepts `rk_test_`).

## 4. Architecture: the `stripe` class with a pay-later session

### 4.1 Code

- **`adapters/stripe/bnpl.ts`** (same folder: `adapter_sources_are_isolated` forbids importing another adapter's folder): `StripeBnplProvider extends StripeProvider`, with

  - `protected override sessionParams(input)`: `sessionParams(input)` of `stripe.ts` with `payment_method_types[0]=card` replaced by the pay-later list of §6.1, every other parameter unchanged (metadata, `expires_at`, URLs, line item).
- **`adapters/stripe/stripe.ts`**, one change: `createPayment` calls `this.sessionParams(input)`, a new `protected sessionParams(input: CreatePaymentInput)` that returns the exported `sessionParams(input)`. The card path is byte-identical: the existing `stripe.unit.test.ts` (which pins `sessionParams`), `stripe-flow.test.ts`, the `stripe` contract subject and the manifest hash of §12 all run unedited.
- **`adapters/index.ts`**, one line: `new StripeBnplProvider()` after `AirwallexProvider`.
- Everything else is inherited: HTTP, the key check per mode (`sk_test_`/`rk_test_` in test mode), Stripe's idempotency, lookup by key, retrieve, cancel (`expire`), refunds, disputes, webhook signature, event parsing and error mapping. They already pass the 37 clauses.

### 4.2 One Stripe account per adapter key (the cost of D2)

The core matches an event only among the payments of the provider account that received it (`webhooks.service.ts`, `processOnce` and `matchPayment`), and a Stripe webhook endpoint receives every event of its Stripe account (endpoints filter by event type, not by method). So if the `stripe` account and the `stripe_bnpl` account of our panel used the **same** Stripe account, each would receive the other's events and open a "Payment webhook for an unknown payment" task for each one. Money would still be matched correctly (never across accounts), but the noise would be real.

Hence: **`stripe_bnpl` needs its own Stripe account** (A9), with its own keys, webhook endpoint and payouts. The guide says so in bold, and the panel row's credential label says "a Stripe account used only for pay later". If A9 is false, or Oscar prefers one Stripe account, follow-up **F4** (a reviewed change to both Stripe variants: each ignores the other family's sessions, refunds and disputes by `payment_method_types`, A11) replaces this rule. That would change the `stripe` adapter, so it is not done here.

### 6.2 Create

`createPayment(ctx, input)`:
1. **Refuse before the network**, non-retryable `provider_rejected` (no request sent, so no object exists and none ever will under that key): `input.method !== 'bnpl'`; `input.customerCountry !== 'AU'`; currency not AUD; no method of the table holds the amount. The key check of the account comes first, as in `stripe` (`provider_auth_failed` for a malformed key).
2. Then the inherited path: late-create lookup, `POST /v1/checkout/sessions` with the idempotency key, `idempotency_error` → lookup, replay → read again, answer `requires_action` with Checkout's URL. The core hands the URL out only if it starts with `checkoutOrigin + '/'` (unchanged).
3. Session parameters: exactly `sessionParams` of `stripe.ts` with `payment_method_types[i]` = the eligible types in the table's order. **No** `card`, no `shipping_address_collection` (A3), no `payment_method_options`, no fee, no customer data (Checkout collects it on Stripe's page).

### 6.3 Statuses, cancel, retrieve

Inherited unchanged (`sessionStatus`, `sessionToPayment`, `expire`). A pay-later decline leaves the session open (A4); an async outcome uses the existing `async_payment_*` events (A5).

### 6.4 Refunds and disputes

Inherited. Windows (A6): a refund the method no longer allows is refused by Stripe or fails later; the core's existing paths record it (`provider_rejected` → refused refund with a task; `refund.failed` → failed refund) and staff use a manual refund (P13, `manual-refunds`). The adapter does **not** guess the window before the network: which method the customer used is only on the charge, and a wrong guess would block a refund Stripe allows. The guide warns that pay-later deposits paid more than 120 days (Afterpay) or 180 days (Klarna, Zip) before a cancellation will be refunded by bank transfer.

### 6.5 Born off, no surcharge, amount from the server

- **Born off.** `defaultRules` skips `bnpl` (existing, `routing-rules.ts`), so a new `stripe_bnpl` account gets **no** routing rules: it offers nothing until staff add a `bnpl` rule (AU, AUD, with limits; the guide suggests A$1 to A$4,000). Accounts are also born paused (4.1).
- **No surcharge by method.** The only amount sent is `input.amount`, which the core takes from pricing and the payment plan. Nothing adds a fee or changes a price for pay later. Test: `no_surcharge_by_payment_method` for this adapter (same amount for the same booking under `card` on `stripe` and `bnpl` on `stripe_bnpl`), and the session body contains no fee or surcharge parameter.
- **Total includes every mandatory component.** Unchanged: the web shows what the API returns; pay later is one more route for the same payment plan amount.
- **No promotion.** The web shows only the existing neutral label "Pay later" (`apps/web/messages/en-AU.json`); no BNPL banner, calculator or "approved" wording (Klarna's DDO note, §2). No web change in this task.

### 6.6 What the customer sees

The existing checkout lists `bnpl` when a rule routes it (label already exists), and redirects to Stripe's page like a card payment. No web change.

## 19. Plan review, round 1 (approve with changes): how each finding is resolved (overrides the sections above)

**Source note.** Unchanged: every Stripe, Afterpay, Klarna, Zip and PayPal fact is UNVERIFIED (SIN VERIFICAR) until the sandbox run. New assumptions A15–A17.

- **1 (high), a pay-later charge completed after the session expired must never be lost.** Afterpay gives the customer 3 hours; our session lives 45 minutes (`SESSION_LIFETIME_SECONDS`) and the attempt 60. The parent reads `expired` as `cancelled` without looking at the PaymentIntent. Resolution, all in `adapters/stripe/bnpl.ts` (the card path does not change):
  - **New A15:** what Stripe does with a PaymentIntent still at the provider (`requires_action`, `processing`) when its Checkout Session expires or is expired by us, and whether a PaymentIntent created by Checkout may be cancelled with `POST /v1/payment_intents/{id}/cancel`. The design is safe under every answer (below).
  - **Reading.** `StripeBnplProvider` overrides `toPayment`. A session `open` or `complete` reads as in `stripe`. A session `expired` reads **by its expanded PaymentIntent**: none → `cancelled`; `succeeded` → `succeeded`; `processing` or `requires_capture` → `pending`; `canceled` → `cancelled`; any other state (the customer may still be at the provider) → `requires_action`, with no URL. A `payment_intent` that is an id and not an object makes the read unknown (retryable): every read of ours expands it.
  - **Cancel.** `cancelPayment`: a money state is answered as it is; else (a) an `open` session is expired; (b) the session is read again and an open PaymentIntent is cancelled (`POST /v1/payment_intents/{id}/cancel`, idempotency key `<key>:pi`); (c) it is read again and that is the answer. **It never answers `requires_action`**: if the PaymentIntent is still open after (c) (A15: Stripe refuses the cancel), it throws retryable `provider_unavailable`, so the attempt stays live, blocks a second payment (P2) and the core's 24 h "unresolved" task tells staff.
  - **Events.** `checkout.session.expired` with a PaymentIntent is read as `unsupported` (pulls decide; the event cannot say whether money is coming). Without one it is `cancelled`, as now (the customer never reached the provider).
  - **Why not `payment_intent.succeeded` as a payment event.** The PaymentIntent does not carry the session id, which is our payment reference, and the core compares the event's `ref` with the stored one (`webhooks.service.ts`, `processOnce`): an event with the PaymentIntent id as `ref` opens a "reference mismatch" task for **every** pay-later payment, and accepting a different `ref` would weaken that check for every gateway (a core change I do not make). It is not needed either: with the reading above, an attempt never ends while its PaymentIntent is open, so the money is always met by a pull (`sync` on return, `drive`, the expiry sweep, which calls `cancelPayment` and records what it reads). `payment_intent.*` events stay `unsupported`.
  - Tests (`stripe-bnpl-flow.test.ts`): `bnpl_paid_after_session_expiry_is_recorded` (the customer approves at minute 50 after the session expired and its `expired` event was received: the payment is recorded `succeeded`, never `cancelled`; with the fake refusing the PaymentIntent cancel, as A15 may say) and `cancel_while_customer_at_provider` (cancel while the PaymentIntent is `requires_action`: session expired, PaymentIntent cancelled, attempt `cancelled`, booking free; and with the cancel refused: retryable, attempt still live).
- **2 (medium-high), a refund that fails later must reach a person.** Both parts:
  - **(a) Window check before the network** (F6 brought forward). `createRefund` first looks for an existing refund under our key (so a lost answer is never refused); then reads the PaymentIntent with `expand[]=latest_charge` and, when `payment_method_details.type` is `afterpay_clearpay` (120 days), `klarna` or `zip` (180 days), refuses with `provider_rejected` (non-retryable) once the charge is older than the window minus one day. Staff get the existing synchronous 409 `refund_refused_by_gateway`. An unreadable charge (no object, no integer `created`) is unknown (retryable), never guessed; another type has no window and Stripe decides. **New A16:** those types and windows, and that `latest_charge.created` is when the window starts.
  - **(b) A minimal core change** in `core/refunds.service.ts`, `apply`: when an app refund (not a manual one) goes to `failed` with source `webhook` or `sweep` (the gateway reported it after our request, so no person saw it), a system task opens in the same transaction: title `Refund failed at the payment gateway on booking <reference>`, description in Australian English with no personal data, `sourceRef` `payments:refund_failed:<refund id>` (one per refund: `createSystemIn` returns the open one, and a duplicate event makes no transition). Synchronous refusals (source `api`) are already a 409 to staff and staff actions are seen by staff, so they open nothing. No migration. Test: `refund_failed_event_records_failure` (task opened; the same event again opens no second task) and a unit-level check that a refusal through the API opens none.
  - **Correction to §6.4 and §13:** a "manual refund" (P13) exists only for bank transfers (`app-refunds.service.ts`, `refund_not_manual`). For a gateway payment there is **no app path today to record a refund made by bank transfer**. The task tells staff to refund the customer another way and to keep the bank reference for the accountant; recording it in the app is follow-up **9.3-F7**, for Oscar. The flow test `refund_refused_after_window_leaves_manual_refund_path` becomes `refund_refused_after_window_is_a_409_and_nothing_moves`.
