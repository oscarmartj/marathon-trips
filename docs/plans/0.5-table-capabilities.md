# 0.5 Shared capabilities for panel tables

Risk: medium. Source: `docs/plans/phase-0-architecture.md` sections 1.3 (SD columns), 3.1 (`platform/common`, entity registry), 4.4 (history is a query on `AuditLog`), 5 (tables `Tag` to `BulkOperation`) and the 0.5 test line in section 8. No money logic (money is parked); nothing here touches payments, pricing or bookings. Depends on 0.3 (permissions, audit) and 0.6 (panel pages).

## Design

API code under `apps/api/src/platform/common/`; tables in `prisma/schema/platform-tables.prisma`; one migration `0005_table_capabilities`; shared zod schemas in `packages/shared/src/schemas/tables.ts`; panel components in `apps/web/src/components/admin/table/`.

- **`TableDef`** (registered on the existing `EntityRegistry` entry, field `table`): entity type and Prisma model, a whitelist of columns (`key`, `type` text/number/date/boolean/enum, `path`, `sortable`, `filterable`, `searchable`, `exportable`, enum values), the permissions (`read`, `write`, `delete`, `export`, `import`, optional `annotate`), flags (`softDelete`, `taggable`, `notes`), `searchDocument(row)`, `bulkActions` and an optional CSV import. A future module gets every capability by declaring one def and the web page by rendering `<DataTable entityType=... />`. Nothing in a request ever names a Prisma field: the query builder only maps whitelisted keys.
- **Query** (`query.ts`, pure): `q` (case-insensitive contains over searchable columns), AND-combined `filters` (`{field, op, value}`; ops allowed per column type; values coerced and bounded), `sort` (up to 3 columns plus `id` tie-break), `page`/`pageSize` (max 100), `tags` (any/all) and `deleted` (`exclude` | `include` | `only`; the last two need the `delete` permission). The same validator checks saved views, so a stored view can never hold a field the table does not allow.
- **Saved views** (`SavedView`): own views plus shared ones, per entity type; name unique per owner; sharing needs `common.view.manage`; only the owner (or `common.view.manage` for shared views) edits or deletes. `name` and `filters` are `@pii` (free text), `columns` and `sort` are `@nopii`.
- **Bulk actions** (`BulkOperation`): at most 100 ids. Each action is the same function the single-record route uses, run per element in its own transaction, and each element is checked with `permissionFor(row)` (so a mixed selection gives a per-element result, never one all-or-nothing denial). The operation row stores ids and `{id, ok, code}` only; audit gets one entry per element plus one for the operation.
- **CSV** (`csv.ts` pure, `csv.service.ts`): export is a POST (it writes an audit entry and a `CsvJob`) returning `text/csv` with a BOM, CRLF and RFC 4180 quoting; any text cell starting with `=`, `+`, `-`, `@`, tab or CR gets a leading `'` (numbers and dates are written natively, so negatives are not touched), and import removes that guard again. Import is `dryRun` (preview) or commit; both validate every row first (max 500 rows, 90 000 characters, header checked, unknown or duplicate columns rejected) and commit writes everything in one transaction or nothing. Errors are `{row, column, code}` only, never values (plan 4.9). Export is capped at 5 000 rows (422 `export_too_large`).
- **Tags** (`Tag`, `Tagging`): staff-defined tags (`common.tag.manage`), optional `entityTypes` restriction; applying tags is a write of the full set (`PUT .../tags`) that diffs, audits `{tags: {before, after}}` (tag names are `@nopii`) on the record, and refuses soft-deleted records. A tag in use cannot be deleted (409).
- **Notes** (`Note`, SD): staff notes on any registered record; body is `@pii`; audit is recorded against the target record (entity type and id of the record, model `Note`) so the note's changes appear in the record's history and resolve their data subject through the target. Publishes `common.note.added`.
- **History**: `GET .../:id/history` returns per-field `{field, before, after}` from `AuditLog.changes`, plus `@pii` values from `AuditPiiValue` only when the def sets `history.showPii` (the example Task does: staff-written work items; customer tables default to off). Needs the table's `read` permission and `audit.log.read`.
- **Soft delete** (`soft-delete.ts`): `deletedAt`/`deletedById` and `version`; delete and restore are audited (`before`/`after` of `deletedAt`), publish `common.<entity>.deleted|restored` and update the search index; lists hide deleted rows unless asked. Deleting never removes rows or files.
- **Search** (`SearchDocument`): `GET /admin/search?q=` over a `tsvector` (`simple` configuration, prefix match on every word) kept by a database trigger from `title` and `subtitle`; results are filtered to the entity types whose `permissionKey` the caller holds. The index is written in the same transaction as the change (not by a consumer: a consumer would leave a stale window after a delete or a permission change); the events are still published for later consumers. `SearchIndexService.reindex(def)` rebuilds one entity type.
- **Example table**: `Task` (plan section 5) with `TasksService` (create, edit with optimistic lock, status transitions), `TasksController` at `/admin/tasks`, seed rows, and the panel page `/admin/tasks` using every capability. Task permissions: `common.task.read|write|delete|export|import`, plus `common.task.manageAutomated` for tasks whose `source` is not `manual` (this is the per-element permission the bulk path and the single path share).
- **Routes**: one generic controller `/admin/tables/:entityType/...` (meta, rows, export, import, bulk, delete, restore, history, notes, tags, views), `/admin/tags` and `/admin/search`. A route can carry only one static access mark, so these routes are marked `common.table.use` (baseline: "use the shared table tools") and the service then requires the table's own permission for the entity type from the URL and fails closed (unknown type 404, missing permission 403). Unknown entity types and rows the caller cannot read are 404, not 403, where that avoids confirming existence.
- **Web**: `DataTable` (client) reads `meta` and renders: search box, filter builder with removable chips, views menu (apply, save, share, delete), sortable headers with `aria-sort`, row selection with a bulk bar, CSV export, CSV import with a checked preview, tags and notes and history in a record panel, "Show deleted" with restore. All text is in `messages/en-AU.json` (`admin.table.*`, `admin.tasks.*`); labels for a table's columns are `<prefix>.columns.<key>`. Tags are never conveyed by colour alone (name is always shown). A sidebar `GlobalSearch` form lists results with links.

## Failure cases

Unknown field, operator or sort column (422); oversize page or ids list (422); stale `version` (409); deleting an already deleted record (409); tagging a deleted record (409); a viewer reading another owner's private view (404); import with any bad row writes nothing; a failure inside one bulk element does not undo the others and the failed one reports a code only; formula-looking cells in export; CSV with unterminated quote or duplicate headers; permission removed between page load and action (403 at the action).

## Assumptions (instead of questions)

1. `Attachment` is in the plan's table list for 0.5 but is not one of the capabilities this task lists; it is left to the first task that needs files on records (reversible: one migration).
2. `CsvJob` has no `inputFileId`/`outputFileId`: import and export are synchronous and stateless, so no file is stored and none needs purging. Add them when a job becomes asynchronous.
3. The search index is written in the change's transaction instead of by an event consumer (see Search).
4. Dependencies: none. CSV parsing is about 60 lines and is tested against RFC 4180 cases and a round trip.
5. `AuditService.subject` becomes public (`subjectOf`) so notes can resolve their data subject through the target; no behaviour change.

## Tests (written first where practical)

API, against real PostgreSQL (`apps/api/test/platform/tables-*.test.ts`): query builder table (every op by type, bad field/op/value, sort whitelist, pagination bounds); search by title, prefix, permission filter, removal on delete and return on restore; combined filters plus sort over Task; saved view create/apply/share/forbidden/foreign field rejected; bulk with mixed permissions and one failing element; CSV escape table (`=cmd`, `+1`, `-1` text, `@x`, tab, quotes, commas, newlines, accents), round trip, import with one bad row writes nothing, over-limit, unknown column; tags apply/diff/audit/restricted entity type/in-use delete; notes with pii routing to `AuditPiiValue`, event published; history with before/after and pii rule; soft delete/restore/audit/event/index; 403 for a role without the table permission and 404 for unknown entity; `every_route_has_exactly_one_access_mark` keeps passing; schema conventions and field-class regeneration. Web: copy test (no hard-coded text), render checks for the table (caption, `scope`, `aria-sort`, labelled controls), `pages.test.tsx` for `/admin/tasks`. Playwright: the example table end to end (create, search, filter, save and re-apply a view, tag, note, bulk complete, export, import preview, delete and restore, history).

## Not doing

Attachments, custom fields (7.5), asynchronous or file-backed CSV jobs, scoped (per-record) permissions, column-level permissions, drag-and-drop column reordering, automations on tasks, assignee picker in the UI.
