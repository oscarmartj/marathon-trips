# Plan 3.5: checkout on the web, with terms acceptance (simulator only)

Risk: medium. Money is parked: nothing here charges anything except the simulator (test accounts only, test-only adapter). Row of the phase file: "Checkout en la web: métodos activos por país, aceptación de condiciones con versión y fecha." Dependencies 3.2, 3.6 and 2.3 are in `main`. Reference: `docs/payments.md` (Requisitos, Métodos de pago, dispute pack: "condiciones aceptadas con fecha"), `.claude/rules/payments.md`, `web.md`.

## 1. What exists and what is missing

Exists: `GET /booking-requests/:ref/payment-plan` (plan, `nextPayable`, `methods` for the customer's residence country, from the active accounts' manifests), `POST /booking-requests/:ref/payments` (method only; the amount is the plan's), the simulator's hosted page, whose "Back to the site" goes to `${WEB_ORIGIN}/payments/return`. `/checkout` is a placeholder.

Missing: (a) terms of booking with a version and a date, recorded per booking and required before a payment can start; (b) the web checkout page; (c) the return page; (d) a way for the return page to learn the outcome when the webhook has not been processed (3.6 note: with `JOBS_WORKERS=off` the webhook stays stored and the booking moves only when the attempt is resumed or swept); (e) Playwright journey.

## 2. Terms of booking (API, payments module)

- The terms are the published content page `terms` (locale `en-AU`) that staff already edit (8.1). Content pages are edited in place (their `version` counter rises on every edit and the old text is not kept), so an acceptance stores its own **snapshot**: title, intro, body, the page's `version` and a SHA-256 digest of the canonical JSON of `{slug, locale, title, intro, body}`.
- New table `terms_acceptances` (migration `0023_terms_acceptance`, model in `payments.prisma`): `bookingId`, `customerId` (both Restrict), `documentSlug`, `locale`, `contentVersion`, `textDigest`, `title`, `intro`, `body`, `acceptedAt`. Unique `(bookingId, documentSlug, locale, textDigest)`. Immutable: triggers reject UPDATE, DELETE and TRUNCATE (not marked `@appendOnly`: that marker only allows foreign keys to other append-only rows, and this table points at bookings). No personal text: editorial text and digests only.
- `GET /booking-requests/:ref/checkout-terms` (customer, owner only) returns the current text, `version`, `digest` and `acceptedAt` (null until accepted). No published page: 409 `terms_unavailable`.
- `POST /booking-requests/:ref/terms-acceptance` body `{ version, digest }` (strict). The server reads the current page; if version or digest differ from what the customer saw, 409 `terms_changed` (the web reloads the text). Otherwise inserts with `ON CONFLICT DO NOTHING` (accepting twice is the same acceptance and keeps the first date), writes an audit entry, answers `{ version, acceptedAt }`. Only for a booking in a payable state (`approved`, `deposit_paid`, `confirmed`); otherwise 409 `booking_not_payable`. The acceptance is by the signed-in owner of the booking; the digest is the server's, never a text from the browser.
- `POST /booking-requests/:ref/payments` now requires an acceptance of the **current** digest: 409 `terms_not_accepted` (or `terms_unavailable`). Checked before the idempotency record is opened, so a rejected call stores nothing. Editing the terms after acceptance means the next payment needs a new acceptance (conservative; reversible by dropping the check).
- Rate limit: acceptance and refresh reuse `PaymentAttemptRateLimitGuard`'s windows through a second instance with their own keys.

## 3. Outcome on return (API)

- `POST /booking-requests/:ref/payments/refresh` (customer, owner only, no body): if the booking has a live attempt, runs the existing `sync` path (retrieve from the gateway, record through the state machine, coverage in the same transaction); then answers the latest attempt `{ status, method, amountMinor, currency }` or `null`, plus the booking `status`. It never creates an attempt and never takes an amount. A gateway that fails gives the same neutral 503 as a start does; the customer sees "still checking".
- `returnUrl` carries the booking reference: `${WEB_ORIGIN}/payments/return?ref=MT-XXXXXX`. The reference is already in the customer's own URLs and in gateway metadata (`bookingId`); the page trusts nothing in the query except as the name of a booking the signed-in customer must own.

## 4. Web

- `/checkout/[reference]` (server shell, `no-store`, `noindex`, `no-referrer`) + client form. Shows the plan as the API returns it (items, due dates, the amount payable now, `depositDueBy` in Brisbane time), the methods the API says are active for the customer's country, the terms text (scrollable region plus a link to `/legal/terms`) with the version and a checkbox, and a "Pay" button. The browser never computes or sends an amount: the request is `{ method }` plus an `Idempotency-Key` generated once per page load and per method.
- Sequence: tick terms, POST acceptance `{version, digest}`, POST payments `{method}`, then `window.location.assign(nextAction.url)` only when the URL is absolute `https:` (or `http:` on localhost in development builds) as the API returned it. States: signed out (sign-in link), not payable (reasons mapped to copy), no methods (a plain "payments are not open yet; we will contact you", no error), terms changed (reload text, tick again), provider unavailable (503, try again), already in progress (resume).
- `/payments/return?ref=` (client): validates `ref` against the reference pattern, calls `refresh`, polls up to six times two seconds apart while the attempt is `created|pending|requires_action`, then shows paid / declined or cancelled / still processing, with links to the booking and back to checkout. Success is shown only from the API's attempt status, never from the query.
- `/trips/requests/[reference]`: when the status is `approved` or `deposit_paid`, a link "Continue to payment".
- All copy in `messages/en-AU.json` (Australian English); no "official partner"/"guaranteed entry"/accreditation claims; labels and `aria-live` status, visible focus via existing styles, radio group in a `fieldset`/`legend`, checkbox with label.

## 5. Failure cases (tests first)

Terms: no published page; accept with stale version, stale digest, malformed body, extra keys; booking not payable; another customer (404, also for refresh); double accept keeps the first row; concurrent accepts give one row; row cannot be updated or deleted (as the API role and as owner); editing the page invalidates the acceptance for the next payment; payment start without acceptance writes no attempt and no idempotency record; with all gateways off the plan says `no_payment_method_available` and acceptance still works. Refresh: no live attempt; live attempt paid at the simulator with the webhook unprocessed (booking moves); declined; gateway error is a 503 without changing state; a second refresh is a no-op. Existing 3.1/3.2/3.6 tests keep running unchanged except the `pay` helper, which accepts the terms first (their subject is payments, not terms).

Web: request body has no money, date or rule keys; redirect URL guard (javascript:, data:, relative, `http:` off localhost); error-code mapping; `ref` pattern; copy test (no hard-coded strings, Australian spelling); components render the API's numbers untouched.

E2E (`apps/web/e2e/checkout.spec.ts`, slot `E2E_STAFF_17`): staff publish a terms page and a priced package through the panel's API, a customer requests, staff approve, the customer opens checkout, sees only the simulator's methods, cannot pay without ticking terms, ticks, pays, completes the simulator page, lands on `/payments/return`, sees "payment received", and the booking is `deposit_paid`; a second customer declines at the simulator and sees the failure; a signed-out visit shows the sign-in prompt. Accessibility basics asserted by role/label locators.

## 7. Assumptions made without Oscar

1. Terms = the published `terms` page; no page means no payment (conservative: no acceptance without a stored text).
2. One acceptance per booking per exact text; a text change asks again.
3. `legalReviewPending` does not block payment (Oscar controls publication and the page already shows the notice); recorded in the done file for his review.
4. Return URL carries the booking reference; the page only displays what the API says for a booking the signed-in customer owns.
5. Migration number 0023 (0022 is reserved by 6.5); renumber if `main` moves.
