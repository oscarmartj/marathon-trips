## 1. Data model (`payments.prisma`, migration `0034_provider_accounts_admin`)

New columns on `provider_accounts` (all `@nopii`, no secret):

| Column | Type | Meaning |
|---|---|---|
| `credentialsChangedAt` | `timestamptz(3) NOT NULL DEFAULT now()` | when the credentials or webhook secret last changed; a connection test counts only if it is not older |
| `pauseReasonCode` | `text NULL`, `CHECK IN ('staff','boot_adapter_missing','boot_adapter_planned')` | why the account is paused; NULL unless `status = 'paused'` (`CHECK`) |

Changes to existing nets:

1. **`provider_accounts_test_mode_only_check` is kept unchanged.** Only additive nets, none of which needs it lifted:
   - `BEFORE UPDATE` (extends `mt_provider_account_guard`): status pairs only `active>paused`, `paused>active`, `active>retired`, `paused>retired`, `retired>archived` (same status allowed for other column changes); `archived` and `retired` never go back. Any change of `credentialsCiphertext`, `credentialsKeyVersion`, `webhookSecretCiphertext` or `webhookKeyVersion` must raise `credentialsChangedAt`. `paused>active` needs `lastConnectionTestResult = 'ok'` and `lastConnectionTestAt >= credentialsChangedAt` (every mode: it also guards a future live mode without permitting it).
   - Unchanged: id, mode, adapter and `createdAt` never change; no DELETE, no TRUNCATE (3.1).
2. Accounts that exist (console, seed) keep `status` and get `credentialsChangedAt = createdAt` in the migration (backfill of a metadata column, not of money).

Settings (code, no migration): `paymentDisputeWindowDays` (default 180, int 60–540, plan 0.1, 6.4). The setting definition gets `internal: true` support (§9).

Migration is additive only (two columns, the backfill, the extended trigger function, the pause-reason CHECK); undoing it is a new migration. `prisma migrate diff` runs in CI; DDL written by hand with Prisma's names as in 0017 and 0033.

## 2. Adapter descriptors (credentials)

`AdapterManifest` gains `account`:

```ts
account: {
  fields: readonly { key: string; label: string; pattern: { test: string; live: string } }[]; // regex sources, per mode
  webhookSecret: { source: 'entered'; pattern: string } | { source: 'generated' };
  generated?: readonly { key: string; prefix: string }[]; // simulator apiKey: server-made, never typed
}
```

- Stripe: `secretKey` (`^(sk|rk)_test_…$` / `^(sk|rk)_live_…$`, the regexes `stripe.ts` already applies), webhook secret entered (`^whsec_…$`).
- Simulator: no fields; `apiKey` generated (`sim_test_` + 18 random bytes hex); webhook secret generated. Test-only: creatable only in `development`, `test`, `ci`.
- Manual: no fields, webhook secret generated (unused). Its connection test also runs `ManualMethodsService.test` for the enabled manual methods (plan 0.1, 5.5).
- `manifestProblems` (3.1/3.6) also checks: field keys unique and `^[a-z][A-Za-z0-9]{1,40}$`, every pattern compiles and is anchored, test and live patterns of a field never both match one example (each adapter lists a sample per mode in its test, not in the manifest). The contract clause `manifest_is_valid` keeps calling it: no clause added or loosened, so no verified evidence is invalidated (there is none).
- Validation of a request: unknown key, missing key, wrong pattern for the account's mode, length over 500, control characters → `422 credentials_invalid` with `{ fields: [<key>] }` only. Never the value, never zod's `received` (the schema is `z.record(z.string())`; the descriptor check is ours).

## 3. API (REST, `/admin/payments/...`; every route one access mark, step-up from the permission manifest)

Permissions (manifest, `apiKeyScopable: false`):
- `payments.providerAccount.read` (exists): catalogue, accounts, warnings.
- `payments.providerAccount.manage` (new, **step-up**): rename, status changes, connection test.
- `payments.providerAccount.manageCredentials` (new, **step-up**): create an account, rotate credentials, regenerate the webhook URL.

| Route | Permission | Behaviour |
|---|---|---|
| `GET /admin/payments/adapters` | read | catalogue: manifest data without patterns' internals beyond field key/label, plus `creatable: true \| { reason }` for this environment and mode |
| `GET /admin/payments/provider-accounts` | read | extends today's view: `version`, `pauseReasonCode`, `credentialsChangedAt`, `connectionTestCurrent` (bool), `lastWebhookReceivedAt`, `lastWebhookRejectedAt` + reason, `hasHistory`, `allowedTransitions`, adapter status; never a secret column (`ACCOUNT_VIEW_SELECT` stays the only select) |
| `GET /admin/payments/provider-accounts/warnings` | read | §6 |
| `POST /admin/payments/provider-accounts` | manageCredentials | body `{ adapterKey, displayName, mode, credentials }`; §4.1; 201 `{ account, webhookUrl }` (URL only here) |
| `PATCH /admin/payments/provider-accounts/:id` | manage | `{ version, displayName }` |
| `POST /admin/payments/provider-accounts/:id/status` | manage | `{ version, status, confirmCoverageLoss?: true, reason? }`; §4.3 |
| `POST /admin/payments/provider-accounts/:id/connection-test` | manage | §4.2 |
| `PUT /admin/payments/provider-accounts/:id/credentials` | manageCredentials | `{ version, credentials }`; §4.4 |
| `POST /admin/payments/provider-accounts/:id/webhook-url` | manageCredentials | `{ version }`; new path token, old one stops matching at once; 200 `{ webhookUrl }` once |

There is **no DELETE route** (and the trigger refuses DELETE): `account_with_history_not_deletable` checks both. Bodies of these routes are payments bodies: never logged (plan 0.1, 4.1); the test of §7 captures stdout/stderr to prove it.

## 4. Flows

### 4.1 Create

1. `mode = 'live'` → `409 live_mode_not_available` at once, in every environment, before validation, decryption or any gateway call (audited as a refusal). Then: adapter exists and is not `planned`; the environment must charge in test mode (`modeForEnv(APP_ENV) = 'test'`), so in production the panel creates nothing until the future live task (`409 account_mode_not_for_environment`); a test-only adapter outside its environments → `409 test_adapter_blocked_in_environment`.
2. Validate credentials against the descriptor (§2).
3. **Candidate connection test** through a new `ProviderGateway.testCandidate(adapterKey, mode, plaintextCredentials, webhookSecret)`: applies `callBlockReason` with `op = 'test_connection'` to the virtual account *before* touching the provider, builds the `ProviderContext` from the candidate values (never from the database), with the same timeout and closed error codes. `gateway.ts` stays the only door to a provider.
   - The result is stored whatever it is (Oscar may set up an account before his sandbox works); it only gates activation.
4. One transaction: insert with `status = 'paused'`, `pauseReasonCode = 'staff'`, `lastConnectionTest*` from step 4, `credentialsChangedAt = now()`, ciphertexts with AAD bound to the new id (3.1), `createdById = actor`. Audit `payments.providerAccount.created` (secrets `"[changed]"`). Return the webhook URL once.
5. Every refusal is audited (`payments.providerAccount.creationRefused`, code only, a fresh entity id), so attempts to create live accounts are visible.

A new account is **born paused** in both modes: it is offered nowhere until someone activates it (§4.3). The console commands of 3.1/3.3/3.4 keep creating `active` test accounts (development and CI tools; the e2e of 3.5 relies on them); they are refused in production as today.

### 4.2 Connection test

`gateway.call(id, 'test_connection', provider.testConnection)` (allowed on every status, never live outside production). Manual accounts also check the manual methods' instructions. Result codes: `ok` or a closed list (`provider_auth_failed`, `provider_unavailable`, `provider_timeout`, `provider_busy`, `provider_rejected`, `provider_not_found`, `webhook_secret_missing`, `manual_instructions_invalid`, `credentials_unreadable` for a key version that is not configured or a ciphertext that fails). Stored with `UPDATE … SET lastConnectionTestAt, lastConnectionTestResult WHERE id = $1 AND credentialsChangedAt = $usedAt` (the `credentialsChangedAt` read with the credentials): a test of old credentials that finishes after a rotation never marks the new ones as tested (`stale_connection_test_not_recorded`). Does not bump `version` (it is not an edit). Audited `payments.providerAccount.connectionTested` with the code.

The response also reports webhook health from our own tables: last event received and last rejection (reason) since `credentialsChangedAt` for this account. A `bad_signature` rejection after the last change is shown as "the webhook secret may be wrong". Checking the gateway's endpoint registration (for example Stripe's webhook endpoints) is not built: adapter-specific and needs a wider key scope (assumption A6).

### 4.3 Status changes

One transaction: `pg_advisory_xact_lock(<payments.provider_account_status>)` (serialises all account status changes, so two people pausing the last two accounts cannot both skip the warning), then `SELECT … FOR UPDATE` of the account, compare `version` (409 `version_conflict`), check the pair (409 `status_transition_not_allowed`), then:

- `paused → active`: connection test `ok` and not older than `credentialsChangedAt` (409 `connection_test_required`); adapter still registered and not `planned`. Clears `pauseReasonCode`. An account paused by the boot check can be reactivated only once that cause is gone (the same checks).
- `active → paused` and `active|paused → retired`: **coverage loss check** (§5). If any `(method, country)` loses its last account and `confirmCoverageLoss` is not `true` → `409 coverage_loss_unconfirmed { lost: [{ method, country }] }`, nothing changed. With confirmation: done, and the lost pairs are written to the audit context.
- `retired → archived`: no live attempt (`created`, `requires_action`, `pending`, manual intents included) on the account; no refund `requested` or `pending`; no succeeded payment or refund on it newer than `paymentDisputeWindowDays` (`archive_rejected_within_dispute_window`); `409 archive_blocked { reasons: [...] }`. A hook `archiveBlockers` lets 4.5 add open disputes and 4.6 unsettled clearing balances without changing this flow.
- Audit `payments.providerAccount.statusChanged` (before/after, reason in `AuditPiiValue` as plan 0.1, 4.4), outbox event `payments.providerAccount.statusChanged` (ids only).

What a status does (unchanged, `callBlockReason`, plan 0.1, 6.4): only `active` takes new charges; `paused`, `retired` and `archived` still retrieve, cancel, refund, test and receive webhooks, always under the environment guard. A live attempt on an account that stops being active is not resumed (3.1/3.2 already refuse `create` and the redirect); the customer's next attempt replaces it through the existing P2 path.

### 4.4 Credential rotation and webhook URL

Rotation: validate (§2) → candidate connection test → **only if `ok`**: one transaction with the row locked and `version` compared, new ciphertexts, `credentialsChangedAt = now()`, test result stored, `version + 1`; audit `payments.providerAccount.credentialsChanged` with `"[changed]"` only. Not `ok` → `422 connection_test_failed { code }`, nothing stored, the old credentials keep working (test-then-swap: a typo never breaks a working checkout). The webhook secret is rotated with the credentials (Stripe gives a new `whsec_` when the endpoint secret is rolled).

Webhook URL: new 32-byte path token, new HMAC in `webhookPathTokenHash`, `version + 1`, audited, URL returned once. The old URL answers 404 at once (no grace: the signature is the real protection and a leaked URL is the reason to regenerate). Events missed meanwhile: gateways retry for days, the attempt sweep re-reads open attempts, and 4.6 reconciles. `webhook_url_shown_once_and_regenerated_with_step_up`.

### 4.5 Boot check (`ProviderAccountsBootCheck`, `onApplicationBootstrap`)

- Every `active` account whose adapter is not in the registry (`boot_adapter_missing`) or whose manifest is `planned` (`boot_adapter_planned`) → `paused`.
- Compare-and-set (`WHERE status = 'active'`), so several API instances pause it once; audit with `SYSTEM_ACTOR`; one task per account (`payments:account_paused_at_boot:<id>`); a warning in §6. It never activates anything and never decrypts.

## 5. Coverage loss

`PaymentRouting.coverage(db, { excludeAccountIds })`: for each country of `salesCountries` and the currency `defaultCurrency` (AUD), the methods offered (the existing `methods()`, so manual methods follow their own switches). Lost = coverage now − coverage without the account. Built on the routing service so 4.2's rules change it in one place. Table test `coverage_loss_table`: one card account; two card accounts; card + manual PayID off/on; account for another currency only; test-only adapter in production; country added to `salesCountries`.

## 6. Warnings (`GET …/warnings` and the panel banner)

Closed list of codes with ids only: `no_method_for_country` (a sales country where no method is offered), `active_without_current_test` (active account whose last test is not `ok` or older than its credentials, e.g. accounts from the console), `paused_by_system` (`pauseReasonCode` boot_*), `webhook_rejected_since_change` (`bad_signature` after `credentialsChangedAt`, last 7 days), `adapter_missing`, `adapter_planned_with_account`. Pausing the last account is the blocking warning of §4.3 (criterion "Pausar la última cuenta que atiende un método muestra un aviso").

- **A8.** Dispute window 180 days from the last succeeded payment or refund of the account.

## 11. Risks

1. **Live mode.** Resolved by keeping `CHECK (mode = 'test')` (coordinator decision): no live row can exist, and the API refuses `live` first. Residual risk: the future task that lifts the CHECK must add the live-only nets (§14) in the same migration.
2. **New ways for a secret to leak**: request bodies, validation errors, the candidate test context, audit, connection-test errors, the once-only URL in logs or the web. Closed error codes, no body logging, `"[changed]"` audit and the capture tests of §7.
3. **Concurrency of warnings and tests**: two pauses at once (advisory lock), a test of old credentials recorded after a rotation (`credentialsChangedAt` compare-and-set), a pause racing an attempt (routing reads without a lock; `callBlockReason` re-reads the status before the call, so the charge is refused, as today).
4. The boot check pauses an account whose adapter disappeared from the code (a bad deploy): fail-closed by design, with a task and a warning.
