**Assumptions the sandbox run must confirm** (each has a test against the fake now and a line in `docs/done/4.3.md` under "Sin verificar"):

- **A1** A create replay whose body differs (the lookup probe of §5.5) is answered from the idempotency store before the body is validated. If wrong, a lookup by key answers "none" for an existing order; §5.5 shows why that cannot move money.
- **A2** A capture copies the purchase unit's `custom_id`, and capture events carry `supplementary_data.related_ids.order_id`.
- **A3** Refund events carry the `up` link to the capture.
- **A4** Sandbox certificates are served from `api.sandbox.paypal.com` or `api-m.sandbox.paypal.com` under `/v1/notifications/certs/`, the leaf is named `messageverificationcerts.sandbox.paypal.com` (live: `messageverificationcerts.paypal.com`), and the chain ends at a root in Node's bundled store.
- **A5** A retried delivery is a new transmission (new time and signature). If PayPal reuses the original time, our 300 s window refuses retries; the sweep still reaches the right state (§7.6).
- **A6** A `COMPLETED` order stays readable long after 72 h (refunds start from the order). If not, an API refund of an old payment fails with `provider_not_found` and Oscar refunds from PayPal's dashboard, which our webhook path records (§6).
- **A7** After `INSTRUMENT_DECLINED` the order's `update_time` does not change, and a new approval changes it (it is part of the capture's `PayPal-Request-Id`, §5.3). If a decline changed it, one more capture would be tried against the declined instrument per customer read: no money risk (it declines again), only extra calls.
- **A8** An order created without `payment_source` (return URLs in `application_context`) is `CREATED`, so the cancel marker can be written (PATCH works only on `CREATED` or `APPROVED`). With `payment_source.paypal` PayPal answers `PAYER_ACTION_REQUIRED` (community report below), where PATCH is refused. If A8 is false, `cancelPayment` still answers `cancelled` (nobody will capture it and it expires), but a later read says `requires_action`, and the sandbox clause `cancel_is_idempotent_and_final` fails.
- **A9** The lookup probe (§5.5): PayPal may answer `PAYPAL_REQUEST_ID_PREVIOUSLY_USED` to any second body (then a lookup by key never finds the order: retryable forever, safe, but `retrieve_by_ref_and_by_key_agree` fails in sandbox), or may store the probe's 400 under a key no create used yet (then the next create under that key is refused definitively and the attempt fails without money moving). The fake models both behaviours behind options and tests show both are safe.

## 3. Manifest and credentials

- `key: 'paypal'`, `displayName: 'PayPal'`, `status: 'experimental'`, `testOnly: false`, `cardDataHandling: 'hosted_only'` (the payer approves on PayPal's page; card details, if the payer uses one, stay with PayPal).
- `methods: ['card']` (D1), `currencies: ['AUD']`, `countries: 'any'`, `checkoutOrigin: 'https://www.sandbox.paypal.com'` (D8).
- `capabilities: { refunds: 'partial', deferredCapture: false, lookupByIdempotencyKey: true, declineOutcome: 'stays_payable' }`: a declined instrument leaves the order payable (the payer approves again with another one, §5.3).
- `account.fields`:
  - `clientId`, label "Client ID (sandbox REST app)", pattern `^(?!(sk|rk|pk|whsec)_)[A-Za-z0-9_-]{20,128}$`.
  - `clientSecret`, label "Secret (sandbox REST app)", same pattern.
  - PayPal client IDs and secrets carry no test or live marker, so the pattern only checks shape. What keeps a test account on test money is the host (§4): a test-mode context only ever calls `api-m.sandbox.paypal.com`, where a live credential fails with 401 (`provider_auth_failed`). This is stated in the guide and in the field label help.
- `account.webhookSecret`: `{ source: 'entered', label: 'Webhook ID (from the sandbox app's webhook settings)', pattern: '^[A-Z0-9]{10,32}$' }`. The webhook ID is not a secret: it binds a PayPal-signed delivery to our subscription (a delivery PayPal signed for another merchant's webhook does not verify here). It is still stored encrypted and never shown, like every `webhookSecret`.
- Samples are built at runtime from filler (`'A' + 'x'.repeat(79)`), never a real or key-shaped literal. Rejected samples: `sk_live_…`, `sk_test_…`, `pk_test_…`, `whsec_…`, a 19-character value, values with a space, `.`, `=` or `:`; for the webhook ID: lowercase, 9 characters, 33 characters, a `WH-` event ID.

## 4. HTTP layer

- Hosts fixed in code by `ctx.mode`: test → `https://api-m.sandbox.paypal.com`; live → `https://api-m.paypal.com` (unreachable today: the gateway refuses live for `experimental`). No option or variable changes them. A unit test checks a test context never reaches any other host.
- Token: `POST /v1/oauth2/token` once per adapter operation, no cache (D7). 401 or 400 `invalid_client` → `provider_auth_failed`, non-retryable. The token, client ID and secret are never put in a `ProviderError`, a result or a log.
- Each request: `fetch` with `redirect: 'error'`, a 4.5 s timeout, JSON in and out, response body capped at 1 MiB (else `provider_unavailable`). The gateway's 10 s limit bounds an operation of several requests.
- Error bodies are read only for `name` and `details[].issue`, compared with closed lists (§8); PayPal's words never leave the adapter.
- Malformed IDs (anything but `^[A-Z0-9]{1,20}$`, or `capture:` plus that) are never put in a URL. They are checked after the token, so bad credentials are still `provider_auth_failed` (contract `bad_credentials_are_auth_failed`); then retrieve answers `null` and cancel `provider_not_found`.

## 5. Payments

### 5.1 Money

- Only currencies with two decimals are accepted, and only `AUD` is in the manifest; anything else is refused before any call (`provider_rejected`, definitive: contract `definitive_refusal_means_no_object`).
- `toValue(amountMinor: bigint)`: `1n ≤ amount ≤ 999_999_999n` (A$9,999,999.99, D14), else refused before any call. `${amount / 100n}.${(amount % 100n).toString().padStart(2, '0')}`. Bigint only.
- `fromValue(value: string)`: `^(0|[1-9][0-9]{0,11})(\.[0-9]{1,2})?$`, the fraction padded to two digits, then `BigInt`. `1e3`, `15.001`, `-1.00`, `01.00`, `1,000.00` and spaces are refused (`provider_unavailable`: we cannot read the answer). No `Number`, `parseFloat` or arithmetic on strings; a static test greps the adapter for them.
- Rounding: none. The conversion is exact both ways (the rounding rule of `.claude/rules/pricing.md` is not involved: the amount comes from the core, already in minor units).

### 5.2 Create

Body, fully derived from the input (byte-identical on every retry of the key: `JSON.stringify` of a fixed object):

```json
{ "intent": "CAPTURE",
  "purchase_units": [{ "custom_id": "mt1:o:<paymentId>:<d>", "description": "Booking payment",
                       "amount": { "currency_code": "AUD", "value": "15.00" } }],
  "application_context": { "return_url": "<returnUrl>", "cancel_url": "<returnUrl>", "user_action": "PAY_NOW",
                           "shipping_preference": "NO_SHIPPING", "locale": "en-AU" } }
```

- No `payment_source`: with it PayPal answers `PAYER_ACTION_REQUIRED`, where the cancel marker cannot be written (A8). `application_context` is PayPal's older place for the same settings.
- `<d>` = first 20 hex characters of `sha256('paypal:key:' + idempotencyKey)`: it lets a lookup by key check the order is the one of that key (§5.5). `custom_id` is at most 61 characters (limit 127). No payer data, no booking reference, no invoice ID.
- `NO_SHIPPING`: PayPal does not collect an address we do not need (less personal data in stored raw events).
- Answer: the order, `CREATED`, with its `approve` (or `payer-action`) link. The link must start with `checkoutOrigin + '/'`, else `provider_unavailable` (the core also checks it). A replay returns the order's current status (documented), so no second read is needed.
- `createdAt` is not sent: PayPal's three hours run from its own creation, and our attempt ends at 60 minutes.

### 5.3 Approval and capture: `completePayment` (core change, D2)

PayPal moves no money when the payer approves: the merchant must call capture. Capturing in `retrievePayment` would charge on reads the core makes to cancel, replace, close orphans or process refunds, and on paused or retired accounts. So capture is a separate, optional member, called only when the core wants money now:

```ts
/**
 * Optional (task 4.3): finishes a payment the customer approved at the gateway (PayPal's capture). The core calls it
 * only for a live attempt of a payable booking on an active account (sync, drive, expire); never to cancel, replace,
 * close an orphan or process a refund. Returns the payment as retrievePayment would after it.
 */
completePayment?(ctx: ProviderContext, ref: string, idempotencyKey: string): Promise<ProviderPayment>;
```

- Core calls (`PaymentAttemptSyncService.run('sync')`, `PaymentAttemptsService.drive`, and `settle` for `expire` only): read with `retrievePayment`; if the answer is `requires_action`, the provider has `completePayment`, the attempt is live, the booking is in a payable state and the account is `active`, call `completePayment` and use its answer. `cancel`, `replace`, `cancel_orphan` and refund processing never call it. A test per path checks it.
- PayPal's implementation: `GET` the order; only `APPROVED` with the open marker `mt1:o:` is captured, with `POST /v2/checkout/orders/{id}/capture` and `PayPal-Request-Id = 'mt-capture:' + id + ':' + sha256(update_time)[0..16]` (A7: a repeat after a decline is answered from PayPal's store, not captured again); anything else is returned as read.
- Capture outcomes:
  - Capture `COMPLETED` → `succeeded`; capture `PENDING` → `pending` (then `pending → succeeded | failed`).
  - Order `COMPLETED` with capture `DECLINED` or `FAILED` → `failed`, terminal (the order can no longer be approved).
  - 422 `INSTRUMENT_DECLINED`, `ORDER_NOT_APPROVED`, `TRANSACTION_REFUSED`, `REDIRECT_PAYER_FOR_ALTERNATE_FUNDING` → `requires_action` with the approval link and a `failureCode` from a closed list: the payer picks another method (`declineOutcome: 'stays_payable'`).
  - 422 `ORDER_ALREADY_CAPTURED` → read the order again and map it. 422 `PREVIOUS_REQUEST_IN_PROGRESS` → `provider_busy`. Timeout or 5xx → retryable; the next call finds the capture done or replays the same request ID.
- When: the customer's return page (`refresh` → `sync`) right after PayPal sends them back; the next `drive`; the expiry sweep at the attempt's 60 minutes if they closed the window (within PayPal's three hours).
- So "a cancelled order cannot be paid" holds because nobody captures it, not because PayPal refuses the approval: the payer can still approve on PayPal's page, but no money moves and the order expires.

### 5.4 Cancel

PayPal has no cancel for an uncaptured order (D3), and PATCH is refused outside `CREATED` and `APPROVED`:

1. `GET` the order. 404 → `provider_not_found` (contract). `COMPLETED` → report it (`succeeded`, `pending` or `failed`), nothing changed.
2. `CREATED` or `APPROVED` without the marker: `PATCH [{ op: 'replace', path: "/purchase_units/@reference_id=='default'/custom_id", value: 'mt1:c:<paymentId>:<d>' }]`. Any refusal of the PATCH is not an error.
3. `GET` again. `COMPLETED` → report it (a capture finished meanwhile: late success, an allowed transition). Anything else → `cancelled`: no capture will be asked for it (§5.3), and PayPal forgets it within three hours. Reads later say `cancelled` when the marker is there; without it (A8 false) they say what PayPal says.

The `idempotencyKey` argument is unused: the PATCH replaces one value.

### 5.5 Lookup by key

PayPal has no search of orders. `retrievePayment({ idempotencyKey })` sends a **probe**: `POST /v2/checkout/orders` with `PayPal-Request-Id = key` and a body PayPal must refuse if processed (`{"intent":"CAPTURE","purchase_units":[]}`):

| Answer | Meaning |
|---|---|
| 2xx with an order whose `custom_id` digest matches the key | that order, as read (never captured here) |
| 2xx with any other order | `provider_unavailable`, retryable ("unknown", never "none") |
| 400 `INVALID_REQUEST` (schema) | no order under this key: `null` |
| 422 `PAYPAL_REQUEST_ID_PREVIOUSLY_USED`, `PREVIOUS_REQUEST_IN_PROGRESS`, 409, 429, 5xx, timeout | `provider_busy` or `provider_unavailable`, retryable |
| 401 | `provider_auth_failed` |

Why a wrong "none" (A1 or A9 false, or the key aged out of PayPal's store) cannot cost money: the core then ends the attempt without a reference, so it never asks to complete that order (§5.3). If PayPal stored the probe's 400 under a key no create used (A9), the next create under it is refused definitively and the attempt fails, again without money moving. The customer's return page finds no live attempt and offers a new one. Where the core uses this lookup: after a definitive refusal of `createPayment` (`lookupAfterRefusal`) and in the sweep for an attempt with no reference. A probe never creates an order: its body cannot pass validation.

### 5.6 Statuses

| PayPal | Ours |
|---|---|
| marker `mt1:c:` (not `COMPLETED`) | `cancelled` |
| `CREATED`, `SAVED`, `PAYER_ACTION_REQUIRED`, `APPROVED` | `requires_action`, redirect to the approval link when the order has one |
| capture `DECLINED` or `FAILED` seen in a webhook (`PAYMENT.CAPTURE.DECLINED`) | `requires_action`, no redirect: the read decides (an `INSTRUMENT_DECLINED` order is still payable) |
| `VOIDED` | `cancelled` |
| `COMPLETED` + capture `COMPLETED`, `PARTIALLY_REFUNDED`, `REFUNDED` | `succeeded` |
| `COMPLETED` + capture `PENDING` | `pending` |
| `COMPLETED` + capture `DECLINED`, `FAILED` | `failed` |
| 404 on a well-formed ID | `null` (D9) |

`amount`: for `succeeded`, the sum of the captures `COMPLETED`, `PARTIALLY_REFUNDED` or `REFUNDED`; for `pending`, of the captures `PENDING`; otherwise the purchase unit's. So a capture of another amount reaches the core's amount check. `ourPaymentId` from `custom_id` when it parses to a UUID.

## 6. Refunds

- `createRefund(paymentRef = order ID)`: `GET` the order; refused without a call (`provider_rejected`, definitive) unless it is `COMPLETED` with one capture `COMPLETED` or `PARTIALLY_REFUNDED`, the currency matches, `amount > 0` and `amount ≤ capture − (refunds COMPLETED or PENDING listed in the order)`. Then `POST /v2/payments/captures/{captureId}/refund` with `PayPal-Request-Id = key`, `Prefer: return=representation`, body `{ amount: { currency_code, value }, custom_id: 'mt1:r:<refundId>:<d>' }` (always the amount, never the empty body; no `note_to_payer`: it reaches the payer's email).
- 422 `REFUND_AMOUNT_EXCEEDED`, `CAPTURE_FULLY_REFUNDED`, `REFUND_NOT_ALLOWED`, `REFUND_TIME_LIMIT_EXCEEDED`, `TRANSACTION_REFUSED` and other 422 → `provider_rejected`, definitive. `PREVIOUS_REQUEST_IN_PROGRESS` → `provider_busy`. A replay returns the refund's current state.
- Statuses: `COMPLETED` → `succeeded`, `PENDING` → `pending`, `FAILED` → `failed`, `CANCELLED` → `cancelled`.
- `paymentRef` of a refund read from PayPal: `capture:<captureId>` from its `up` link (A3). `retrievePayment({ ref: 'capture:…' })` resolves it through the capture's order (contract `refund_webhook_verifies_and_resolves_payment`).
- `retrieveRefund({ ref })`: `GET /v2/payments/refunds/{id}`; 404 → `null`. `{ idempotencyKey, paymentRef }`: the order's refunds, each read (`custom_id` digest), at most 20, beyond that `provider_unavailable` ("unknown, never none").
- A refund made on PayPal's dashboard carries no `custom_id` of ours: `ourRefundId` undefined (contract `gateway_refund_has_no_our_id`), recorded by the core as `external` (3.3).
- If A6 is false, an old order no longer reads: the API refund says `provider_not_found` and Oscar refunds on PayPal's dashboard; the webhook names the capture, which stays readable, and the core records it. A durable second reference (the capture ID) in the core would be a contract change for a later task.

## 7. Webhooks

### 7.1 Events

| Event | `kind` | From |
|---|---|---|
| `CHECKOUT.ORDER.APPROVED` | `payment` (§5.6, row "seen in a webhook") | resource = order |
| `PAYMENT.CAPTURE.COMPLETED`, `.PENDING` | `payment` | resource = capture; ref = `related_ids.order_id` (A2); status from the capture |
| `PAYMENT.CAPTURE.DECLINED` | `payment`, `requires_action` | the read decides (§5.6) |
| `PAYMENT.CAPTURE.REFUNDED`, `PAYMENT.REFUND.PENDING`, `PAYMENT.REFUND.FAILED` | `refund` | resource = refund |
| `PAYMENT.CAPTURE.REVERSED`, `CUSTOMER.DISPUTE.*`, anything else | `unsupported` | stored raw, not processed |

`providerEventId` = `id` (`^WH-[A-Za-z0-9-]{1,100}$`), `type` = `event_type`, `occurredAt` = `create_time`. A resource that does not parse makes the event `null` (verify says `malformed`). Statuses come from the resource, never from the event name, so an old event read late states its own older state and the core's state machine (forward only) ignores it. Duplicates share `id`, which the core stores once per account. These seven events are the subscription list in the guide and the connection test.

`APPROVED` events do not trigger a capture (D10): the capture happens on the return page, the next `drive` or the sweep (§5.3).

### 7.2 Verification (synchronous, no network)

1. Headers `paypal-transmission-id` (≤ 100), `paypal-transmission-time` (≤ 40), `paypal-transmission-sig` (base64, ≤ 1024), `paypal-cert-url` (≤ 300), `paypal-auth-algo` (≤ 40). Missing, oversized or not ASCII → `bad_signature` (`malformed` only for a body that is not an event). Never throws.
2. `paypal-auth-algo` must be `SHA256withRSA`.
3. `paypal-cert-url` must match the allowlist of the context's mode exactly: test `^https://api(-m)?\.sandbox\.paypal\.com/v1/notifications/certs/CERT-[A-Za-z0-9-]{1,100}$`, live the same without `.sandbox`. So a test account refuses a live-signed delivery and the reverse (the mode check Stripe does with `livemode`). No userinfo, port, query, fragment, `..` or other host can match.
4. The certificate for that URL must be in the cache (§7.3) and valid at `now`; otherwise `bad_signature`.
5. Message `${transmissionId}|${transmissionTime}|${ctx.webhookSecret}|${crc32(rawBody)}` (CRC-32/ISO-HDLC, unsigned decimal, computed by a 15-line function checked against the standard vector and `zlib.crc32`); `crypto.verify('sha256', message, publicKey, signature)` (PKCS#1 v1.5). Fails → `bad_signature`. A webhook ID of any shape just fails here (contract "other secret" gives `bad_signature`, never `malformed`).
6. `paypal-transmission-time` strict `YYYY-MM-DDTHH:MM:SS(.ffffff)?Z`, more than 300 s from `now` either way → `stale_timestamp` (contract 299 s / 301 s / 1 h). Checked after the signature, so only genuine deliveries get that code.
7. Body: JSON object with the fields of §7.1, else `malformed` (with `claimedEventId` when an ID is readable).

RSA verification compares no secret, so the contract's "constant time" requirement has nothing to compare; the webhook ID is only hashed into the message.

### 7.3 The certificate: `prepareWebhook` (core change, D5)

`verifyWebhook` must stay network-free, and PayPal's key is only reachable at `paypal-cert-url`. One optional member is added to `PaymentProvider`, next to 4.5's optional `retrieveDispute`:

```ts
/**
 * Optional (task 4.3): fetches from the gateway, and caches, what verifyWebhook needs to check this delivery offline
 * (PayPal's signing certificate). Called by the gateway wrapper before verifyWebhook; never throws.
 */
prepareWebhook?(ctx: ProviderContext, headers: Readonly<Record<string, string>>): Promise<void>;
```

- `ProviderGateway.verifyWebhook` calls it after the existing checks (adapter allowed, secret present), under a 5 s limit, ignoring any failure; then calls `verifyWebhook` as today. If the certificate could not be fetched, verification fails closed (`bad_signature`, a rejection row, 400) and PayPal retries the delivery later. Adapters without the hook are unchanged. `HEALTH_OPS` still excludes `webhook`.
- PayPal's implementation: URL must pass §7.2 step 3 for the context's mode, else nothing is fetched (no SSRF: a fixed host pair, `https`, a fixed path shape, `redirect: 'error'`, 5 s, body ≤ 64 KiB). PEM blocks parsed with `X509Certificate`. Accepted only if: the leaf's subject or SAN is the mode's name (A4), each certificate is issued and signed by the next, the last is signed by a root in `tls.rootCertificates` (Node's bundled Mozilla store), and all are valid now. Then the leaf's public key and `validTo` are cached under the URL.
- Intermediates must have `ca === true` and `keyUsage` containing `keyCertSign`; the leaf `digitalSignature` when it lists key usage. A test uses a non-CA leaf as intermediate.
- Cache: at most 16 URLs, least recently used out, an entry dropped once expired. A failure is cached for 60 s (negative cache); one download per URL at a time (single flight); at most two downloads at once, others give up at once (verification then fails closed and PayPal retries). No revocation check (D6).
- The contract harness calls `prepareWebhook?.()` before each `verifyWebhook`, as the gateway does (additive, compatible with 4.5).
- Tests construct the adapter with `{ transport, certificates: { fetch, roots } }`; the registered adapter has neither, so a certificate from the fake's CA is refused by it (a test checks that).

### 7.4 What the core already does

Signature failure → rejection row and 400; raw event stored once per `(account, event id)` with the job queued; processing matches by our payment ID within the account, then by reference; amount and currency mismatches open a task; refunds re-read the gateway before believing a failure. Nothing changes there.

### 7.5 Personal data

PayPal events can quote the payer (name, email). The core keeps raw bodies 180 days and drops them for erased customers (5.5); PayPal adds no new store. `NO_SHIPPING` keeps addresses out.

### 7.6 What a refused or lost delivery costs (A5, certificate failures)

If PayPal's retries reuse the transmission time (A5), or the certificate cannot be fetched for longer than the retries last, a delivery is refused for good. Payments still reach their real state through the return page, `drive` and the expiry sweep, and refunds we started through their re-reads. But two things arrive only by webhook: a refund made on PayPal's dashboard, and a capture reversal or dispute. Those would be missing from the ledger until reconciliation (4.6) reads PayPal's transactions. Even when they arrive, `PAYMENT.CAPTURE.REVERSED` and `CUSTOMER.DISPUTE.*` are `unsupported` (D12) and open no task. Both are listed in §14 for Oscar and 4.6; 4.5's dispute support (PR #75) is not declared, because PayPal disputes are not implemented here.
