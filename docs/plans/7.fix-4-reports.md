# 7.fix-4 Reports review fixes

Risk: high (permissions and report totals). Fixes three findings of the independent review of 7.7 in
`apps/api/src/modules/reports/`. Does not touch organiser exports (7.fix-3 works there in parallel).

## 1. Scheduled sends must cover contiguous days (medium)

**Problem.** A scheduled send of a `last_days` report covers the N whole days before the send. That only tiles time when
the gap between sends is exactly N days. Monthly sends never have a fixed gap (28 to 31 days), so with 30 days the
1 March send counts 30 and 31 January twice and the 1 April send misses 1 March. Weekly sends with N other than 7 have
the same fault (gaps with N < 7, double counts with N > 7). `pure.test.ts` row 107 blesses the overlap.

**Options considered.**
- Reject `last_days` for monthly schedules. The panel only builds `last_days` ranges, so this would remove monthly
  sending from the panel, and stored monthly reports would become unsendable. Not chosen.
- "Previous calendar month" for monthly sends only. Only tiles time when the send day is the 1st; a report sent on the
  15th would cover a month that ended two weeks earlier. Not chosen.
- **Chosen: a scheduled send of a `last_days` report covers the whole Brisbane days from the day of the previous
  scheduled time up to the day before this one**, for both frequencies. Consecutive sends then tile time by
  construction: each one starts on the day the previous one was due, and ends the day before its own. A `dates` range is
  still sent as given. The `days` value keeps choosing what the panel and on-screen runs show.

Weekly with 7 days, which is what the 7.7 tests and the panel default use, gives exactly the same range as today. Weekly
with another number of days changes: it now always covers 7 days. This is the honest reading of the promise the module
already makes ("no request falls between two reports"), it is a pure function with no stored data, and it is undone by
reverting the `schedule` branch of `resolveRange`.

**Design.**
- `dates.ts`: `previousOccurrence(schedule, at)` = the latest occurrence strictly before `at`;
  `resolveRange(range, now, { schedule })`: with a schedule, `now` is the scheduled time and a `last_days` range becomes
  `{ from: Brisbane day of previousOccurrence, to: day before the Brisbane day of now }`. The `completeDaysOnly` option
  goes (its only caller is the email).
- `engine.run(tx, def, now, { schedule })` passes it on. `emails.ts` parses the report's current schedule and refuses the
  email (`MAIL_NOT_SENDABLE`) when there is none or it is invalid. That state already means the email cannot go
  (unscheduling a report needs its recipients cleared, and an email to someone no longer on the report is refused).
- If the schedule is edited while an email is still queued, that email is refused (`MAIL_NOT_SENDABLE`): `update()`
  restarts `scheduleStartedAt` exactly when the schedule changes, so `scheduleStartedAt > run.scheduledFor` marks it.
  Otherwise the new schedule's previous occurrence could fall after the run's own day and the range would end before it
  starts (run of Monday 08:00, schedule moved to Monday 07:00). Changing only the name or recipients keeps the clock, so
  those emails still go.
- Panel: one hint under the schedule fields saying what each email covers (translation layer, `en-AU.json`). No other
  web change; nothing is computed in the browser.

## 2. Deleting a report needs the permission of its data (low)

`remove()` does not call `assertEntity`, so someone with `reports.report.manage` but not `bookings.booking.read` can
delete a bookings report and stop other people's scheduled email. Add `assertEntity(tx, auth, before.entity)` (the
`entity` column is the `ReportEntity` enum, so it is always known, also for a stored definition that no longer parses),
inside the transaction after the lock and before the version check, like `update()`.

## 3. Tests

Written first; they fail on the current code where they cover a fault.
- `pure.test.ts`: row 107 is corrected (it asserted the overlap). New: 15 consecutive monthly sends (1st, 15th and 28th,
  at 00:00, 08:00 and 23:55, January 2027 to March 2028, so a 28-day February, the leap February 2028 and 30/31-day
  months) leave no gap and count no day twice, and their days sum to the days between the first and last send; 60 weekly
  sends with 1, 3, 7, 30 and 366 days tile the same way; the range does not depend on `days`; `dates` unchanged;
  `previousOccurrence` table.
- `reports.test.ts` (database):
  - delete of a bookings report by someone without `bookings.booking.read` is 403 and the report and its schedule stay;
    a funnel report can be deleted by the same person.
  - a definition that no longer parses: the tick makes a `skipped` run with `report_invalid` and queues no email.
  - a queued email whose report definition became invalid is refused (`not_sendable`), nothing is sent.
  - a monthly schedule through `tick`: 1 March and 1 April sends make one run each at the right instant; their emails
    cover 1 to 28 February and 1 to 31 March, and a request made on 1 March appears in the April email only.

Only the reports tests, lint and typecheck of the touched packages run locally, on a fresh database of this thread; CI is
authoritative for the rest.

## Not doing

No migration, no change to stored reports, no change to the schedule or definition schemas, no catch-up of missed
occurrences, nothing in organiser exports.
