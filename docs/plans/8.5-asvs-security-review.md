# 8.5 Security review of the whole product against OWASP ASVS

Risk: high. Source: `docs/phases/phase-8.md` (row 8.5 and the criterion "la revisión de seguridad deja un informe con hallazgos por gravedad, y los graves están corregidos"), `docs/architecture.md` ("Seguridad y calidad": validation everywhere, rate limits, CORS restricted, security headers, CSRF, logs without personal or payment data, ASVS as reference), the open items handed to this task by 8.4 and 8.7 (real client IP behind Caddy), and the plans of 0.3 (threat model T1–T16, M1–M8, G1–G4), 4.1–4.6 of the 0.3 plan, 5.5 and 8.4. Money stays parked: nothing about real payments, ledger, refunds, GST/FX or supplier payments changes; no live mode, keys, deployment or external accounts.

## 1. Standard, level and scope

- **OWASP ASVS 5.0.0** (May 2025), **level 2** as the target: the product holds customers' personal data, staff with powerful permissions and (later) payments through hosted checkout. L3 items are noted only where they are cheap and already met.
- **In scope:** `apps/api` (every controller, guard, service with a security property, the schema's database roles and triggers), `apps/web` (proxy route `/api/*`, `proxy.ts`, `next.config.mjs`, pages that read tokens, client components that post), `packages/shared` (validation schemas), `deploy/` (compose, Caddyfile, env template, db roles), `scripts/backup/`, `docker/`, CI's dependency check (read only), and the dependency tree (`pnpm audit`, all deps).
- **Out of scope, stated in the report:** live behaviour of Caddy/TLS/Docker on a real server (no deployment; checked by configuration and by tests of our own code that consumes their headers), third-party gateways (only the simulator exists), penetration testing of infrastructure, chapters that do not apply (V10 OAuth/OIDC: we are neither client nor server; V17 WebRTC).

## 2. Method

For each ASVS 5.0 chapter, the L1+L2 requirements are walked against the code, and each gets one verdict in the report's coverage table: **cumple** (with the file or test that shows it), **corregido en 8.5** (finding ID), **no aplica** (why), or **hallazgo abierto** (finding ID). Requirements are grouped where one control answers several (e.g. all of V7.2 by `SessionService`), so the table stays readable (~120 rows, not 350).

| Chapter | What is read and probed |
|---|---|
| V1 Encoding & sanitisation | Every raw SQL (`$queryRawUnsafe`, `$executeRawUnsafe`, `Prisma.raw`): parameters only, identifiers from code-side allow lists; every `dangerouslySetInnerHTML`; JSON-LD serialisation; CSV/formula guard in **every** export path (table capabilities, catalogue, trip lists, organiser exports, privacy export); `Content-Disposition` filenames; mail subjects and bodies built from customer data (header injection, HTML); PDF generation inputs. |
| V2 Validation & business logic | Every body/query/param has a Zod pipe or a parse pipe (a route walk, as the access-mark walk does); unknown keys rejected (`.strict()` or stripped, never mass-assigned into Prisma); limits on sizes, counts and lengths; anti-automation on every public route that sends mail or writes (alerts, sign-in links, booking requests, race events, quotes, privacy requests); business-flow order (state machine only). |
| V3 Web frontend | Security headers on every web response (CSP, `X-Content-Type-Options`, framing, `Referrer-Policy`, `Permissions-Policy`, HSTS from Caddy), cookies (`__Host-`, `Secure`, `HttpOnly`, `SameSite`), tokens only in fragments, open redirects (`proxy.ts` locale redirects, content redirects, post-sign-in navigation), `target=_blank`, cross-origin isolation of the panel. |
| V4 API | The web proxy as the only door: path traversal, header allow lists both ways, body size, method list, `Cache-Control` on proxied personal data; API not published (compose check); HTTP method override; error shape. |
| V5 Files | Stored files: content-type allow list, size limit, storage key not user controlled, download disposition and `nosniff`; content images by URL only (8.1); backup bundles (encryption, permissions). |
| V6 Authentication | Staff password + TOTP, step-up, enrolment and reset links, recovery codes; customer magic links; attempt limiting and delays (G2, M2); enumeration (T2); password policy vs ASVS 6.2 (length, no composition rules, breached-password check); default and demo accounts never in production. |
| V7 Sessions | Token entropy and storage, idle/absolute timeouts, rotation at sign-in, revocation on sign-out, disable, reset, role change and step-up failures; session list/termination for staff. |
| V8 Authorisation | Access marks walk; `@OwnedBy` checks; permission grants (T9: nobody grants what they lack); step-up permissions; API key scopes (8.4); IDOR on every customer route and every `:id` admin route that is customer data; field-level exposure (staff notes, custom fields' visibility). |
| V9 Tokens | Payment-link, checkout, unsubscribe and alert tokens/HMACs: entropy, expiry, single use where needed, constant-time comparison. |
| V11 Cryptography | `secret-box` (AES-256-GCM, nonce, key version), HMAC uses, `timingSafeEqual`, random sources, argon2id parameters, outgoing webhook signatures. |
| V12 Communication | TLS at Caddy, HSTS value, internal HTTP inside the compose network (accepted, documented), outgoing webhooks https-only with SSRF guard (8.4), SMTP TLS settings. |
| V13 Configuration | Secrets only from env; `loadConfig` refusals in production; dev-only defaults and demo data can never run in production; dependency audit; debug/simulator routes off in production; container users and read-only mounts; `.env.example` holds no real values. |
| V14 Data protection | Personal data classes in audit (`field-classes.generated.ts`), logs without personal values, `no-store` on personal responses, privacy export/erasure (5.5), backups encrypted, data minimisation in public endpoints. |
| V15 Secure coding & architecture | Dependency inventory and audit, least-privilege DB roles (`mt_app` cannot alter audit or schema), append-only audit trigger, concurrency (compare-and-set, locks), resource exhaustion (in-memory limiter bounds, query limits, pagination caps), unsafe deserialisation (none expected). |
| V16 Logging & errors | Error filter (fixed codes, no stack), what is logged for security events (sign-in, step-up, permission denied, key use), absence of tokens, emails and payment data in logs, log injection (newlines from user input). |

Probing is done by reading code and by **tests that try the attack**. No external scanner is installed (no new dependency); `pnpm audit` runs on the lockfile.

### Preliminary findings from the first pass (to be confirmed, rated and extended during the review)

- **F-a** The web adds `X-Frame-Options`/`Referrer-Policy` only to `/admin/*`, `/pay*` and a few token pages. Account pages (erase account, sign out, change booking) and all others can be framed (clickjacking), there is no `X-Content-Type-Options: nosniff` anywhere (the proxy drops the API's own `nosniff`, e.g. on the template PDF preview), no CSP and no `Permissions-Policy`.
- **F-b** Proxied API responses that carry personal data have no `Cache-Control` unless the API set one; the proxy should default to `no-store`.
- **F-c** `proxy.ts` builds a redirect from the path after a language prefix (`/en-AU//host` would give `//host`). Next.js normalises repeated slashes before the proxy runs, so this is likely not exploitable; the review confirms it against a real `next start` and adds a defensive check either way.
- **F-d** `loadConfig` in production accepts the published dev-only key values and the same value for two different keys.
- **F-e** Real client IP behind Caddy (left open by 8.4 and 8.7): verify the chain Caddy → web (`WEB_TRUSTED_PROXY_HOPS=1`) → API (`TRUST_PROXY=uniquelocal`) gives the browser's address and that a forged `X-Forwarded-For` cannot change it.
- **F-f** In-memory limiters are per process and their LRU can be churned by many distinct keys: document as accepted for the single-instance deployment, with the condition that a second API instance needs a shared store.

## 3. Severity scale and fix policy

| Severity | Meaning | Policy in this task |
|---|---|---|
| Crítica | Remote, unauthenticated, leads to account takeover, another customer's data, code execution or money movement. | Fixed here, with a failing test first. |
| Alta | Same impact needing a precondition (a signed-in customer, a staff member without the permission, user interaction such as a framed click), or a missing L2 control on authentication, sessions or access. | Fixed here, with a failing test first. |
| Media | Defence in depth missing where another control already limits the impact, or a disclosure of non-sensitive data. | Fixed here when the change is local and does not touch parked money; otherwise documented with the follow-up task. |
| Baja / Informativa | Hardening, documentation, accepted risk for the current deployment. | Documented with the reason; fixed if trivial. |

"Los graves están corregidos" = every Crítica and Alta is fixed and has a regression test; none may stay open. If one cannot be fixed without touching parked money (payments ledger, refunds) or without a deployment, it is fixed as far as it can be outside those areas, and the rest goes to the report as blocked, with the PR not merged until the coordinator decides.

Fixes in `apps/api/src/modules/payments/` or `pricing/`/`bookings/` follow `.claude/rules/payments.md` and `pricing.md`: no change to amounts, ledger, provider modes or the state machine's meaning; failure-path tests; reviewer.

## 4. Deliverables

1. **Report** `docs/security/asvs-review.md` (Spanish, for Oscar): scope, method, versions (ASVS 5.0.0, commit reviewed), summary by severity, each finding (ID `S-NN`, ASVS references, location, description, impact, how it was found, status `corregido`/`aceptado`/`pendiente`, test that covers it), the coverage table per chapter, accepted risks, and what only Oscar can check (live Caddy/TLS, a scanner against staging, the real IP).
2. **Fixes** for every Crítica/Alta and the local Medias, each in its own commit with its test.
3. **Regression tests** that keep the reviewed properties from coming back:
   - `apps/api/test/security/` (new folder): route walk that every handler argument from body/query/params goes through a validation pipe; every CSV-producing route goes through the guarded writer (convention test over the source, like the module-boundaries tests); every `Content-Disposition` filename is built from a safe pattern; raw SQL only through parameters (convention test over `*Unsafe` calls: the SQL text is a literal or built from code constants); log calls never include request bodies, emails or tokens (convention test on `Logger` calls); production config refusals (F-d).
   - `apps/web`: unit test of `next.config.mjs` headers for every route class (public, account, admin, pay, API proxy); proxy test for `Cache-Control: no-store` default (F-b); `routeLocale` never returns a target that starts with `//` or `/\` (F-c).
   - e2e `apps/web/e2e/security-headers.spec.ts` (CI and local when ports are free): real `next start` responses carry the headers; `/en-AU//example.com` and `/en-AU/%5Cexample.com` never redirect off-site; a framed account page is refused by the browser.
   - Client IP chain (F-e): a test of `forwardHeaders` with Caddy's header shape plus an API test that builds the app with `TRUST_PROXY=uniquelocal` and checks `req.ip` from a private peer with a forged and a real entry (using `proxy-addr`'s compiled trust function, the same Express uses, since a test socket comes from loopback).
4. `docs/done/8.5.md`.

## 5. Failure cases the tests must cover

Headers missing on an error page (404, 500) and on the API proxy's error answers; CSP that breaks the site (e2e of the public pages and the existing `public-site-quality.spec.ts` keep passing); a proxied response that already has `Cache-Control` keeps it (public catalogue caching from 8.3 is not broken); forged `X-Forwarded-For` with 0, 1 and several entries; production config with a dev key, with two equal keys, with a short key; a convention test fails on a planted bad example (each convention test has a negative fixture, so it cannot pass vacuously).

## 6. Assumptions (instead of questions)

1. ASVS 5.0.0 L2 is the bar; the report says which L2 requirements are consciously not met and why (e.g. breached-password check against an online service would send data to a third party: an offline top-passwords list is used instead if missing, or the gap is accepted and documented).
2. CSP: Next.js App Router with static and ISR pages cannot use per-request nonces without making every page dynamic (against `.claude/rules/web.md`), so the CSP is `default-src 'self'`, `script-src 'self' 'unsafe-inline'`, `style-src 'self' 'unsafe-inline'`, `img-src 'self' https: data:` (content images are https URLs, 8.1), `connect-src 'self'`, `frame-ancestors 'none'`, `base-uri 'self'`, `form-action 'self'`, `object-src 'none'`. It still blocks framing, plugins, base hijacking, foreign scripts and exfiltration by fetch. The report records "nonce/hash-based script CSP" as a later hardening. The simulator checkout page (dev/test/ci only) is checked so it still works.
3. HSTS stays at Caddy (`max-age=31536000`); `includeSubDomains` and preload are left to Oscar (they affect the whole domain).
4. Rate limits stay in memory (single API instance per the hosting decision); a shared store is a condition for scaling out, written in the report.
5. Findings in the parked money tasks' future code are not invented: the report reviews what exists (simulator payments, payment links) and lists what 9.x must re-check.

## 7. Not doing

Deploying or scanning a live host; adding scanners or security libraries as dependencies (Helmet is not needed: the API is not public, and the web sets headers in `next.config.mjs`); changing CI; changing money behaviour; rewriting working controls for style; editing `docs/STATE.md`, `BLOCKED.md`, `FINAL-REVIEW.md` or `decisions.md` (the report's "para Oscar" list goes into `docs/done/8.5.md` for the phase close to collect).
